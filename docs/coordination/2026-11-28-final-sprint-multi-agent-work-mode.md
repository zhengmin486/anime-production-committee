> 本文记录协作与排程原则，不新增游戏规则，也不替代各模块已有 Issue、PR 和验收标准。

## 二、默认工作模式：多智能体并发

11月28日至首版截止，负责人自身的工作默认采用多智能体并发执行，而不是逐项串行亲自完成。

### 执行原则

1. **能独立就并行**：代码实现、局部测试、文档核对、缺陷定位等相互独立的工作，拆分给不同 Agent 同时执行。
2. **任务边界明确**：每项任务给出目标、输入、允许修改范围、禁止事项、验收标准和交付格式。
3. **避免写入冲突**：不同 Agent 尽量分配不同模块或文件；同一核心文件指定唯一主执行者，其他 Agent 只做只读审查或提出补丁建议。
4. **先完成再汇报**：Agent 在既定规则内自行处理完整任务，不因局部细节频繁中断负责人；遇到规则冲突、接口缺失或跨模块决策才升级。
5. **执行者自审**：交付时报告修改文件、关键改动、测试命令与结果、未解决问题及潜在影响。
6. **失败隔离**：非关键路径任务允许失败或延后，不得自动转化为负责人的新增返工任务。

### 负责人职责

负责人集中处理：
- 规则与跨模块冲突裁决；
- 必须由总负责人作出的优先级和范围决策；
- 首版关键闭环的最终验收；
- 无法由模块负责人或 Agent 在既定约束内解决的阻塞。

不再默认由负责人逐项完成所有模块工作，也不要求负责人重复审查每个执行过程。

## 三、人工协作者内容的处理口径

- 预计交付的人物卡、事件卡属于额外内容供给，不构成首版必须完成的新增工作量。
- 收到后优先判断能否直接使用；符合当前内容结构和规则、没有明显冲突的即可纳入。
- 只有存在明确阻塞性问题时才做最小必要调整；不为追求精修而逐张重写或增加多轮审核。
- 不适配首版规则、需要新增机制或需要大量返工的内容，暂存到后续版本，不影响首版。
- 宁世清原始卡与其转化稿保持关联：原件保留创作者原始设定，转化稿作为游戏化适配参考。
- 不为消化协作者交付而制造额外工作。内容可用则增加首版内容；不可用则暂缓。

## 四、Much 的任务边界

- #134 四场景入口与明显问题走查、#135 电视台探班事件卡文案练习均为小型、非阻塞任务。
- #135 是独立练习；负责人已另行形成一份独立参考稿并归档，但不向 Much 提供，不将其作为必须达到的标准。
- 不把 Much 纳入首版关键路径，不安排需要负责人持续指导、复核或承担返工风险的工作。
- 不以 Much 的任务完成情况作为首版排期前提。

## 五、冲刺节奏

- **11月28日**：优先并发推进仍在首版范围内的开发、接口对接、文档同步、局部测试与缺陷定位。

## 六、优先级总原则

**首版可交付性优先于内容完整度和局部完美度。**

凡是不能直接提高首版可交付性、又需要负责人投入大量决策或返工时间的事项，默认延后。多智能体并发的目标是减少负责人亲自执行和反复介入，而不是增加并发任务数量或制造新的审核负担。
