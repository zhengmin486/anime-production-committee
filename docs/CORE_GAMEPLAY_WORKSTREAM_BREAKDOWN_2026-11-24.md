## 1. 拆分原则

核心框架不再作为一个必须整体通过的“大方案”。拆成三类：

- **可先行工作包**：已有方向足够明确，产物可独立完成，暂时不依赖尚未决定的运行规则。
- **决策包**：需要负责人明确选择；决策后只解锁受影响的工作，不要求全框架一次性拍板。
- **依赖型工作包**：必须等待一个或多个决策包/上游契约，当前只能做调研、静态样本或接口草案，不能进入运行时实现。

所有工作包都应有独立交付物、验收标准和明确禁止范围。文档、静态数据、原型与运行时实现分开验收。

## 3. 可立即开工的工作包

### WP0：领域边界与数据所有权

**目标：** 先把“谁拥有数据、谁负责生命周期”说清楚，不先冻结全部字段和 API。

**可执行内容：**
- 梳理 Company、Project、Staff、StaffAllocation、Supplier、SupplierReservation、Committee、PartnerRelationship、Market、Event、WorkHistory、LedgerEntry、WeeklySettlement 的关系；
- 标明公司级、项目级、历史快照、周度临时记录；
- 标明每个实体的创建、更新、结束与归档时机；
- 标明哪些模块只能读取、哪些模块拥有写入权；
- 画出项目完结、委员会停止、关系沉淀、作品历史归档的生命周期。

**交付物：**
- 实体关系图；
- 数据所有权矩阵；
- 关键生命周期图；
- 未决字段/规则列表。

**验收：**
- 同一事实只有一个权威数据所有者；
- 公司状态与项目状态边界清楚；
- 项目结束后哪些数据保留、转移或归档有明确说明。

**禁止：** 不设计完整 ORM/API；不把旧 GameState 结构直接搬进新模型；不改变已确认的核心员工严格单项目分配规则。

### WP1：每周玩家决策流程

**目标：** 先回答玩家每周实际做什么，再反推 UI 与自动化。

**可执行内容：**
- 设计普通周、风险周、项目阶段完成周、项目交付周四种流程；
- 区分必须玩家决定、持续方针自动执行、仅报告不打断三类事项；
- 设计公司总览、项目详情和周回执的信息层级；
- 用 1 个项目、2 个项目、3 个项目对照操作步骤和注意力负担。

**交付物：** 流程图、信息分层表、打断候选清单、双/三项目场景脚本。

**验收：** 玩家能快速识别本周最重要的经营问题；项目数增加不会让每周确认步骤同比增加；重大不可逆操作不会被静默自动化。

**禁止：** 不改变已确认的自动执行边界；不接旧 API；不开发完整前端。

### WP5：员工与组织内容资产

**目标：** 继续既有员工模块内容工作，避免等待新运行时。

**可执行内容：**
- 员工样本与岗位/专业能力/潜力/性格/成长倾向；
- 招聘候选人、临时员工和外包人员的内容样本；
- 员工之间可读、可区分的特征；
- 疲劳、士气、成长的表现文案和状态描述。

**交付物：** 员工内容库、岗位与特征词表、样本说明。

**验收：** 样本有差异、有用途，不只是随机拼接数值；内容能在未来数据模型中映射，但不依赖最终 API。

**禁止：** 不改员工运行时或周结算公式；核心员工严格单项目规则已确认，技术实现由架构智能体自主设计。

### WP6：企划、作品、供应商与合作方样本

**目标：** 为新模型准备可替换的静态内容，而非继续扩展旧项目逻辑。

**可执行内容：**
- 不同规模和类型的作品企划样本；
- 承制、委员会、原创企划的样本差异；
- 供应商专业方向、产能特点、可靠性描述；
- 发行、版权、渠道与合作方样本；
- 不同公司阶段可能接触到的机会样本。

**交付物：** 企划库、作品样本、供应商/合作方样本表、字段语义说明。

**验收：** 样本能体现规模、资源需求、商业机会与风险差异；数值标记为参考样本或待平衡，不冒充正式参数。

**禁止：** 不决定经济公式、正式收益系数、市场刷新算法或运行时数据结构。

### WP7：事件内容与风险表达（仅内容层）

**目标：** 让事件内容可以先创作，但触发和结算机制留给核心规则。

**可执行内容：**
- 项目级/公司级事件主题样本；
- 预警信号、事件描述、选项文案；
- 每个选项的确定成本、可能收益、风险方向和适用情境；
- 普通事件与重大事件的内容层区别。

**交付物：** 事件卡片库、风险提示文案库、选项设计说明。

**验收：** 不存在明显无脑最优答案；选项体现不同经营价值取向；事件有可理解的前因或风险线索。

**禁止：** 不编写旧事件触发器；不接入旧周结算；不自行定义触发概率、事件优先级算法和跨模块状态写入。

### WP9：成长、IP 与 520 周目标

**目标：** 先形成成长目标结构，不急于确定所有解锁数值。

**可执行内容：**
- 前期/中期/后期/终局的经营课题；
- 声望、IP、人才、合作关系、组织能力分别能解锁什么；
- 新能力对应的新成本、新风险或新经营难题；
- 不同公司定位的代表作和终局履历样本。

**交付物：** 成长转化图、阶段目标草案、解锁—挑战配对表。

**验收：** 成长改变可选行动，不只是数字变大；阶段目标不是强制打卡；不同路线可以形成不同公司履历。

**禁止：** 不确定具体数值门槛、设施树、完整科技树或后期收益公式。

### WP10：UI 信息架构与静态原型

**目标：** 在 API 未冻结前，先确定玩家看什么、如何理解公司经营。

**可执行内容：**
- 公司总览：现金、项目组合、人员负荷、近期风险；
- 项目详情：阶段、计划、实际执行、资源占用、风险；
- 周回执：本周结果、变化原因、下周关注点；
- 重要事件：信息、代价、风险和选项；
- 用静态数据制作可点击或不可点击的低保真原型。

**交付物：** 页面结构图、关键页面线框图、静态原型、信息字段清单。

**验收：** 能区分公司级与项目级信息；多项目状态可比较；普通周不要求逐项目打开；不把界面做成密集数据工作台。

**禁止：** 不绑定旧 API、旧 GameState；不实现真实周推进；不自行冻结尚未决定的计划参数。

## 4. 需要先做设计、但暂不进入正式实现的工作包

### WP2：多项目资源分配

基线已经确定：每名核心员工每周严格归属一个项目，不允许同周跨项目支援、借调或拆分工时；周结算后可以重新分配。项目计划自动执行已配置的资源方针，但不会自动招聘临时员工或新增外包合同。

智能体应围绕已确认边界设计分配数据、冲突处理、项目优先级、确定性求解和周结算接口。临时员工与供应商的跨项目调度属于独立问题，可基于仓库规则自主判断；只有改变核心员工单项目约束才构成重大决策变更。

### WP3：统一周结算契约

先写结算阶段和模块职责草案：
1. 收集本周计划与输入快照；
2. 预检现金与共享资源；
3. 锁定资源和强制费用；
4. 计算项目工作量与质量；
5. 计算员工状态、市场与事件；
6. 统一提交状态；
7. 生成周回执。

资金不足的产品方向已确认：强制费用预检失败时整周不提交，公司进入限时资金危机，不立即自动破产、不自动借款；危机期限内未解决才破产。资金危机期间周数、工资与运营费语义仍需设计。事件阻塞、项目暂停、项目完结与事务失败回滚由架构智能体结合已确认的统一周结算原则自主设计。

### WP8：市场、委员会与商业规则迁移

已有承制/委员会、投资比例、公司现金池、项目账归因等历史规则可先整理成“旧规则—新框架—待核验”映射表。

暂时不重写运行时。重点核验：
- 哪些既有规则与多项目、统一现金池冲突；
- 项目级委员会结束后如何归档；
- 长期合作关系哪些数据可保留；
- 商业收入与投资本金、制作经营盈亏如何分账。

### WP4：最小多项目模拟器

必须等 WP0 的领域边界、WP2 的资源分配原则和 WP3 的周结算契约至少形成可用版本后再开始。

首个模拟器只验证：
- 一个 Company；
- 两到三个 Project；
- 少量 Staff 与 Supplier；
- 共享资源竞争；
- 统一现金池；
- 工作量/质量分离；
- 固定 seed 回放；
- 周结算原子性。

不要一开始加入完整委员会谈判、复杂市场、全量事件和设施系统。

## 7. 团队协作与提交约定

- 每个工作包独立分支或独立文档，避免多人同时修改同一核心框架。
- 接任务的人先看 GitHub 线上 main 和当前相关 PR，不只依赖本地旧仓库。
- 每项交付都标注：已确认事实、设计建议、待负责人决定、待验证假设。
- 不得将候选规则写成已确认规则。
- 内容任务不改运行时；静态 UI 不接旧 API；核心规则任务不擅自跨模块改代码。
- 每次提交说明：完成了什么、依据是什么、还缺什么、需要负责人决定什么。
- 任何运行时实现必须附对应测试；只完成文档或原型，不得宣称功能已实现。
