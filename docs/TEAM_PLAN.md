## 内容协作边界

1. **系统机制归原模块负责人。** Sqks183 继续负责企划与员工系统；pyxz0 继续负责事件系统。包括机制规则、生成/触发逻辑、数值计算、状态变化、系统实现与模块交付。
2. **具体内容由 Muchbv 协作。** 包括具体员工人物/简历、企划和作品设定、事件内容与文本，以及与经营流程相配合的轻量剧情。
3. **内容不能自行改变机制。** 内容设计应使用模块负责人提供的字段、触发条件、效果类型和约束；如发现现有机制无法承载内容，先提出需求，由系统负责人评估，涉及全局规则或契约时交 zm 决定。
4. **机制不能擅自改写内容设定。** 系统负责人可提出内容无法落地、数值不平衡或与规则冲突的问题，双方协商；无法达成一致时交 zm 裁定。
5. **内容尽量独立存放。** 员工、企划、事件的具体内容优先采用独立数据文件/内容清单维护，不直接混入核心经营代码。具体格式由内容协作者与对应系统负责人对齐；如需新增契约字段或共享核心改动，仍按共享文件流程处理。
6. **内容交付分层验收。** Muchbv 对内容本身负责，交付时说明内容范围、设定约束、字段填写情况、重复/冲突检查及未完成项；对应系统负责人负责检查数据结构、字段合法性、机制适配、数值/触发约束和进入游戏后的可用性。内容无法被现有机制承载时，系统负责人提出具体差异与建议，不要求内容协作者自行改机制。涉及全局规则或公共契约时交 zm 决定。
7. **内容不以文件提交视为验收完成。** 至少经过格式/数据校验和对应模块负责人审核；影响实际运行结果的内容，还需在游戏内或对应模块测试中抽查实际效果。
6. **轻量剧情不等于新增剧情系统。** 首版只允许在既有员工、企划、事件和经营流程中提供轻量叙事内容，不因此引入独立剧情状态机、复杂分支或额外经营系统。

## 三条标注

**1. 公司经营层归入 zm。** 时间、资金、声望、终局和经营总结由 zm 设计与实现。声望状态由这一层唯一写入；其他模块只在各自结算节点产出 `reputation_delta`，不自行修改 `company.reputation`。

**2. 边界约定：**

- **渠道分账（K3）** 归核心规则层。企划系统提供报价与委员会成员候选，`start_project` 固化渠道并校验委员会模式成员；只有选择 committee 后才生成 Project.total_investment=contract_budget×2；BD 公司所得初始为毛收入50%，`channel_breakdown` 精确对账、付费电视服务由核心规则层实现。合同预算就是制作预算；承制不生成投资规模。
- **事件系统** 只能调用既有员工、供应商、财务与阶段配置规则，不能直接改状态、不能改合同目标或条件。应急外包走供应商系统，承制不可延期、委员会最多一次延期仍按既有规则。
- **作品履历** 由跨系统集成层唯一写入 `WorkRecord` 与 `previous_work_id`。核心规则层只产出阶段质量、作品评价和结算输入，不另写一份历史。
- **员工提案** 由企划系统提供报价形状与生命周期，采纳/拒绝后进入 `custom_offer` 槽位；核心负责开工校验与资金原子入账。

**3. 共享核心文件按模块负责、串行集成，不再由 zm 独占编写：**

- **模块负责人可以直接实现所属模块的核心逻辑。** Sqks183 可提交企划、员工、招聘、用工与供应商相关的 C++ 核心实现；pyxz0 可提交事件相关的 C++ 核心实现。对应模块的测试、必要界面和模块文档也由模块负责人一并维护。不得因为文件名属于“核心”就要求模块负责人只交规则提案、由 zm 代写实现。
- `packages/game-core/src/game_core.cpp`、`packages/game-core/include/game_rules.hpp` 等多人会触及的共享文件，允许模块负责人在自己的分支中修改，但必须把改动限制在所属模块及已确认契约范围内。若两个任务需要修改同一文件，应通过 PR 基线/堆叠关系串行推进，明确先后顺序；不得让多个分支各自基于旧版本并行改写后直接合并。
- **zm 保留全局规则和公共契约的最终决定权，以及共享核心的集成与合入责任。** 涉及跨模块状态所有权、公共数据结构、存档兼容、随机协议、全局结算顺序或其他模块行为的改动，必须先提出影响说明并经 zm 确认；模块内部实现细节由模块负责人自主决定。
- `packages/game-core/bindings/embind.cpp`、`apps/web/src/types/gameV3.ts`、`apps/web/src/test/fixtures.ts`、存档格式/校验及跨模块浏览器测试属于跨层共享契约与集成面。模块负责人可以提交必要的配套改动，但 PR 必须明确契约影响，并由 zm 审查后集成；不得绕过契约审查自行改变公共协议。
- 原生/WASM 测试由模块负责人为所属功能补充和维护；zm 负责组织跨模块回归与整体验收。各模块自己的界面改动由模块负责人提交，避免把模块实现与集成工作全部集中到 zm。
- **模块验收**由模块负责人完成：覆盖本模块正常路径、边界条件、失败/回滚路径及必要的数据校验，并说明未验证项。
- **接口验收**由发生交互的模块负责人共同完成：验证真实调用、输入输出、状态归属、错误处理和结算时序；不能只用 Mock 结果宣称已集成。
- **整体验收**由 zm 组织：以玩家实际操作路径跑通完整核心循环，检查跨模块状态变化、资金/声望/履历等账目一致性、阶段推进和存档兼容。涉及 WASM/浏览器运行的功能，需在真实目标环境验证；环境不具备时明确标记未验证，不以类型检查或单元测试替代。
- 内容协作者可维护模块约定的数据文件/内容清单；涉及字段、运行时行为或共享文件时，先与对应系统负责人对齐，再按上述契约审查流程处理。

## 推进方式

1. 模块负责人从最新 `main` 建短期分支，先提交规则提案和验收用例，再提交实现。
2. 内容协作者先与对应模块负责人对齐内容需求和数据格式，再提交独立内容清单/数据文件或 PR；不直接修改系统机制和共享核心文件。
3. 模块负责人可在所属模块范围内直接修改共享核心文件并提交 PR；涉及全局规则或公共契约时先由 zm 确认。多人需要修改同一文件时，先在对应 Issue/PR 声明文件、改动范围和基线；后续 PR 基于先行 PR 分支堆叠，或等待其合入 main 后再同步。同一共享文件同一时间只推进一条独立集成链；不同文件且无契约冲突的工作可并行。上游合入后，下游提交者负责更新基线、解决冲突并说明差异。zm 确认集成顺序、审查跨模块影响并最终合入；PR 作者不得自行合并涉及共享核心/公共契约的 PR。不得让多个分支基于同一旧版本各自改写后直接合并。
4. 一个 PR 对应一个可验收任务，系统任务认领走对应模块议题；跨模块内容协作由内容设计议题追踪。
5. 数值全部 `TODO(待定)`，集中进核心参数配置；前端不另写公式。

## 验收纪律

- 规则以 C++ 核心为准，前端不复制计算公式；验收只认真实 WASM 和可以手算的账。
- 契约字段存在不等于玩法已实现。核心行为落地前，新决策返回 `INVALID_INPUT`，文档和议题按这一边界表述。
- 规则变化进 `GAME_RULES.md`，协议变化进 `API.md` / `DATA_MODEL.md`，实现状态进 `PROGRESS.md`。文档不得领先于实现。
- 同一初始状态、种子和决策序列必须可复现；新增随机消耗点须同步随机协议并保持存档兼容纪律。
