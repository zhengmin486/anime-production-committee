# 员工人物卡转化规范与样例：宁世清

> 状态：内容生产流程归档；宁世清数据仍为候选提案，未标定、未接入运行时、未进入招聘池。
> 来源：团队空间「共享资料库」中的《宁世清_定稿》，提交人 @笑歌自若。
> 本文只归档内容转化方法与本张卡的候选映射，不新增玩法规则、不修改 V4 存档契约。

## 1. 转化原则

人物卡转化采用“原稿保留、运行时映射、提案隔离、数值待标定”的方式：

1. **原稿完整保留**：人物履历、性格、原话、视听提示等作为角色风味内容资产保存，不因当前开发阶段暂不使用而删除。
2. **只提取游戏当前需要的数据**：员工身份、基础职业、雇佣类型、六项能力、潜力、天赋候选，以及后续经系统确认的特性。
3. **严格遵守 V4 契约**：使用现有字段和合法枚举；不得为了容纳人物创意擅自新增存档字段。
4. **运行时数据与内容提案分离**：当前没有对应 V4 字段的特性、潜力线索等，暂存于内容提案，不写入 Staff 存档。
5. **创作者提供方向，系统负责人裁决规则**：创作者可提出强弱倾向、潜力方向和特性创意；能力数值、职业资格、天赋映射、潜力机制、特性效果与幅度由系统负责人确认。
6. **占位公式不得冒充正式标定**：由当前临时运行时公式推导出的薪资、签约费只能标注为占位结果，不作为正式内容数值。
7. **不得把人物设定写成规则例外**：人物的职业资格、主责/协力/不适配关系均服从全局职业规则；监督职业与项目级监督岗位资格按现行规则校验。

## 2. 标准转化分层

| 来源内容 | 游戏侧落点 | 处理方式 |
|---|---|---|
| id、姓名、基础职业、雇佣定位 | `staff.id/name/role/employment` | 映射为 V4 员工基础字段 |
| 六项能力画像（强/中/弱） | `staff.abilities` | 先记录定性倾向，再由系统负责人按统一能力分布标定六项数值 |
| 潜力线索 | `staff.potential`、`staff.revealed_potential` | 按成长系统契约映射；未揭示状态遵循统一规则，不自创展示字段 |
| 天赋类型 | `staff.talent_type` | 只使用 V4 合法枚举；原始创意标签保留为待映射提案，不强行近似替换 |
| 特性创意 | 当前无 Staff traits 存档字段 | 暂存内容提案；由系统负责人决定是否映射到既有系统或走契约变更 |
| 简历、性格、原话、视听提示 | 角色风味文本 / 内容资产 | 完整保留，不塞入运行时 Staff 存档 |
| 初始经验、疲劳、士气、项目归属 | V4 初始化字段 | 使用统一初始化规则，不由人物作者随意指定 |
| 周薪、签约费 | `weekly_salary`、`signing_fee` | 依据统一薪酬/招聘标定计算；占位公式结果不得定稿 |

## 3. 责任边界

- **人物内容作者**：身份、职业背景、性格、视觉、能力强弱倾向、潜力方向、特性创意。
- **内容转化人员**：字段映射、合法性检查、运行时数据与风味文本分离、缺口登记、候选数据文件整理。
- **系统负责人**：能力数值标定、职业资格与主责/协力映射、天赋映射、潜力机制、特性机制与数值、薪酬/签约费，以及是否需要契约变更。
- **运行时接入**：只有经系统负责人确认且通过当前 Schema/契约审计的数据，才可进入正式内容目录或招聘池。

### 4.4 特性提案（不进入当前 Staff 存档）

**多岗位协力兜底**
- 创意：在职业资格允许的工作项中具备较强协力价值；多项工作参与可能增加疲劳压力。
- 边界：不得改变基础职业、授予不适配资格、突破一周一项目或绕过疲劳规则。
- 状态：待系统负责人判断是否能映射既有特性体系及标定效果。

**质量守门**
- 创意：关键检查类工作项更容易提前发现主要问题、降低返工风险；检查推进速度可能较慢。
- 边界：不直接增加最终质量分，不绕过质量计算与返工流程。
- 状态：待系统负责人判断是否能映射既有特性体系及标定效果。

### 4.5 薪酬与初始化

- 转化稿中的签约费 313000、周薪 42800 来自占位公式，**不作为正式数值**。
- 正式周薪与签约费等待统一能力/薪酬/招聘标定后计算。
- 经验、疲劳、士气、项目归属等由 V4 统一初始化，不沿用人物作者或转化稿的任意默认值。
- “核心候选”不等于已经入职；招聘完成后再按正式流程生成在职员工状态。

### 4.6 风味内容保留

宁世清的简历与入行背景、AC 社经历、性格辨识度、原话、视听提示继续保留在原始人物卡/角色内容资产中。当前不扩展固定人物关系或个人剧情系统；AC 社内部恩怨可在游戏侧简介中压缩表达，但原始作者稿不删改。

## 5. 待系统负责人确认

1. 六项能力候选值是否符合职业能力分布及当前员工数值标尺。
2. `generalist` 是否存在合适的 V4 天赋映射；若没有，保留为待映射提案，不强行使用 `steady_floor`。
3. 潜力候选值与成长/揭示规则是否匹配。
4. 两项特性是否能映射现有特性体系；若不能，是否值得提出契约或系统扩展。
5. 薪酬和签约费按统一标定结果重新计算。

## 6. 接入门槛

- 不把宁世清加入招聘池；
- 不将本文件中的候选值写入 DECISION_LOG 作为已确认规则；
- 可以继续保留原始人物卡与本转化记录，供后续内容生产和标定使用。
