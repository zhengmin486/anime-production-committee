# 开源项目借鉴调研（第一轮）

- 调研日期：2026-11-22
- 调研对象：《动画制作委员会》（Anime Production Committee）
- 目标：从公开 GitHub 项目中寻找可借鉴的经营玩法、制作流程、系统架构、事件反馈、员工管理、UI 表达和数值平衡方法。
- 本文性质：第一轮案头调研 + 一轮补充搜索。不是完整代码审计，也不构成新增需求或改动已确认规则的授权。文中“五阶段制作”是调研当时的旧玩法引用，现行制作结构以 [DECISION_LOG.md](DECISION_LOG.md) 的项目级公共制作 + 单集六阶段为准。
- 补充搜索（2026-11-22 晚）：新增 3 个项目，见标注「补」的行；结论从三类扩展为四类。

## 一、结论摘要

值得继续深入的项目分成四类：

1. **经营模拟与项目循环**：SimDev、Agency Simulation、Tech Empire。
2. **模拟引擎、经济与可测试性**：SimCorp、MarketForce、Game Inc.。
3. **动画制作流程与员工工作流**：Animation Workflow Manager、Stalker、SHS_infoGal_tycoonGame。
4. **数值设计与平衡（补）**：econ。与 SimCorp 互补——SimCorp 保证账目记对，econ 提供验证数值不崩的校验方法。

对本项目最有价值的不是照搬功能，而是借鉴以下做法：

- 把每周推进、项目阶段、资金流水、人员状态和事件触发放在可解释、可复现的模拟流程中。
- 让项目机会同时呈现预算、工期、付款/收益条件和风险，而不只是一个“接不接”的按钮。
- 让员工疲劳、压力、工作进度通过明确反馈影响玩家判断。
- 让重大事件留下可查询的项目履历，让玩家能理解事件如何影响结果。
- 用分层的任务、场景、素材、版本和审核记录表达动画制作过程；但本项目只抽取适合经营游戏的轻量概念，不做真实生产管理软件。

**本轮不建议新增玩法系统。** 优先把已有规则做出清晰反馈和可验证的实现。若要吸收新机制，先写成提案，说明它解决的现有问题、影响哪些系统、是否扩大首版范围。

## 三、逐项观察

### 1. SimDev — 游戏开发公司经营

仓库：[SuitedTom/SimDev](https://github.com/SuitedTom/SimDev)

README 提到新建/读取存档、公司资金与员工、项目开发周期（计划、开发、测试、打磨）、研究和声望系统。游戏主要通过命令行式交互操作，项目目前仍处于 Beta，README 将 DLC、续作、竞争公司和终局等列为后续计划。

**值得借鉴**
- 项目生命周期被表达为清晰的阶段，而不是一个孤立的完成进度条。
- 公司经营、员工管理、项目决策和作品评价在同一循环中。
- 题材相近，可用来检查玩家是否能理解“经营公司”和“制作作品”两层目标。

**不宜照搬**
- 其命令行交互与本项目的像素经营界面不同。
- README 列出的后续规划不能视为已实现功能。
- 不要因为它有研究/技术树，就给本项目增加类似成长系统。

**建议继续检查**：项目创建流程、阶段间玩家决策、项目结束后的声望/评价反馈、存档结构。

### 2. Agency Simulation — 制作公司接单与财务

仓库：[banyapon/agency-empire](https://github.com/banyapon/agency-empire)

README 描述了广告制作公司的项目机会、接受/拒绝、预算、工期、账单、预付款、员工招聘、工资、运营成本和随机事件。它以 VS Code 扩展 WebView 运行，不是传统独立游戏。

**值得借鉴**
- 项目机会不只显示题目，还涉及预算、时间和付款条件。
- 项目完成、生成账单、等待回款与公司日常支出分开处理。
- 通知流能让项目完成、付款和突发事件成为持续反馈。

**对本项目的启发**
- 承制合同的合同收益、项目成本、超支和结算应在玩家界面上清楚区分。
- 项目结算后的现金变化要能追溯来源，避免玩家只看到一个总数变化。
- 项目进展和公司资金压力应形成连续反馈。

**注意**：README 中部分功能被标注为未来更新；本轮未实际运行确认。仓库声明 MIT 许可证，但借鉴代码或素材前仍需保留许可证与版权声明。

### 3. Tech Empire — 覆盖面较广的工作室经营模拟

仓库：[stark-studio-labs/game-dev-empire](https://github.com/stark-studio-labs/game-dev-empire)

README 描述周制 tick、员工能力/疲劳/士气、培训、财务、贷款、发行商合同、动态事件、解锁进度、竞争公司和多个结局；并列出模块化模拟逻辑、CDP 测试与 Playwright E2E 测试。

**值得借鉴**
- 周制 tick 和倍速控制的表达方式。
- 用解锁节奏控制信息量，避免开局同时展示所有系统。
- 事件、里程碑、结局目标和历史记录可以在 UI 中形成反馈。
- 将模拟逻辑模块化，并把逻辑测试与真实界面测试分开。

**风险与限制**
- README 宣称的测试数量、系统数量和完成状态尚未独立核验。
- 其游戏开发公司题材与本项目相似，但玩法体量远大于本项目首版。
- 贷款、培训、多个业务线、IPO 等不属于本项目已确认范围，不应因为看到就加入。

**建议继续检查**：周结算顺序、状态变更入口、模块之间如何传递数据、事件如何影响结算、UI 是否能解释数值变化。

### 4. SimCorp — 确定性模拟与账目审计

仓库：[Splortch/Simcorp](https://github.com/Splortch/Simcorp)

README 描述 Python 确定性经济模拟、SQLite 持久化、双重记账、交易流水、React 仪表盘和 pytest 测试；项目仍在演进，部分需求列在后续里程碑。

**值得借鉴**
- 资金变化以交易记录为基础，而不是在多个系统里直接随意修改余额。
- 现金余额、收入、利润、估值等指标区分展示。
- 经济计算与 UI 分离，便于对公式做独立测试。
- 用自动化测试检查库存约束、偿付能力提示和交易完整性。

**对本项目的启发**
- 继续强化承制合同、投资本金、制作成本、商业收益、BD 分成等账目来源的可追溯性。
- 对关键结算编写可手算样例与自动化断言。
- 确定性随机和固定结算顺序要有回归测试。

**注意**：其 AI 管理团队和制造业库存模型与本项目无直接关系。不要照搬双重记账架构，先判断现有资金模型是否真的需要。

### 5. MarketForce — 市场竞争和结算解释

仓库：[scottwleonard/marketforce](https://github.com/scottwleonard/marketforce)

README 描述 Godot 企业竞争模拟：玩家在研发、营销、生产、财务四个部门做决策，与 AI 公司竞争；结算后给出损益表、资产负债表、现金流、市场份额和细分市场分析。

**值得借鉴**
- 市场结果不仅给出一个总评分，还能拆解需求、价格、份额和财务结果。
- 竞争者的行为会对玩家决策产生反馈。
- 经营阶段结束后有结构化报表，帮助玩家理解决策后果。

**对本项目的启发**
- 作品结算页应尽量解释评价、收益、成本、声望变化来自哪里。
- 市场热度和企划预期的影响应在结果反馈中可理解，而非完全隐藏。
- 不需要引入完整竞争市场或多部门操作。

### 6. Game Inc. — 数据驱动内容和事件

仓库：[pierreyoda/GameInc](https://github.com/pierreyoda/GameInc)

README 描述一个早期 Unity 项目，使用 JSON 配置平台、员工能力、功能、事件、世界新闻等内容；事件可用触发条件和动作脚本表达，并有动态市场与随机员工生成。README 明确说明项目处于早期阶段且暂停。

**值得借鉴**
- 内容数据与代码逻辑分离，适合配置大量企划、事件和员工特性。
- 事件包含触发条件、触发限制和动作，而不是单纯随机弹窗。
- 可以从数据层控制事件的可触发次数与前置条件。

**不宜照搬**
- 自制脚本语言会带来解析器、调试和安全维护成本。
- 项目早期且暂停，不适合作为成熟实现的范本。
- 本项目首版不需要自制 DSL；简单结构化配置足够。

### 7. Animation Workflow Manager — 动画制作任务流程

仓库：[Rak2k6/WorkFlow-Manager](https://github.com/Rak2k6/WorkFlow-Manager)

README 描述动画项目的场景与任务生命周期、人员分配、Google Drive 素材关联、协作审核、评论反馈和操作审计。

**值得借鉴**
- 动画生产的任务、场景、负责人、素材和审核状态之间的关联。
- 变更记录与评论反馈可以保留工作过程，而不是只保存最终状态。
- 任务状态机能帮助明确“待处理、进行中、待审核、完成”等状态。

**对本项目的启发**
- 作品制作阶段、阶段任务、人员配置和重大事件履历应保持清楚的关联。
- 重大事件可以记录处理方式和最终结果，形成作品履历。
- 只吸收玩家需要理解的流程概念，不做真实动画团队协作平台。

### 8. Stalker — 动画/VFX 项目与资产关系

仓库：[eoyilmaz/stalker](https://github.com/eoyilmaz/stalker)

README 将其定位为面向动画和 VFX 工作室的生产资产管理库，支持项目、任务、里程碑、截止时间、镜头/场景/序列与素材引用，并强调可定制对象模型和 TDD。其许可证为 LGPL-3.0。

**值得借鉴**
- 项目、任务、素材、版本引用之间的关系模型。
- 里程碑与任务进度可以分层管理。
- 测试驱动有助于在复杂关联下防止数据关系回归。

**不宜照搬**
- 这是专业生产管理库，不是经营游戏。
- PostgreSQL、TaskJuggler 等技术栈与本项目无直接迁移价值。
- LGPL-3.0 有其许可证义务；本项目只研究概念，不复制代码。

### 9. SHS_infoGal_tycoonGame — 员工工作与压力反馈

仓库：[8feet/SHS_infoGal_tycoonGame](https://github.com/8feet/SHS_infoGal_tycoonGame)

README 描述 GameMaker 员工与建筑经营原型：员工被分配到工作地点后产生工作进度和压力，休息区恢复压力，界面通过进度条显示状态，并对批量更新做性能处理。

**值得借鉴**
- 员工状态需要有玩家可读的视觉反馈。
- 工作进度与压力并行展示，玩家能理解效率与疲劳之间的关系。
- 工作完成、没有后续工作、工作地点被移除等情况都有明确状态转换。

**限制**
- 项目偏原型，README 未列明确许可证。
- 其空间建筑/拖拽分配机制与本项目周制岗位配置不同。
- 不应复制其代码或素材；仅参考状态反馈思路。

### 10. econ — 游戏经济平衡校验工具（补）

仓库：[samw3/economy](https://github.com/samw3/economy)

README 描述一个用 YAML 描述游戏经济规则、再用三种手段交叉验证的 Python 工具链：linter 找 money pump、物品复制、死亡刷钱、惩罚规避、风险收益倒挂、生命周期过长/过短和缺少回收口；Lean 4 内核检查「任何交易/合成组合都不能凭空创造价值」这类证明；Monte Carlo 模拟器按策略跑多次并输出成长与财富曲线。命令包括 `lint`、`sim`、`prove`、`tables`、`diff`。

**值得借鉴**
- 验证账目正确不止靠手算样例和回归测试，还可以检查「是否存在无中生有的操作路径」。线性规划 + 内核证明给了一个更强的正确性边界。
- `diff old.yaml new.yaml` 这类「一次参数改动修好了什么、弄坏了什么」的输出，适合本项目的待定参数表。
- 规则用数据表描述、校验与游戏运行时分离，和本项目「公式集中在核心、前端不另算」的分层一致。

**不宜照搬**
- 其模型是 RPG 战斗掉落经济，与承制/委员会、周制制作、分账不是同一域；迁移的是校验方法，不是公式和 YAML 格式。
- 0 star、2026-10 新建、README 的方法自述未独立运行验证；本项目首版不需要引入 Lean 4 工具链。
- 可作为后续「参数平衡验收」的思路储备，不进入当前实现范围。

### 11. numeric-kit — 中文游戏数值工具链（补）

仓库：[limoaCatherine/numeric-kit](https://github.com/limoaCatherine/numeric-kit)

README 描述以框架工作簿为单一事实来源，做表驱动战斗模拟、场景覆盖率、属性边际分析和多场景平衡提案，并配本机 Excel MCP；仓库明确不包含框架表。

**值得借鉴**
- 「框架表是唯一事实来源、代码只读表再出提案」的工作流，与本项目参数集中配置的约束同向。
- 模拟跑完先写回结果，再由单独步骤生成平衡提案，避免边模拟边改参数。

**限制**
- 战斗数值向，不覆盖经营游戏的现金流与声望平衡。
- 缺框架表就无法复现流程，0 star，仅参考工作流，不作为实现范本。

## 四、跨项目归纳：对本项目真正有用的点

| 主题 | 可借鉴的通用做法 | 本项目落点 | 是否新增系统 |
|---|---|---|---|
| 项目机会 | 同时展示预算、工期、条件与风险 | 企划卡片、承制/委员会决策 | 否，改善现有信息表达 |
| 制作循环 | 阶段推进有状态、有反馈、有明确结算 | 项目级公共制作 + 单集六阶段、工作项依赖与周推进 | 否 |
| 员工状态 | 能力、工作进度、疲劳/士气同时可读 | 员工与外包模块 | 否 |
| 事件机制 | 条件触发、次数限制、效果范围、处理结果 | 制作事件模块 | 否，已有规则 |
| 资金结算 | 每笔收入/支出有来源，能复核 | 财务与作品结算 | 否，强化正确性 |
| 数值校验（补） | 检查是否存在无中生有的资金路径；参数改动出 diff | 待定参数表、结算回归 | 否，方法储备 |
| 市场反馈 | 结果拆解为评价、需求、收益等可理解因素 | 作品结算、市场热度 | 否 |
| 制作履历 | 记录任务/事件/版本/处理结果 | 作品历史与重大事件履历 | 否，按既定契约实现 |
| UI 反馈 | 进度、状态、风险和结果有一致视觉语言 | 游戏经营与制作界面 | 否 |

## 五、对当前项目的具体建议

### P0：不改变玩法，先保证玩家看得懂

1. **企划选择**：每张企划卡片明确来源、规模、热度、合同/投资路线限制、预期风险与收益方向。
2. **周推进反馈**：推进一周后，显示本周发生的关键变化，不只刷新数字。
3. **员工配置**：推荐配置与手动调整结果要能解释差异；疲劳、士气、能力变化需要可见。
4. **事件处理**：选项旁明确确定代价、潜在风险等级和效果持续范围；重大事件写入作品履历。
5. **作品结算**：拆分合同收入、投资支出、制作成本、商业收益、分账和最终净变化。
6. **公司状态**：声望、资金、团队和历史作品的变化都能追溯到具体原因。

### P1：实现过程中重点检查

- 周结算顺序是否唯一、稳定、可重放。
- 随机事件是否在固定检查点消耗随机数。
- 同一笔资金是否可能被多个系统重复入账。
- 事件是否绕过员工、供应商、延期、合同和终局规则。
- 作品历史是否只在正确的结算节点写入一次。
- UI 展示的数值是否来自核心状态，而不是前端自行计算出另一套口径。

### 暂不建议增加

- 复杂研发/科技树、培训系统、办公室扩建、贷款、IPO、多业务线。
- 真实动画生产工具中的素材版本管理、云盘、多人评论、审核工作流。
- 自制事件脚本语言、完整市场竞争模拟、多个并行项目。
- 大量随机员工剧情或跨项目永久事件。

这些功能可能在其他作品中有用，但会明显扩大本项目首版的开发和维护成本，且不是当前核心循环的必要条件。
