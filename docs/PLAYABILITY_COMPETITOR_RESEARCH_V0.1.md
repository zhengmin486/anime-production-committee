# 可玩性竞品研究：第一轮桌面研究与实机观察提纲

状态：2026-11-24 · 第一轮研究记录。桌面资料已整理；实机游玩观察尚未完成。本文不构成正式规则。

> 规则更新说明（2026-11-25）：本文早期讨论的“限时资金危机”仅是当时的设计建议，已由 DEC-FIN-002/003 覆盖。首版当前规则为刚性支出预检不足时整周回滚并直接破产；危机周、负现金欠付与融资自救仅保留为未来更新候选。本文不授权按旧建议实现。

## 1. 研究目标

本项目不再只问「动画公司现实中怎样运作」，还要问：

- 玩家在每个时间点具体做什么决定？
- 玩家掌握哪些信息，哪些信息未知？
- 哪些系统会让玩家期待下一次推进？
- 随机结果如何形成新的决策，而非纯粹惩罚？
- 玩家为什么会在结算后想继续经营或重新开局？

研究单位是玩家体验过程，不是功能清单。每个案例都要记录「机制 → 玩家选择 → 即时反馈 → 长期后果 → 情绪/动机」。

## 2. 第一轮核心案例

### A. 开罗《游戏发展国》（Game Dev Story）

**适合研究：** 轻量经营循环、员工成长、创作组合、作品交付与市场评价。

公开商店介绍确认的核心要素包括：经营游戏公司、聘用和训练员工、员工转职、随经验解锁更多游戏类型与内容、寻找受欢迎的题材组合、开发自有主机。官方描述可作为功能事实来源，但不能单凭商店描述判断实际节奏与乐趣。

对本项目的研究问题：
- 从接项目/选题到作品交付，玩家每个阶段做什么决定？
- 作品开发前，题材、类型、人员和投入如何组合？
- 开发中的数值成长是否足够可见？
- 作品评价、销量和公司成长怎样形成下一轮目标？
- 玩家是否能从员工职业变化与培养中形成长期规划？

**对本项目的初步假设：** 动画企划需要成为玩家能主动塑造的作品，而不只是一个有固定工作量的合同。选题、定位、人员搭配与投入应能在最终作品上留下可识别的差异。

来源：
- Steam 商店页：https://store.steampowered.com/app/1847240/Game_Dev_Story/
- Apple App Store：https://apps.apple.com/us/app/game-dev-story/id396085661

### B. 《白箱》（SHIROBAKO）

**适合研究：** 多角色协作、制作协调、依赖关系、制作危机与跨团队沟通。

《白箱》把制作助理/制作进行放在叙事中心，展示其如何协调动画师、导演、上层制作人员、自由职业者、外包公司、配音和声音团队等角色。它特别适合帮助我们发现：项目不是单一产能条，而是大量人员和交付物之间的依赖网络。

但《白箱》是戏剧化虚构作品，不应当作行业事实的最终依据。学术分析也提醒，其呈现可能戏剧化或省略现实生产结构；应把它当作协作冲突与叙事素材，而非完整行业调查。

对本项目的研究问题：
- 一项工作为什么会卡住？卡点是人、物料、确认、外包还是上游交付？
- 制作进行如何通过信息和关系解决问题？
- 一个小环节延误如何影响其他部门？
- 团队成员的个性、经验和关系怎样改变解决方案？
- 哪些危机能让玩家做出选择，而不是只等待计时器？

**对本项目的初步假设：** 项目应体现跨阶段依赖和交付协调；玩家作为经营者/制作统筹，不应直接控制每一张原画，但应能处理资源冲突、交付风险和沟通决策。

来源：

- Crunchyroll Anime Academy 制作流程介绍：https://www.crunchyroll.com/news/features/2020/8/6/feature-anime-academy-teaches-all-about-the-anime-production-process
- 3D 导演访谈：https://bukuro-souken.com/en/article/34740/

### C. 《RimWorld》

**适合研究：** 涌现故事、事件节奏、人物自主性、随机事件的连锁后果。

桌面研究中最重要的发现是：RimWorld 的故事感并非来自孤立的随机事件卡，而是来自玩家可控行动、角色状态、持续事件与系统之间的相互作用。事件能够延续并重叠，造成连锁后果；叙事导演会根据局势安排事件节奏。相关开发者访谈强调，角色数量与个体特征设计也服务于让玩家记住人物，而不是无限扩大模拟规模。

对本项目的研究问题：
- 事件是否与当前项目、员工、现金流和声望状态相关？
- 一次事件是否会留下持续状态，而不是弹窗关闭就结束？
- 两个事件重叠时是否产生新局面？
- 系统如何避免玩家遭遇无法恢复的连续坏运气？
- 玩家是否能从员工有限但鲜明的特征中读出人物故事？

**对本项目的初步假设：** 建立一个轻量的「制作故事导演」可能比堆大量随机事件更有效。它读取公司和项目状态，选择适合当前局面的事件，并控制强度、间隔和恢复窗口。

- Game Developer：RimWorld 事件系统与故事生成设计访谈：https://www.gamedeveloper.com/design/how-i-rimworld-i-fleshes-out-the-i-dwarf-fortress-i-formula

## 3. 专项参考

### 《Game Dev Tycoon》

与本项目同属创作公司经营题材，可作为「作品开发—市场反馈」的交叉对照。重点观察作品方向选择、研发过程、人员配置、评审反馈、销量曲线与公司成长如何构成闭环。不要因为题材相似就直接照搬其公式。

来源：https://store.steampowered.com/app/239820/Game_Dev_Tycoon/

### 《足球经理》（Football Manager）

仅研究人员经营：球员/员工评估、潜力、状态、团队适配、长期培养与短期成绩的取舍。重点是人员决策如何产生长期投入感，不需要复制其庞大数据规模。

### 《双点医院》（Two Point Hospital）

仅研究信息呈现与经营反馈：问题如何被看见、反馈是否易懂、轻量事件如何打断重复流程、幽默如何缓冲压力。重点不是增加更多管理面板。

## 4. 第一轮对本项目的设计假设

以下是待验证假设，不是决定：

1. **制作故事生成**：项目状态、员工状态、资源和外部环境共同决定可能发生的事件。
2. **随机结果有后续**：事件可以改变持续状态，影响后续周、人员关系、交付或市场机会。
3. **作品是玩家的创作成果**：六维质量、题材定位、制作策略共同形成作品个性，结算不止一个综合分。
4. **员工是有限的个体**：员工的专业、能力、状态和少量鲜明特征影响其工作表现与事件互动。
5. **玩家控制方向而非每个动作**：玩家主要决定项目、资源、人员配置和危机处理，常规制作由系统推进。
6. **反馈要有层次**：周反馈让玩家知道发生了什么；阶段反馈让玩家理解趋势；作品结算让玩家看到长期决策结果。

## 5. 实机观察记录模板

桌面资料不能替代实际游玩。每款核心作品至少记录一个完整经营周期；时间有限时，先记录首小时和一次完整作品交付/危机处理。

| 观察项 | 记录问题 |
| --- | --- |
| 开局目标 | 游戏给玩家什么短期目标和长期目标？ |
| 推进频率 | 玩家多久做一次有意义的决定？ |
| 决策类型 | 选方向、分配资源、人员安排、危机处理、投资？ |
| 信息可见性 | 玩家提前知道什么？哪些结果不确定？ |
| 随机性 | 随机从哪里来？是否与局势相关？ |
| 反馈 | 玩家如何知道决策有效？ |
| 人物 | 玩家是否记住具体员工？为什么？ |
| 作品 | 作品是否有个性？玩家是否期待结果？ |
| 挫折 | 失败是否可理解、可恢复、可归因？ |
| 重玩动力 | 下一局会尝试什么不同策略？ |

每次记录至少选一个具体片段，写成：
「当时局势 → 我有哪些选择 → 我为什么选 → 系统反馈 → 后续影响 → 我产生的感受」。

## 6. 当前研究结论（暂定）

- 开罗提供轻量经营与成长循环的参照。
- 《白箱》提供制作协作、交付依赖和危机处理的叙事参照。
- RimWorld 提供随机事件与系统交互生成故事的参照。
- 三者并非同一层面的竞品：前者是经营游戏、第二者是动画叙事作品、第三者是系统驱动的故事生成游戏。必须按各自适合回答的问题使用，不能简单拼接。
- 当前项目最值得验证的方向是：**玩家做出经营决策后，系统能否把它与员工、制作流程、随机事件和作品结果结合，持续生成有因果关系的制作故事。**

## 7. 下一步

1. 对《游戏发展国》和《RimWorld》做实机观察；若条件允许，用户实际游玩并提供体验记录。
2. 对《白箱》按关键制作危机片段拆解，不把剧情事件直接转换成随机事件表。
3. 为本项目写一份「玩家一季体验脚本」，明确每周可见信息、决策、随机反馈和阶段目标。
4. 用纸面/轻量原型验证体验后，再决定是否修改正式规则与模拟器。
