# 团队异步协作约定

状态：2026-11-23 · 适用于当前非全职、按天异步沟通的开发团队。

> 当前 Agent 默认决策权与文档冲突处理按 [ADR-0004](decisions/ADR-0004-agent-decision-authority-and-local-blocking.md) 和 [ADR-0005](decisions/ADR-0005-document-conflict-resolution.md) 执行；本文件提供操作摘要，不另设更高或不同的规则。

## 目标

团队成员的可投入时间有限，沟通也不保证即时。因此协作不以实时同步为前提，而以**模块自治、契约先行、异步交接、阶段集成**为原则。

本约定不要求每日打卡、固定在线或频繁开会。目标是减少等待和返工，让成员在几天没有收到回复时，仍能安全推进大部分工作。

## 1. 模块自治

1. 模块负责人对自己模块的规则细节、内部实现、模块测试和交付质量负责。
2. 任务拆分时，优先划出可独立完成的完整工作包，不把大量细碎任务分派给不同成员。
3. 模块内部可以自行决定、且不影响其他模块的细节，由模块负责人自行处理并记录，不必逐项等待总负责人批准。
4. 模块对外的接口、共享数据结构、跨模块状态写入权和全局规则不得自行改变；需要变更时先提出契约变更。
5. 内容协作者按对应系统负责人提供的字段、约束和数据格式工作，不自行创造运行时机制或接口。

## 2. 依赖先行，避免互相等待

任务开始前，标明依赖属于哪一种：

- **无依赖**：可直接独立开发。
- **契约依赖**：外部模块尚未实现，但输入、输出、错误处理和调用时机已确定。可以使用 Mock、Fixture 或临时适配层继续开发。
- **强依赖**：缺少上游行为会导致实现方向不确定或产生不可逆改动。先完成必要的接口确认或等待上游交付。

默认应尽量把强依赖转化为契约依赖。不能因为上游模块尚未完成，就让整个下游模块停工。

使用 Mock 或 Fixture 时，应标明它们只是开发替身，不得把替身行为误当成真实集成结果。

## 3. 异步沟通与决策

1. 默认通过对应 GitHub Issue / PR 评论沟通，重要结论进入文档或议题，不依赖口头消息作为唯一记录。
2. 不要求即时回复，也不默认要求当天回复。提出问题时应给出背景、具体问题、自己的建议和受影响范围，方便对方有空时一次性处理。
3. **没有冻结决策不等于阻塞。** 先查 DECISION_LOG、架构/契约、当前 main、已有测试和实际调用；能由既有依据推导的直接实现。
4. 将未决问题分为：
   - **模块内实现选择**：不改变产品语义、既有契约和跨模块权威，由模块负责人自行决定。
   - **低风险临时假设**：局部、可逆且不改变玩家可见行为/经济结果，采用最小方案继续推进，并在 PR 标注假设、理由、影响和回退方式。
   - **实质性裁决**：涉及冻结规则、玩家行为/经济结果、既有字段/命令语义、状态权威、Finance/Archive 权威数据或失败原子边界，才升级 zm。
5. 任何未决问题都必须局部化：明确可独立推进、可临时推进和真正受阻的部分。只暂停直接依赖裁决的最小范围，不得暂停整个模块。
6. **阻塞问题必须形成可处理的问题单。** 提问者说明任务/分支基线、已完成部分、具体卡点、为何不能自行决定、需要谁确认、推荐方案与备选方案，以及不处理会影响哪个交付节点。
7. **等待期间默认继续推进。** 将工作拆成“被阻塞部分”和“可独立部分”；后者继续开发、测试或整理。可用 Mock/Fixture 的先用替身并标注边界。涉及公共契约、存档兼容、随机协议、跨模块状态所有权和全局结算顺序的决定，未获 zm 确认前不得擅自落地。
8. **暂停范围必须最小化。** 没有安全替代方案时，只暂停受影响的代码/决策，不自动暂停整个模块；提出者给出解除阻塞所需的最小决定。zm 负责兜底未认领任务、处理全局决策和真实跨模块阻塞。
9. **文档口径冲突按 ADR-0005 分类处理。** 先按信息领域找到规范来源，不以“最新文件”简单排序；表述差异自行统一，已明确过期的副本按规范来源修正，两个现行正式决定实质冲突时才升级裁决。修正文档时检查同一机制的其他引用点，不只修改当前文件。
10. **不得把最小实现理解为删减既定功能。** 冲刺期优先保证已确认主流程和玩家功能完整，再简化内部实现；不能用占位、静态假数据或擅自延期替代已承诺的真实流程。
11. **新增与修改字段区别处理。** 不影响既有契约的独立新增字段由模块负责人自主处理；修改既有字段语义、枚举、可空性、状态边界或公共接口时，必须核对生产者、消费者、存档与测试，并按工程变更治理升级。

## 4. 每次交接需要说明什么

不要求每日汇报。开始一项跨模块工作、提交阶段成果或遇到阻塞时，提供足以让其他成员接手的信息：

- 本次完成了什么，以及对应的 Issue / PR / 文件；
- 当前进度和尚未完成的部分；
- 使用了哪些接口、契约或临时假设；
- 是否存在未提交的本地改动，远端分支是否同步；
- 当前阻塞、需要谁确认什么；
- 下一步准备做什么。

无需为了汇报而制造提交或把尚未完成的工作包装成完成状态。没有实质进展时，可以只报告“暂无变化”和真实原因。

## 5. 分支、PR 与共享文件

1. 开始工作前先检查 GitHub 最新目标分支，再核对本地分支、未提交改动和未推送提交；不得用旧远端内容覆盖本地工作。
2. PR 应说明：目标分支和基线、任务范围、依赖契约、修改文件、测试结果、未验证事项及已知风险。
3. 一个 PR 尽量对应一个可独立审查和验收的交付，不把无关模块改动捆绑在一起。
4. 模块负责人可以直接修改所属模块的核心实现文件，包括多人共用的 C++ 核心源文件和规则头文件；不因文件共享而被限制为只能提交设计提案。涉及公共契约、跨模块状态所有权、存档兼容、随机协议或全局结算顺序时，先由 zm 确认。多人需要改同一文件时，明确 PR 基线和堆叠顺序，串行集成，避免并行分支基于旧版本互相覆盖。跨层契约文件（如 TS 类型、绑定、存档校验）可由模块负责人提交必要配套改动，但需标明影响并由 zm 审查集成。具体边界见 `TEAM_PLAN.md`。
5. 有依赖的 PR 应明确基础分支和堆叠关系；上游变化后，提交者负责说明是否需要 rebase 或调整。
6. 未经明确授权，不自行合并他人 PR，也不覆盖、重置或删除他人的分支和提交。
7. 同一共享文件需要多人修改时，先声明目标文件、改动范围和基线；同一文件同一时间只推进一条独立集成链。后续 PR 基于前序 PR 分支堆叠，或等待前序 PR 合入 main 后再同步；上游变化后由下游提交者负责更新基线并报告冲突处理结果。不同文件且无契约冲突的任务可并行。zm 负责确认共享文件集成顺序、审查跨模块影响并最终合入。

## 6. 测试与交付边界

1. 模块负责人先保证模块自身可验证：关键路径、边界条件、错误分支和必要回归测试。
2. 外部模块尚未接通时，可以用契约测试、Mock 或 Fixture 验证本模块，但必须注明尚未完成真实集成。
3. 交付时区分“代码已提交”“模块测试通过”“真实跨模块集成通过”，不能用其中一项代替另外两项。
4. 测试范围应与改动风险相称。小范围内容或文档修改不要求无意义地跑完整套测试；涉及核心结算、共享状态或构建链路时，应执行对应的高风险验证。
5. 发现问题时，优先修复当前模块内的问题；若属于公共契约或上游规则，附上复现方式和建议，交对应负责人处理。
6. 内容协作者交付时说明内容范围、完整性和设定约束；对应系统负责人审核字段/格式、机制适配和实际可用性。影响运行效果的内容应抽样进入真实模块或游戏流程验证。
7. 模块负责人对模块内验收负责；接口两端负责人共同确认真实交互；zm 组织玩家完整流程的整体验收，至少覆盖核心循环、跨模块状态流转、关键账目一致性和必要的存档读写。
8. 当前环境无法执行的验证必须列为未验证项并说明原因，不得用静态检查、Mock 或单元测试替代真实运行结论。

## 7. 总负责人和模块负责人的职责

- **模块负责人**：独立推进本模块，主动维护对外契约，判断模块内部方案，提供可验证交付，并提前暴露真实阻塞。
- **内容协作者**：在系统负责人给定的内容接口内独立产出；发现接口承载不了内容时提出需求，不自行扩展机制。
- **总负责人 zm**：维护全局规则和公共契约，处理跨模块冲突与共享文件，优先解决提出者的真实阻塞，并顺带检查是否存在同类共性问题；负责阶段集成和整体验收，不代替模块负责人管理每个内部细节。

## 8. 集成节奏

不设置强制每日会议或每日汇报。按实际开发进度，在以下节点做异步集成检查：

- **契约确认**：模块并行开发前，确认必要的公共接口和边界。
- **模块可交付**：模块负责人提交可独立验证的阶段成果。
- **跨模块接通**：依赖模块具备可用实现后，验证真实调用、状态流转和错误处理。
- **完整流程验收**：按玩家实际操作路径验证核心循环，不只检查单个模块测试通过。

每次集成检查只处理当前阶段真正影响推进的问题，不要求所有成员同时在线。

## 最低执行要求

每项跨模块任务至少做到三件事：

1. 写清楚依赖和对外契约；
2. 写清楚没有即时回复时可以继续做什么；
3. 写清楚交付如何验证，以及哪些部分尚未真实集成。
4. 发现文档冲突时，指出规范来源、分类及受影响引用点；不只报告“文档不一致”。

除此之外，尽量让成员自行安排时间和模块内部工作方式。协作制度应降低沟通成本，而不是增加额外工作量。
