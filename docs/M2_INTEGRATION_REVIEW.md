> 审查日期：2026-11-23  
> 基线：`main` @ `4044a7085afcfb62a875c079bb426044149f1b5c`  
> 范围：依据当时的 `GAME_RULES.md`、`DATA_MODEL.md`、`API.md`、`PROGRESS.md` 进行的规则与契约交界审查。本文是历史设计审查，不是对全部 C++/WASM 行为的源码审计，也不代表下列功能已经实现或测试通过。

> **2026-11-25 归档说明：**本文仅保留历史审查背景，不再作为当前 M2 契约。已被后续规则覆盖的内容包括：临时员工按周领取正薪酬；事件使用项目级 `pending[]`；正常周费用预检失败按限时资金危机处理；项目流水只是公司账本归因；交付/中止保留终态项目并释放人员；公司级 `phase` 不再是项目生命周期字段。现行契约与实现边界见 [M2_DATA_CONTRACT.md](M2_DATA_CONTRACT.md)、[M0_CONTRACT_FREEZE.md](M0_CONTRACT_FREEZE.md) 和 [DOMAIN_ARCHITECTURE.md](DOMAIN_ARCHITECTURE.md)，不得按本文旧表述补建状态或金额规则。

## 1. 审查结论

当前 M2 的主要风险不是缺少更多系统，而是多个模块在同一笔交易、同一个项目状态或同一个结算节点上同时产生影响。集成时必须守住以下原则：

1. **单一写入者**：每个状态字段、规则结果和资金动作只有一个权威写入入口；其他模块提交意图或结果，不直接改写别的模块状态。
2. **一次结算、一次入账**：公司账与项目账是同一交易的两个统计视图，不是两次现金变化。
3. **阶段与生命周期优先**：所有跨模块动作先验证公司状态、项目阶段和动作时点，再检查资源，最后原子应用。
4. **快照与运行态分离**：企划报价、立项快照、制作过程、历史作品各自有明确生命周期；历史快照不能反向修改当前经营状态。
5. **核心规则唯一**：C++ 是规则与数值的事实源；TypeScript 负责协议校验、交互和展示，不复制经营公式。
6. **未实现不冒充已实现**：契约字段、文档规则、静态夹具、模拟服务和真实 WASM 行为分别记录，验收证据不能互相替代。

## 2. 优先级与模块交界

### P0：资金、立项与终局

| 交界 | 必须保持的规则边界 | 主要风险 | 验收要求 |
| --- | --- | --- | --- |
| 企划 × 财务 | `contract_budget` 是制作预算；仅委员会模式生成 `total_investment = contract_budget × 2`。承制不生成投资规模。 | 把预算和投资规模混为一谈；承制误扣投资；投资被重复扣除。 | 同一报价分别走承制、委员会 10%/100%立项，逐笔核对立项前现金、投资支出、合同预算入账和立项后现金。 |
| 立项 × 财务 | 记录 `opening_funds`；委员会资格按拨款前现金判断。委员会先扣公司投资，再将合同预算并入公司现金；承制只并入合同预算。整个立项必须原子成功或失败。 | 用尚未到账的制作预算支付投资；失败后残留半个项目或部分资金变化。 | 资金恰好足够、差 1 日元、合同预算较大但投资前现金不足三种边界；失败时 state、资金、seed 均不变。 |
| 项目成本 × 公司财务 | 工资、运营、阶段生产、临时员工、外包、事件、延期、扣罚等每笔支出只改变一次现金；公司与项目 finance 同步记录。 | 同一费用在两个 ledger 重复扣现金，或只记项目账不记公司账。 | 对每类成本做单笔账例；核对现金变化、公司累计成本、项目区间成本三者一致。 |
| 作品结算 × 财务 | 合同预算开工时已到账，交付时不再次发放；BD 公司所得为毛收入的初始 50%；承制成功奖励是委托方额外支付，委员会不适用。 | 交付重复发合同预算；BD 先按 50%入账后又扣一次成本；成功奖励混入渠道收入。 | 承制与委员会分别覆盖 BD、非 BD、成功奖励、投资本金、成本；逐渠道核对毛收入和公司实际所得。 |
| 破产 × 项目结算 | 当周强制费用支付失败时不得推进该周；交付扣罚导致资金缺口时进入不可逆关闭/破产。破产后不能靠回款恢复经营。 | 资金不足仍产生工作量/收入；终局后重新接单；负现金状态被错误拒绝或被自动救活。 | 周费用预检失败、交付后净资金为负、已破产后尝试经营动作三组测试。 |

**统一账务断言**

- 公司现金变化只由实际交易改变；项目账、公司账、阶段成本快照、任务 `fee_paid` 和历史 finance 不得被相加成第二笔支出。
- 项目利润、公司现金变化和项目区间账必须按当前规则口径解释；不能把合同预算既当收入又在结算时重复计入。
- 委员会投资本金损失与制作经营亏损分开核算；投资本金损失上限不保护工资、运营和制作成本亏损。

### P0：企划、委员会与商业结算

| 交界 | 必须保持的规则边界 | 主要风险 | 验收要求 |
| --- | --- | --- | --- |
| 企划来源 × 槽位 | 市场固定四槽；IP 上门占其中一槽；自定原创与员工提案是独立槽位。员工提案不能直接开工，必须采纳到自定槽位。 | 槽位数量膨胀；提案绕过采纳；不同来源混用生命周期。 | 同时存在市场报价、自定企划和提案时验证槽位独立；采纳、拒绝、丢弃、开工和刷新后验证清理规则。 |
| 企划 × 合作模式 | 普通企划可选承制/委员会；原创仅委员会。模式与投资比例在开工时确定并锁定。 | 来源或规模错误限制普通企划模式；制作中途切换模式。 | 对四类来源及普通/原创报价逐项验证 allowed_modes、立项条件和开工后锁定。 |
| 委员会投资 × 成员渠道 | 玩家投资比例与成员拉入是两个独立维度。一个成员对应一个渠道；成员加入开放渠道；成员不携带投资比例或渠道分账比例。 | 把成员渠道与投资金额绑定；按成员重复分账；承制项目错误携带委员会。 | 投资比例 10%/50%/100% 与成员组合交叉测试；成员加入只改变渠道开放，不改变投资额；承制 committee 必须为 null。 |
| 渠道 × 作品结算 | BD 是基础渠道；非 BD 渠道来自企划条件与委员会成员；委员会非 BD 公司所得按玩家投资比例计算；承制不参与非 BD 分成。 | 企划自带渠道、成员渠道和投资比例重复叠加；承制获得委员会分账。 | 每个渠道分别记录毛收入、公司所得；验证 `Σ渠道毛收入 = commercial_revenue`、`Σ公司所得 = commercial_share_received`，且恒含 BD。 |
| 市场热度 × 声望 | 声望影响机会档次/准入等经营机会；热度影响题材供给、IP 上门和非合同商业表现。热度不影响合同收益；声望不改变企划槽位数量或员工提案概率。 | 两个全局变量被混用，造成合同金额、市场数量或员工提案概率被错误联动。 | 固定企划和合同条件，仅改变声望/热度分别跑对照；逐项检查只改变被授权的结果。 |
| 历史成绩 × 新企划 | `required_works` 只读取已结算历史作品；当前在制作品、未结算项目不能提前满足解锁条件。 | 未来/当前作品引用导致循环解锁，或历史快照被当前状态污染。 | 无历史、刚结算达标、未达标、跨来源限制四类边界；历史 ID 只能引用更早作品。 |

### P0：制作、人员、外包与事件

| 交界 | 必须保持的规则边界 | 主要风险 | 验收要求 |
| --- | --- | --- | --- |
| 员工 × 阶段配置 | 核心员工和当前项目临时员工是不同雇佣类型；配置只能引用当前可用人员；角色、专业能力和阶段权重不能混为一套枚举。 | 招聘池员工被直接安排；临时人员跨项目残留；用岗位名替代专业能力。 | 核心/临时/招聘池 ID 隔离；阶段配置引用、重复分配、无效专业和项目结算释放测试。 |
| 临时员工 × 财务 | 临时员工项目费在雇佣动作时支付一次，按 `temporary` 归类；不再按周发核心工资；项目结束释放。 | 项目费重复扣款、周薪再次扣款、释放后仍被配置引用。 | hire 前后现金、finance、成本类别对账；多阶段使用同一临时员工不重复支付；结算后名册和配置引用清理。 |
| 供应商 × 外包任务 | 供应商专业、阶段权重、剩余产能、报价和任务状态共同决定合法外包；费用确认时一次支付，任务推进不再次扣费。 | 不匹配专业仍接单；超过产能；任务交付与费用重复结算。 | 专业不匹配、容量边界、任务跨周推进、成功/失败与项目结束释放测试。 |
| 制作阶段 × 事件 | 事件只能在合法项目/阶段状态触发；待处理事件暂停推进；事件选项只应用核心目录定义效果。常规阶段配置锁不能被事件绕过，只有明确允许重配的选项可附完整配置。 | 事件在终局/交付后弹出；跨阶段修改；自造 effect 直接改状态；同周多事件。 | active/ready/event_pending/project_ready/closing 各阶段触发边界；每周最多一个、待处理时不能推进、选项费用与效果原子应用。 |
| 事件 × 财务/人员/工期 | 事件支出归属唯一成本类别；调用供应商的费用归 outsourcing；独立事件费用归 events。延期必须走正式延期规则，不可由事件直接绕过资格、次数和付款检查。 | 同一事件重复收费；事件免费延长工期；事件绕过供应商与财务校验。 | 付费事件、供应商事件、延期事件分别做 ledger 对账和资格拒绝测试。 |

### P1：延期压力、声望与长期经营

| 交界 | 必须保持的规则边界 | 主要风险 | 验收要求 |
| --- | --- | --- | --- |
| 延期 × 委员会 | 延期仅委员会项目可申请，首版最多一次；承制不可延期。延期费用支付一次、工期按规则延长，委员会压力上升。 | 承制绕过限制；重复延期；延期费重复扣除；压力与声望被当成同一变量。 | 首次成功、现金不足、已延期、承制项目、已过截止五类测试。 |
| 延期周 × 压力 × 交付 | 延期期间压力按周变化；压力越高，违约/交付后果越严重。压力属于项目状态，不是公司声望；声望变化仍由公司声望唯一入口记录。 | 压力没有随周推进；把压力直接写入声望；压力结算与违约扣罚重复惩罚。 | 同一项目在不同延期周数交付，比较压力变化、交付结果和声望日志；每个后果只结算一次。具体系数由规则参数确定，不在集成层另造公式。 |
| 声望 × 各模块 | 公司声望只能通过公司经营层唯一入口变更；其他模块在自身结算节点提供变化原因与增量，不直接写 `company.reputation`。当前基础机制已落地，项目结算三档仍是暂定值；市场、招募、供应商、融资等影响路径仍待实现。 | 模块直接写声望、重复记账、在错误时点变化，或把未实现影响当成已实现。 | 每个声望来源均检查 reason、实际生效 delta、reputation_after 和追加顺序；重复结算不得重复记账。 |
| 作品历史 × 续作/结局 | 作品结算生成不可变历史快照；续作引用前作 ID；公司总结只读历史，不再次支付或改写旧作品。 | 作品快照依赖已释放员工；续作读取当前企划而非历史；总结二次入账。 | 结算后释放临时员工仍能完整展示团队快照；多部作品串联、公司关闭后总结不改变资金和历史。 |

## 3. 跨模块动作时序

以下时序是集成验收的逻辑顺序，不要求每个模块采用相同内部实现。

### 3.1 立项

1. 验证公司仍为 running、phase 为 idle，报价 ID 属于合法市场或自定企划槽。
2. 验证企划来源、声望门槛、合作模式和投资比例。
3. 记录立项前 `opening_funds`。
4. 委员会模式按拨款前资金验证投资能力，并计算公司投资额；承制模式不计算投资规模。
5. 原子完成投资扣款（仅委员会）、合同预算入账、项目快照建立、槽位清理与 phase 切换。
6. 任一步失败，状态、资金和 seed 不得部分变化。

### 3.2 每周推进

1. 验证公司状态、当前阶段和配置状态；待处理事件、待交付、待结算均不得推进。
2. 汇总本周强制支出并预检现金。
3. 预检失败：不扣款、不推进周、不产生工作量/经验/疲劳/士气/随机结果；按终局规则锁定公司。
4. 预检成功：原子扣款，公司账和项目账同步记账。
5. 推进当前阶段工作、外包任务与阶段质量；只推进当前阶段。
6. 结算核心员工经验、疲劳、士气；临时人员不培养。
7. 周数推进，处理延期压力等周度状态变化。
8. 按终局优先级决定阶段切换、项目交付、公司终局；只有仍合法推进的项目才可触发事件。
9. 事件待处理时暂停后续推进，不能靠再次调用 advance_week 跳过。

### 3.3 项目交付

1. 确认项目处于唯一可结算状态，确定 completed/deadline/company_closed 等交付原因。
2. 基于作品质量、商业表现、题材热度、渠道开放情况计算毛收入。
3. 按渠道逐项计算公司所得：BD 采用当前 BD 公司所得比例；委员会非 BD 按玩家投资比例；承制不分非 BD。
4. 计算合同扣罚、承制成功奖励、投资本金损失及其他结算项目，严格区分来源。
5. 一次性更新公司资金、公司 finance、项目 finance、作品历史快照与声望日志。
6. 释放项目临时员工和在途任务引用，清空当前项目；根据公司状态进入 project_settled 或 closing。
7. 相同结算快照不得再次结算或重复入账。

## 4. 统一验收清单

以下用例应由对应模块负责人在实现时认领。标记说明：`[ ]` 尚待验收；不是对当前实现状态的断言。

### A. 财务与终局

- [ ] 承制立项：不产生 `total_investment`，不扣投资本金，合同预算只入账一次。
- [ ] 委员会立项：10% 与 100% 投资额计算正确，拨款前现金不足时原子拒绝。
- [ ] 公司账与项目账对同一笔工资、运营、生产、临时、外包、事件、延期和扣罚支出只反映一次现金变化。
- [ ] BD 毛收入、公司所得和综合成本一致，不重复扣除；非 BD 分账符合模式与投资比例。
- [ ] 承制成功奖励只由委托方额外支付，不混入商业收入；委员会不获得该奖励。
- [ ] 强制周费用不足时周数、工作量、经验、疲劳、士气、seed 均不变化。
- [ ] 结算扣罚造成负现金时进入不可逆破产；已关闭公司不能再接单。

### B. 企划与委员会

- [ ] 市场四槽、custom_offer、pending_proposal 互不混用；IP 上门占市场槽。
- [ ] 普通企划同时允许 contract/committee；原创只允许 committee。
- [ ] 员工提案不能直接开工；采纳、拒绝、丢弃、刷新和成功开工均正确清槽。
- [ ] 委员会成员只提供渠道，不提供投资比例；投资比例变化不改变渠道开放。
- [ ] 一个成员对应一个渠道；承制项目无委员会成员快照。
- [ ] 作品历史解锁条件只读取已结算历史，不能引用当前或未来作品。

### C. 制作、人员与事件

- [ ] 阶段配置只能引用当前可用员工；核心员工与临时员工按 employment 分开校验。
- [ ] 临时员工项目费只支付一次，周薪为零，项目结算后释放。
- [ ] 外包专业与阶段权重匹配，容量不超限，费用支付与任务推进不重复扣款。
- [ ] 事件每周最多一个，同一时间最多一个待处理；事件待处理时不能推进。
- [ ] 事件只能通过目录选项改变状态；重配选项必须明确允许并提交完整配置。
- [ ] 事件不能绕过阶段锁、公司关闭锁、延期资格、财务预检和供应商规则。

### D. 延期、声望与长期记录

- [ ] 承制不能延期；委员会最多延期一次；现金不足时状态不变。
- [ ] 延期压力按周变化，且与公司声望分开保存、分开计算。
- [ ] 声望只有唯一入口写入；日志 delta 是实际生效变化，钳制到 0 后为零则不记账。
- [ ] 市场、招募、供应商、原创融资等声望影响只在规则授权路径接入，不得改变无关变量。
- [ ] 作品历史保存阶段和团队快照；释放临时员工不破坏历史记录。
- [ ] 公司总结不重复付款、不修改作品历史，终局状态不可逆。

### E. 核心与前端一致性

- [ ] 每个带 state 的动作先校验完整状态，再校验 phase、动作条件、资金/产能，最后原子应用。
- [ ] C++/WASM 是经营公式和参数的唯一事实源；TS 不复制预算、投资、收入、压力、声望或质量公式。
- [ ] 相同初始状态、动作序列和 seed 得到相同状态与结果；失败动作不消费 seed。
- [ ] 静态夹具、模拟器、原生测试、WASM 测试、浏览器流程分别标记，不互相替代。
- [ ] 旧 v3 存档的可选字段缺省语义持续有效；新增字段不得未经批准改变迁移策略。

## 6. 当前已知缺口与执行顺序

依据当前进度文档，M2 的企划/委员会、员工/供应商、制作事件仍处于功能落地中。下列项目应作为实现提交的审查入口，而不是额外开新系统：

1. **先完成 P0 资金和立项链路**：没有正确的立项、周成本、交付与破产账务，其他模块无法可靠集成。
2. **再接入企划/委员会的生命周期和渠道结算**：先保证来源、槽位、合作模式和渠道快照正确，再调商业参数。
3. **并行接入员工/供应商行为**：人员引用、临时费用和外包任务要与阶段推进、财务唯一记账联通。
4. **最后接入事件效果与延期压力**：事件必须调用既有动作/结算入口，不建立绕过规则的第二条通道。
5. **M2 稳定后推进 M3**：作品长期履历、续作和公司结局以已结算历史为唯一输入。

### 不在本清单中擅自冻结的参数

- 声望等级阈值、称号和各影响系数。
- 市场热度变化概率、企划生成权重和非合同收益系数。
- 各商业渠道公式、商业规模、质量兑现曲线和成功奖励门槛。
- 违约扣罚、延期固定周数/费用/压力增量及压力后果的具体数值。
- 事件触发概率、冷却、具体选项成本与效果。

这些参数由对应模块提出并说明来源、影响面和验收方式；涉及跨模块规则时再由总体负责人裁定。不得在前端或集成层另写一套公式。
