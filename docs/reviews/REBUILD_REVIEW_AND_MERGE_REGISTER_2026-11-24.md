# 2026-11-24 仓库改动审查与合并登记

> 审查范围：截至 2026-11-24（北京时间）可见的 main、开放 PR、独立研究/审计/实验分支。
> 本文是仓库状态与迁移建议登记，不替代正式游戏规则，也不把研究推论自动升级为负责人决策。财务机制按 2026-11-25 的 DEC-FIN-002/003 更新：旧限时危机周只保留为未来更新候选。

## 1. 总体结论

当前工作已经形成研究、历史审计、机制实验和新框架四层材料，但它们尚未形成统一的数据模型。旧核心仍以单个 `GameState.project` 为中心；员工、外包、事件、财务和阶段推进均存在单项目假设。直接在旧模型上增加项目数组不足以支持多项目经营。

建议先完成 Company、Project、Staff、Supplier、Committee、Market、WorkHistory、WeeklySettlement 等领域边界与共享资源账本，再拆分实现任务。当前不应继续扩展旧单项目模拟器，也不应把旧模型实验参数直接作为正式规则。

## 2. 今日材料分层

### 2.1 研究材料

- `docs/research/CORE_GAMEPLAY_ARCHITECTURE_RESEARCH.md`：已由 PR #25 归档到 main 的多轮游戏研究与整合推论。主要价值是提供设计启发和证据边界，不是正式规则。
- `docs/PLAYABILITY_RESEARCH_AND_RANDOMNESS.md`、`docs/PLAYABILITY_COMPETITOR_RESEARCH_V0.1.md`：制作随机性和竞品可玩性研究。应保留为研究材料，后续由新模型重新验证。
- `docs/CORE_GAMEPLAY_REBUILD_FRAMEWORK.md`：当前重构设计基线。明确作品为核心目标、公司成长为长期动力、产业关系为实现作品目标的手段；提出公司/项目双层结构、项目级周计划、共享资源、多项目同周结算和阶段性重构顺序。

### 2.2 历史审计材料

- `docs/COMMITTEE_BUSINESS_AUDIT.md`：委员会、投资、渠道与商业结算的历史规则和实现差异。
- `docs/COMPANY_ECONOMY_GROWTH_AUDIT.md`：公司资金、固定成本、成长、设施和破产边界。
- `docs/STAFF_ORG_AUDIT.md`：员工能力、潜力、成长、招聘、组织和外包。
- `docs/WORKS_PRODUCTION_SYSTEM_AUDIT.md`：作品阶段、工作量、质量、交付及单项目代码约束。

四份审计应作为迁移时的历史证据。审计报告中的“旧规则”不代表新架构必须照搬；仓库未检索到的历史对话决定也不能仅凭代码缺失而否定。

### 2.3 实验材料

- 员工排班模拟：提供能力权重、团队协作和动态分配的实验线索。
- 制作随机性模拟：提供工作量与质量分离、独立随机流、均值与稳定性等实验线索。
- 跨模块账目审计脚本：提供独立对账方法，但当前针对 v3 单项目状态格式。

实验结论均受旧数据模型限制。它们可以迁移计算方法与测试思路，不能直接迁移为新规则或平衡参数。

### 2.4 事件模块

M2-a/M2-b 已涉及核心 C++、前端类型、事件目录、数据模型和测试。当前实现把事件状态挂在单个项目上，并通过全局 phase/pending_event 控制推进。多项目架构下必须重新定义事件作用域和推进阻塞范围。

M2-b 暂存事件的未到期恢复路径会推进周数，但不执行正常工资、运营与制作结算，存在利用事件暂存跳过周成本的行为漏洞。该路径在修正前不应进入正式主线。

## 3. 统一审查结论

| 主题 | 当前证据 | 新架构处理意见 |
|---|---|---|
| 公司与作品 | 研究与框架均支持双层主体 | 公司持有长期资源和财务；作品作为独立项目实体 |
| 多项目 | 旧核心以单项目为中心 | 项目独立计划与状态；公司统一调度共享资源 |
| 员工 | 单项目排班实验 | 员工归公司所有；核心员工每周严格单项目分配，不允许同周支援/借调/拆分工时 |
| 外包 | 旧系统缺乏跨项目预留 | 作为外部产能资源，必须有容量、成本、交付和占用记录 |
| 委员会 | 旧规则较丰富，代码未完整实现 | 作为项目级合作结构；成员关系可沉淀为公司长期关系资产 |
| 财务 | 旧账目部分可核对 | 公司统一现金池；项目独立成本/收益归因；同周统一预检和原子结算 |
| 事件 | 全局事件状态与全局 phase | 重新定义公司级/项目级事件及阻塞规则；不沿用当前单槽位 |
| 随机性 | 两类随机模拟已有初步探索 | 在周结算发生，推进前不泄露结果；保留 seed 便于复现 |
| 作品质量 | 旧方案将工作量与质量分离 | 保留为候选原则，维度、公式和随机幅度待新模型验证 |
| 成长 | 旧系统经验与能力转化不完整 | 经验、能力、潜力和组织能力分开建模，避免纯数值膨胀 |

## 5. 新架构必须补齐的系统契约

1. **Company：** 周数、现金池、固定成本、公司声望、长期关系、员工与供应商资产。
2. **Project：** 项目阶段、企划、计划方针、工作量、质量、预算归因、风险、委员会与事件。
3. **StaffAssignment：** 员工本周唯一项目归属、实际参与、能力贡献、冲突与疲劳结算；不得包含核心员工支援项目或拆分工时。
4. **SupplierCapacity：** 外包产能、项目预留、履约可靠性、成本与交付结果。
5. **Committee：** 项目级成员、投资、资源贡献、权益、渠道及生命周期；合作方可跨项目复用，但委员会随项目结束。
6. **WeeklySettlement：** 统一时间步、资金预检、资源分配校验、项目结算、公司成本、状态写回和回执。
7. **Event：** 事件归属、触发条件、处理期限、阻塞范围、升级与效果结算；不得以全局单事件槽位限制所有项目。
8. **WorkHistory：** 记录每周项目投入、员工贡献、随机结果、成本与质量变化，支持复盘和可复现模拟。

## 7. 建议实施顺序

1. 冻结领域边界、状态归属和实体关系。
2. 定义共享资源账本与周结算事务边界。
3. 定义项目计划、资源分配、事件和财务的数据契约。
4. 用新数据模型重建最小可运行模拟器。
5. 验证多项目资源竞争、随机性、现金流和事件并发。
6. 再拆分员工、项目制作、委员会、市场、财务与 UI 的实现任务。

## 8. 审查限制

本登记基于仓库当前可见分支、PR、文档与代码差异。没有在本轮执行完整构建、浏览器端到端测试或长周期平衡模拟；“适合合并”表示改动范围和设计定位可接受，不代表所有脚本已通过运行验证。
