## 2. 三层结构：职能、场景、窗口

初稿把"三个部分"和"四张地图"混在一起讲，导致导航项数说不清。本版明确拆成三层，三者互不替代：

| 层 | 数量 | 是什么 | 是否出现在 UI |
| --- | --- | --- | --- |
| **职能** | 3 | 公司经营、作品制作、市场经营。产品定位层面的玩法分类 | **否**。只用于解释"为什么需要 4 个场景" |
| **场景** | 4 | 办公室、制作现场、会议室、发行与市场。玩家实际点击的界面单位 | **是**。就是 4 项导航 |
| **窗口** | 4 | 正常经营 / 事件待处理 / 资金危机 / 关闭中。同一场景在不同窗口下的可用操作不同 | 是，体现为状态与按钮可用性 |

三者关系一句话：

> **三个职能，四个场景，四种窗口。** 职能决定场景存在的理由，场景决定信息在哪看，窗口决定此刻能做什么。

职能到场景的映射：

| 职能 | 主要承载场景 | 说明 |
| --- | --- | --- |
| 公司经营 | 办公室 | 人员、设施、公司状态、招聘 |
| 作品制作 | 制作现场（会议室负责相关决策） | 项目、单集、六阶段、工作项、外包 |
| 市场经营 | 发行与市场（会议室负责相关决策） | 企划机会、发行、反馈、结算、履历 |

> 注意：市场经营被拆到两个场景不是重复，而是**决策**（会议室：要不要接、和谁合作）与**结果**（发行与市场：播出了、反响如何、赚了多少）分开。这两个时刻的情绪完全不同，合并会互相削弱。

## 3. 现状与差距

### 3.1 代码现状（2026-11-24，main）

| 项 | 现状 |
| --- | --- |
| 页面 | `App.tsx` 只有 `screen: 'home' \| 'studio'`，无路由 |
| 主界面 | `StudioPage.tsx` 216 行，一个滚动页面同时承载状态、企划、项目、员工、事件、回执、存档 |
| 状态 | `gameStore` 128 行，围绕 v3 单项目形状 |
| 数据 | 直连 v3 运行时（C++/WASM），**尚无 v4 读模型** |
| 样式 | `index.css` 单文件，`--site-*` 变量，米白底 + 砖红强调 + 衬线标题 |

### 3.2 三个真实差距

初稿归纳为"缺少空间感、缺少差异、缺少反馈"，方向对，但落点不够具体。改成可执行的说法：

1. **信息没有分层。** 216 行里所有内容平铺在同一滚动轴上，玩家无法判断"现在最该看哪一行"。这不是美观问题，是决策优先级问题。
2. **没有"此刻能不能做事"的表达。** 4 种经营窗口（正常/事件/危机/关闭）在现有界面上只体现为按钮 `disabled`，玩家看不到原因和出路。
3. **数据形状是单项目的。** v3 状态里没有 `works[]`。画布再漂亮，也只能画一部作品。

### 3.3 因此 F1 是什么

> **F1 不是"给现有页面换皮"，而是新建一个场景壳 + 一层读模型适配层，跑在 mock fixture 上。**

这也直接说明为什么 `feat/frontend-visual-pass-1` 不能作为 v4 前端基础：它改的是 216 行那个页面的措辞与纸纹，而 v4 需要的是这 216 行被拆进 4 个场景。该分支中可复用的只有排版气质（留白、栏目感、衬线标题），不含结构。

## 4. 全局壳（跨场景常驻）

### 4.1 结构

```text
┌──────────────────────────────────────────────────────────────┐
│ 品牌        第 37/520 周 · ¥1,284万 · 声望 12 · 在制 2 部        │ ← 状态栏
│                              [待处理 1] [危机]                 │
├──────────────────────────────────────────────────────────────┤
│  办公室        制作现场        会议室        发行与市场         │ ← 4 项导航
├──────────────────────────────────────────────────────────────┤
│                                                              │
│                      当前场景主视图                           │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│  事务中心：待处理事件 / 本周回执 / 危机提示      [推进下一周 →] │ ← 底部常驻
└──────────────────────────────────────────────────────────────┘
```

### 4.2 状态栏字段

只放"每一周都要看"的 6 个字段。全部来自核心读模型，**不直接读 GameState 原始字段**：

| 字段 | 读模型来源 | 交互 |
| --- | --- | --- |
| 当前周 / 520 | `company.week` | 静态 |
| 现金 | `finance_summary.balance` | 点击 → 发行与市场 · 结算区 |
| 声望 | `company.reputation` | 点击 → 办公室 · 公司信息 |
| 在制项目数 | `company_overview` 项目组合长度 | 点击 → 制作现场 |
| 待处理事件 | `event_card` 是否存在 | 点击 → 展开事务中心 |
| 偿付状态 | `crisis_board` 是否存在 | 危机时高亮，点击 → 危机面板 |

**不放**：风险六维、`preview` 逐项明细、种子、派生质量分。这些要么是派生值，要么只在特定场景有决策意义。

### 4.3 导航

- 4 项，固定在顶部，文字 + 图标，不用纯图标（避免猜谜）。
- 键盘：`1/2/3/4` 切换，`Tab` 顺序进入场景内容。
- 每项带一个"有事"角标：办公室（无）、制作现场（门槛达标可交付 / 延期风险）、会议室（待处理决策）、发行与市场（新回执）。
- 切换保持每个场景的上次选择（选中的员工、展开的单集、滚动位置）。

### 4.4 事务中心

三块内容，默认收起为一行摘要：

| 区块 | 来源 | 展开后 |
| --- | --- | --- |
| 待处理事件 | `event_card` | 标题、影响对象、选项、确定成本、后果提示；选项对应 `resolve_event` |
| 本周回执 | `week_receipt` | 各项目变化、原因、人员变化、现金变化、下周关注 |
| 危机提示 | `crisis_board` | 缺口、剩余期限、受影响项目、可采取的自救动作与代价 |

> 回执是"结算后的解释层"，不是玩法空间。它默认折叠，这一点是 D4 的核心。

### 4.5 周推进按钮的三态

| 态 | 表现 | 原因来源 |
| --- | --- | --- |
| 可推进 | 实心主按钮 | `advance_week` 守卫全部满足 |
| 被事件阻断 | 按钮禁用 + 上方一句"先处理 1 件待处理事项"，点击跳到事务中心 | `INVALID_PHASE`（事件未处理） |
| 危机中 | 按钮保留可用，但旁边常驻危机入口 | 危机期间**允许** `advance_week`（DEC-FIN-003） |

> 危机中周推进是允许的，因为危机期限本身用经营周计量。这一条容易做错，必须写进实现检查单。

## 5. 四个场景

每节统一 7 小节：定位 / 构图 / 信息层级 / 读模型映射 / 命令入口 / 状态差异 / 首版不做。

### 5.1 办公室（主地图）

**定位**：玩家持续观察公司的地方。回答"我的公司现在是什么样、谁在做什么、缺什么"。

**构图**：一张完整办公室场景（复用现有 `studio_office.png`，1280×720，中央留白就是为叠人物与 UI 准备的）。斜俯视，固定视角，不做自由缩放与漫游。

| 区域 | 内容 | 交互 |
| --- | --- | --- |
| 办公主区 | 核心员工与当前状态（待命/工作中/疲劳） | 点击员工 → 人物面板 |
| 工位区 | 按项目分组的工作位 | 点击 → 该项目在制作现场的对应视图 |
| 设施区 | 已实现设施 | 点击 → 设施面板（锁定态只读） |
| 管理入口 | 招聘、人员调整、公司信息 | 打开管理面板 |

**信息层级**

1. 首屏：场景 + 顶栏。不叠加任何常驻表格。
2. 一层点击：人物 / 工位 / 设施面板（侧滑，不跳页）。
3. 二层：完整员工名册、招聘池，作为面板内的"展开全部"。

**读模型映射**

| 展示 | 来源 |
| --- | --- |
| 员工头像、姓名、角色 | `staff_board` |
| 员工当前归属项目 | `staff_board.assignment_work_id` |
| 疲劳 / 士气 / 预警 | `staff_board` |
| 人员负荷 | `company_overview` 人员负荷 |
| 设施列表与效果 | **读模型缺口**，见 §13 |

**命令入口**

| 动作 | 命令 | 失败提示 |
| --- | --- | --- |
| 招聘核心 | `hire_core` | `INSUFFICIENT_FUNDS` → 显示缺口与"去融资" |
| 抽卡/寻访 | `scout` | 同上 |
| 解雇 | `dismiss_staff` | 危机期**允许**（自救动作） |
| 调整归属 | `assign_staff` | `INVALID_PHASE` → 指向"项目非制作中" |
| 融资 | `arrange_financing` | 仅危机/资金压力周开放 |

**状态差异**：危机中办公室是**自救主入口**（融资、解雇），此时场景默认高亮缺口区域。

**首版不做**：自由装修、寻路、员工实时行为 AI、拖拽换工位、设施建造树。

### 5.2 制作现场

**定位**：回答"这部作品做到哪了、卡在哪、还差什么才能交付"。

**构图**：半空间化制作工作区——背景是一张制作现场构图，前景是**作品 / 单集 / 六阶段**三级导航 + 摘要面板。不是第二张可漫游地图。

**信息层级**（全文最关键的一处，做错就退回"工作项长列表"）

| 层 | 内容 | 默认 |
| --- | --- | --- |
| L1 作品 | 在制作品卡片：状态、剩余工期、门槛缺口、风险 | 显示 |
| L2 单集 | 12 集网格，每集 6 阶段进度条 | 显示 |
| L3 阶段 | 阶段摘要：已解锁 / 门槛达标 / 完成 三态计数 | 点击展开 |
| L4 工作项 | 单个工作项的进度、依赖、参与人 | **默认折叠**，仅主动查看 |

12 集 TV 项目约 **174 个工作项**。任何默认铺开工作项的方案直接判为不通过。

**硬性表达约束**（对应 Issue #39 验收）

1. 六阶段属于**每个单集内部**，不是整部作品一条线性流水线。UI 上必须表现为"12 列 × 6 段"，不能是"1 条 6 段"。
2. 公共制作与单集制作**分开呈现**，公共制作单独一个区块。
3. 工作项三态是**派生**的（已解锁 / 门槛达标 / 完成），界面只显示结果，不显示推导过程。
4. 员工归属表现为"归属某项目"，**不提供任何跨项目借调、拆分、拖拽支援**的操作或暗示。

**读模型映射**

| 展示 | 来源 |
| --- | --- |
| 作品列表与状态 | `company_overview` 项目组合 |
| 单集 / 阶段 / 门槛项 / 质量 | `work_detail(id)` |
| 工作项依赖视图 | `production_board(id)` |
| 人员与外包占用 | `work_detail` 人员与外包占用 |
| 定向目标是否生效 | `work_detail` 计划与实际差异 |

**命令入口**

| 动作 | 命令 |
| --- | --- |
| 立项 | `start_work` |
| 改计划（强度/取向/外包/赶工/定向） | `set_work_plan` |
| 分配人员 | `assign_staff` |
| 雇临时人员 | `hire_temporary` |
| 签外包 | `sign_outsourcing` |
| 交付 | `deliver_work` |
| 终止 | `abort_work` |
| 延期申请 | `request_extension` |

**错误码处理要点**

- `GATE_UNMET`：不能只报错，要**直接列出未达标的门槛项**并跳到 `production_board` 对应行。
- `DEPENDENCY_UNMET` → 指向阻塞项。
- `CAPACITY_EXCEEDED` → 显示该供应商剩余产能。

**每集优先级的边界**：P5 单集优先级尚未裁决，界面**预留扩展位但不实现强制控制**——即不出现"插队/暂停某集"的可点按钮。

### 5.3 会议室

**定位**：把"要不要接这个企划""和谁合作""这个突发事项怎么处理"这些**有分量的决策**集中到一处，而不是散在弹窗里。

**构图**：静态场景构图（会议桌 + 参会席位 + 文件），配决策面板。不做可漫游地图、不做会议演出动画。

**内容**

| 区块 | 内容 | 来源 |
| --- | --- | --- |
| 议题列表 | 待决事项：委员会组建、合作邀请、重要事件 | `event_card` + **缺口**（委员会/伙伴无读模型） |
| 参会方 | 合作方身份、关系、已知条件 | **读模型缺口**，见 §13 |
| 决策文件 | 选项、确定成本、后果 | `event_card` |
| 会议记录 | 已确认的历史结果 | `Archive` / 只读事实 |

**边界（必须守住）**

- 会议室是"决策的空间化呈现"，不是新增玩法。**不新增**会议小游戏、谈判数值、好感度、独立资源。
- 只有核心已提供合法选项时才允许提交；否则一律只读 + 明确标注。
- M4 产业关系未实现前，委员会相关交互**只做结构验证**，不宣称可玩。

**首版不做**：可漫游地图、谈判玩法、参会角色动画、会议室多镜头。

### 5.4 发行与市场

**定位**：回答"我的作品进了行业之后发生了什么"——机会、发行、反响、钱、履历。这是唯一有"结果揭晓"情绪的场景。

**构图**：专用展示构图——作品海报/展示墙 + 发行信息 + 反馈区 + 结算区。不做市场街区地图、不做人群模拟。

| 区块 | 内容 | 读模型 |
| --- | --- | --- |
| 市场机会 | 企划槽、热度、锁定原因、可获得的最佳机会 | `market_board` |
| 发行 | 已交付/在发行的作品、渠道 | `market_board` + `work_detail` |
| 反响 | 评价、质量 | `work_detail` 质量维度 |
| 结算 | 余额、分类汇总、项目归因、现金可支撑周数、贷款与下周还款 | `finance_summary` |
| 履历 | 已交付作品、系列关系、历史成绩 | **读模型缺口**（Archive 无独立读模型） |

**合并原则**：机会、发行、反馈、结算、履历是**同一场景的不同区域**，不拆成独立地图；"结算"不是第二个现金池，只是 `finance_summary` 的一个视图。

**命令入口**：`create_custom_offer`、`adopt_proposal`、`reject_proposal`、`buy_tv_service`、`request_extension`。

**边界**：结算记录是**只读事实**，不可编辑金额（对应 DEC-FIN-001 唯一现金池：项目账只是按 `work_id` 过滤的归因视图）。

## 6. 经营状态 × 场景差异矩阵

Issue #39 要求"事件待处理、资金危机、正常经营三种状态有清晰的操作差异"。这里是完整版（含关闭中）：

| 场景 | 正常经营 | 事件待处理 | 资金危机 | 关闭中 |
| --- | --- | --- | --- | --- |
| 办公室 | 招聘/调整/设施 | 仅 `assign_staff`、`set_work_plan` | **高亮自救**：融资、解雇；禁止招聘、立项 | 只剩总结 |
| 制作现场 | 全部项目命令 | 仅调整计划与人员 | 允许终止、交付、调计划；禁止立项、签外包、雇临时 | 交付结清 |
| 会议室 | 议题可提交 | **主战场**：`resolve_event` | 只读，禁止新合作 | 只读 |
| 发行与市场 | 机会/发行/结算 | 只读 | 只读 + 缺口展示 | 终局总结 |
| 周推进 | 可推进 | **禁用**，先处理事件 | **可推进**（危机期限按周计） | 禁用 |

这张表就是"操作差异"的实现依据，也应当直接变成测试用例。

## 7. Issue #39 六项范围的覆盖

| Issue #39 要求 | 落在哪里 | 说明 |
| --- | --- | --- |
| 1. 公司总览（现金/声望/员工/在制项目/风险/近期回执） | 办公室 + 全局状态栏 | 风险只做"高/中/低 + 一句原因"，六维留给项目详情 |

| 3. 周经营（归属/计划/缺口/预览与回执） | 全局事务中心 + 制作现场 | **不单独做"周经营页"**：周经营是多场景动作的汇总，做成独立页会变成第四张仪表盘 |

## 8. 视觉语言

### 8.1 决策

> **像素只出现在场景层；信息面板保持现代排版。**

| 层 | 风格 | 理由 |
| --- | --- | --- |
| 场景层（办公室、制作现场背景、人物、设施、图标） | 像素风，暖色木质调 | 复用已有 3 张自生成素材与既有色板（蜂蜜木、米白、薄荷、珊瑚） |
| 面板层（数字、表格、表单、正文、回执） | 现代无衬线，真实字重，无像素字体 | 174 工作项与长文本回执必须可读；像素字体做正文在 12px 以下直接不可读 |

**明确废弃两条路线**

| 路线 | 出处 | 废弃理由 | 可保留的部分 |
| --- | --- | --- | --- |
| 纸质胶片 / 打孔档案 | `feat/frontend-visual-pass-1` | 它把办公室图当壁纸（渐变蒙版压到 0.08 透明度），恰好强化了"后台感" | 留白节奏、栏目分隔、衬线标题 |
| 全站像素 HUD 换肤 | 本地未提交改动（`--hud-*`） | 全站像素化会牺牲信息密度，且与"现代面板"冲突 | 像素图标（`PixelClapperboard`）、硬阴影、方块边框 |

> 这两条都是**审美上成立、结构上不成立**。它们解决的是"看起来像什么"，而 v4 缺的是"信息怎么分层"。

### 8.2 色板

沿用现有 `--site-*` 变量，不新造一套：

| 用途 | 变量 | 值 |
| --- | --- | --- |
| 页面底 | `--site-bg` | `#f4f1e8` |
| 主文本 | `--site-fg` | `#303931` |
| 强调（砖红） | `--site-accent` | `#a43c2d` |
| 面板 | `--site-surface` | `#fffdf7` |
| 次级文本 | `--site-muted` | `#656b61` |
| 描边 | `--site-border` | `#c9cbbd` |

场景层额外允许：蜂蜜木 `#d9a86a`、薄荷 `#9fcbb5`、珊瑚 `#e08a72`。**场景色不得进入面板层**，避免两套色系互相污染。

### 8.3 排版与节奏

- 标题：`--display-font`（衬线），仅用于场景标题与作品名。
- 正文与数字：`--site-font`（无衬线），数字统一 `font-variant-numeric: tabular-nums`。
- 字号阶梯：12 / 13 / 15 / 17 / 22 / 28 / 36，不新增中间值。
- 间距：8 的倍数；场景内区块间距 24，区块内 8/12。

### 8.4 状态反馈清单（首版必须可见）

| 对象 | 状态 | 表现 |
| --- | --- | --- |
| 员工 | 待命 / 工作中 / 疲劳 | 姿势或色调差异，不新增文字标签 |
| 项目 | 进行 / 门槛达标可交付 / 延期风险 | 卡片边条 + 角标 |
| 单集 | 六阶段进度 | 6 段进度条 |
| 设施 | 可用 / 锁定 | 锁定态灰化 + 只读 |
| 发行 | 已交付 / 已发行 / 已结算 | 依次解锁的区域 |
| 全局 | 事件待处理 / 危机 | 状态栏高亮 + 事务中心角标 |

### 8.5 动效预算

- 只做"状态变化可见"，不做装饰循环。
- 单次过渡 ≤ 200ms；场景切换 ≤ 250ms。
- 必须支持 `prefers-reduced-motion`：全站降级为无位移的淡入。
- 动画不得遮挡操作，不得表现核心尚未确认的结果。

## 9. 场景渲染技术验证（F1-T）

初稿的 5 条证明保留，但改成可判定：

| # | 必须证明 | 判定方式 |
| --- | --- | --- |
| 1 | 画出办公室 | 1280×720 场景在 1366px 与 768px 下都完整可见且不变形 |
| 2 | 显示 8–12 名员工 | 每人可独立定位、可点击，重叠时不误命中 |
| 3 | 按状态切换表现 | 给定 mock `staff_board`，状态变化后一帧内更新 |
| 4 | 点击打开 React 面板 | 场景层与 React 层互不阻塞，`Esc` 可关闭 |
| 5 | 可测试 | 员工与设施可被 RTL 以 role/label 选中，而非只能靠坐标 |

三方案对比：

| 方案 | 优势 | 代价 | 适合条件 |
| --- | --- | --- | --- |
| React DOM + CSS | 零新依赖、可测试性最好、可访问性天然成立 | 元素多时性能下降；复杂绘制（透视、光照）麻烦 | **员工 ≤ 12、无逐帧动画** |
| SVG | 矢量清晰、可交互、可测试 | 大量节点重绘成本高 | 中等复杂度、图标化场景 |
| Canvas / PixiJS | 精灵与动画性能好 | 不可访问、不可测试（需额外层）、增量包体 | 精灵数量大或需要逐帧动画 |

**决策规则**（不预设结论）：若 F1 的办公室满足"≤ 12 人、无逐帧动画、需键盘可访问"，则 DOM/CSS 胜出，不引入渲染库。只有证明 DOM 方案在 12 人 + 状态切换下出现掉帧，才进入 Canvas 评估。

## 10. 工程边界

### 10.1 路由

**首版不引入路由库。** 用 `uiStore.activeScene` 表示当前场景。

理由：4 个场景无深链需求；引入 router 会同时带来"URL 是否进存档""刷新后恢复到哪个场景"的新问题。若 M6 需要分享链接，再以 `location.hash` 补 `#scene=office&work=w1`，成本很低。

### 10.2 UI 状态边界

| 允许进 `uiStore` | 绝不允许进 `uiStore` |
| --- | --- |
| 当前场景、选中员工、展开的单集、面板开合、场景滚动位置 | 任何 GameState 字段的副本 |
| 表格排序、筛选、折叠状态 | 派生质量分、风险、可交付判定 |
| 动画/过渡开关 | 现金、声望、周数（只能读读模型） |

原则一句话：**UI 状态可以丢，游戏状态不能丢。**

### 10.3 目录

```text
apps/web/src/
  app/shell/          全局壳：状态栏、导航、事务中心、周推进
  scenes/company/     办公室
  scenes/production/  制作现场
  scenes/meeting/     会议室
  scenes/market/      发行与市场
  view-models/        读模型 → 展示模型适配
  features/           跨场景复用：staff / projects / events / finance / archive
  fixtures/v4/        M0 契约下的 mock 数据
```

这是逻辑职责，不要求立刻整体搬迁。实际目录由前端负责人结合现有结构决定，**不为架构图制造大规模重构**。

### 10.4 与 v3 页面共存

- v3 运行时仍在 main 上跑，现有 5 个测试文件（`App.test.tsx`、`HomePage.test.tsx`、`StudioPage.test.tsx`、`gameStore.test.ts`、`StatusBadge.test.tsx`）不得被破坏。
- v4 前端在独立分支/独立入口推进，F3（M6）才替换旧路径。
- 旧入口移除时必须留一条明确记录，不能"悄悄下线"。

### 10.5 测试与可访问性

| 层次 | 要求 |
| --- | --- |
| 场景壳 | 4 场景切换、导航键盘可达、保持选择 |
| 场景内容 | 关键断言走 role/label，不依赖 class 名（`feat/frontend-visual-pass-1` 改了 `text-button` 类名就踩到这类坑） |
| 状态矩阵 | §6 的 4×5 表格化为参数化用例 |
| 可访问性 | 全站焦点可见、`aria-label` 完整、对比度 ≥ 4.5:1、支持 reduced-motion |

### 10.6 性能

- 174 工作项默认折叠；展开超过 50 行时启用虚拟化。
- 场景层与面板层分离渲染，场景重绘不触发面板重排。
- 首屏 JS 增量不超过现有基线 + 30KB（gzip）。

## 13. 读模型缺口清单

按架构 §8.4，现有 9 个读模型：`company_overview`、`work_detail`、`production_board`、`staff_board`、`finance_summary`、`crisis_board`、`market_board`、`event_card`、`week_receipt`。

四个场景里有 3 处无法只靠这些读模型表达，需要向架构侧提需求（**不是前端私造字段**）：

| 缺口 | 影响的场景 | 需要的形状 | 建议处理 |
| --- | --- | --- | --- |
| 设施视图 | 办公室 · 设施区 | 现有设施 id、名称、效果、状态 | 可先由 `company_overview` 扩展一节；P1 阶段用只读 mock 占位 |

另有一类**不是缺口、但必须说清**的：员工在场景里的**站位与朝向**是纯表现数据，由前端根据 `assignment_work_id` 与状态推导，**不得反推出任何业务含义**。
