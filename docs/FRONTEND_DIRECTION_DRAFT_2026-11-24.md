# 前端方向初稿：三空间混合型经营模拟

> 状态：**方向初稿 / 待前端与产品评审，不是最终 UI 规范**
> 日期：2026-11-24
> 适用范围：v4 前端信息架构、视觉表现与分阶段开发
> 产品选择：负责人选择 **C「混合型模拟经营」**——公司经营、作品制作、市场经营三个部分均有独立玩法界面。
> 权威关系：玩法规则以 [DECISION_LOG.md](DECISION_LOG.md) 为准；状态与命令契约以 [DOMAIN_ARCHITECTURE.md](DOMAIN_ARCHITECTURE.md) v1.4、[M0_CONTRACT_FREEZE.md](M0_CONTRACT_FREEZE.md) 为准；阶段依赖以 [DEVELOPMENT_ROADMAP.md](DEVELOPMENT_ROADMAP.md) 为准。本文只定义前端表达方向，不改变玩法规则、状态模型或 API。

## 1. 本轮审查结论

### 1.1 现状判断

本轮审查基于 2026-11-24 的 main 文档、M0 契约、开发路线、Issue #39，以及负责人提供的 WP10 页面截图。截图只代表当前展示样式，不据此推断未展示页面的全部实现。

当前页面已经具备一些可复用基础：

- 有统一的公司名称、周数、资金、在制项目等经营信息层级；
- 有公司总览、作品详情、每周经营等页面入口；
- 米白底色、深绿、砖红强调色和衬线标题形成了初步视觉识别；
- 周报能集中说明经营结果，适合作为周推进后的回执内容。

但截图呈现出的主体验仍然是：

**读取经营报告 → 查看数字 → 阅读文字结论 → 处理少量选项。**

这会让游戏被理解成经营后台或文字经营游戏。主要缺口不是卡片样式，而是三个方面：

1. **缺少可感知的经营空间**：公司没有成为玩家持续观察和建设的场景，员工、设施、工作区域没有形成视觉主体。
2. **缺少不同玩法空间的差异**：公司、制作、市场目前还没有各自独立的操作节奏和表现方式。
3. **缺少行动后的可见反馈**：人员安排、作品推进、发行结果和公司成长，不能只靠周报中的数字变化来表达。

因此，当前周报和数据面板不应删除，但应从“游戏主体”调整为“信息与结算辅助层”。

### 1.2 仓库现状与开发边界

审查后确认以下边界：

- main 已包含领域架构 v1.4 与 M0 契约冻结。UI 版式、文案和交互细节并未被 M0 冻结。
- M1 运行时工作在独立分支 / PR 推进；现有 M1 切片明确没有修改 apps/web，当前不能把旧 V3 页面视为 v4 前端。
- Issue #39 已允许前端先做信息架构、低保真线框和 Mock 可交互原型；不接真实 v4 API、不修改核心状态模型、不自行发明业务字段或玩法规则。
- DEVELOPMENT_ROADMAP 明确：UI 信息架构与可读性现在持续做 Mock；M2 后可用真实读模型做只读静态验证；M6 才完成完整交互、v4 存档接入和旧运行时切换；M7 验收操作负担。
- 当前正式前端技术栈是 React 19、TypeScript、Vite、Zustand。WP10 的 Babylon Standalone + React 18 UMD 仅用于视觉验证，不应直接作为正式工程技术基线。

这份方向稿是对 Issue #39 的产品表达升级，不替代 M0–M7，也不提前启动真实 API 集成。

## 2. 产品定位与核心结构

### 2.1 定位

《动画制作委员会》采用**三空间混合型经营模拟**：

- 公司经营：经营一家持续成长的动画公司；
- 作品制作：组织多部作品的生产，处理计划、人员、质量、工期和风险；
- 市场经营：寻找企划机会、经营产业合作，并观察作品发行后的商业结果。

三者不是三个独立小游戏，也不是三个只有数据表格的后台页面。它们共享同一份 GameState、公司资金、员工、作品、关系、周数和存档。

作品是核心目标；公司成长提供长期动力；产业关系帮助作品获得资金、制作资源和商业回报。三个空间分别表达这条经营循环的不同侧面。

### 2.2 三空间职责

| 空间 | 玩家主要感受 | 主要信息与操作 | 视觉主体 |
|---|---|---|---|
| 公司经营 | 我正在经营一家动画公司 | 员工、组织、办公环境、公司资金与声望、招聘和设施 | 可观察的公司场景 |
| 作品制作 | 我正在组织一部或多部动画的生产 | 作品计划、公共制作、单集制作、六阶段、工作项进度、质量与风险 | 作品制作流程与项目工作区 |
| 市场经营 | 我的作品正在行业中寻找机会并接受市场反馈 | 企划机会、合作伙伴、委员会、渠道、发行反馈、商业表现 | 市场机会、发行与作品反馈 |

推荐默认进入“公司经营”作为公司主空间；玩家可从全局导航直接进入作品制作或市场经营。默认入口属于交互建议，可在原型测试后调整。

### 2.3 统一主框架

三个空间应共享同一套全局框架，避免切换时丢失时间、资金和当前经营重点。

~~~text
┌────────────────────────────────────────────────────────────┐
│ 全局状态：公司 / 周数 / 资金 / 声望 / 风险 / 待处理事项      │
├────────────────────────────────────────────────────────────┤
│ 公司经营             作品制作             市场经营           │
├────────────────────────────────────────────────────────────┤
│                                                            │
│                 当前空间的主要游戏内容                     │
│                                                            │
│                                                            │
├────────────────────────────────────────────────────────────┤
│ 事件与消息 / 周回执 / 历史记录 / 推进下一周                 │
└────────────────────────────────────────────────────────────┘
~~~

全局框架建议包含：

1. **全局状态栏**：当前周数、公司现金、声望、在制作品数量、经营风险与待处理事项。只展示最有决策价值的信息，不把全部数值塞进首屏。
2. **三空间导航**：公司、作品、市场。切换空间不改变游戏时间，也不重置当前选择。
3. **空间主视图**：每个空间拥有自己的视觉主体和主要操作。
4. **事务与消息中心**：事件、待处理决策、周回执、历史记录集中管理；避免每周强制打开一份长报告。
5. **统一周推进控制**：在任一空间都能看到是否存在阻断推进的待处理事项，并明确推进后将发生什么。

周报保留为周推进后的简短回执：说明本周主要变化、异常、项目进展和下周风险；完整明细可展开查看。周报不再承担整个游戏的主要画面。

## 3. 三个空间的设计方向

### 3.1 公司经营空间

**目标：让玩家看见自己经营的公司，而不是只看见公司的统计数据。**

建议以 2D 俯视 / 斜俯视办公室场景作为主要视觉内容，采用可控范围内的像素风或像素感场景表达。场景可以包含：

- 办公区域、会议区域和少量有明确用途的设施；
- 员工角色及其当前工作状态；
- 随公司发展发生变化的空间、设施和人员规模；
- 可点击的员工、区域与设施入口。

交互建议：

- 点击员工打开人物信息与当前状态；
- 点击工作区域查看人员和项目安排；
- 点击设施查看效果与建设状态；
- 招聘、人员调整、公司经营事务通过明确的管理面板处理；
- 重要状态变化在场景中同步反馈，例如员工进入工作状态、设施变化、员工数量变化。

不要求首版实现复杂寻路、实时行为 AI 或完整的模拟城市。员工可以根据游戏状态显示在对应区域，并使用少量循环动画表达工作状态。场景位置和动画是表现数据，不是第二套游戏规则。

规则边界：

- 核心员工每周严格归属一个项目，不得把 UI 做成同周跨项目借调或拆分工时。
- 招聘、抽卡和解雇不要求全公司空闲；具体成本与生效时机遵循 DECISION_LOG。
- 设施只表达已确认或已实现的辅助成长，不擅自扩展成复杂科技树、培训树或部门晋升系统。
- 公司只有一个真实现金池；员工、项目和设施面板不得制造多个可支配现金账户。

### 3.2 作品制作空间

**目标：让玩家理解作品如何被组织生产，并能看见制作状态变化。**

作品制作空间建议分为三层：

1. **作品总览**：在制作品列表、项目状态、计划重点、预计工期、风险和关键问题。
2. **项目详情**：作品概况、公共制作、单集结构、制作计划、人员归属和交付条件。
3. **制作过程视图**：按单集查看六阶段进度，并在需要时展开具体工作项、依赖和最低交付情况。

必须忠实表达既有制作结构：

- 一部作品由一个公共制作容器和 N 个单集容器组成；
- 公共制作与单集制作分开呈现；
- 每个单集固定六阶段：单集内容设计、分镜与原画、动画制作、美术与视觉制作、摄影与剪辑、声音与最终交付；
- 工作项是唯一生产原子，依赖可以跨容器；达到最低交付要求即可解锁下游工作，前序工作仍可继续完善；
- 质量与工作量分离，质量与商业表现也分开表达。

界面不能把“六阶段”画成整部作品共用的一条线性流水线，也不能让玩家面对全部工作项的长列表。默认先显示作品、单集和阶段摘要；需要排查依赖或交付问题时，再逐层展开工作项。

计划操作遵循现有契约：投入强度、项目取向、外包策略、赶工与至多一个项目内定向目标。持续方针自动执行；不要求玩家每周重复填写全部选项。任何尚未进入规则或命令契约的按钮都只能作为明确标注的原型占位，不得伪装成可用功能。

### 3.3 市场经营空间

**目标：让玩家感受到作品进入行业、获得机会、产生反馈和商业结果。**

市场空间不应退化为财务表格。建议将信息组织为：

- **企划机会**：市场槽位、可接触的作品机会、作品来源和关键条件；
- **产业合作**：合作伙伴、委员会成员、投资和渠道关系；
- **发行与反馈**：作品播出 / 发行后的市场反馈、评价和表现；
- **商业结果**：收入、分成、项目归因和公司现金变化；
- **作品履历**：已交付作品、系列关系、代表作和历史成绩。

市场经营空间的具体功能必须按 M2–M5 的实际实现逐步开放。Archive 最小记录、企划槽、供应商、委员会、渠道和系列等能力分别受对应里程碑约束。界面可以先定义信息结构和 Mock 样例，但不能提前创造不存在的命令、字段或经营规则。

市场视图的重点是“机会—选择—作品结果—长期积累”的因果链，而不是一次性展示一张收益排行榜。

## 4. 三空间之间的统一经营循环

三个空间共享同一个周时间步。建议把玩家的操作组织为：

1. 在市场空间观察机会，选择是否接触或启动项目；
2. 在公司空间观察人员、资金和公司条件；
3. 在作品空间配置项目计划、查看制作结构和进度；
4. 处理真正需要玩家决定的事件或异常；
5. 推进一周；
6. 核心完成统一结算，前端展示本周变化；
7. 公司、作品和市场三个空间同步更新，玩家继续经营。

~~~mermaid
flowchart LR
    A[市场：机会与合作] --> B[公司：人员与经营条件]
    B --> C[作品：计划与制作]
    C --> D[统一周推进]
    D --> E[周回执与事件]
    E --> F[公司状态更新]
    E --> G[作品状态更新]
    E --> H[市场与商业结果更新]
    F --> A
    G --> A
    H --> A
~~~

注意：

- 周推进与数值结算始终由 Game Core 负责；前端只提交命令并展示结果。
- 随机结果在周结算后揭晓，不在推进前向玩家泄露完整结果。
- 已配置的持续方针自动执行；玩家主要处理新增承诺、重要调整和异常决策。
- 事件应突出影响对象、已知代价和后果，不用大量无意义弹窗填充每周操作。
- 周回执是结算后的解释层，不是另一个独立的玩法空间。

## 5. 视觉表现方向

### 5.1 总体风格

建议采用：

**像素风经营场景 + 清晰现代的信息面板 + 有辨识度的作品展示。**

不是把所有界面都像素化，也不是把像素插画作为卡片装饰。三个空间可以有不同的视觉重心，但必须共享统一的字体、色彩、图标、边框、间距和交互状态规范。

建议保留当前米白、深绿、砖红的基础识别作为 UI 色彩起点，重新分配页面权重：

- 公司空间：场景占主导，状态栏和员工管理面板辅助；
- 作品空间：作品视觉、制作结构和进度占主导，数值细节按需展开；
- 市场空间：企划 / 作品展示和市场反馈占主导，财务数据作为解释信息；
- 事件与周回执：采用统一的消息、决策和结果反馈样式。

不要照搬开罗游戏的具体布局、角色、素材或图标。参考的是其“场景本身承载经营状态、角色与空间变化提供反馈”的表达方式。

### 5.3 动画与反馈原则

首版优先做“状态变化可见”，而不是追求动画数量：

- 员工：待命、工作、疲劳或特殊状态有轻量表现；
- 设施：升级或启用后能看见变化；
- 项目：进度、阶段解锁、延期、交付等状态有明确反馈；
- 市场：作品发行、评价、商业结果和关系变化有独立反馈；
- 周推进：使用统一的结算过渡与回执，避免每个数字都单独弹跳。

动画必须服务于信息理解。不能让装饰动画遮挡操作，也不能用动画表现尚未发生或未被核心确认的结果。

## 6. 前端工程架构建议

### 6.1 已确定的工程基线

沿用现有正式工程：

- React 19 + TypeScript + Vite；
- Zustand 作为当前状态管理依赖；
- 现有 Tailwind CSS 与 lucide-react 继续作为 UI 基础；
- 前端展示核心返回的状态 / 读模型，并提交契约允许的命令；
- 不把旧 V3 运行时或 WP10 临时验证工程作为 v4 正式架构。

### 6.2 建议的模块边界

~~~text
apps/web/src/
  app/
    shell/                 全局框架、导航、状态栏、事务中心
  spaces/
    company/               公司经营空间
    production/             作品制作空间
    market/                 市场经营空间
  features/
    staff/                  员工信息与分配 UI
    projects/               作品与项目摘要
    events/                 事件处理
    finance/                财务与流水展示
    archive/                作品履历
  presentation/
    scene/                  场景渲染适配层
    animation/              状态反馈动画
  view-models/
    adapters/               核心读模型到 UI 展示模型的适配
  services/
    commands/               命令提交与错误处理
  fixtures/
    v4/                     遵守 M0 契约的 Mock 数据
~~~

以上是逻辑职责建议，不要求立即按目录整体搬迁。实际目录应由前端负责人结合现有 apps/web 结构确定，避免为了架构图制造大规模无收益重构。

### 6.3 场景渲染技术不在本稿锁定

公司空间需要 2D 场景能力，但当前不直接批准新增 PixiJS 或其他渲染依赖。

建议先做小型技术验证，比较：

- React DOM + CSS / SVG：适合静态或轻量交互场景，工程简单；
- Canvas / PixiJS：适合较多精灵、图层和连续动画；
- 其他方案：必须说明其必要性、构建体积、可访问性、测试方式和与 React 的边界。

技术验证至少要证明：能绘制一间办公室、显示若干员工、根据 Mock 状态切换员工表现、响应点击并打开 React 信息面板。验证完成后再决定是否引入场景渲染库。

不要为了一个办公室原型引入完整 3D 引擎，也不要让 Canvas 场景接管业务状态、规则或存档。

### 6.4 前端与核心的职责边界

| 责任 | Game Core / API | 前端 |
|---|---|---|
| 资金、质量、工作量、疲劳、事件概率 | 计算与校验 | 展示结果 |
| 员工项目归属与周结算 | 保存、验证、结算 | 提交合法命令、展示安排 |
| 工作项解锁与最低交付 | 计算派生状态 | 汇总展示、展开依赖 |
| 随机性 | 按冻结规则计算 | 不预测、不重算 |
| 事件效果与资金流水 | 结算并写入状态 | 展示代价、选项和结果 |
| 读模型 | 提供或由核心重算 | 适配为页面 View Model |
| 场景位置、动画、面板展开状态 | 不负责 | 作为纯表现状态管理 |

前端可以有本地 UI 状态（当前选中员工、展开的单集、场景视角等），但不能复制一份游戏规则状态。

M0 中的派生值、周回执和读模型不应被前端当作持久存档字段。新增 UI 需要的数据应先核对架构与契约；缺字段时提出读模型需求，不得私自扩展 GameState。

## 7. 分阶段开发路线

本路线是前端工作流，与 M0–M7 游戏能力里程碑并行，不替代 DEVELOPMENT_ROADMAP。

| 前端阶段 | 目标 | 交付物 | 与游戏里程碑关系 |
|---|---|---|---|
| F0 方向与信息架构 | 三空间职责、导航、主要用户流程、页面层级 | 本方向稿、导航图、低保真线框 | 现在；不依赖真实 API |
| F1 Mock 视觉原型 | 三空间可切换；公司场景、作品制作、市场结果有不同视觉主体 | 可点击 Mock 原型、关键状态样例、场景技术验证 | 可与 M1/M2 并行 |
| F2 真实读模型可读性验证 | 用真实读模型替换 Mock 展示，验证字段和信息组织 | 只读原型、字段映射、缺口清单 | M2 后，按路线进行 |
| F3 完整交互接入 | 命令提交、事件、周推进、存档与读档、错误反馈 | v4 正式前端 | M6 |
| F4 体验验收与打磨 | 操作负担、信息可读性、异常状态、长局体验 | 浏览器验收、可用性问题清单、修订记录 | M7 |

### 7.1 F1 首个视觉纵切片

不要一次性把三个空间做成完整产品。先做一个能证明整体方向的视觉纵切片：

1. 公司空间：一间可显示员工和工作状态的办公室；
2. 作品空间：一部作品的公共制作 + 单集六阶段摘要，能展开查看工作项；
3. 市场空间：一个作品发行 / 放映结果场景，显示评价和商业结果的 Mock；
4. 全局框架：三空间切换、统一周数和公司状态；
5. 周推进演示：使用固定 Mock fixture 演示一次结算前后状态变化，明确标注为 Mock，不连接真实核心。

这个切片的验收目标是证明“同一家公司在三个空间中呈现同一份经营状态”，不是证明 M1/M2 玩法已经可运行。

### 7.2 F1 验收标准

- 三个空间不是同一套卡片模板换标题；每个空间有明确的视觉主体和主要操作。
- 玩家进入公司空间能看见公司与员工；进入制作空间能理解作品结构；进入市场空间能理解机会或作品结果。
- 三空间的公司资金、周数、员工和作品状态来自同一份 Mock fixture，不出现相互矛盾的数字。
- 作品制作视图准确区分公共制作、每集六阶段和工作项依赖。
- 员工安排视图不提供同周跨项目借调。
- 周报 / 回执作为辅助信息出现，不占据整个游戏主体。
- 不连接真实 v4 API，不修改 GameState、M0 契约或游戏规则。
- 场景渲染技术经过小型验证后再决定是否引入依赖。
- 所有 Mock 字段都能追溯到现有架构 / M0 契约，或明确标注为纯表现数据。

## 8. 本轮明确不做

1. 不修改 M0 冻结的 GameState、命令、错误码、存档和规则。
2. 不提前接入 M1/M2 尚未完成的真实 API，不以 Mock 结果冒充核心计算。
3. 不重写游戏核心，不改变 M0–M7 里程碑与前置条件。
4. 不将三空间做成三个独立存档或独立时间线。
5. 不将周报继续作为唯一主界面，也不把所有内容都做成卡片、表格和长文本。
6. 不在首版实现复杂寻路、员工实时 AI、3D 场景或完整动画制作工具。
7. 不直接引入 PixiJS / Babylon 等新渲染依赖，先做技术验证。
8. 不把开罗游戏截图或其他商业游戏素材直接打包进项目资源；参考图只用于内部讨论，正式素材另走来源、授权和入库审核。
9. 不为了视觉展示发明新玩法、数值、业务字段或后端命令。

## 9. 四个实际场景：区域、交互对象与首版资源边界

> 本节根据负责人确认补充：**实际场景按四个设计**。原文“三空间”仍用于描述三类经营职能；它不是实际地图数量。市场机会、作品发行、反馈与结算统一放在第四个“发行与市场”场景中。以下是前端表达与原型范围建议，不代表新增玩法规则已经获批。

### 9.1 场景总表

| 场景 | 承载职能 | 核心视觉主体 | 主要交互方式 | 首版定位 |
|---|---|---|---|---|
| 公司办公室 | 公司日常经营、员工与设施、公司状态 | 可观察的办公室地图与员工 | 点击员工、工位/区域、设施；打开管理面板 | 主场景，持续经营的空间锚点 |
| 动画制作现场 | 作品生产、项目进度、工作项与交付 | 制作现场、项目看板或制作区域 | 选择作品/单集/阶段；查看工作项与人员安排 | 制作操作主场景 |
| 会议室 | 委员会、合作关系、企划讨论与重要决策 | 会议桌、参会角色、议题与文件 | 进入会议议题、查看参与方、处理已存在的决策命令 | 低频但重要的决策场景 |
| 发行与市场 | 市场机会、发行、首映反馈、商业结果与结算 | 作品海报/展示区、发行信息与反馈 | 查看机会、作品表现、收入归因、历史履历 | 将市场与作品结算合并，不再拆成两张地图 |

### 9.2 公司办公室

**空间结构建议**
- 办公主区域：员工、工位与日常工作状态。
- 管理区域：公司信息、招聘/人员管理入口。
- 设施区域：已实现设施及其状态；设施数量和效果严格跟随实际规则。
- 公共信息入口：财务、声望、事件和待处理事项的入口，不另造第二套公司账本。

**可交互对象**
- 员工角色：查看人员信息、疲劳/士气等已存在状态，以及当前项目归属。
- 工位或工作区：查看当前区域人员与工作状态；若点击后涉及项目分配，必须走契约允许的命令。
- 设施：查看已存在的设施状态与效果；未实现设施只能显示锁定/规划占位，不得提供虚假建造按钮。
- 管理入口：打开招聘、解雇、公司经营信息等现有功能面板。

**场景反馈**
- 员工数量或分布变化应能被看见。
- 员工工作/待命等表现来自当前状态，不由场景动画自行推断业务结果。
- 设施状态变化应有视觉反馈，但不要求首版支持自由装修或完整建造系统。

### 9.3 动画制作现场

**空间结构建议**
- 制作主区域：当前作品、项目状态与制作中的视觉主体。
- 单集/阶段导航：按作品和单集展开六阶段。
- 工作项区域：显示工作项状态、依赖阻塞和最低交付情况。
- 人员安排入口：显示项目成员及合法归属，不把办公室员工拖拽成可跨项目自由借调。

**可交互对象**
- 作品/项目：切换当前查看的作品。
- 单集：查看单集制作状态。
- 六阶段：查看阶段摘要及阶段内工作项。
- 工作项：查看进度、依赖、交付门槛与参与人员。
- 人员安排：通过合法命令配置项目计划和人员归属；核心员工每周只能归属一个项目。

**表现约束**
- 六阶段是每个单集内部的制作结构，不是整部作品的一条线性总流水线。
- 公共制作与单集制作必须分开呈现。
- 工作项是唯一生产原子；达到最低交付门槛即可解锁下游，前序工作仍可继续完善。
- 默认展示摘要，只有用户主动深入时才展开工作项细节，避免把 174 个工作项同时铺满屏幕。

### 9.4 会议室

**空间结构建议**
- 会议桌与参会席位：表达参与方和当前议题。
- 议题展示区：显示企划、委员会或合作议题。
- 决策文件区：显示当前可处理的选项、条件和结果摘要。
- 历史记录入口：查看已发生的关键会议与合作记录；历史记录不应伪装成可再次执行的命令。

**可交互对象**
- 参会方/合作方：查看其身份、关系和已知条件。
- 议题：打开对应的企划或合作信息。
- 决策项：仅当核心/API 已提供合法选项时允许提交；否则作为只读信息或明确标记的 Mock。
- 会议记录：查看已确认的历史结果。

**边界**
- 会议室是委员会、合作和重要决策的空间化表达，不代表所有决策都必须被设计成“开会”。
- 不新增会议小游戏、谈判数值、好感度或独立资源，除非玩法规则后续明确批准。
- M4 产业关系能力未实现前，委员会和投资相关交互只做结构验证，不提前宣称可玩。

### 9.5 发行与市场

**空间结构建议**
- 市场机会区：展示已存在的企划机会、来源与条件。
- 发行展示区：展示已交付或进入发行环节的作品。
- 首映/反馈区：呈现作品评价、市场反馈和重要结果。
- 商业结算区：展示收入、分成、归因与公司现金变化。
- 作品履历区：展示已交付作品的历史记录和长期成绩。

**可交互对象**
- 企划机会：查看机会信息；只有对应阶段已实现的合法命令才可采纳/拒绝。
- 作品展示物：查看作品信息、发行状态和反馈。
- 结算记录：查看收入来源、分成和财务归因；结算记录是只读事实，不可编辑金额。
- 历史作品：查看 Archive 中已保存的作品履历。

**合并原则**
- 市场机会、发行过程、首映反馈、商业结果和作品结算属于同一个场景中的不同区域/视图，不拆成独立地图。
- “结算”是市场场景中的信息与反馈环节，不是另一个经营空间，也不形成第二个现金池。
- 具体能力按 M2 Archive、M3 企划槽、M4 委员会/渠道、M5 长期积累的实际实现逐步开放。

### 9.6 场景之间的关系

四个场景不是四套互不相干的系统，也不要求玩家每周按固定顺序走完四个房间。它们是同一经营状态的四种空间化入口：

- 办公室：谁在公司、公司当前状况如何。
- 制作现场：作品正在做什么、哪里受阻。
- 会议室：有哪些重要合作与决策需要处理。
- 发行与市场：作品如何进入市场、产生什么反馈和商业结果。

全局状态栏、事件/消息中心和周推进控制跨场景常驻。场景切换本身不推进时间、不触发结算，也不改变业务状态。

### 9.7 首版资源量控制

资源量按“可验证体验”分层，不按完整游戏场景一次性铺开：

| 层级 | 场景资源 | 交互范围 | 验收目标 |
|---|---|---|---|
| P0 线框 | 四个场景的布局草图、区域命名、导航关系 | 点击区域进入对应 Mock 面板 | 玩家能理解四个场景各自负责什么 |
| P1 Mock 原型 | 办公室一张基础地图；制作现场一张主视图；会议室一张基础构图；发行与市场一张基础构图 | 场景切换、对象点击、信息面板、Mock 状态变化 | 四场景不再呈现为单纯文字报告，核心循环可被理解 |
| P2 视觉验证 | 办公室少量员工/设施素材；其他三场景必要的角色、作品展示和状态素材 | 轻量动画、选中态、反馈状态 | 验证场景渲染技术与视觉语言 |
| P3 真实读模型 | 用 M2 后可用的真实读模型替换 Mock 数据 | 只读展示、异常和结算回执 | 验证数据结构能支撑四场景表达 |
| P4 完整接入 | 依 M6 接入合法命令、存档与错误反馈 | 完整经营交互 | 浏览器端完整游玩 |

**首版不做**：四张高精度大地图、自由装修、复杂寻路、员工实时 AI、会议演出动画、市场人群模拟、完整 3D、为每个工作项单独制作美术资产。优先复用组件、图标、状态标签和有限角色素材。

### 9.8 待前端负责人验证的事项

以下属于技术与体验验证，不要求负责人现在逐项裁决：
1. 办公室地图采用 React DOM/SVG 还是 Canvas/PixiJS。
2. 制作现场采用空间化工作区还是以项目看板为主、辅以制作场景背景。
3. 会议室和发行与市场是否需要可漫游地图，还是静态场景构图加交互面板更合适。
4. 四个场景在桌面端和窄屏下的布局适配方式。
5. 角色、设施、作品海报等素材的复用策略与最低资产清单。

前端负责人应先提交四场景低保真线框和一份最小资产清单，再决定是否投入正式美术资源。本文不把任何一种场景渲染技术或美术风格细节提前锁死。
