## 2. M3 与 M4 的边界

### 2.1 M3：能同时经营多部作品

M3 必须形成可由正常玩法启动的多项目经营闭环，不能只靠手工 fixture：

1. 多个 Project 可同时处于 producing，项目状态相互隔离。
2. 核心员工严格单项目归属；全局分配先确定员工归属，再在项目内部由规则内核分配到工作项。
3. 工作项级磨合损失按 DEC-STAFF-001 计算，不得退化为整集/整阶段惩罚。
4. 基础供应商目录与外包合同可通过正常玩法获得；外包合同落到具体 WorkItem。
5. 同一供应商的 active 合同周产能按公司范围汇总，不能因项目分开结算而重复出售。
6. Market 提供企划槽和正常项目来源；项目立项后冻结 OfferSnapshot 并消费对应企划。
7. 通过 520 周压力验证，持续保持状态、现金、员工归属、供应商容量和事件不变量。

M3 不要求完成完整委员会产业关系与商业分账；这些属于 M4。

### 2.2 M4：能经营产业合作

M4 在 M3 多项目基础上补齐：

1. 合作方、合作关系、邀请与接受。
2. 单作品委员会的成立、成员/渠道快照、关闭与关系沉淀。
3. 投资本金、制作合同预算、实际制作成本和商业收入的独立核算。
4. BD 与非 BD 渠道收入规则、渠道开放/代理手续费、电视服务倍率和费用。
5. 委员会净商业池由玩家按投资比例取得，其他成员合计取得剩余份额，交付后可对账。
6. 作品交付后写入 Archive 的渠道对账与合作快照；委员会关闭，合作关系结果沉淀到 Partnership。
7. 委员会成员中期诉求复用 Event，不另建委员会事件系统。

M4 不引入委员会投票、席位政治、逐个投资人谈判或独立好感度子系统。

## 3. 跨模块数据交接

| 流程 | 权威来源 | 消费方 | 交接内容/约束 |
|---|---|---|---|
| 企划立项 | Market | Application → Project | Offer 整体快照复制；包含来源、规模、预算、期限、蓝图、集数、渠道基线与合作模式资格；Market 消费原 Offer |
| 员工归属 | Staff | Application / Kernel | 每名核心员工每周最多一个 `assignment_work_id`；不得由 Project 或 Kernel 另存一份归属事实 |
| 工作项分配 | Project + Staff + Vendor 快照 | Rules Kernel | 输入工作项需求、员工唯一归属与状态、active 外包合同交付；输出本周确定性分配结果，不形成第二份持久分配账本 |
| 磨合判定 | Staff 的参与历史 + Project WorkItem | Rules Kernel | 以具体工作项是否已开工、员工是否参与过该项为依据；只影响工作量，不影响质量 |
| 外包签约 | Vendor | Finance + Project/Kernel | Vendor 独占合同与供应商产能；Finance 独占费用流水；Project 只接收实际交付工作量/质量结果 |
| 周结算 | Application | 所有参与领域 | 读取不可变快照，按 M0 §14.7 八阶段顺序计算，全部成功后一次提交；失败不留部分状态 |
| 委员会成立 | Partnership | Project + Finance | 委员会绑定单一 work；成员/渠道关系唯一；投资比例归 Project，实际资金变更归 Finance |
| 商业结算 | Rules Kernel / commerce | Finance + Archive + Partnership + Company | 内核计算渠道毛收入和分配结果；Finance 记唯一流水；Archive 追加对账快照；Partnership 关闭委员会并沉淀关系 |
| 事件效果 | Event 提供事件与选项 | Application → 对应领域 | Event 不直接写 Staff/Project/Finance；效果通过正式领域命令/事务写入；委员会诉求只引用该项目真实成员/渠道 |

## 4. M3 集成顺序与验收

### M3-A：多项目生命周期

- 从正常 Market Offer 启动至少两个项目。
- 项目制作进度、计划、事件、交付状态完全隔离。
- 一个项目交付/中止，不得误清理另一个项目的员工、合同或事件引用。

### M3-B：跨项目人员竞争

- 至少两个项目同时存在工作项需求。
- 同一核心员工不得同时进入两个项目的当周产能。
- 全局员工归属在项目内工作项分配之前确定。
- 改变项目遍历顺序、插入顺序或 ID 遍历顺序，不得改变同一输入下的最终结果。
- 工作项级磨合按 DEC-STAFF-001 生效；未开工工作项不产生接手损失。

### M3-C：供应商共享产能

- 至少两个项目同时向同一供应商购买产能。
- `sum(active weekly_cap)` 不得超过供应商 `capacity_per_week`。
- 外包合同只绑定具体工作项；项目、单集与工作项引用必须一致。
- 外包交付进入工作项进度；费用只通过 Finance 入账。
- 合同交付、失败或项目终止后，供应商可用产能正确释放。

### M3-D：正常项目来源

- 至少一条真实 Market Offer → start_work → Project 的链路。
- 不允许仅靠测试夹具创建所有项目来宣称 M3 已完成。
- Offer 被消费后不可重复立项；OfferSnapshot 不随 Market 后续刷新而变化。
- 已确认的企划槽数量、锁定、定金、有效期和到期语义遵循当前 M0/DECISION_LOG，不在集成层重新定义。

### M3-E：长周期压力验证

- 运行路线图要求的 520 周压力验证。
- 重点观察状态不变量、现金非负、员工单项目归属、供应商容量、项目/事件引用、随机复现与存档恢复。
- 发现平衡问题先归类为参数/内容/规则问题，不以修改冻结规则的方式掩盖实现缺陷。

**M3 出口：** 多项目可由正常玩法启动；人员和供应商资源竞争真实生效；项目遍历顺序不影响结果；520 周压力验证通过。单项模块测试通过不等于 M3 出口通过。

## 5. M4 集成顺序与验收

### M4-A：合作方与委员会生命周期

- Partner 由 Partnership 独占；合作关系为公司长期资产。
- Committee 绑定单一 Project，随项目立项成立，交付结算后关闭。
- Committee 成员不重复、渠道不重复；一个成员对应一个渠道，BD 不挂成员。
- 承制项目不创建 Committee；委员会项目必须有玩家投资比例与合法成员渠道归属。
- 作品结算后委员会快照进入 Archive，合作关系结果留在 Partnership；不能让已关闭委员会继续作为活动组织复用。

### M4-B：资金与商业口径

所有现金变化只进入 Finance 唯一现金池与追加式流水；不创建项目独立钱包。

必须分别识别以下金额，禁止重复入账或混为一类：

- 委员会项目总投资池及玩家实际投资额；
- 制作费/合同预算（制作公司的收入）；
- 项目实际制作成本（制作公司的费用）；
- BD/DVD 收入（始终归制作公司）；
- 非 BD 商业收入与适用的前置商业成本；
- 玩家按投资比例、其他成员合计按剩余份额分配的非 BD 净商业池；
- 代理手续费、电视服务费及其他已确认渠道成本。代理手续费按 DEC-COMM-001 冻结的公司声望/同类渠道历史成功合作次数分档（45%/40%/35%）；委员会有对应渠道成员时为 0%，两项代理准入条件均未满足时渠道关闭。

委员会投资本金不是制作收入；制作费不是实际制作成本；项目超支可以形成制作亏损。承制项目不参与非 BD 常规窗口和委员会特殊商业分配。具体规则以 DEC-COMM-001/002/003、DEC-BD-001 与相关已确认决策为准。

**统一口径：** 非 BD 委员会商业结算先汇总渠道毛收入，扣除适用且已约定的前置商业成本，得到净商业池；玩家按 `Project.investment.percent` 分配，其他成员合计取得剩余份额。当前只记录玩家比例和实际投资金额，不记录其他成员细分比例或分配明细。DEC-COMM-003 为权威决策；DOMAIN_ARCHITECTURE §10.6 已在本 PR 同步为该公式，不再保留旧的毛收入直接乘投资比例的表达。

### M4-C：渠道结算与对账

- 渠道集合由企划自带渠道、委员会成员渠道及玩家主动购买的电视服务按规则组成。
- 逐渠道计算毛收入，再按适用热度、声望、系列/电视等系数计算结果。
- BD/DVD 始终归制作公司；非 BD 委员会商业净池由玩家按投资比例取得，其他成员合计取得剩余份额。
- 电视倍率只作用于 DECISION_LOG 指定的渠道，不作用于海外发行及电视版权收入本身。
- Finance 每笔收入/成本只记一次；Archive 记录逐渠道毛收入、适用成本、公司所得、玩家分配、其他成员合计及可复算的对账数据。若现有 `channel_breakdown` 形状无法承载某项事实，必须先提交契约差异，不得由模块私加字段。
- 对账恒等式必须能从渠道毛收入推导至公司与委员会各方最终金额，不能依赖 UI 展示值或手工修正。

### M4-D：Event 与委员会诉求集成

- 委员会成员中期诉求遵循 DEC-COMM-005。
- 仅委员会项目可触发；事件来源必须属于该项目真实参与的成员/渠道。
- 复用 Event.pending[]、期限、查看与解决规则。
- Event 只描述触发和效果意图；Application 将效果路由至 Project、Finance、Partnership 等唯一写入方。
- 不增加委员会专属事件队列、投票、派系或复杂政治系统。

**M4 出口：** 委员会生命周期正确；投资、制作、商业分账互不混淆；逐渠道对账恒等式成立；交付后 Archive 与 Partnership 历史一致；关键流程具备端到端验证。

## 6. 当前已确认规则与实现边界

以下内容是集成约束，不是新决策：

- 多项目并行且不设固定项目数量上限；不新增独立管理负荷。
- 核心员工严格单项目归属；不允许同周支援、借调或拆分工时。
- 外包按具体工作项签约；供应商产能按公司范围共享。
- Offer 槽位现行 M0 为初始 4、上限 10，但 #59 2026-11-27 最新归档已改为固定 4（3 循环＋1 外援）；槽位上限与刷新语义待 #53 收口，暂不得按 cap10 实现。定向锁单为终身一次，锁定覆盖 W/W+1、W+2 周初失效，到期定金不退；有效锁定期内开工按已付定金抵扣对应应付款，不得重复计支出。具体状态与流水以 M0 §14.13 及已合入的 Market 契约为准。
- 公司只有一个真实现金池；项目账只做归因。
- 委员会随单部作品成立与关闭；委员会成员是渠道/IP 伙伴，不设置纯财务出资方。
- 委员会商业分配采用直接 Pro-rata：玩家按投资比例取得，其他成员合计取得剩余份额；不采用本金优先返还。
- 不恢复危机周、融资自救、负现金欠付或危机命令白名单。
- 不把特殊商业机会、复杂委员会政治、供应商内部员工管理或整集外包之外的扩展，未经规则确认就塞入 M3/M4 核心出口。

## 9. 最小集成证据

不为追求覆盖率机械增加测试。M3/M4 只保留能够证明关键跨模块约束的少量端到端场景：

1. 两个项目竞争同一核心员工，结果唯一且遍历顺序无关。
2. 两个项目竞争同一供应商产能，不能超卖；交付/失败后释放正确。
3. 两个项目分别立项，其中一个交付/中止不影响另一个项目。
4. 委员会项目交付：投资、制作费、制作成本、BD、非 BD 分配和 Archive 对账闭合。
5. 承制项目交付：BD 归制作公司，不产生委员会非 BD 分配。
6. 同一组输入与 seed 在不同项目遍历顺序下得到一致的结算结果。

仅对本次修改直接涉及的模块运行测试；不要求无差别全仓库测试、压力测试重复跑或机械覆盖所有字段组合。520 周长跑属于 M3 里程碑本身的独立压力验收，不与每个小 PR 的测试要求混为一谈。
