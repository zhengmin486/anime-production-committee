# 模块依赖与并行开发矩阵

> 状态：v0.2，依赖关系重构稿，待 zm 最终审定
> 日期：2026-11-24
> 用途：将 M0–M7 路线拆解为模块责任、接口依赖、数据引用、流程编排和阶段验收条件。
> 权威关系：玩法决策以 DECISION_LOG 为准；状态、领域边界与流程契约以 DOMAIN_ARCHITECTURE 和 M0_CONTRACT_FREEZE 为准；阶段出口以 DEVELOPMENT_ROADMAP 为准。本文件只负责将上位文档转成协作关系，不覆盖上位文档。

## 1. 管理原则

1. **里程碑是整体能力验收，不是全员同步开发批次。** 成员不因其他成员尚未完成当前里程碑而停止独立工作。
2. **跨模块依赖由 zm 提前规划。** zm 维护跨模块依赖、接口交付要求、开发顺序、冲突处理和集成节点；模块负责人自主处理模块内部技术设计与实现。
3. **依赖按具体交付物判断，不按模块名称判断。** “依赖 Staff”必须进一步说明依赖员工状态结构、人员分配结果、工资交易还是完整员工生命周期。
4. **区分四种关系：**
   - 代码/接口依赖：一个模块是否需要调用另一个模块的公开接口。
   - 数据引用：状态中是否保存另一个领域的 ID；ID 引用不等于直接依赖其内部实现。
   - 流程编排：由 Application 在一个用例或周结算中协调多个领域。
   - 阶段前置：某个里程碑验收是否必须具备某项能力。
5. **领域不直接读写彼此字段。** 跨领域读取由 Application 组装不可变快照；领域命令接收明确输入并返回新状态、交易列表和领域事件。遵守 DOMAIN_ARCHITECTURE §8。
6. **Finance 是资金权威，但不依赖其他领域。** 其他领域/用例向 Finance 提交已计算的交易；Finance 不反向读取 Company、Project 或其他领域。
7. **Rules Kernel 无状态。** 不拥有业务状态，不依赖领域，不读 IO、系统时间或随机设备；由 Application 传入输入并调用。
8. **准备、独立实现和正式集成分开管理。** 上游接口未稳定时，可做领域设计、纯逻辑、测试、Fixture、内容、Mock 和适配准备；不得假定未冻结接口已存在。
9. **冻结契约优先于进度。** M0 已冻结的状态结构、命令边界、错误码、结算时序和核心玩法规则不得因实现便利而漂移。变更遵循 M0 契约 §13。
10. **局部阻塞不扩大为全模块阻塞。** 只暂停确实依赖未满足交付物的子项，其他独立工作继续。

## 2. 依赖状态与工作准入

| 状态 | 判定 | 可开展工作 | 不代表什么 |
|---|---|---|---|
| 已冻结 | 契约/Schema/接口已明确并纳入权威文档 | 按契约实现、编写契约测试 | 不代表上游已有可运行代码 |
| 稳定可用 | 上游实现已存在，测试和行为可依赖 | 正式接入、联调 | 不代表所有后续功能均已完成 |
| 草案 | 设计方向明确但细节仍可能调整 | 独立逻辑、测试设计、适配准备 | 不得把草案当成冻结接口 |
| Mock | 以模拟数据或替代实现提供协作输入 | 前端原型、读模型可读性验证、适配开发 | 不得宣称真实 API 已接通 |
| 阻塞 | 某项必要交付物缺失，且无安全替代方案 | 处理不受影响的工作；列明阻塞项 | 不得把整个模块无差别停工 |

每条实际依赖都应记录：**提供方、交付物、使用方式、当前状态、开工条件、正式集成条件**。状态针对交付物，不针对模块笼统打标签。

### 3.1 Rules Kernel 的边界

Production 不再是独立领域或有状态模块。原矩阵中的 Production 行改为 Rules Kernel 下的 production 规则能力。Allocation 同理，是规则内核能力，不是独立领域。

- Project 保存制作状态；Kernel 只计算，不保存工作进度。
- Staff 保存员工状态与项目归属；Application 组装人员输入，Kernel 计算分配结果。
- 随机由坐标式无状态规则提供；不得调用系统随机设备。
- 领域状态的最终写入由对应领域命令/周结算提交完成。

### 3.2 Finance 的边界

- Company 是全局经营主体；Finance 是唯一现金余额与流水的写入权威。
- 其他领域不得直接修改余额，也不得要求 Finance 反向读取自己的内部字段。
- Application 汇总交易请求并协调预检、记账和原子提交。
- 项目账仅用于财务归因；全公司共用唯一现金池。

## 5. M1 最小依赖切片

M1 目标是能可靠运行一周，不是提前完成所有领域。为了避免“完整 Staff/Finance 尚未完成导致 M1 无法运行”，明确以下最小切片：

| 能力 | M1 必须有 | M1 不要求 |
|---|---|---|
| Company | v4 状态根、周数/经营状态、状态校验 | 完整声望成长与长期经营 |
| Project | works[] 多项目状态形状、空项目隔离所需 ID/基础字段 | 完整公共制作、12 集、六阶段和交付 |
| Staff | 可供结算使用的最小人员输入/Fixture；人员归属字段与一人一周约束的最小验证 | 招聘、解雇、成长、临时员工等完整生命周期 |
| Finance | 现金余额、最小流水/交易类型、正常周强制费用预检和记账 | 完整融资、偿付状态机、危机自救 |
| Rules Kernel | M1 周结算所需的纯规则、坐标随机、哈希 | 所有后续商业/产业/竞争公式 |
| Application | 正常周结算的快照、阶段编排、工作副本、原子提交 | 完整危机周、所有命令和终局流程 |
| Event / Vendor / Market / Partnership / Archive | 契约可预留，独立设计可推进 | 不作为 M1 正常周切片的完整实现前置 |

M1 仍须满足 Roadmap/#38 的正式出口：一周结算与独立手算对照一致；seed/state_hash 可复现；两个空项目并存且状态隔离；遍历顺序无关；失败原子性有测试和运行证据。最小 Fixture 不能冒充完整领域实现。

## 6. 阶段依赖与并行边界

### M1：内核与状态骨架

**必须集成：** Company/v4 状态根、Application 最小周结算、Project works[] 最小形状、Staff 最小人员输入、Finance 最小资金预检/记账、Rules Kernel 核心切片。

**可以并行准备：**
- Sqks183：Staff、Finance、Vendor、Market、Partnership 的领域设计、数据模型、Fixture、对账样例；其中 Staff/Finance 的 M1 最小接口优先与 zm 对齐。
- pyxz0：Event 领域设计、旧事件审查、事件规则与测试场景；不需要等待 M1 完成。
- Muchbv：员工、企划、供应商、事件等内容蓝图和内容数据；Schema 未冻结的部分先保持内容草案。
- impossable-6：静态信息架构、经营界面、Mock 数据和回执可读性验证；不接真实 API。
- zm：M1 状态、核心规则、Application 周结算、跨模块接口与集成。

### M2：单项目全链路

- Project 完整制作结构、公共制作、12 集六阶段、工作项依赖和交付进入正式集成。
- Staff 提供单项目制作所需人员能力、分配、磨合和人员结算能力。
- Finance 提供完整项目相关费用、交付收入和财务归因。
- Archive 提供最小交付履历 append。
- Event 完成触发、待处理、选项、效果和恢复的最小闭环。
- **M2 Event 最小闭环不得以 Vendor 已完成为前提。** M2 先实现不依赖外包目录的事件效果；依赖供应商目录、专业匹配、容量、报价的应急外包事件效果延后至 M3 Vendor 稳定后接入。

### M2.5：资金危机

- Finance 提供危机状态、融资/偿付等资金规则。
- Application 负责正常预检失败后的独立危机结算、动作守卫、原子提交和恢复/破产流程。
- 验收包括预检失败不产生正常周部分状态、危机期间固定成本/周数规则、融资或削减承诺/交付回款路径，以及恢复或破产。

### M3：多项目经营

- Project 多项目状态与生命周期能够并存。
- Staff 多项目人员竞争、一人一周只归属一个项目、结果顺序无关。
- Market 提供企划槽和项目来源。
- Vendor 提供供应商目录、容量、专业匹配、外包合同与交付。
- 这些能力按具体接口集成，不要求所有模块同一时间完成。

### M4 及以后

- Partnership：委员会、投资、渠道、合作关系和分账。
- M5：成长、声望、系列与长期积累；Archive 扩展。
- M6：完整 UI、读模型和 API 接入，移除旧 V3 路径。
- M7：平衡、长跑、可玩性与最终验收。

## 7. 开工、集成与升级机制

### 7.1 模块负责人可自主开工

满足以下条件即可开始相应工作，不需要逐项向 zm 申请：
- 已有冻结契约：按契约实现。
- 只有草案：可以做独立逻辑、设计、测试、Fixture 和适配准备；不得擅自把草案升级成共享契约。
- 使用 Mock：可以验证界面、读模型和交互可读性；必须明确标记 Mock。
- 上游缺失：拆出不依赖该交付物的工作，具体记录被阻塞的子项。

### 7.2 正式集成的最低交付

模块准备接入时，至少提供：
1. 对外接口/状态/Schema 说明，明确输入、输出、错误与写入所有权。
2. 对应测试和 Fixture；涉及数值规则时提供手算或可复核样例。
3. 对冻结契约的符合性说明；如需变更，先按变更流程提出。
4. 运行证据、已知限制和未完成项。
5. 明确哪些是正式实现、哪些仍是 Mock 或临时适配。

### 7.3 zm 介入条件

以下情况由 zm 负责协调或裁决：
- 新增跨模块依赖或依赖方向与架构冲突。
- 两个模块对同一状态字段、命令、错误码或结算时序有不同理解。
- 影响里程碑出口、团队顺序或多人并行的优先级冲突。
- 提议修改 M0 冻结契约或已确认玩法。
- 集成失败涉及多个领域，无法由单一模块负责人局部解决。

模块内部实现细节由模块负责人自主决定，不因矩阵存在而增加逐项审批。
