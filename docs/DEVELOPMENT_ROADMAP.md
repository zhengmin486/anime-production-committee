# 开发路线与里程碑（M0–M7）

> 状态：**已确认路线**（2026-11-24）
> 适用范围：v4 重构、运行时实现、前端接入与完整游戏验收。
> 权威关系：玩法规则以 [DECISION_LOG.md](DECISION_LOG.md) 为准；领域与状态契约以 [DOMAIN_ARCHITECTURE.md](DOMAIN_ARCHITECTURE.md) 和 [M0_CONTRACT_FREEZE.md](M0_CONTRACT_FREEZE.md) 为准；本文只定义阶段目标、依赖与出口标准。
> 阶段编号是工程能力里程碑，不是团队任务编号，也不是全体成员必须同步切换的开发批次。成员按模块和依赖独立推进；满足前置条件的模块可以提前进入后续阶段的实际实现，但不得绕过前置契约、把准备工作计为阶段完成。

> **开放式增量开发说明：** 本路线中的“未来更新候选”与“首版范围”用于标注当前最低交付目标、优先级和工作量边界，不构成对提前实现的禁止。成员若在不违反已确认决策、不破坏主框架和跨模块契约的前提下提前完成候选能力，且通过相应工程验收，默认接纳；但不得因此跳过依赖或替代阶段出口验收。详见[开放式增量开发与提前实现原则](OPEN_INCREMENTAL_DEVELOPMENT_POLICY.md)。

## 总体原则

1. **阶段成果可演进，禁止无依据重构。** M0/M1 及后续阶段的契约、数据结构、模块和测试是可持续修补的工程基线，不是一次性交付后不可触碰的遗产。缺陷修复、遗漏补齐和经批准的规则演进优先采用最小增量修改；不得因进入新阶段或个人偏好推翻已有成果。具体变更分级、审批与验收见 [工程变更治理](ENGINEERING_CHANGE_GOVERNANCE.md)。
2. **按可玩的能力验收，而不是按模块数量验收。** 每个阶段结束时，游戏必须获得一项可验证的新能力。
3. **M1 从第一天采用多项目状态形状。** M1 的“单项目”仅指纵向切片的验收范围，不得实现成单项目架构。
4. **基础设施随首次需要它的阶段落地。** 事件、存档、状态哈希、Archive、UI 可读性不得全部推迟到最后。
5. **阶段可以并行推进，里程碑统一验收。** 例如 M1 实现时可准备 M2 内容；某模块满足接口和数据依赖后，也可提前开始 M2 实际实现，不必等待所有成员完成 M1。M2 实现时可继续设计或实现已具备前置条件的 M3 模块。提前开发不代表整体里程碑完成，也不能绕过依赖和契约。
6. **个人进度不被全员进度锁定。** 成员完成当前分配或遇到可独立推进的后续工作时，可以转入后续阶段任务；不得仅因其他成员尚未完成当前里程碑而要求其停工。跨模块接口尚未稳定时，可先完成隔离的领域逻辑、测试、fixture、适配准备，不得私自猜测或改写共享契约。
7. **出口标准必须有可复现证据。** 代码、自动化测试、模拟记录、浏览器验收和人工试玩结果应区分记录。
8. **里程碑完成不等于产品发布。** M7 才是整体平衡与发布准备验收。

## 未来更新候选（不属于 M0–M7 首版范围）

限时资金危机周与经营自救机制可在首版完整可玩、520 周模拟与实际试玩后重新评估。当前路线只交付直接破产失败路径；未来候选不得成为 M2.5 的隐含前置或验收项。

## 阶段边界与防止重复劳动

### M1 与 M2
- M1 只证明 v4 状态和规则内核能安全推进一周，不承诺完整作品生产。
- M2 才负责把单部作品从立项跑到交付。
- M1 的数据结构、周结算编排必须从一开始支持 `works[]`，但 M1 出口只要求两个空项目并存与隔离。

### M2 与 M3
- M2 可使用固定初始项目/员工/供应商 fixture 完成单项目纵向切片。
- M3 必须补上正常玩法可获得的项目来源（企划槽）和基础供应商目录/外包能力；不得只用手工夹具证明多项目经营成立。

### M2 与 M5
- M2 Archive 只记录交付所必需的作品事实、结果、质量、财务归因及必要参与方快照，采用只追加语义。
- M5 才扩展系列、声望沉淀、成长、排名与长期商业影响。不得把 M2 必需的交付记录推迟到 M5。

### M6 与 UI
- UI 不是最后阶段的纯接线任务。#39 的 Mock 原型现在继续；M2 结束后以真实读模型做只读静态原型验证，重点检查周回执、174 个工作项的组织与信息层级。
- M6 才完成完整交互、命令接入和旧运行时切换。

## 当前阶段判定（2026-11-26）

**M0、M1 已完成并验收；当前处于 M2 单项目全链路实现与验收阶段。M2.5 保留为独立的财务失败路径里程碑。**

- M0：架构 v1.4、状态/命令契约、蓝图规范与校验证据已随 PR #40 合入 main。
- M1：v4 状态骨架、纯规则内核、坐标式随机、正常周结算最小切片与 `state_hash` 已随 PR #66 合入；PR #111 补齐员工 `fatigue`、`morale` 必填校验并合入。M1 出口测试及官方 Emscripten CI 均已通过，详见 [M1 运行时切片](M1_RUNTIME_SLICE.md) 与 [当前进度](PROGRESS.md)。
- M1 验收仅覆盖路线定义的“能跑一周”能力；交付、事件、Archive、完整存档 round-trip、破产终局和前端切换仍按后续阶段交付，不因 M1 完成而提前视为完成。
- PR #95 已合入 M2 主要纵向能力，但 M2 尚未正式验收；Issue #53 负责基于当前 main 重新执行端到端契约审计。
- #51 的唯一现金权威与三层金额语义、#52 的多项目编排和状态隔离、#49 的 SaveRecord 目标信封已写入工程契约；其中 v4 存储层与完整存读档验收仍未交付。
