# 前端同学协作指导手册

> 版本：v1.0
> 日期：2026-11-25
> 适用对象：负责《动画制作委员会》前端设计与实现的成员
> 本文用途：帮助前端成员快速理解项目、明确当前任务、知道哪些可以自主决定、哪些不能自行改变。
> 权威关系：产品与场景方向以 [前端方向与信息架构](FRONTEND_DIRECTION_DRAFT_2026-11-24.md) 为准；玩法规则以 `DECISION_LOG.md` 为准；状态、命令和错误码以 `DOMAIN_ARCHITECTURE.md`、`M0_CONTRACT_FREEZE.md` 为准；阶段依赖以 `DEVELOPMENT_ROADMAP.md` 为准。本文是协作说明，不取代上述文档。

---

## 1. 我们在做什么

《动画制作委员会》是一款动画公司经营模拟游戏。

玩家经营一家动画制作公司，通过招聘员工、承接企划、组织动画制作、建立产业合作、发行作品和经营财务，让公司逐步发展。

前端不是传统管理后台，也不只是把数据放进表格。它要让玩家直观感受到：**自己正在经营一家动画公司，能看见公司、员工和作品的状态，并能理解当前应该做什么。**

## 2. 你负责什么

你负责把游戏规则和数据转化为清晰、可操作、有辨识度的游戏界面，主要包括：

- 前端信息架构与页面组织；
- 四个场景的视觉表现和交互；
- 全局状态栏、场景导航、事务中心与周推进入口；
- 员工、项目、事件、财务等信息的展示；
- Mock 数据下的界面验证、交互测试和体验优化；
- 后续与真实读模型、命令接口的接入。

你可以自主决定组件拆分、目录组织、局部布局、交互细节和实现方式；但不能为了实现方便而改变游戏规则或数据契约。

## 3. 游戏界面由什么组成

界面固定为四个场景，导航也只有四项：

| 场景 | 玩家来这里做什么 | 表现方式 |
| --- | --- | --- |
| 办公室 | 看公司、员工、设施，进行人员管理 | **唯一完整主地图**，能看到员工与办公空间 |
| 制作现场 | 查看作品、单集、制作阶段和工作项进度 | 制作工作区构图 + 分层信息面板 |
| 会议室 | 处理重要议题、合作与委员会决策 | 会议桌场景构图 + 决策面板 |
| 发行与市场 | 查看企划机会、作品发行、市场反馈、财务结算和履历 | 作品展示构图 + 市场与结算面板 |

注意：

- 四个场景不是四套独立游戏系统，而是同一家公司状态的不同展示入口。
- 只有办公室需要完整地图；其他场景不需要做成可自由行走的大地图。
- 市场反馈与作品结算在同一个场景中。
- 会议室在产业关系功能开放前仍保留入口，清楚标注尚未开放，不要做成空白页面或假按钮。
- 切换场景不推进周数、不触发结算、不重置玩家当前选择。

## 4. 视觉方向

已经确认的方向是：**像素场景 + 现代信息面板**。

- 场景、人物、设施、场景图标使用像素风，整体偏温暖的动画工作室氛围。
- 数字、正文、表格、表单、回执使用现代无衬线排版，优先保证清晰和信息密度。
- 不要把整套 UI 做成像素 HUD，也不要退回纯后台表格。
- 不要把办公室背景仅仅当作页面壁纸；员工、工位和设施应成为场景的一部分。
- 视觉细节可以自主探索，但不要另起一套与既定方向冲突的风格。

## 5. 当前应该先做什么

当前前端按 F0–F4 推进。眼下优先完成 F1 的分批纵切片，不需要等待整个游戏内核全部完成。

| 顺序 | 当前任务 | 交付目标 |
| --- | --- | --- |
| F0 | 方向与信息架构 | 理解本文及方向文档，形成四场景低保真方案 |
| **F1a** | **办公室纵切片** | 全局壳、办公室主地图、员工/设施面板，能用 Mock 数据演示 |
| F1b | 制作现场 | 作品、单集、六阶段分层展示，工作项默认折叠 |
| F1c | 会议室与发行市场 | 两个专用场景构图、结算区、经营状态差异 |
| F2 | 真实读模型只读验证 | 用真实读模型检查字段映射和信息组织 |
| F3 | 完整交互接入 | 接入命令、事件、周推进和存档 |
| F4 | 体验验收 | 检查操作负担、信息可读性和长局体验 |

**每批完成后都要先交付评审，再进入下一批。** 不要把三个场景全部做完才第一次展示。

F1 阶段使用 Mock fixture，不接真实 API。页面应明确标注 Mock，避免让人误以为功能已经接通。

## 6. 必须遵守的工程边界

### 6.1 前端不负责制定或复算规则

前端只负责展示核心提供的数据、提交合法命令、解释执行结果。

禁止：

- 自己计算质量、风险、可交付状态、门槛是否达标等派生结果；
- 自己推算现金、声望、周数或项目结算；
- 自己增加命令、错误码、状态字段或规则；
- 因为某个读模型暂时没有字段，就在前端复制一套业务状态或算法。

如果缺少展示所需的数据，先记录字段缺口并反馈负责人，不要私自造字段。

### 6.2 游戏状态与界面状态分开

游戏状态由核心持有，前端只读取其投影。

可以放在 UI 状态中的内容：

- 当前选中的场景；
- 当前选中的员工或作品；
- 展开的单集、面板开合；
- 筛选、排序、折叠状态；
- 场景滚动位置和动画状态。

不能把现金、声望、周数、员工归属、项目进度等游戏事实复制成前端自己的权威状态。

### 6.3 不要破坏现有 v3

v4 前端按独立入口/分支推进。不要为了做 v4 而直接删除或破坏现有 v3 页面与测试。旧运行路径何时切换，由整体 M6 接入阶段处理。

### 6.4 不做未确认的玩法

不要自行增加会议小游戏、好感度、拖拽跨项目支援、独立现金账户、自由装修等玩法。可以提出设计建议，但先讨论确认，再实现。

## 7. 制作现场最容易做错的地方

制作现场不是一张工作项清单。必须按层级组织：

1. **作品层**：先让玩家看清有哪些在制作品、各自进度和风险。
2. **单集层**：每部作品的单集以网格呈现。
3. **阶段层**：每一集内部有固定六阶段，不能误画成整部作品共用一条六阶段流水线。
4. **工作项层**：查看具体工作项、依赖和参与人；默认折叠，玩家主动点开才展示。

另外：

- 公共制作与单集制作要分开呈现。
- 工作项状态由核心派生，前端只展示结果。
- 员工同一周只能归属一个项目，不得提供跨项目借调、拆分工时或拖拽支援的入口。
- 不要在首屏铺开大量工作项；一部作品可能有上百个工作项。

## 8. 经营状态必须有区别

界面不能只靠按钮禁用表达状态。至少要让玩家看懂当前处于哪种经营窗口，以及为什么某些操作不能做。

重点覆盖：

- 正常经营；
- 有待处理事件；
- 资金危机；
- 公司关闭中。

特别注意：**资金危机期间仍允许推进周数**，但只能执行契约规定的危机白名单动作；事件待处理时则必须先处理事件，不能推进下一周。具体操作权限以 M0 契约为准，不要凭直觉实现。

## 9. 每次提交应该交付什么

每个可评审批次至少提供：

1. 本次完成了什么，哪些内容还只是 Mock；
2. 可运行的启动方式；
3. 关键页面截图或录屏；
4. 修改文件与主要实现说明；
5. 测试命令及结果；
6. 已知问题、字段缺口和需要负责人决策的事项。

PR 描述建议按以下格式：

```text
## 本次目标
## 已完成
## Mock / 未接通部分
## 关键截图
## 测试与结果
## 已知问题
## 需要确认的事项
```

提交应保持范围清晰。不要把无关重构、全局格式化或其他模块改动夹带进一个前端 PR。

## 10. 遇到问题时怎么处理

| 遇到的情况 | 正确做法 |
| --- | --- |
| 规则或交互含义不清楚 | 先查权威决策文档；仍不清楚就提问，不自行猜规则 |
| 读模型缺少字段 | 写明场景、需要字段、用途和缺失影响，交由负责人协调 |
| 觉得现有架构不方便 | 先提出局部方案与影响，不直接推翻共享架构 |
| 发现已有功能有缺陷 | 优先做最小修补，不因进入新阶段而整体重构 |
| 设计方向有更好的方案 | 给出对比、收益和代价，确认后再改变既定方向 |
| 当前任务被依赖阻塞 | 说明阻塞点，转做不依赖该接口的布局、Mock 或测试准备 |

协作以异步推进为主。遇到阻塞时尽早说明，不必等到整批任务结束才反馈。

## 11. 完成标准

一个前端批次不是“页面写出来了”就算完成。至少要满足：

- 玩家能看懂当前场景的用途；
- 重要信息有清晰层级，不是所有内容平铺；
- 展示数据来源明确，Mock 与真实数据不混淆；
- 关键操作有明确入口、状态和反馈；
- 不违反游戏规则与 M0 契约；
- 在目标屏幕尺寸下可用，键盘焦点和基本可访问性正常；
- 有可复现的运行和测试说明，能够让其他成员独立评审。

## 给前端同学的一句话

**你的工作不是给经营数据做一个后台，而是把一款动画公司经营模拟游戏做成玩家愿意进入、看得懂、操作得明白的游戏界面。** 先把办公室做出空间感和经营感，再逐步扩展制作、会议和发行场景；规则和数据契约由项目组统一维护。
