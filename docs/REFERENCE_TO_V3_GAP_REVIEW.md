## 一、结论先行

两轮调研提出的主要工程建议，大部分已经在 V3 契约或 M1 核心中有对应设计。当前真正的差距不是「缺少一套模拟框架」，而是：

1. **M1 的周推进、阶段快照、终局和确定性测试已有基础实现。** 这些不应重复设计。
2. **M2 的委员会、市场、员工/供应商、事件等契约扩展已经进入 V3，但不能因为类型存在就视为行为完成。** 应继续按 #6/#7/#8/#11 的模块分工实现。
3. **当前缺少逐笔资金流水、声望变化历史、作品重大事件履历等可追溯信息。** 其中部分已经在 V1_GAP_REVIEW 的跨系统缺口中登记；不应借参考项目直接自行加字段，按契约裁定流程处理。
4. **固定种子回归已有 M1 测试，但尚无成体系的经营场景批量模拟和参数版本差异报告。** 这属于后续平衡与验证工具，不是当前 M2 开发的前置阻塞。
5. **文档状态存在一处明确漂移：** `docs/PROGRESS.md` 仍写前端 v3 接入待完成，但议题 #5 已于 2026-11-22 08:25 关闭，评论记录了前端切换 v3、浏览器 8/8、单元 202/202、WASM 9/9、native 47/47。应更新进度文档，而不是重新打开已完成任务。

## 三、当前实现证据与限制

### 1. M1 已有实现

从当前 `game_core.cpp` 可直接确认：

- `initialize_game` 建立 v3 状态、四个市场企划、公司、员工和预览。
- `start_project` 当前仅允许 contract；committee 明确返回 MODE_NOT_ALLOWED。
- `apply_decision` 已处理阶段配置锁定、主动结束、返回市场等 M1 行为；招聘/外包等仍拒绝或未开放。
- `advance_week` 已实现空闲周与制作周费用预检、一次性扣款、阶段工作量/质量、经验、疲劳、士气、阶段完成、截止交付和 520 周终局。
- `resolve_event` 明确返回当前没有待处理事件；事件库尚未接入。
- `calculate_result` 已实现承制项目结算、违约/中断扣罚、声望变化、作品历史追加和公司总结；委员会渠道分账尚未实现。

核心测试已覆盖初始化、模式拒绝、阶段配置锁、空闲周、黄金制作回执、阶段切换、方针差异、质量传递、截止/破产/520 周终局、结算只执行一次、主动结束、确定性重放和状态校验。

### 2. 前端 v3 状态

议题 [#5](https://github.com/zhengmin486/anime-production-committee/issues/5) 已关闭。负责人 2026-11-22 08:25 的验收评论记录：

- 前端六个核心导出已切换到 v3；
- 存档只写 v3，旧档拒绝且不覆盖；
- store 使用 busy 锁，成功后整体采用核心状态；
- 周制制作台、五阶段配置/锁定、回执、项目结算、经营总结和作品履历已接入；
- 真实 WASM 浏览器 8/8、单元 202/202、WASM 9/9、native 47/47、typecheck 与 dist 验收通过。

因此，`PROGRESS.md` 中「前端主流程仍需完成 v3 接入」与当前议题状态不一致。建议在下一次进度维护中修正该句，并明确 M1 前端已完成、M2 行为未完成。

### 3. 文档中的目标契约，不等于当前代码能力

下列内容在 `gameV3.ts` / `DATA_MODEL.md` / `API.md` 已有形状或规则，但 M1 核心尚未实现：

- committee_members、committee、channel_potentials、channel_breakdown；

- buy_tv_service；
- 供应商、临时员工、外包与完整成长；

- 作品 rating、历史成绩解锁、声望变化历史、重大事件履历和特殊评价。

这不是契约设计失败，而是 M1 → M2/M3 的正常分阶段交付。实现时要继续遵守可选字段兼容纪律：字段尚未由核心统一输出前，旧 M1 v3 存档仍须合法。

3. 不要将 M2 字段已经进入 TypeScript 类型，描述成 C++ 已实现。

### P0：沿既有模块分工完成 M2

- #6 企划系统：市场生成、来源/规模、委员会候选与固定阵容、自定原创/员工提案槽位、商业机会门槛等。
- #7 员工系统：招聘抽卡、保底、核心/临时人员、供应商和外包。

### P1：在现有记账模型上补足可解释性

- 先明确玩家界面和测试究竟需要看到哪些资金变化来源。
- 若 Finance 分类 + WeekReport + StageResult + WorkRecord 已足够，不必新增逐笔账本。
- 若确实需要逐笔追踪，再由负责人定义最小交易记录形状，明确公司账/项目账双视图不能重复扣现金，并覆盖 development、distribution、临时员工、外包、事件、延期和扣罚。
- 声望变化历史、作品重大事件履历等既有缺口按 V1_GAP_REVIEW §11 逐项裁定；不让参考仓库替代规则决策。

### P1：把 numeric-kit 的思想转为轻量平衡工具

等 M2 主要行为和正式参数进入 `game_rules.hpp` 后，再建立：

1. 固定初始资金、员工、seed 和决策序列的代表性经营场景；
2. 输出经营周期、完成作品数、破产周、现金余额、成本分类、作品质量/档次、声望和员工状态；
3. 参数变更前后运行同一场景；
4. 保存基准结果并生成指标差异；
5. 将已发现的账务/状态异常固化为自动化测试。

不引入 Excel MCP、Lean 4 或复杂通用经济规则引擎。先用项目现有 C++/WASM 测试与脚本完成最小闭环。

## 五、明确不采纳

- 不增加真实动画软件的场景素材库、评论标注、云盘同步和审核工作流。
- 不引入第二套随机数系统或前端经营公式。
- 不因参考项目有逐笔账本就默认需要完整会计系统；不引入复式记账。
- 不把 AnimeStudioSimulator 的财务/状态实现当成代码范本；只吸收其题材模型的对照价值。
- 不把 numeric-kit 的占位模块当成成熟可用的平衡工具。
- 不改变五阶段、520 周、四个市场企划、单项目制作和已确认的收益/终局规则。

## 六、最终判断

两轮调研已经完成其主要任务：验证现有方向、暴露外部实现反例、补充工程质量检查方法。当前不需要继续扩充参考仓库，也不需要另起一套模拟架构。

下一阶段重点应从「参考项目研究」切换为「按现有分工完成 M2 行为 + 由负责人做跨系统契约与账务集成 + M2 后开展固定场景平衡」。这与现有 V3 路线一致，没有新增玩法要求。
