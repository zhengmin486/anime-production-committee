# 2026-11 重构复盘与协作约定

> 日期：2026-11-25  
> 性质：项目复盘与后续协作规范，不新增玩法规则，不替代 DECISION_LOG、领域架构或 M0 契约。  
> 复盘范围：2026-11-24 至 2026-11-25 的架构切换、M1 迁移、事件系统返工、旧 PR 清理与游戏愿景重建。

## 1. 结论

这次不是整个项目推倒重来，而是一次代价不小、但有必要的架构纠偏。真正无法直接沿用的部分，主要集中在旧事件系统的运行时假设及其周边设计；M0 契约、M1 的大部分工作、已确认玩法、研究资料和多项独立成果都得到了保留、迁移或归档。

本次最重要的教训是：

**先统一产品规则和工程契约，再并行实现；先验证跨模块不变式，再扩大功能；架构切换时迁移有价值的成果，不要让旧分支继续定义新系统。**

问题不在于团队使用了多个智能体，也不在于某个成员单独做错了事。根因是不同工作曾基于不同时间点的规则、架构和分支状态推进，局部任务各自合理，合在一起却不再满足同一套产品约束。

## 2. 本次重构中暴露的问题

### 2.1 产品规则、架构文档和实现没有始终使用同一基线

多项目并行已经是明确的产品方向，但旧事件实现仍沿用全局单事件槽：一周只有一个待处理事件，其余候选可能被丢弃。另有暂存事件后仍可推进周数的旧方案，与“未处理事件会阻塞周推进”的当前规则冲突。

这不是局部代码瑕疵，而是底层模型没有表达当前玩法。继续在旧模型上补丁，只会把冲突扩散到事件触发、待处理状态、周结算和前端表现。

**教训：** 任何跨领域功能动工前，都要把相关产品规则翻译成可验证的不变式。不能只确认“事件系统能运行”，还要确认它在多项目、同周多事件、事件未处理、项目结束等边界下仍符合游戏规则。

### 2.2 并行任务的局部正确，不代表系统整体正确

不同分支、PR 和智能体可能分别完成了事件、运行时、领域设计、经济实验或愿景文档，但它们依赖的规则版本并不总是一致。单个 PR 的代码可以自洽，多个 PR 合并后却可能出现全局单例、状态所有权重复、结算语义不一致等问题。

**教训：** 并行开发的前提不是“把模块分出去”，而是先冻结共同依赖：产品规则、状态所有权、接口契约、事件/结算时机和验收标准。跨模块依赖未明确前，不应让多个智能体各自补全关键规则。

### 2.3 历史分支和过时 PR 延续了旧架构假设

部分旧 PR 已经无法直接合并，但其中仍有可复用的代码、文档、测试或研究结论。若继续在旧分支上叠加工作，会让新架构不断承担兼容旧假设的成本；若直接丢弃，又会损失已经投入的有效成果。

本次处理采用了区分策略：M1 的有效部分迁移到最新架构；旧事件运行时及冲突设计关闭并保留历史记录；旧愿景中仍然成立的产品方向被重新整理进当前愿景，而冲突内容服从现行决策。

**教训：** 关闭 PR 不等于删除成果；保留历史也不等于继续支持旧实现。每次架构切换都要逐项判断：直接合并、迁移后合并、仅归档、关闭作废，不能按 PR 数量或投入时间一刀切。

### 2.4 文档状态和决策来源曾经容易被误读

过去的部分产品方向已经通过讨论明确，但当时未必都登记在统一决策文件中。因此，不能仅因一项设计没有 DEC 编号，就断言它从未得到负责人确认。另一方面，旧提案、研究建议和已实现行为也不能自动升级为正式规则。

**教训：** 判断一项规则是否确认，必须追溯其决策来源和上下文；不能只检查它是否出现在某份登记册里。今后以 DECISION_LOG 为现行规则的权威登记入口，并逐步把仍有效的历史确认补齐；对来源确实不清楚的内容，明确标为待确认，不自行推断。

### 2.5 研究和模拟结论可能因前提变化而失效

模拟器、平衡报告和经济实验只对其输入假设负责。当制作成本、投资分配、渠道结构或现金流规则变化时，旧模拟结论不能直接作为新模型的平衡证据。

**教训：** 每份实验必须记录模型版本、参数配置、规则假设、随机种子和运行方式。规则发生变化后，先判断旧实验哪些仍然有效，再决定复跑；不能只保留结论而丢失前提。

### 2.6 “架构完成”不等于“游戏可玩”

领域边界、状态所有权、事务和契约可以设计得很完整，但这并不自动证明玩家能理解系统、经营过程有趣、操作负担合适。工程闭环只是交付条件之一，不是产品验收的替代品。

**教训：** 架构正确性、规则完整性、可玩性和体验反馈要分别验收。开发必须持续回到 GAME_VISION 所定义的核心体验，避免把项目做成复杂但缺少经营乐趣的管理工具。

## 3. 后续必须遵守的工作约定

### 3.1 统一文档权威与状态标记

后续材料必须明确区分以下两组状态，不能混写：

**产品规则状态**
- **已确认**：负责人已明确决定，设计和实现必须遵守。
- **方向已确认、参数待定**：方向不得被推翻，数值通过模拟、测试或标定确定。
- **待验证**：需要原型、模拟、技术测试或试玩验证，不代表产品方向尚未决定。
- **待裁决**：确实涉及玩家体验、规则或控制权，且负责人尚未作出决定。
- **已废弃/被覆盖**：历史上存在，但已被后续决定替代。

**工程交付状态**
- **提案**：仅描述计划，不代表设计已经成立。
- **已设计**：接口、数据形状和边界已说明，不代表代码已实现。
- **已实现**：代码已提交，不代表验收通过。
- **已验证**：对应测试或人工验收已通过。
- **已集成**：已进入目标分支，并确认与当前基线一致。

文档的权威分工保持如下：
- GAME_VISION：产品定位、核心体验、设计支柱和复杂度边界。
- DECISION_LOG：负责人已确认的具体玩法规则。
- DOMAIN_ARCHITECTURE：领域边界、状态所有权、接口和架构裁定。
- M0_CONTRACT_FREEZE：底层状态、命令、不变式、错误码、结算与存档契约。
- PROGRESS / DEVELOPMENT_ROADMAP：当前开发阶段和里程碑状态。
- 研究、审计、复盘和实验文档：提供证据与历史，不自动成为规则或工程事实。

文件写入、PR 合并、测试通过都不能单独代替负责人确认玩法规则。

### 3.2 新任务必须从当前基线开始

- 所有新分支从最新 main 创建；开始前先 fetch 并记录基线 SHA。
- 不在已经过时的架构分支上继续开发新功能。
- 任务开始前先阅读 GAME_VISION、DECISION_LOG、相关领域架构和 M0 契约；只阅读与任务有关的模块，不要求每个成员重复通读全部仓库。
- 若任务依赖的规则或接口与 main 冲突，先报告冲突，不自行选择旧分支或自行创造新规则。
- 架构切换后，必须明确唯一目标架构；旧运行时可以作为迁移参照，但不得与新运行时长期并列成为两个可选的产品真相。

### 3.3 先列不变式，再写实现

对涉及多个领域、周结算、事件、财务、存档或多项目的功能，任务说明必须包含：

1. 所属产品规则及其来源；
2. 状态由哪个领域唯一持有，其他模块能否写入；
3. 正常路径、失败路径和边界情况；
4. 对多项目、同周并发、重复调用和重试的行为；
5. 对现金、周数、项目状态、历史记录和随机状态的影响；
6. 必须通过的测试与验收标准。

事件系统的已确认边界是一个典型例子：事件按项目独立触发，每个项目每周最多一个，不同项目可以同周触发；未处理事件保留并阻塞周推进。新实现必须直接表达这些规则，不能先实现全局单槽，再用迁移或兼容层补救。

### 3.4 智能体任务必须有共同上下文和明确边界

给智能体的任务说明至少包括：
- 当前产品方向和权威文档；
- 本任务允许修改的文件、模块和接口；
- 明确不允许改变的已确认规则；
- 依赖项及其当前状态；
- 交付物、验收条件和需要运行的定向测试；
- 发现规则冲突、接口缺口或未决问题时的报告方式。

智能体可以自主完成专业范围内的设计和实现，但不能把研究建议改写成已确认规则，不能为了让局部实现通过而改变跨模块语义，也不能擅自扩展任务范围。

### 3.5 PR 合并前执行统一检查

合并前至少检查：

- 是否基于最新 main，是否仍有未解决的冲突；
- 是否符合 GAME_VISION 和 DECISION_LOG；
- 是否符合领域状态所有权与 M0 契约；
- 是否覆盖正常、失败、边界和多项目场景；
- 是否存在静默丢弃数据、重复记账、部分周结算或修改历史事实的路径；
- 是否更新必要文档、测试和进度状态；
- CI 与定向测试是否通过；
- PR 是否包含超出任务范围的改动。

CI 通过是必要条件，不是充分条件。涉及核心玩法或跨领域契约的 PR，还必须进行产品方向和系统行为审查。

### 3.6 架构迁移时先盘点，再处置

架构切换时，对旧分支和 PR 按以下类别处理：

| 处置 | 使用条件 |
|---|---|
| 直接合并 | 与当前规则、架构和接口完全兼容 |
| 迁移后合并 | 有价值，但依赖旧基线；需要在最新 main 上重建或移植 |
| 归档保留 | 研究、实验、历史决策或代码仍有参考价值，但不再进入当前实现 |
| 关闭作废 | 核心假设与当前方向冲突，继续维护只会增加兼容成本 |

关闭前说明原因和可复用部分；迁移后核对文件、测试和行为是否真正进入目标分支。不要把“关闭了多少 PR”当作损失指标，也不要为了挽回沉没成本而兼容已经废弃的模型。

### 3.7 实验结论必须绑定版本和前提

模拟和实验报告要记录：
- 所依据的规则、架构和代码版本；
- 配置文件、关键参数和随机种子；
- 运行命令、样本量和评价指标；
- 结论适用范围及已知限制。

关键规则变化后，旧实验标记为历史结果。只有确认模型假设仍然成立，才能继续引用；否则重新运行并明确比较差异。

## 4. 每个任务启动前的简短检查表

- [ ] 我知道当前唯一有效的产品规则和架构基线。
- [ ] 我确认任务从最新 main 开始，而不是从过时分支续写。
- [ ] 我知道本任务不能改变哪些已确认规则。
- [ ] 我已经列出跨模块不变式和关键边界场景。
- [ ] 我明确了交付文件、测试和验收条件。
- [ ] 我知道遇到规则冲突时应停下来报告，而不是自行补规则。

## 5. 本次复盘后的执行原则

1. **优先保护产品方向，而不是保护旧代码。** 旧实现与已确认玩法冲突时，迁移有价值的成果，不为旧模型增加长期兼容负担。
2. **优先冻结契约，而不是提前铺开并行开发。** 模块可以并行，关键状态和跨模块语义必须先统一。
3. **优先验证完整行为，而不是只验证局部功能。** 尤其关注多项目、周结算、事件、财务和存档之间的组合。
4. **优先保留可追溯证据，而不是只保留结论。** 规则来源、实验前提、PR 处置和迁移记录都应可查。
5. **最终以可玩性验收。** 系统数量、代码规模和文档完整度都不能替代玩家是否能理解、是否需要权衡、是否愿意继续经营。

本文件是后续协作的复盘基线。若未来需要修改这些工程协作约定，应更新本文；若涉及玩法规则，则必须回到 DECISION_LOG 的决策流程，不得借复盘文档改变产品规则。
