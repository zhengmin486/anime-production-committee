## 2. M2 出口标准

依据 [DEVELOPMENT_ROADMAP.md](DEVELOPMENT_ROADMAP.md)，M2 至少满足：

1. 固定 fixture 可正式立项并实例化 12 集、174 个工作项的 `tv_standard` 蓝图。
2. 工作项依赖、阶段锁、最低交付门槛和人员单项目归属在周结算中生效。
3. 主动交付和截止强制交付均停止生产，并只结算一次。
4. 现金、公司流水和项目归因满足统一账本恒等式，不重复扣款或入账。
5. 最小 Archive 保存交付必需事实，不引用结算后已释放的人员实体。
6. 项目事件支持多项目各自触发、任意顺序解决，未处理事件阻塞周推进。
7. v4 手动存档完整保存并恢复状态和随机状态，读档不推进周、不结算、不改变随机结果。
8. 非法命令保持状态、资金、周数和随机状态不变。
9. 交付回执、项目财务流水、Archive 可由测试直接断言；真实前端展示不属于 M2 出口。

## 5. M2 任务拆分

### P0-1：M2 数据字典与契约收敛

- 对应：#53、#38。
- 依赖：无。
- 主要文件：`packages/game-core/include/apc/v4/model.hpp`、`packages/game-core/src/v4/model.cpp`、`packages/game-core/include/apc/v4/runtime.hpp`、M0 契约。
- 交付：
  - M2 必填字段、可空字段和后续里程碑字段清单；
  - 枚举、ID 唯一性、引用完整性和阶段状态不变量；
  - `EventState.pending[]` 的读写规则；
  - `last_participation` 的周级快照语义；
  - 固定 fixture 的合法与非法样例。
- 验收：同一 fixture 通过 C++ 状态校验；缺字段、错类型、悬空引用和重复 ID 均被拒绝；失败不修改状态。

### P0-2：Finance 唯一账本与交易接口

- 对应：#51。
- 依赖：P0-1。
- 主要文件：`model.hpp/.cpp`、`runtime.cpp` 及财务测试。
- 交付：
  - 收入、支出、应收、现金和项目归因的分类；
  - 一次交易只改变一次现金；
  - 流水条目的稳定字段和幂等约束；
  - 立项制作费、周费用、交付回款的统一入口。
- 验收：公司现金、公司流水、项目归因和回执可逐笔对上；重复调用不产生第二笔现金变化。

### P0-3：多项目周结算边界

- 对应：#52。
- 依赖：P0-1、P0-2。
- 主要文件：`runtime.cpp`、`scripts/v4.test.mjs`。
- 交付：
  - 项目顺序无关的结算结果；
  - 事件数组非空守卫；
  - 项目状态、人员归属、Archive 和随机状态的原子更新；
  - 终态项目保留时 Finance、Archive 与事件 `work_id` 引用的完整性规则。
- 验收：交换项目遍历顺序得到相同状态哈希；多个事件并存时不丢失、不覆盖；失败周不产生部分结算。

### P0-4：v4 存档工程契约

- 对应：#49。
- 依赖：P0-1；完整实现依赖 P1 各领域形状稳定。
- 主要文件：`runtime.hpp/.cpp`、`bindings/v4_bindings.cpp`、存档测试。
- 交付：
  - `SaveRecord { version: 4, saved_at, rules_version, state }`；
  - 严格字段校验和损坏处理；
  - v1/v2/v3 拒绝加载；
  - save/load round-trip；
  - 读档后继续推进与未读档路径结果一致。
- 验收：保存不改变游戏状态；读档不推进周、不结算、不消费随机；损坏或不支持版本不破坏当前会话。

### P1-1：固定 fixture 的正式 `start_work`

- 对应：#53 端到端 fixture、#51 财务接口。
- 依赖：P0-1、P0-2。
- 主要文件：`runtime.hpp/.cpp`、`bindings/v4_bindings.cpp`、v4 测试。
- 交付：
  - 固定 offer 校验；
  - 蓝图实例化；
  - 项目、制作费和现金的原子创建；
  - 立项失败回滚。
- 非目标：完整市场刷新、原创提案、委员会和投资比例。
- 验收：成功只创建一个项目和一组正确流水；资金不足、非法 offer、重复 ID 或非法模式时状态和 seed 不变。

### P1-2：交付与最小 Archive

- 依赖：P1-1、P0-2、P0-3。
- 交付：
  - 主动 `deliver_work`；
  - 全部门槛已交付的校验；
  - 截止强制交付；
  - 停止生产、释放人员归属；
  - 最小 Archive 快照；
  - 结算项目在 M2 保留 `delivered` 终态记录，释放人员归属；
  - 结算回执和重复结算防护。
- 验收：同一项目只能结算一次；门槛不足时拒绝且状态不变；截止与主动交付走同一结算不变量；Archive 不依赖已释放人员实体。

### P1-3：事件最小闭环

- 对应：#50、#11。
- 依赖：P0-1、P0-3；效果涉及财务或人员时依赖 P0-2。
- 交付：
  - `pending[]` 状态和校验；
  - 每项目每周最多一个事件；
  - 多事件保留和任意顺序解决；
  - 未处理事件阻塞周推进；
  - 选项效果经 Application 调用 Project、Staff、Finance 正式接口；
  - 解决后恢复合法周推进。
- 验收：同周两个项目各触发一个事件；调换解决顺序不丢事件；非法选项和重复解决保持状态不变；事件费用只记一次。

### P1-4：M2 端到端 fixture 与验收

- 依赖：P1-1、P1-2、P1-3、P0-4。
- 交付：
  - 固定初始公司、员工、offer 和蓝图；
  - 12 集从立项到交付的脚本；
  - 财务对账断言；
  - 事件触发、选择、效果和恢复断言；
  - 存档/读档后结果一致性；
  - 失败命令状态哈希不变断言。
- 验收：M2 出口标准全部可自动断言，并保留固定 seed 的结果。

## 6. 推荐实施顺序

1. 完成 P0-1，先冻结 M2 数据形状，不并行修改共享核心模型。
2. 完成 P0-2 和 P0-3，确保现金与周结算是单一、原子、可审计入口。
3. 实现 P1-1，打通固定立项；再用真实财务流水验证，而不是继续依赖 `instantiate_work` 作为产品入口。
4. 实现 P1-2，打通交付、Archive、终态项目保留和人员归属释放。
5. 修订 #11 和领域架构中的旧单槽描述，再实现 P1-3。
6. 数据形状稳定后完成 P0-4 的运行时保存/读取。
7. 最后用 P1-4 做整链路验收；通过后才进入 M2.5 或扩大 M3 范围。
