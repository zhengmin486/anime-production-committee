# 游戏规则：V3 历史运行规则与现行目标玩法决策

> 当前目标玩法决策以 [DECISION_LOG.md](DECISION_LOG.md) 为准。本文后续 V3 章节保留旧契约、历史参数和既有实现的规则依据；其中“五阶段、单项目、资金不足立即破产”等口径不再代表当前目标玩法。V3 代码与契约仍需在新架构实施时迁移，不能直接将本文历史条目当成新架构的规则。

## 目标玩法决策（2026-11-24）

- 项目级公共制作 + 单集制作两层结构；单集固定六阶段：单集内容设计、分镜与原画、动画制作、美术与视觉制作、摄影与剪辑、声音与最终交付。
- 单集制作按工作项依赖推进；达到最低交付即可解锁下游，前序仍可继续完善，允许并行。
- 核心员工每周严格单项目分配；禁止同周跨项目支援、借调和拆分工时；周结算后可重新分配。
- 多项目并行，不设固定数量上限；首版不引入独立管理负荷数值。
- 已配置计划自动执行，但不自动招聘临时员工、不自动新增外包合同；新花钱承诺由玩家决定。
- 资金不足进入限时资金危机，不立即自动破产、不自动借款；期限内未解决才破产。
- 周结算采用中等随机性，具体参数由模拟验证。

完整决策边界与其他确认事项见 [DECISION_LOG.md](DECISION_LOG.md)。

### 2026-11-25 已确认规则补充

以下规则已正式归档，不再作为待讨论问题：

- 委员会由渠道伙伴/IP 伙伴组成，无纯财务投资方；成员不可退出。六个常规商业窗口、渠道三档开放、电视曝光倍率与 BD/DVD 收入归属见 DECISION_LOG 第 11 节。
- 委员会总投资池为制作费的两倍，制作费占 50%；投资本金一次性投入，制作费与实际成本分账，商业结算按投资比例直接 Pro-rata，不采用本金优先。
- 特殊商业机会独立于常规窗口，接受时锁定义务并立即支付不可退前置费用；结算收入按实际履约结果确认。
- 项目直接制作成本、公司固定成本、承制路线和委员会路线的收益边界按 DECISION_LOG 第 11 节执行；标定目标不构成收益保证。
- 公司声望与合作方好感分离；声望影响机会和人才/曝光，不改变作品制作质量。
- 核心员工不会主动辞职；玩家可随时解雇。项目临时员工随项目交付或中止自动解绑；提前解约细节仍待定。
- 事件按项目独立触发，每项目每周最多一个；多个项目可同周触发。未处理事件保留，玩家决定处理顺序，存在待处理事件时禁止推进周。
- 首版手动存档须完整恢复游戏与随机状态；不兼容版本明确拒绝，不静默丢字段。

以上条目属于现行目标玩法；V3 历史章节仍只描述旧运行时，不得反向覆盖这些规则。

## V3.2 周结算与冲突优先级（历史运行规则；资金不足立即破产已被限时危机决策覆盖）

0. 校验 state、公司仍 running、phase 可推进。当前阶段 ready 或有事件/待交付/待结算时拒绝，不能借等待跳过配置。
1. **强制费用预检先于任何实际制作**：用当前现金检查本周核心工资、运营、阶段直接生产及已确定的其他强制支出。此前已经支付的临时合同/外包/延期不得再收一次。若不足，原现金、周数、进度、经验、疲劳士气、seed 均不变；公司锁定 closing/bankrupt，有项目则 project_ready/company_closed，无项目维持关闭的 idle；回执增量为 0。
2. 资金足够，原子扣本周费用，并按 Costs 分类记入公司账；在制项目同时记入自己的区间账，但**现金只扣一次**。
3. 根据当前配置计算内部工作；推进本阶段临时人员与外包交付，合并有效工作量与批次质量。只推进当前阶段，不跨阶段消费剩余产能。已付费但无有效工作量的人员也不凭时间获得专业经验。
4. 结算本周实际工作对应的专业经验、疲劳、士气；休整者恢复但核心工资照付。临时人员不培养；项目结束的集中展示不能再加一次经验或扣一次疲劳。
5. week 加 1，形成周回执。阶段完成时写 StageResult，非末阶段进入下一阶段 ready。截止按已结算周与 deadline_week 比较；最后一个允许生产周结束后必须交付，不能等下周再罚。
6. 按以下优先级判定并保留结算状态：公司 520 周到期锁 closing/time_limit；作品完成时交付原因 completed；否则达到项目截止为 deadline；否则公司到期截断在制作品为 company_closed。**作品在第520周完成仍记 completed，但公司同时终局，不能接下一部。**
7. 只有公司仍运行、项目未交付、当前阶段仍 active 才选择满足经营条件的事件；不在阶段切换、项目交付或终局后追加弹窗。使用稳定顺序和种子抽取，事件暂停后续推进。
8. idle 周支付工资/运营并恢复状态，未终局则重新生成四企划；不是免费刷新，也不会因真实时间经过自动刷新。关闭后不生成新企划。

议题 #2 的“制作→费用→事件→终局”是建议顺序，本契约增加前置可支付检查并将终局优先于事件，避免没钱仍免费获得工作量、或靠最后一周随机延期规避交付。**同周预计完工但付不起本周费用：先破产，不先发收入，不完成该周。** 有钱付完本周即使现金恰为0，也不提前破产；可完成作品并按交付规则获得合法收入，之后再检查下一笔强制支出。

阶段配置后按周自动执行，不每周清除 overtime；玩家每次仍只推进一周，不提供批量跳周。工程上的内部计算可以用临时副本，但对外必须是一次原子成功或失败。

## V3.3 投资、合同与分类账

- 接约先记录 opening_funds；委员会资格以**拨款前**的公司现金能否支付投资为准，不能用尚未取得的制作预算凑投资。资金不足是可选动作失败，不是破产。
- 接约成功时，委员会模式先扣公司承担的投资，再将合同预算（即制作预算）并入公司现金；两步与新建项目是一个原子动作。承制模式不支付投资，合同预算作为制作资金并入公司现金。其他合作方共同补足委员会项目剩余投资规模，既不进入公司现金，也不是公司收入。
- contract_budget 始终表示制作预算。选择委员会模式时，在 start_project 建立 Project 后生成 total_investment = offer.contract_budget × 2；选择承制模式时不生成 total_investment，不得生成一个无意义的投资规模。委员会投资金额=floor(total_investment×investment_percent/100)。金额使用安全整数，核心采用不会溢出的整数计算。
- 制作预算即合同预算，开工时一次性并入公司现金；公司不另设独立预算钱包。制作过程中的员工、外包等支出持续从公司统一现金池支付，预算资金不足后仍必须由公司现有现金承担；未花完的制作预算自然留在公司，不另行发放“预算结余”。若公司现金不足以支付当周强制制作费用，立即破产结算并判定游戏失败，不贷款、不追加投资。
- 承制项目不参与委员会成员开放的非 BD 渠道分成；BD 为所有企划的基础商业收入渠道。承制与委员会统一按 BD 毛收入的初始 50% 计入公司收入、另 50% 计为 BD 综合成本，不受投资比例影响；比例后续可按产业调查与数值平衡调整，但成本比例必须大于 0。实现时可直接按毛收入×0.5计算公司所得，或先计毛收入再扣除50%成本，结果必须一致，不能重复扣除。委员会项目非 BD 渠道收入按玩家投资比例分配。
- 承制项目可获得委托方额外支付的成功奖励：作品商业表现达到预设目标时触发，奖励不从作品商业收入中划拨；具体目标、奖励金额与计算方式待数值平衡。委员会项目不适用该承制成功奖励。
- 合同预算在开工时全额到账；交付时结算扣罚、BD 收益与符合条件的成功奖励。成功奖励单独记账，不混入渠道商业收入；合同预算不是交付时再次发放的收入。履约收入=contract_received−penalty，成功奖励另计。
- 交付时先计算整个结算的合法分成与扣罚，原子入账。如果净后资金为负，锁 closing/bankrupt，允许终局显示欠付缺口；不创建贷款、追加投资或再接单救活机制。已锁的 bankruptcy 不因之后回款转正而撤销。
- 公司强制关闭时按当前完成度与质量结清在制作品；尚未产出的阶段按0贡献，不假定自动完成。合同扣罚函数、商业表现函数统一复用正常交付参数，不另设终局奖励。未履约扣罚的具体系数仍待定，须覆盖完全未开工、部分完成、全部完成三个边界。
- 凡钱已在先前动作支付，结算只汇总历史，不再次扣款。可选付费事件/招聘/外包/延期金额不够时拒绝动作并保留状态；预付任务的失败结果与退款规则在后续任务中确认，M0 不伪造退款收入。

```text
项目累计成本 = salary + operations + production + temporary + outsourcing + events + extension + penalty
项目利润 = contract_received + commercial_share_received + success_reward_received - investment_paid - 项目累计成本
项目利润 = 结算后公司现金 - opening_funds（项目区间没有其他未归属交易）
公司累计现金变化 = 公司 contract_received + commercial_share_received + success_reward_received - investment_paid - 公司 costs 总和
公司最终现金 = initial_funds + 公司累计现金变化
公司累计现金变化 = 所有项目利润之和 - 项目区间外的工资及运营等成本
```

在制期间核心工资与运营计入该项目区间的成本；空闲期同类成本只进公司账，不事后塞给下一项目。事件若调用供应商，钱归 outsourcing 而非再计 events；独立事件支出才归 events。阶段 costs、任务 fee_paid、历史 finance 是分析/快照，不能相加为第二笔实际支出。

## V3.5 关闭、延期和待定表

- 公司结束是不可逆锁：主动结束不推进周，先清 pending_event；未交付项目转 project_ready、按当前成果结算；没有项目或已结算则直接允许经营总结。company_result 不重复付款。
- 第520周付款检查若先失败，理由 bankrupt、week保持519；成功完成第520周则 time_limit。交付扣罚造成负现金时 bankruptcy 优先于 voluntary/time_limit；无资金缺口则保持原关闭理由。关闭后有回款也不能接新单。
- 已经正常完成/到截止的项目被主动结束时，保留 completed/deadline 的作品交付原因；只有被提前截断的项目用 company_closed。
- 委员会最多延期一次，申请成功必须同时满足未使用、未过截止、现金足够；首版不加入投票或随机审批。固定延长周数、费用和压力增量集中配置；再次超期强制交付。承制任何路径都不能延期，事件不得绕过。

## V3.9 跨系统规则确认补充（2026-11-22）

本节汇总 2026-11-22 在议题 #6、#8、#11 及总体设计讨论中确认、但此前尚未完整进入规则总文档的规则。**本节记录规则口径，不表示对应玩法已经实现。** 具体参数、概率、阈值和内容清单仍交执行阶段细化。

### 1. 公司声望

- 公司声望同时具有数值与等级；初始声望为 **100**，最低为 0，不允许负数，不设数值上限。
- 声望不自然衰减，只由经营行为和项目结果改变；等级按固定数值区间晋升/降级，不采用动态排名。最高等级暂不设数值上限，具体阈值与称号统一设计。
- 声望变化不加入随机浮动；每次变化记录原因和数值，并保留历史记录。
- 作品评价、商业成绩、项目履约在各自结算节点影响声望；严重负面事件允许即时扣除，正常奖励在对应结算节点统一计算。
- 声望影响企划档次与质量分布、外部委托档次/报价、招募候选人的质量分布、供应商解锁、原创企划其他投资方愿意提供的投资规模，以及媒体关注和初期曝光。
- 声望不改变市场企划数量、员工候选人数或员工提案触发概率；永久解锁资源不会因声望下降而收回，动态准入资源按当前声望重新判断。
- 声望不直接改变员工专业能力、疲劳、士气、制作效率、阶段质量或委员会压力。委员会压力与公司声望是两套独立数值。
- 公司必须承担的原创投资比例与前期开发费用不因声望下降而改变；投资方不划分档次，声望只影响其愿意补足的投资规模，不改变其渠道类型。
- 2026-11-23 基础数值机制已实现（#4 公司经营层）：`initial_reputation = 100` 生效；核心只有 `change_reputation` 一个写入点，负责钳到下限 0、不设上限、不随时间衰减、不加随机浮动，并把实际生效的变化按 `{week, reason, delta, reputation_after}` 追加进 `company.reputation_log`。已接通的是项目交付结算三档（成功/未达目标/违约），数值仍是 `game_rules.hpp` 的 M1 暂定值。本节其余口径仍未实现：等级阈值与称号、企划档次与质量分布、外部委托报价、招募候选人质量、供应商解锁、投资方补足规模、媒体关注与初期曝光，以及事件结果的即时扣除。

### 2. 轻量市场热度

- 每种题材各自具有一个市场热度状态，只有四档：大热、高、中、低；不使用连续热度数值。
- 所有题材使用同一套变化规则，各自独立变化；不设置题材专属基础热度表，也不做题材之间直接竞争。
- 热度变化挂接经营周推进，但按较长周期更新；短时间内不会大幅变化，每次最多升降一档。
- 热度变化使用固定种子下的确定性随机机制。玩家只看到当前档位，不显示升温/降温方向或历史曲线；内部只保存重放所需状态。
- 热度影响相关题材的市场企划与 IP 上门出现概率，也影响作品交付时的非合同商业收益。结算读取交付时的题材热度，不锁定开工时热度。
- 热度不影响合同收益，不影响员工提案触发概率，不影响原创企划创建资格、前期开发费、公司必须承担的投资比例或其他投资方补足规则。
- 不建立受众群体系统，不建立题材热度配置表，不展示热度趋势或历史曲线，不模拟题材间竞争。

### 3. 制作评价框架（V3 五阶段历史模型；目标玩法改为项目公共制作 + 单集六阶段）

- 五个制作阶段分别产出阶段质量，最终制作质量由五阶段质量综合计算，范围为 0–100。
- 第一版按作品规模选择阶段权重模板，企划来源暂不影响权重；常规模板的权重顺序由前期向后期递减：企划与脚本 ＞ 分镜与演出 ＞ 原画制作 ＞ 动画与作画检查 ＞ 摄影与后期。
- 作品评价为 S/A/B/C/D 五档，使用固定分数线，不按同期作品排名。
- 企划适配度是作品评价的辅助因素，影响小于制作质量；第一版由系统根据企划定位和最终成品自动判定，玩家不直接干预。适配度只影响作品评价，不反向修改最终制作质量。
- 重大事故独立影响最终评价，不简单混入阶段质量平均值。完全放弃解决核心环节的重大事故可能导致作品评价崩盘，甚至作品彻底失败；非核心事故不必然导致作品失败。
- 制作评价与商业表现分开，不能因为作品卖得好就直接提高制作评价。

### 4. 商业渠道框架

- 商业收入按渠道分别计算，再汇总为作品总收入；不同渠道采用各自的核心影响因素，不把所有渠道套用同一公式。
- BD 是所有企划自带的基础收入渠道，不依赖委员会成员；承制与委员会统一按初始50%毛收入计入公司收入、另50%作为BD综合成本，独立于投资比例。
- 其他商业渠道按企划自带条件及玩家额外拓展情况确定。委员会投资玩法包含控制玩家投资比例和拉入成员开放渠道两个操作维度；一个成员对应一个渠道，加入即开放，但渠道开放不由投资比例或投资金额推导。
- 玩具等渠道有独立商业潜力值，第一版使用 0–100 单一数值，不拆分角色、机体、道具等子项；潜力与作品质量分开，实际收入结合作品表现和市场情况。
- 网络播放版权与海外发行统一归发行商渠道；不另设海外渠道。
- 有电视台股东时获得电视播出渠道；没有电视台股东时，委员会项目可付费购买电视播出服务。购买服务记入 distribution 成本，并带来宣传效果，间接提升 BD、玩具等其他渠道收益。
- 第一版不做广告与品牌赞助。所有渠道收入在作品制作完成后统一结算，不按播出或销售时间分批入账。
- 承制项目不参与非 BD 渠道分成；承制与委员会统一按初始50% BD毛收入归公司、另50%计为综合成本。委员会项目非 BD 渠道按玩家投资比例分配。承制项目可另获委托方支付的商业表现成功奖励。
- WorkRecord.channel_breakdown 必须能逐渠道对账：渠道收入合计等于商业总收入，公司渠道入账合计等于公司商业分成收入。爆款机制的收入放大作用于分账前渠道毛收入（含 BD）。

### 5. 原创企划与员工提案

- 原创企划不进入普通市场。玩家主动创建与员工提案是两种不同发起方式。
- 玩家主动创建时可选择少数核心方向，其余企划参数由系统生成；需要具备企划能力的员工。
- 员工提案按周期概率触发，触发概率不受公司声望或市场热度影响；提案内容由员工形成，玩家只决定采纳或拒绝，不重新选择题材、规模等方案内容。
- 员工提案不占市场四槽，只展示一次；未采纳即随空闲周推进消失，拒绝无经济惩罚。
- 玩家主动创建自定企划时，在 `create_custom_offer` 创建动作中支付固定前期开发费；员工提案在 `adopt_proposal` 采纳动作中支付同额费用。提案展示本身不扣款。
- 原创必须采用委员会投资，公司必须承担 10%–100% 投资，其他投资方自动补足剩余比例；100% 表示公司独资。前期开发费独立于投资本金，不参与商业分成。
- 契约已为自定企划与员工提案预留独立槽位；相关行为实现状态见 PROGRESS，不因字段存在而视为已实现。

### 6. 作品系列与长期记录

- 同一 IP 可推出续作、前传和外传；上一部作品影响最大，更早作品提供较弱的长期系列积累。
- 前作表现影响后续作品的商业基础；前作差评会降低预期，但不会抹掉系列此前积累。
- 续作的制作质量和作品评价独立计算，不继承前作质量或档次；第一版不加入系列市场疲劳。
- 作品历史记录名称、类型、题材、制作人员快照、综合质量、作品档次、商业成绩、结算结果、重大事件经历及前作关联。
- 不建立独立年度经营报告；竞争公司只在作品结算阶段参与比较，不模拟其日常经营。

### 7. 公司结局与特殊评价

- 公司结局采用综合评价，不只看最终资金或声望；累计作品成绩、商业成果、声望积累和团队成长为主，最终资金、声望、团队规模与状态为辅。
- 破产拥有最高判定优先级，因破产终止经营直接判定经营失败，不参与其他档次竞争。
- 十年期满与玩家主动结束经营使用同一套综合评价标准；结束原因单独展示，不额外加减评价。
- 突出的单项成就允许突破基础结局档次，可跨越多个档次；达到门槛时可同时获得对应特殊评价。特殊评价也可独立获得。
- 特殊评价分正面和负面，不设置等级；同类正负评价可以同时存在，不互相抵消。负面评价只进入经营总结，不直接降低已判定结局档次。
- 结局展示至少包括十年累计作品数量与代表作、累计商业收入、最终资金与声望、团队成长、正负特殊评价和结束原因；展示最佳作品及其制作团队快照。
- 公司结束时展示核心员工最终状态、能力成长和代表作品经历，不为每名员工生成复杂个人命运剧情。

### 8. 制作事件框架

- 首版事件只依附当前制作项目，不做独立公司级事件；正面机会与负面异常统一纳入制作事件。
- 事件由项目表现与随机机制共同触发；每周最多一个事件，同一时间最多一个待处理事件。事件出现后暂停后续周推进，处理完成后才能继续。
- 同周满足多个触发条件时按固定优先级选择，不额外消耗随机种子；同周处理完毕后不再触发第二个事件。不同周可连续触发，同类事件需冷却或重复限制。
- 事件在原定周结算事件检查节点进行；只有公司仍运行、项目未交付、当前阶段仍 active 时才检查。阶段切换、项目交付和公司终局后不追加事件。
- 效果分即时、阶段、项目三类；可影响尚未开始的后续阶段，但不得追溯修改已结算阶段；首版不做跨项目永久事件效果。
- 事件库分固定重大事件与普通事件。重大事件可设置前置条件、预兆和跨阶段连锁影响；同一重大事件在同一项目中最多触发一次。
- 事件选项按事件性质提供，不要求所有事件支持相同处理方式。已知确定代价必须明确展示，主要风险可展示等级或成功预期，不强制公开精确概率。
- 处理方式包括放弃解决、加班解决、应急外包、延期处理等候选类型；正面机会可接受或放弃。每个事件只能选择一次，不可撤销或反复刷取。
- 应急外包复用供应商系统；事件不能修改合同目标/条件、不能绕过财务与终局规则。承制不可延期，委员会最多延期一次。
- 重大事件进入作品履历；普通事件按需要汇总，不逐条堆积。历史事件不直接提高下一部作品的事件触发概率。

## 确定性与责任边界

同一初始状态、相同决策和相同种子应产生相同结果。C++ 不获取系统时间、系统随机源、浏览器状态或网络数据。TypeScript 持有完整状态和种子，通过请求显式传入，并整体采用 C++ 返回的状态；存档记录种子。`?seed=12345` 可用于固定新局种子，不能用前端规则代替核心复现。

规则属于 C++ 核心，不属于 React 或 Zustand。React 只发出操作，Zustand 协调异步调用并采用结果。C++ 接口保持明确输入输出，不保存全局游戏会话、不读写存档；种子计算发生在纯规则调用内，不另建内部随机状态。当前核心以 `nlohmann::json`（`Json`）承载状态，不要求独立的强类型状态结构体。

所有带 state 的动作验证完整状态与阶段，必须传入 schema v2；初始化只接收 seed。不得通过修改员工技能、报价或事件选项绕过固定目录校验。

## 2. 决策与每日固定顺序

排班、方针持续到再次修改；外包和加班只安排今天，均可通过 `enabled: false` 撤销。启用外包或加班时校验**全部已安排的当日总费用**，此时不扣款、不增加进度或 spent。排班为 `rest` 会清除该员工加班，休息员工不能启用加班。

`advance_day` 仅允许 `producing`，顺序不可调换：

1. 计算 `cost = 120000 + 45000 × 4 + 25000 × 加班人数 + 500000 × 外包工序数`。资金不足时直接成功返回 `ended / bankrupt`；**不扣款、不改变 spent、制作数值、日期或 seed，也不执行后续标记清除**。报告变化为 0，工序变化数组为空。
2. 资金充足则 `funds -= cost`、`spent += cost`。记录本日加班人数供后续事件判定。
3. 按 `pre → mid → post` 计算员工和外包工作量、流水线进度与质量；后工序使用本日已更新的上游进度，计算细节见第 3 节。
4. 对本日新增进度且质量低于 45 的工序返工，进度回退 4（最低 0）。随后再次按流水线钳制下游，清除各工序 `outsourced`。返工不回滚已扣费用或重新计算质量。
5. 工作员工按方针消耗士气，加班额外 -6；休息 +10。钳制到 0–100，清除全员 `overtime`。
6. `day += 1`。报告的 `day` 仍为刚结算的旧日期，工序增量为整日净变化，`morale_delta` 为全员实际变化之和除以 4。
7. 推进一次 LCG 种子，依其结果最多生成一个事件候选。
8. 判定终局：三工序均 100 → `completed`；否则 `day > deadline_day` → `deadline`。终局优先于事件，转 `ended` 并清空事件候选；非终局才保留 `event_pending`，否则继续 `producing`。

截止日当天仍可制作；当日日结后若未完成，立即强制按现有进度交付/违约结算，不能一直制作到完成。截止日当日完成按 `completed` 处理；当日新事件不能在终局后补救延期。此前已处理的延期事件会修改截止日。

## 3. 整数公式与流水线

C++ 整数除法向零截断；非负计算等同向下取整。定义 `T(v, k) = floor(v × k / 1000)`（核心用商余拆分实现），`clamp(x) = min(100, max(0, x))`。**每一层 T 和除法分别截断，不能先合并浮点系数再统一取整。** 金额加法超过安全整数上限会报 `INVALID_INPUT`，不会回绕。

对分配到某工序的每位员工，取其擅长系数 `fit`（1200 或 800）、企划速度系数 `project_speed`：

```text
speed = 9 × skill × 10
speed = T(speed, fit)
speed = T(speed, policy_speed)
speed = T(speed, 600 + 4 × morale)
speed = T(speed, project_speed)
若加班：speed = T(speed, 1300)
points = floor(speed / 1000)

worker_quality = T(T(skill, fit), policy_quality)
若加班：worker_quality = T(worker_quality, 900)
worker_quality = clamp(worker_quality)
```

每工序 `work = Σpoints`，`quality_sum = Σ(points × worker_quality)`；已安排外包则额外 `work += 8`、`quality_sum += 8 × 50`。外包质量是本批工作固定为 50，并不是把整个工序质量乘以折扣。

```text
upstream = 100                          // 前期的上限
new_progress = min(upstream, old_progress + work)
gain = new_progress - old_progress
若 gain > 0：
  batch_quality = floor(quality_sum / work)
  new_quality = clamp(floor(
    (old_quality × old_progress + gain × batch_quality) / new_progress
  ))
否则：质量保持不变
upstream = new_progress                 // 供下一工序使用
```

上游堵塞或工序已满时，超出上限的工作量丢弃，无退款、无跨日储备；无新增进度也不单独提升质量。返工判定后再钳制一次，始终保证 `0 ≤ post.progress ≤ mid.progress ≤ pre.progress ≤ 100`；回退与二次钳制只改进度。`stage_deltas` 记录最终进度/质量减去日初数值，可为负。士气平均变化含负数时向零截断（不是向下取整）。

## 4. 随机协议与固定事件目录

LCG 使用 uint32：

```text
s' = (s × 1664525 + 1013904223) mod 2^32
触发条件：s' % 1000 < 150 + 50 × 当日加班人数
事件索引：floor(s' / 1000) % 3
```

每次实际完成日结仅推进一次种子，无论是否触发事件、是否成为终局；阈值与目录索引复用同一个 `s'`，不二次抽签。初始化按请求保存 seed；接取、决策、事件处理、结算不消耗种子。费用不足导致破产时没有完成日结，日期与 seed 均不推进。加班影响当日概率，没有“连续加班天数”隐藏计数器。

事件目录固定为以下 3 项，每项 2 个选项，顺序对应索引 0–2。只允许从当前待处理事件选择，前端不能传入任意效果。

| 事件 | `opt_a` | `opt_b` |
| --- | --- | --- |
| `evt_001` 原画支援请求 | funds -300000、全员 morale +8 | deadline_day +1、mid.quality -3 |
| `evt_002` 临时修改分镜 | pre.quality +5、全员 morale -5 | pre.quality -4、全员 morale +5 |
| `evt_003` 摄影设备维护 | funds -200000、post.quality +4 | 全员 morale -6、post.quality -2 |

事件费用计入 `spent`；支付不足返回 `INSUFFICIENT_BUDGET`，不改变原状态且事件仍待处理。质量和士气变化钳制到 0–100；延期修改绝对截止日，不改变当前日。当前目录无进度效果。处理成功后清空事件、回到制作并执行终局检查，不额外推进日期或种子。

## 5. 结算公式

`calculate_result` 仅允许 `ended`。按以下顺序计算，所有除法仍逐步截断：

```text
quality_score = floor((pre.quality × 300 + mid.quality × 400 + post.quality × 300) / 1000)
progress_average = floor((pre.progress + mid.progress + post.progress) / 3)
revenue = T(T(budget, quality_score × 10), progress_average × 10)
若 quality_score < target_quality：revenue = T(revenue, 700)
若 end_reason == 'deadline'：revenue = T(revenue, 600)
若 end_reason == 'bankrupt'：revenue = 0
cost = spent
profit = revenue - spent
```

收入没有另一个“类型乘数”；类型差异通过当前报价的预算、速度、目标质量与工期体现。`quality_score` 不因未完成而另打折，完成度已作用于收入。评级仅看质量：S ≥85、A ≥75、B ≥65、C ≥50、否则 D，不另按终局原因改评级。

完成且达到目标质量时声望基础 +10，否则 -5；超预算（`spent > budget`）再 -3。公司声望最低 0，`result.reputation_delta` 返回钳制后的实际变化，而非未经钳制的惩罚值。

最后 `funds += revenue`，更新声望，清空企划、事件、终局原因，重新供应相同 3 个报价并转 `idle`；保留日期、seed、员工士气和排班，清除加班。

**经济口径待复核：** 开工拨款已加入公司资金，但草案利润只定义为 `revenue - spent`，不含拨款，所以不是该企划对公司现金的总净贡献。工资、固定费用、加班、外包和付费事件均计入 spent。不要在 TypeScript 中自行改成另一套利润公式。

## V3.9 市场竞争与商业表现规则（2026-11-23）

本节记录 2026-11-23 已确认的市场竞争与商业表现规则。未定公式和参数明确保留为 TODO；本节是规则记录，不代表核心代码已实现。

### 1. 市场与竞争公司

- 市场热度属于全局市场，按作品**主要题材**维护，不按 TV、剧场版、OVA、短篇等作品形式区分。题材目录待定。
- 热度分为大热、高、中、低四档；短期不会大幅变化，不向玩家显示变化方向。
- 热度按周期变化，不是每周自然波动；周期、概率和具体数值留待执行阶段配置。
- 热度影响市场合同与 IP 上门机会的出现概率；IP 上门占用四个市场企划槽位，共用刷新机制。
- 市场机会生成时读取当时热度；作品商业结算时读取结算时当前热度。竞争作品题材生成使用上一轮市场热度快照；同一轮竞争作品生成共用一份快照，避免结算顺序造成差异。
- 上一轮商业收入排名第一的作品，其主要题材获得额外一个热度周期；持续时间等于该作品的制作周期。该奖励在本轮结算后生效，不回头影响本轮已经生成或结算的作品。
- 竞争公司共 30 家，是单机市场模拟对象，不模拟完整经营过程。固定大型动画公司名单、名称与实力固定，每局都存在；小型公司数量固定，每局按游戏 seed 生成名称、综合实力、制作能力与商业能力。
- 小型公司的实力分布以弱为主、少量中等；小型公司的制作能力与商业能力独立生成，允许偏科。
- 首版建议不生成强于固定大型公司的小型公司；该强度上限仍作为待确认的平衡约束，不擅自视为已冻结规则。
- 竞争公司不模拟资金、员工、制作进度或完整企划经营状态。
- 每次玩家作品结算触发一轮市场竞争；竞争公司各自独立判断是否推出作品，推出概率不受公司实力影响。
- 竞争作品只为当轮市场模拟临时生成，不保存完整作品记录。
- 竞争公司与竞争作品使用统一 LCG，保证相同 seed 和相同操作下可重放。
- 竞争作品的商业收入计算方式尚未确定；本节不将玩家作品收入公式直接套用到竞争作品。

### 1.1 竞争作品生成与排名

- 每轮由 30 家竞争公司分别独立判断是否推出作品；是否推出不受该公司的制作能力或商业能力影响。
- 竞争作品与玩家本轮作品一起，按商业收入统一排名，取实际参与排名作品的前一半；不为凑足数量额外生成作品。具体取整边界留待实现时明确。
- 玩家作品即使没有进入排名，仍正常计算并获得自己的商业收入；排名不作为玩家作品获得收入的前置条件。
- 竞争作品先生成参与商业表现计算所需的简化数据，再进行收入计算和排名；只有进入排名的竞争作品，才进一步生成名称、作品形式、介绍等展示详情。未入榜作品不生成这些详细内容。
- 本轮竞争作品只用于本轮模拟，不保存完整作品记录。排名结果是否持久化保存尚未决定。
- 竞争作品的题材生成读取上一轮市场热度快照；商业收入计算读取本轮结算时的当前热度。每轮生成统一使用同一份上一轮快照，避免竞争作品之间读取时点不一致。

### 1.2 竞争作品质量与商业收入

- 竞争作品质量由竞争公司的制作能力映射基础质量（五档分别为 30、40、50、60、70），再叠加均匀分布的整数随机波动 `[-30, +30]`；所有竞争公司使用相同波动范围，不对小型公司额外补偿。
- NPC 竞争作品最终质量限制在 `0–90`；超过 90 分的质量只允许玩家后期作品达到。
- 竞争作品商业表现沿用“商业实力影响规模、作品质量决定规模兑现、题材热度轻量修正”的分工。竞争公司的商业实力决定基础商业规模，作品质量决定兑现程度，题材热度修正最终商业表现。
- NPC 质量突破规则：质量不超过 72 分时不突破；质量高于 72 分后，每增加 4.5 分突破一档。具体区间为：`(72, 76.5]` +1 档、`(76.5, 81]` +2 档、`(81, 85.5]` +3 档、`(85.5, 90]` +4 档。突破档次叠加在竞争公司原有商业实力档次上。
- 每突破一档，商业收入计算使用的质量兑现分扣除 5 分；扣分只影响商业计算，不修改作品原始质量。突破不拆分为额外收入部分，仍按同一套商业表现计算得到一个最终商业收入数值。
- NPC 质量兑现系数暂定为 `0.25 + 商业计算质量 / 200`；质量为 0 时兑现 25%，质量为 100 时兑现 75%。最终商业收入 = 基础商业规模 × 质量兑现系数 × 题材热度系数。题材热度系数仍待数值平衡。
- NPC 商业实力分为五档，基础商业规模（日元）暂定为：一档 1 亿、二档 5 亿、三档 20 亿、四档 80 亿、五档 300 亿。该组数值作为首版基础参数，后续根据实际结算与排行榜表现再调整。
- 竞争作品商业收入不额外乘统一的 `0.9` 折减系数。

### 2. 玩家作品商业收入

商业收入直接按**商业规模**计算，不模拟观众人数、播放量或观众转化人数。

- 每种已开放商业渠道拥有独立的基础商业规模。
- 多个渠道的基础商业规模直接累加；首版不考虑渠道之间的受众重叠。
- 作品质量决定商业规模的兑现程度，采用平滑的阶梯曲线：低质量作品仍有基础收入；普通质量区间持续提供正向反馈；优秀作品获得更明显的收入增长；顶级质量保留提升空间但限制增长。
- 低质量作品可能无法充分兑现商业规模，商业收入可以低于制作及发行投入，不设置保本线。
- 题材热度作为轻量收入修正，暂定考虑 1.2–1.3 的系数范围；具体档位、系数和公式待数值平衡。
- 公司声望使用独立的商业收入系数，具体映射和系数待定。
- 前作表现使用独立系数，和公司声望系数分别计算，最后相乘。

### 3. 前作积累与续作系数

- 前作积累只对同一系列的续作生效。
- 每部前作按 BD 销量区间换算为固定积累值；不直接按 BD 实际销量线性累计。
- 最近三部前作参与积累，越早的作品权重越低；三档权重采用固定比例，具体比例待数值平衡。
- 加权累计值映射为五个档位：`-1、0、1、2、3`。其中 `-1` 为负向修正，`0` 无影响，`1–3` 为逐级增强的正向修正。
- 续作更换主要题材时，前作档位直接降低一档，最低不低于 `-1`；只比较主要题材，次要题材变化不触发降档。
- 作品形式变化不影响前作积累。
- BD 销量独立计算，只受作品质量影响；不直接套用商业渠道、题材热度、公司声望或前作商业收入系数。BD 销量区间与质量—销量计算方式仍待确定。

### 4. 商业收入与分账顺序

1. 汇总本项目已开放渠道的基础商业规模。
2. 根据作品质量计算商业规模兑现程度。
3. 应用题材热度系数。
4. 应用公司声望系数。
5. 应用前作系数。
6. 得出作品商业总收入。
7. 按 V3.8 K3 的渠道分账约定计算各股东收入及公司实际到账。

所有商业表现修正先作用于作品商业总收入，再进行渠道分账。商业表现计算与财务分账分离；不得把公司实际到账误当成作品商业总收入。

V3.8 K3 的渠道分账框架经 2026-11-23 后续决定修订：BD 为所有企划的基础渠道，承制与委员会统一按初始50% BD毛收入归公司、另50%计为综合成本，独立于投资比例；比例可后续调整，但成本比例必须大于0。委员会投资玩法包含控制玩家投资比例与拉入成员开放渠道两个操作维度；一个成员对应一个渠道，加入即开放，渠道开放不由投资比例或投资金额推导。其他投资方共同补足公司未承担的剩余投资份额。委员会非 BD 渠道按玩家投资比例分配；承制不参与非 BD 渠道分成，但可在商业表现达标时获得委托方另付的成功奖励。无电视台成员时委员会项目可购买播出服务，计入 distribution 支出并提升宣传；爆款 ×5 作用于分账前渠道毛收入。

### 5. 明确未定项

- BD 销量的具体质量—销量曲线、销量区间与固定积累值映射。
- 前作三档权重比例、累计值到 `-1/0/1/2/3` 档位的阈值及各档系数。
- 公司声望到商业收入系数的映射与系数。
- 题材热度各档具体系数及周期变化参数。
- 质量兑现曲线的具体公式、阈值与上限。
- NPC 竞争作品商业表现框架已确认；五档基础商业规模与质量兑现公式已有首版参数，后续可根据实测调整；题材热度系数仍待数值平衡。NPC 与玩家作品不直接共用完整收入公式。
- 以上参数不得由实现者自行补造；在后续规则讨论或数值平衡中确认。



## V3.10 承制与制作委员会模式对比及渠道规则（2026-11-23）

本节记录 2026-11-23 对两种合作模式的补充确认。目标是鼓励公司逐步参与制作委员会，但承制仍应是有经营价值的稳健路线；以下为规则方向，不代表 C++/WASM 已实现。

### 1. 两种模式的经营定位

- **承制模式：** 低风险、现金流相对稳定、收益较可预测，长期收益上限相对有限。公司获得制作预算，预算未花完的部分留在公司；可获得 BD 收益，并可在作品商业表现达到预设目标时获得委托方额外支付的成功奖励；不参与非 BD 渠道分成。
- **制作委员会模式：** 公司需要先投入资金，承担本金无法收回的风险；投资本金最多损失公司实际投入的全部金额。制作经营费用另行核算，可能继续造成经营亏损，不能将其算作投资本金亏损或用投资额上限抵消。
- 两种模式不设成绝对优劣关系：普通或表现不佳的项目，承制可能更有利；商业表现优秀的项目，委员会模式具有更高收益潜力。委员会模式不保证每个项目都比承制赚钱。
- 投资本金亏损边界仅约束公司实际投入的投资本金，不代表项目净收益或公司总经营亏损不能为负。制作经营亏损可能发生在承制和委员会项目中。
- 公司同一时间仍只能推进一个在制项目；不提供多项目并行或纯投资玩法。选择委员会模式时，公司必须实际参与作品制作，不能只出资并获取分成。

### 2. 合作模式选择与投资比例

- 所有企划均可选择承制或制作委员会模式；原创企划仍只能选择委员会模式。allowed_modes 应按此规则生成，不得因企划来源或规模将普通企划排除在委员会模式之外。
- 项目开工后，合作模式与投资比例锁定，制作过程中不允许切换。
- 委员会投资比例以 0.1 为最小调整单位，即每次调整 10 个百分点；现行有效范围仍为 10%–100%。其他投资方自动承担剩余投资份额。
- 投资比例决定公司承担的投资金额，以及委员会项目非 BD 渠道收益的分配基准；不直接决定制作工作量、制作责任、作品质量上限或项目决策权。拉入委员会成员开放渠道是同一投资玩法中的另一操作维度，但渠道开放不与投资比例或投资金额绑定。
- 承制与委员会共用同一套制作能力、人员、资源和制作流程。相同制作条件下，两种模式的作品质量上限相同；经营模式本身不提供制作质量加成。
- 委员会模式不引入与投资比例绑定的投票权或额外决策权系统。第一版不模拟委员会内部投票和决策权争夺。

### 3. 企划初始渠道与额外拓展

- IP 上门企划自带成熟商业渠道。
- 普通合同企划至少自带一个商业渠道。
- 原创企划需要玩家自行寻找渠道。
- 所有企划均可选择委员会模式；只有选择委员会模式时，玩家才能拉入委员会成员拓展渠道。承制模式不拉入委员会成员，也不通过委员会成员机制拓展渠道。渠道应在项目立项时确定，开工后不追加或更换。
- 制作委员会项目中，公司未承担的剩余投资由其他投资方共同补足；不记录其他成员的细分投资比例或投资金额。拉入委员会成员会开放其对应渠道，一个成员对应一个渠道；渠道开放不由玩家投资比例或投资金额推导。
- 制作委员会的非 BD 渠道收益按玩家投资比例分配，不另设渠道细分分配比例。
- BD 是所有企划基础渠道，承制与委员会统一按初始50%公司收入、50%综合成本分配，独立于投资比例；该比例可后续调整，但成本比例必须大于0。



## V3.11 投资玩法、渠道开放与经营亏损边界（2026-11-23）

本节为当前有效口径，覆盖 V3.3、V3.8、V3.9、V3.10 中与委员会成员投资份额、渠道开放关系及 BD 分配不一致的旧表述。

### 1. 委员会投资玩法

- 委员会投资系统包含两个操作维度：**控制玩家投资比例**与**拉入委员会成员开放渠道**。
- 玩家投资比例为 10%–100%，按 10 个百分点调整；公司只记录玩家自己的投资比例和实际投资金额。
- 其他委员会成员共同补足项目剩余投资份额；其投资不进入公司现金，也不是公司收入。不记录其他成员各自的细分投资比例。
- 一个委员会成员对应一个渠道。成员加入委员会即开放对应渠道；渠道开放与玩家投资比例、投资金额没有数值绑定关系。
- 不记录渠道独立投资比例、渠道细分分配比例或成员投资金额明细。非 BD 渠道公司所得统一按玩家投资比例计算。
- IP 上门、普通合同和原创企划的既有渠道来源规则继续有效；所有企划均可选择委员会模式，选择后可通过委员会成员拓展渠道。承制模式仅保留企划本身已有渠道，不拉入委员会成员。渠道是否开放由企划既有条件及已加入成员决定，不由投资比例推导。

### 2. BD 收入分配

- BD 是所有企划的基础渠道，承制与委员会统一采用同一分配规则。
- 初始参数为：BD 毛收入的 50% 计入公司收入，另外 50% 作为 BD 综合成本。
- 50% 是游戏初始平衡参数，不是现实产业统一费率；后续可依据产业调查与数值平衡调整。
- BD 综合成本比例必须大于 0，不能将 BD 毛收入全部计入公司收入。
- BD 分配不受玩家投资比例影响；委员会非 BD 渠道收入按玩家投资比例分配。承制不参与非 BD 渠道分成。

### 3. 制作预算、经营亏损与破产

- 合同预算就是制作预算。仅委员会模式生成投资规模，total_investment = contract_budget × 2；承制模式不生成 total_investment。制作预算在开工时并入公司统一现金池，不另设独立预算钱包。
- 制作过程中的工资、运营、内部制作、临时人员、外包及其他制作费用持续从公司现金支付。制作预算资金不足后，仍必须由公司现有现金承担，不因预算用尽而停止正常制作。
- 制作经营亏损与委员会投资本金亏损分开核算。制作经营亏损可能发生于承制和委员会项目；委员会投资本金亏损只针对公司实际承担的投资本金。
- 当周强制制作费用预检无法通过时，不执行该周制作，立即进入破产结算并判定游戏失败。没有贷款、强制追加投资或靠未来项目回款解除破产的机制。
- 费用预检时公司现金恰好足以支付当周费用，允许完成该周；支付后现金为 0 不单独触发破产，后续无法支付下一笔强制费用时才触发。

本节只冻结规则口径，不代表 C++/WASM 已实现；相关实现与测试由 #6 及核心集成负责人按模块边界推进。

## V3.12 合同预算与委员会投资规模统一口径（2026-11-23，当前有效）

本节覆盖此前文档中“制作预算按总投资的50%生成”以及“所有企划均可在承制模式下额外引入委员会渠道”等旧表述。历史版本与旧验收样例仅作变更记录，不作为当前规则。

### 1. 合作模式

- 所有企划均可选择承制或委员会模式；原创企划仍然只能选择委员会模式。
- allowed_modes 必须保证普通企划同时提供 contract 与 committee，原创企划只提供 committee。不得再因企划来源或规模将普通企划限制为只能承制。
- 玩家在立项时选择模式，开工后锁定。委员会成员及其渠道也在立项时固定。
- 只有选择委员会模式，才能拉入委员会成员并通过成员开放额外渠道。承制模式不加入委员会，不通过委员会成员机制拓展渠道；企划本身已有的基础渠道规则仍然有效。

### 2. 合同预算与投资规模

- contract_budget 是项目制作预算。字段名沿用现有协议，但语义统一为“合同预算/制作预算”，不再把它理解为承制模式专属字段。
- contract_budget 按企划规模与报价规则生成；具体金额参数由数值平衡确定。
- 承制模式不生成委员会投资规模，total_investment 为空或不适用，investment_percent=0，不支付投资本金。
- 委员会模式直接按公式生成投资规模：total_investment = contract_budget × 2。不再独立生成投资规模，也不再通过 total_investment × 50% 反推合同预算。
- 委员会模式下公司投资额为 floor(total_investment × investment_percent / 100)；投资比例为10%–100%，按10个百分点调整。其他投资方共同补足剩余投资规模，不记录其各自细分比例或金额。
- contract_budget 与 total_investment 是两个不同口径：前者是实际制作预算，后者仅在委员会模式下作为投资规模与公司投资额的计算基数。不能把两者混成一个字段，也不能把委员会投资规模当成制作预算。
- 开工时制作预算并入公司统一现金池；公司投资本金按委员会规则支付。制作费用持续从公司现金支付，未花完的制作预算留在公司，不另行发放结余。

### 3. BD 结算实现

- BD 毛收入的初始公司所得比例为50%，另50%为BD综合成本；承制与委员会统一适用，不受投资比例影响。
- 实现可以采用“先记毛收入、再扣50%成本”，也可以直接将公司所得计算为 gross_bd_revenue × 0.5。两种方式的最终公司所得必须一致。
- 若使用直接乘0.5的方式，channel_breakdown 中应清楚区分渠道毛收入与公司实际所得；不得再从公司现金或项目成本中重复扣除同一笔50%综合成本。
- 委员会非BD渠道公司所得按玩家投资比例分配；承制不参与委员会成员开放的非BD渠道分成。

本节是当前规则的统一解释；total_investment 仅属于选择委员会模式后建立的 Project，不属于尚未选择模式的 ProjectOffer。2026-11-23 的独立分支已完成 C++/TypeScript 字段与校验迁移，并同步对应测试；委员会实际开工、投资扣款和渠道结算行为仍未实现，且本次迁移尚待自动化测试验证。


## V3.13 作品商业排名历史记录（2026-11-23）

本节补充作品商业排名的历史留存方式，覆盖前文 1.1 节中“排名结果是否持久化保存尚未决定”及“具体取整边界留待实现时明确”的待决描述。

- 每轮玩家作品结算时，玩家作品与本轮实际生成的竞争作品按商业收入统一排名；不为凑足数量额外生成竞争作品。
- 排名范围内的作品数量为 N 时，前一半的入榜数量按向上取整计算，即 ceil(N / 2)。该规则只决定哪些竞争作品需要生成展示详情，不影响玩家作品收入结算。
- 玩家作品的最终商业排名写入该作品的历史记录，作为永久历史数据；即使未进入前一半，也正常保存其实际名次并正常获得商业收入。
- 不保存完整竞争榜单，不保存全部竞争作品的历史记录，也不提供按轮次回顾完整榜单的功能。竞争作品仍只在当轮模拟；入榜竞争作品的展示详情也不转为长期作品档案。
- 历史作品档案只展示该玩家作品自身的商业排名，不据此重建或推导当轮完整榜单。
- 商业排名字段允许为空：正常参与该轮排名的玩家作品应记录正整数名次；仅未参与排名的特殊作品或没有该字段的旧存档可以为空。空值不代表排名靠后。
- 排名只记录商业收入比较结果，不改变作品收入、渠道分账、作品评价或公司声望。

本节冻结历史记录范围，不代表 C++/WASM、TypeScript 或 UI 已实现；字段接入、旧存档兼容和测试由核心与集成负责人按协议同步。


### 委员会项目的中期成员诉求（首版）

委员会项目在制作期间可能收到实际委员会成员或相关渠道伙伴提出的诉求。该机制复用项目事件系统，不建立独立政治系统。玩家通常可选择妥协或拒绝，事件卡定义对应的工作量、工期、质量、商业预期、委员会压力或渠道影响。两种选择均应有机会成本，且拒绝不必然是负面结果。每部委员会作品最多触发 1–2 次，具体触发次数、概率和效果由数值标定；不要求每部作品必然触发。首版不包含委员会投票、派系或复杂政治博弈。


### 核心员工最低数量

公司至少保留 1 名核心员工，不能通过解雇将核心员工数量降至 0。老板不属于普通核心员工规则，首版不要求实现；后续可通过 Staff 特殊标记或独立角色槽位作为特殊角色实体接入，不重写周结算事务和核心状态机。具体属性与能力留待后续版本设计。
