## 0. 总体审查结论

**旧单项目架构不能通过给 `GameState.project` 增加数组的方式平滑扩展。** 当前阶段应先建立公司级经营主体、项目级制作主体、共享资源分配和全公司统一周结算，再迁移员工、制作、委员会、事件、市场与财务模块。

今日材料形成了四类有效资产：

1. **方向依据：** 游戏性优先，以开罗游戏为主要参考；作品驱动经营，公司成长提供长期动力，产业关系服务于作品目标。
2. **历史事实：** 旧代码与旧实验存在单项目、单事件槽位、跨项目资源未建模、部分商业/招聘/外包流程未实现等限制。
3. **可迁移方法：** 能力权重、工作量与质量分离、随机流隔离、账目对账、阶段性复盘等方法值得保留，但旧参数不能直接成为新规则。
4. **明确风险：** 事件暂存可跳过周成本；多项目同周结算若按项目顺序逐个扣款，会产生顺序偏差；资源分配若无唯一占用账本，会重复使用员工或供应商产能。

**当前重构顺序：先领域模型与状态归属，再共享资源和周结算契约，再定义计划/事件/财务接口，最后重建最小可运行模拟器。** 暂不以旧代码兼容性约束新架构，也不在领域边界未定前迁移旧运行时模块。

## 3. 旧架构问题与必须解决的冲突

### 3.1 单项目状态与多项目经营冲突

- [ ] 旧核心以单个 `GameState.project` 为中心，阶段、计划、事件和结算围绕单项目运行。
- [ ] 不能只把单项目字段改成数组；公司级状态与项目级状态必须分层。
- [ ] 各项目需要独立阶段、制作进度、质量、风险、计划、预算归因、委员会和项目历史。
- [ ] 公司需要统一持有周数、现金、员工、供应商、声望、长期合作关系及经营终局状态。
- [ ] 多项目同周推进必须是一次公司级时间动作，不得按项目分别推进时间。

**处理结论：** 建立 Company 与 Project 两层核心实体；公司统一推进周数，各在制项目在同一结算事务内并行计算。

### 3.2 项目计划与共享资源冲突

- [ ] 项目计划表达项目“希望如何推进”，不能直接等同于实际产能。
- [ ] 员工、外包产能、资金和管理能力是公司共享资源。
- [ ] 同一员工、同一供应商产能、同一笔现金不得被多个项目重复占用。
- [ ] 项目优先级、核心员工单项目归属与供应商预留需要显式记录；核心员工同周支援/借调/拆分工时已明确禁止。
- [ ] 资源不足时必须产生可解释的计划落差、延迟、成本或风险，不得静默复制资源。

**处理结论：** 项目计划与公司资源分配分离；资源分配形成独立的周度记录，作为项目实际工作结算的唯一输入。

### 3.3 项目账与公司现金流冲突

- [ ] 旧委员会/商业规则与代码实现存在差距；部分投资、收入、渠道和分账逻辑没有完整进入现金流。
- [ ] 旧招聘、外包动作存在 invalid/未实现路径。
- [ ] 不能把项目账面预算视为项目拥有独立钱包。
- [ ] 工资、运营费、项目成本、投资流入、商业收入、分账和退款必须有明确现金流归属。
- [ ] 多项目若逐个扣费，可能因遍历顺序不同产生“先结算项目抢走现金”的偏差。
- [ ] 不能让事件、暂停或失败分支跳过工资与运营等时间成本。

**处理结论：** 公司只有一个真实现金池；项目账用于成本/收入归因和项目核算。周结算采用统一预检、统一资源校验、统一扣款/入账与原子提交；失败则整周不推进，或采用明确设计的可结算失败状态，不能部分推进。

### 3.4 员工能力、成长与排班冲突

- [ ] 旧员工成长主要增加 experience，经验到能力的转化不完整。
- [ ] 招聘、外包等动作在旧运行时代码中存在未实现路径。
- [x] **历史实验边界：** 员工排班实验以旧单项目/五阶段为前提，不能证明新架构的多项目资源竞争；仅保留实验方法，不把旧实验规则迁入新系统。
- [ ] 六项能力（企划、演出、作画、动画、管理、后期）可作为候选能力结构，但应验证是否足够区分岗位决策。
- [ ] 当前能力、潜力、经验、疲劳/状态必须分离，不能用单一经验值替代成长。
- [x] **负责人已确认：核心员工每周严格单项目分配，不允许同周跨项目支援、借调或拆分工时；周结算后可重新分配。**

**处理结论：** 员工归公司所有；周度分配记录决定本周能力贡献；项目工作历史记录实际贡献；成长根据实际参与、岗位与结果结算。

### 3.5 事件系统与全局推进冲突

- [ ] M2-a/M2-b 使用全局 `phase`、`pending_event` 单槽位控制事件流程。
- [ ] 多项目下，事件必须区分公司级与项目级。
- [ ] 必须明确事件是否阻塞全公司、仅阻塞所属项目，或允许其他项目继续推进。
- [ ] 多个事件同时触发时需要排队、合并、优先级或并发策略，不能继续依赖单一 pending_event。
- [ ] M2-b 暂存事件未到期恢复路径存在推进周数却跳过工资、运营费和正常制作结算的漏洞。
- [ ] 事件暂存、延期处理、超时升级不能绕开周结算事务。

**处理结论：** 事件系统迁移到新架构后重做。事件处理状态与时间推进解耦；任何实际周数变化都必须经过唯一的 WeeklySettlement 入口。

### 3.6 随机性与可预测性冲突

- [ ] 旧实验探索工作量随机、质量随机，但实验依赖旧单项目和排班模型。
- [ ] 玩家在点击下一周之前不应看到下一周的具体随机结果。
- [ ] 随机性应服务于经营判断，而不是随机决定输赢。
- [ ] 工作量变化与质量变化应分开计算、分开解释。
- [ ] 随机结果需要可复现以便调试与模拟，但 seed 和未来结果不能作为玩家预览信息泄露。
- [ ] 不能把实验中的随机幅度、权重或均值直接当作正式平衡参数。

**处理结论：** 周结算时生成随机结果；随机流按用途隔离并记录 seed/输入快照；能力、管理、资源和计划影响期望值与波动范围。具体分布与参数由新模型实验决定。

### 3.7 作品、委员会与商业权利冲突

- [ ] 委员会是项目级合作组织，不是公司本体。
- [ ] 委员会贡献不能只表达为资金，还可能包括发行、宣传、渠道、版权、商品化与其他资源。
- [ ] 投资比例、收益分配、IP 权利和控制权需要彼此区分，不能默认同一比例。
- [ ] 项目结束后委员会停止活动，但合作方关系和历史结果可留在公司。
- [ ] 旧商业审计发现规则较丰富但代码实现不完整，必须重建数据契约，不应把“文档有规则”误认为“运行时已实现”。

**处理结论：** Committee 作为 Project 的子域/关联实体；Partner/Relationship 作为 Company 长期资产；项目结束时保存委员会结算快照与合作结果。

## 4. 可复用设计与方法清单

以下是可迁移的设计思想或验证方法，不代表旧实现与参数可以原样复用。

### 4.1 制作与质量

- [ ] **工作量与质量分离：** 工作量描述完成了多少生产任务；质量描述成果水平。二者相关但不等价。
- [ ] **阶段性质量：** 前期阶段产出影响后续制作，后期不应无限修复前期缺陷。
- [ ] **作品质量与商业表现分离：** 商业成绩还受 IP 基础、渠道、市场时机、宣传、合作结构和成本影响。
- [ ] **阶段能力权重：** 不同阶段使用不同能力组合；可复用旧排班实验中的权重建模方法，重新校准权重。
- [ ] **管理能力影响协作效率：** 可影响计划执行、协调损耗或波动，但不要重复计算为所有专业岗位产能。
- [ ] **工作历史可追溯：** 每周记录投入、产出、质量变化、成本、人员贡献和随机结果，支持作品复盘与成长。

### 4.2 随机性与模拟

- [ ] 工作量与质量使用不同随机过程或随机流，避免一个随机值同时决定多个结果。
- [ ] 能力提升期望表现并降低波动，而不是只提供线性数值加成。
- [ ] 随机结果在周结算时揭晓；玩家看到的是风险、趋势和可能后果，不是精确未来结果。
- [ ] 采用固定 seed 与输入快照支持回放、对比和回归测试。
- [ ] 对极端结果设置合理边界，避免连续坏运气或单次随机直接摧毁经营。
- [ ] 实验先验证趋势、相对关系和边界，再校准具体数值。

### 4.3 资源分配

- [x] **负责人已确认：核心员工严格单项目周分配，不允许主项目外的同周支援、借调或拆分工时。**
- [ ] 普通员工、临时员工、外包产能应有不同占用和成本语义。
- [ ] 外包作为外部产能合同，需要容量、预留、交付、成本、可靠性与违约记录。
- [ ] 资源竞争结果应能被玩家看懂：谁被占用、哪个项目缺口、付出什么代价。
- [ ] 不用小数工时和大量滑块制造无意义微操。

### 4.4 财务与审计

- [ ] 采用统一现金流水账作为真实资金变动来源。
- [ ] 项目账是归因与分析视图，不是独立资金账户。
- [ ] 同一周内对工资、运营费、项目投入、外包、投资、收入与分账进行统一预检和事务提交。
- [ ] 为关键资金变动记录来源、对象、所属项目、发生周、金额和原因。
- [ ] 保留独立对账脚本的思路，但重写输入适配层，使其面向新领域模型。
- [ ] 财务测试应覆盖跨项目重复扣费、收入遗漏、分账比例、资金不足、事件阻塞与失败回滚。

### 4.5 可玩性与反馈

- [ ] 作品应当持续提供明确目标：接案、开发、制作、交付、形成代表作或系列。
- [ ] 公司成长必须改变未来选择和生产能力，而不只是经验/声望数字上涨。
- [ ] 项目完结后留下可感知资产：作品履历、IP 基础、市场反馈、合作关系、员工经验。
- [ ] 复杂系统不等于好玩；低价值的重复管理应自动化或压缩。
- [ ] 结果反馈应解释“为什么”：企划、人员、制作方针、资源冲突、渠道与市场分别贡献了什么。
- [ ] 探索空间与可学习性并存：玩家可以发现策略，也能通过报告、历史作品和帮助逐步理解机制。
- [ ] 中文版本/平台/版本号需可追踪；研究竞品时区分官方描述、社区实测、个体体验和运营层功能。

## 5. 必须建立的领域实体与责任边界

| 实体/模块 | 唯一职责 | 核心数据责任 | 不应承担 |
|---|---|---|---|
| Company | 长期经营主体 | 当前周、现金池、固定成本、声望、员工、供应商关系、设施、经营状态 | 单个项目的制作细节 |
| Project | 单部作品的制作与交付 | 阶段、企划、目标、计划、工作量、质量、风险、项目账归因、生命周期 | 公司总现金和全局时间 |
| Staff | 公司员工资产 | 能力、潜力、经验、状态、雇佣关系 | 项目制作状态与周度分配结果 |
| StaffAssignment | 周度人员分配事实 | 单一项目归属、实际参与、能力贡献与冲突 | 长期员工档案 |
| Supplier | 外部供应商/合作产能 | 专业范围、容量、可靠性、合同与履约历史 | 内部员工状态 |
| SupplierReservation | 周度外包产能预留 | 项目预留量、成本、交付窗口、冲突 | 供应商长期关系档案 |
| Committee | 单项目合作组织 | 成员、投资、资源贡献、权益、渠道、决策约束、结算快照 | 公司长期合作关系本体 |
| PartnerRelationship | 公司长期合作资产 | 合作历史、信任、履约、可复用资源与邀请条件 | 某项目当前委员会状态 |
| Market | 外部机会与需求环境 | 企划机会、市场趋势、发行/渠道条件、时间窗口 | 直接修改项目制作状态 |
| Event | 具有作用域的突发/机会事项 | 归属对象、触发、期限、选项、效果、阻塞范围 | 绕过周结算直接推进时间 |
| WorkHistory | 制作过程事实记录 | 每周工作、人员贡献、随机结果、成本与质量变化 | 作为可随意覆盖的当前状态 |
| LedgerEntry | 资金变动事实 | 金额、方向、来源、对象、项目归因、发生周 | 代替项目预算与商业合同 |
| WeeklySettlement | 全公司周推进事务 | 预检、资源锁定、费用结算、项目推进、事件时钟、员工状态、回执 | 具体业务规则的长期存储 |

**数据唯一来源要求：**
- Company.cash 是当前现金余额的投影；LedgerEntry 是现金变动的事实来源。
- Project 的成本/收入汇总由 LedgerEntry 按项目归因得到，不另造一套可独立修改的资金余额。
- 员工当前状态属于 Staff；某周唯一项目归属与实际贡献属于 StaffAssignment/WorkHistory。
- 项目当前进度是当前状态；每周推进事实写入 WorkHistory，不能仅靠覆盖当前进度丢失历史。
- 事件定义与事件实例分离；事件实例必须有明确作用域。
- 委员会当前成员/权利属于项目委员会；历史结算快照在项目结束后不可被后续合作修改。

## 6. 周结算必须满足的系统不变量

- [ ] 全公司只有一个周推进入口；任何事件、菜单、项目动作不得自行增加周数。
- [ ] 一次推进覆盖所有符合条件的项目，项目间不因遍历顺序改变结果。
- [ ] 周结算开始前完成资金、人员、外包容量和项目状态预检。
- [ ] 共享资源在结算前锁定，禁止跨项目重复占用。
- [ ] 所有固定成本与时间成本按同一时间边界结算；事件暂存不得跳过。
- [ ] 资金扣款、收入入账、项目状态、员工状态、事件时钟和周数更新具有一致的事务边界。
- [ ] 若结算失败，不允许留下“周数已增加但工资未扣”或“项目已推进但现金未更新”等半完成状态。
- [ ] 项目结束/暂停/等待事件时，是否继续承担成本必须由明确规则决定，不能由代码分支偶然决定。
- [ ] 同一随机 seed 与同一输入快照应得到相同模拟结果。
- [ ] 结算结果提供可解释的摘要：计划、实际资源、工作量、质量、成本、风险与事件变化。
- [ ] 520 周最后一周完成统一结算后，再按终局规则处理未完成项目与公司状态。

## 7. 事件系统迁移检查

- [ ] 事件作用域至少区分 Company 与 Project；是否需要 Staff/Partner 级事件由具体玩法决定。
- [ ] 事件阻塞范围明确：全公司阻塞、单项目阻塞或不阻塞。
- [ ] 项目事件不能无意冻结其他项目。
- [ ] 公司级重大事件不能被项目级事件队列覆盖。
- [ ] 多事件同时发生时有稳定的排序/合并/延后策略。
- [ ] 暂存事件保留触发周、期限、已延后次数和恢复条件。
- [ ] 事件选择只提交业务动作，不直接改周数；实际时间成本统一由 WeeklySettlement 处理。
- [ ] 事件效果必须进入相应账本/状态历史，支持复盘和测试。
- [ ] 重做 M2-a/M2-b 时补充“事件暂存前后工资、运营费、制作结算连续性”回归测试。

## 10. 不作为当前待决事项的问题

以下内容已有明确方向或可以先按重构裁定处理，不再逐项打断框架设计：

- 玩家经营公司而非委员会。
- 公司和项目双层主体。
- 多项目同时推进，项目状态独立。
- 公司统一时间步，周推进覆盖全公司。
- 公司统一现金池，项目账用于归因。
- 项目级委员会、公司级长期合作关系。
- 项目计划与共享资源分配分离。
- 事件不能绕过统一周结算。
- 研究与实验参数不能未经验证成为正式规则。
- 首版避免逐镜头制作、逐人逐小时排班、复杂竞争公司 AI、复杂委员会投票和大量低价值微操。

## 11. 后续重构任务清单与验收门槛

### 阶段 A：领域模型与系统边界（当前阶段）
- [ ] 明确 Company、Project、Staff、Supplier、Committee、PartnerRelationship、Market、Event、WorkHistory、LedgerEntry、WeeklySettlement 的关系图。
- [ ] 为每个实体指定唯一数据所有者与生命周期。
- [ ] 明确公司级状态与项目级状态字段清单。
- [ ] 明确员工、外包、资金、管理能力的共享资源占用规则。
- [ ] 明确项目关闭、委员会解散、合作关系沉淀和历史快照规则。
- [ ] 形成数据模型文档和关键状态迁移图。

**验收：** 不再出现同一数据在 Company/Project/Committee 多处独立维护；任何模块都能说明数据归属、读写权限和生命周期。

### 阶段 B：统一周结算契约
- [ ] 定义周结算输入快照、预检、资源锁定、项目计算、公司成本、事件时钟、写回和回执。
- [ ] 定义资金不足、资源冲突、项目暂停、事件阻塞、项目完结等边界。
- [ ] 定义随机 seed、随机流和回放输入。
- [ ] 定义事务失败与回滚行为。
- [ ] 定义项目遍历顺序不影响结果的测试。

**验收：** 同一输入快照可复现；项目顺序改变不影响总结果；任何失败不会留下跨模块半结算状态。

### 阶段 C：最小可运行模拟器
- [ ] 先只实现 Company + 多个 Project + StaffAllocation + LedgerEntry + WeeklySettlement。
- [ ] 用极少量员工和两到三部不同阶段作品验证资源冲突。
- [ ] 验证工作量、质量、随机性、现金流和员工成长的闭环。
- [ ] 不先加入复杂事件、设施树和完整委员会谈判。

**验收：** 能连续运行多周、多项目；能解释每周结果；不存在重复占用或跳过成本；能通过固定 seed 回放。

### 阶段 D：逐模块迁移
- [ ] 员工与组织。
- [ ] 项目制作与质量。
- [ ] 财务与商业结算。
- [ ] 委员会与长期合作关系。
- [ ] 市场与项目机会。
- [ ] 事件系统。
- [ ] UI 与报告。

**验收：** 每个模块通过新领域契约接入，不直接写入其他模块的私有状态；跨模块行为由应用服务/周结算协调。

## 12. 验证测试目录（重构后必须覆盖）

- [ ] 两个项目争夺同一核心员工时，不重复获得完整能力。
- [ ] 两个项目争夺同一供应商产能时，不重复预留。
- [ ] 多项目同周结算时，交换项目顺序不会改变公司总现金与项目结果。
- [ ] 某项目暂停/等待事件时，其他项目按其状态继续推进。
- [ ] 公司级事件与项目级事件同时存在时，作用域不互相覆盖。
- [ ] 暂存事件不会跳过工资、运营费、制作和其他时间成本。
- [ ] 项目计划投入高于实际资源时，结果能解释缺口与后果。
- [ ] 现金不足时，不出现部分项目已推进、其他项目未推进的半结算。
- [ ] 委员会结束后停止活动，但合作方关系与历史快照保留。
- [ ] 项目收入、投资、成本、分账与公司现金流水账能够完全对平。
- [ ] 同 seed 同输入可复现；不同随机流不会因调用顺序改变而串扰。
- [ ] 520 周最后一次结算后，终局清算只执行一次。
