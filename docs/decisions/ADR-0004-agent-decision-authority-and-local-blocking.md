# ADR-0004：未冻结细节的默认决策权与局部阻塞

## 背景

在首版并行开发中，智能体和模块负责人频繁将“没有单独冻结决策”报告为阻塞，即使问题只是模块内部实现选择、可由现有规则推导的行为，或低风险且可逆的局部细节。这使总负责人变成所有实现决定的人工审批节点，也让一个局部未决项扩大为整个模块等待。

此前的协作原则强调不得擅自改变产品规则、公共契约和权威边界，但部分任务说明将其过度解释为：任何没有明确冻结文本的决定都必须暂停并上报。

## 决定

1. **没有冻结决策本身不构成阻塞。** 执行者先检查 DECISION_LOG、领域架构、契约文档、当前 main、现有测试和真实调用。
2. **已有规则可推导时直接实现。** 不重复提问，不要求为已明确的行为再次审批。
3. **模块内实现选择由模块负责人自主决定。** 前提是不改变产品语义、玩家可见行为、经济结果、既有契约、跨模块状态权威或失败原子边界。
4. **低风险未决细节采用临时假设继续推进。** 假设必须局部、可逆、影响可控，不改变玩家可见行为或经济结果；在 Issue/PR 中标记 `ASSUMPTION`，说明依据、理由、影响范围、回退方式和待验证点。临时假设不等于冻结规则。
5. **实质性问题必须升级裁决。** 包括冻结规则冲突、玩家可见行为或经济结果变化、既有字段/命令语义或兼容性变化、状态权威归属变化、Finance/Archive 权威数据、随机协议、命令原子边界及重大安全/数据风险。
6. **阻塞必须局部化。** 只暂停直接依赖该裁决的最小代码路径或验收项。其他可独立推进的实现、测试、文档核对和跨模块工作继续进行。
7. **阻塞报告必须可处理。** 写明已有依据、真正缺口、受影响的最小范围、为何不能由模块负责人决定、推荐方案/备选方案，以及等待期间仍可推进的工作。不得仅以“缺少冻结决策”或“等待确认”作为阻塞理由。
8. **并行依赖按候选接口推进。** 消费方可反推最小接口，生产方同步实现；接口差异局部修订。最终仍须以真实生产者实现完成集成验证，Mock 不得冒充真实接入。

## 后果

- 模块负责人和智能体获得既定规则范围内的判断权，总负责人只处理真正的全局规则与契约裁决。
- Issue/PR 应区分已冻结规则、可推导行为、模块自主选择、临时假设和待裁决事项。
- 临时假设需要可追溯、可回退；如果后续证据显示它影响产品规则或契约，必须停止相关路径并升级。
- 不改变任何玩法规则、数值、状态字段、命令、存档格式或里程碑出口标准。
- 相关执行规范同步见 `ENGINEERING_CHANGE_GOVERNANCE.md`、`OPEN_INCREMENTAL_DEVELOPMENT_POLICY.md`、`TEAM_ASYNC_COLLABORATION.md` 和 `CONTRIBUTING.md`。

## 替代方案

- **所有未冻结事项一律等待总负责人确认：** 否决。会制造大量人工审批和串行等待，且不符合模块自治。
- **允许智能体自行决定所有未冻结事项：** 否决。可能越权改变玩家行为、经济结果、既有契约或权威数据。
- **仅允许继续无争议工作，不允许临时假设：** 否决。会使大量低风险、可逆细节仍然形成不必要的局部等待。
