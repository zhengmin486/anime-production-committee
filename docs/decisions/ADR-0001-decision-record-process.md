# ADR-0001：决定记录与文档改动流程

## 背景

仓库里同时存在决定文件、研究文件、规则文件、玩法文件和计划文件，且一天内可能多次变更。当前状态有三个具体问题：

1. **同一口径有多份表述**。规则文件、进度文件和审查报告都可能写出“当前规则”，读者无法判断哪份有效。
2. **决定不可追溯**。口径改变后，旧表述被就地改写，看不出改了什么、为什么改、谁确认的。
3. **研究与规则混用**。研究结论和建议容易被后来者当成已确认规则直接实现。

`docs/README.md` 已经区分了“规则 / 研究 / 审计”的阅读顺序，但缺少对**改动方式**的约束，所以随着提交累积仍会重新混乱。

## 决定

1. 决定分两类：规则内容继续写入 [决定登记册](../DECISION_LOG.md) 的 `DEC-*` 条目；流程、治理与契约级决定写入 `docs/decisions/ADR-*.md`。
2. ADR 一旦 `accepted` 即冻结正文。后续变更必须新建 ADR，并在新文件中用 `supersedes` 指向被替代的编号。
3. 规则、协议、架构文档修改时，PR 必须引用对应的 `DEC-*` 或 `ADR-*`；纯措辞与断链修正除外，但要在 PR 中写明“仅措辞”。
4. 研究文件与审查文件只写证据、结论和建议，不得声明“规则已变更”；规则变更只能发生在决定文件里。
5. 文档改动提交前运行 `npm run check:docs`，检查决定文件的结构字段、编号引用和本地链接。
6. 本次不移动现有文档目录。目录调整属于另一项独立变更，需单独评审，避免与在途 PR 冲突。

## 后果

- 规则与研究、审查的边界由文件位置和字段共同表达，而不是靠读者自行判断。
- 每次口径变化都会留下一条可检索的记录，代价是新增了一条“先写决定再改文档”的流程要求。
- `check:docs` 只能校验结构与链接，不能判断结论是否正确；评审仍需人工确认。
- 现有文档不需要一次性补齐 front matter，避免与在途分支产生大面积冲突。

## 替代方案

- **一次性重排全部文档目录**：能立刻得到整齐结构，但会与当前多个在途 PR 冲突，且无法解决“决定不可追溯”的问题。否决。
- **只在 PR 模板加一句提醒**：成本最低，但没有可检索的决定记录，也没有自动校验，历史上已经证明会退化。否决。
- **把所有内容合并成单一规则文件**：会丢掉研究与审查的证据链，且文件过大难以评审。否决。
