# ADR-0005：文档权威、口径冲突与冲刺期决策闭环

## 背景

并行开发期间，执行者可能同时读到决策登记册、架构/契约、模块文档、Issue、PR、历史记录和代码中的不同表述。差异不总是“缺少决策”：也可能是旧文档未同步、同一规则被多处复制、决策只更新了一部分，或两条已确认决定存在细微交叉冲突。

如果把所有差异都交给执行者自行选择，可能将过期文档误当成规则；如果所有差异都上报项目负责人，又会重新形成串行审批瓶颈。本 ADR 与 ADR-0004 配套，规定文档权威判断、冲突分类和冲刺期执行闭环。

## 决定

### 1. 按信息所属领域确定权威来源，不按文件新旧简单排序

执行者先识别问题属于哪一种信息，再使用对应的规范来源：

| 信息领域 | 规范来源 | 其他材料的定位 |
|---|---|---|
| 已确认玩法规则、数值与产品行为 | `docs/DECISION_LOG.md` 中现行有效的 `DEC-*` | 玩法、规则、审计和研究文档只能解释、引用或提供证据 |
| 架构边界、领域归属与系统结构 | `docs/DOMAIN_ARCHITECTURE.md` | 模块设计稿和架构审查不得自行覆盖 |
| 状态、命令、错误、事务、存档等底层契约 | `docs/M0_CONTRACT_FREEZE.md` 及其明确登记的后续契约修订 | API、数据字典和实现必须与契约同步 |
| 流程、协作、Agent 权限与工程变更治理 | `docs/decisions/ADR-*.md` 中 accepted 的 ADR | 团队说明和任务说明负责引用，不另造一套流程 |
| 当前实现、测试与阶段状态 | 当前目标分支代码、CI/测试证据及 `docs/PROGRESS.md` | PR 描述、旧进度快照和本地自述不能替代远程证据 |
| 任务范围与交付验收 | 当前有效 GitHub Issue；PR 负责说明具体实现和验证 | Issue/PR 不得改变上位规则或契约 |

`docs/README.md` 是导航入口，不是另一个规则源。代码现状不自动高于正式规则；旧分支、旧 PR、历史讨论和研究建议不自动具有当前权威性。

用户在当前协作中明确作出的新裁决，在进入规范来源前可作为本轮工作的直接依据；负责执行的人必须将其登记到对应的规范文件，并同步受影响引用，不能让口头/聊天裁决长期成为仓库外的隐形规则。

### 2. 判断冲突时，先确认来源关系，再判断时间

- 明确标记为 `superseded`、被后续 DEC/ADR 替代或仅供历史参考的内容，不再作为当前口径。
- 同一领域的正式决定存在明确 `supersedes`、废止或修订关系时，按该关系执行。
- “文件更新时间较新”本身不能覆盖更高权威来源；Issue/PR 最近更新也不能自动覆盖 DEC/ADR。
- 若两个正式有效决定没有明确替代关系，且对同一行为给出不兼容要求，视为实质冲突，不允许执行者自行按个人偏好或简单的时间先后选边。

### 3. 冲突分级与默认处理

**A 类：表述差异。** 术语、示例或文字不同，但行为、数值、状态边界和责任归属一致。执行者可自行统一措辞、补充规范来源链接，不需上报。

**B 类：过期副本或版本差异。** 某份模块文档、Issue 描述或历史计划仍保留旧口径，而规范来源及替代关系清晰。以规范来源为准，执行者负责修正文档或标记其历史/废弃状态，并检查同一机制的其他引用点。不得只修自己当前打开的文件而留下已知旧口径。

**C 类：实质性决策冲突。** 两项现行正式决定、正式决定与未登记的明确裁决，或两个规范契约之间存在无法推导消解的行为差异。执行者不得自行选择；必须提交最小冲突说明、证据、影响范围、推荐裁决及备选方案。只暂停直接依赖冲突的最小实现/验收范围，其他工作继续。

### 4. 规则与文档采用单一规范定义，其他文件引用而非复制

- 每个重要规则、契约或治理主题应有明确的规范来源；其他文档优先引用 DEC/ADR/架构/契约编号和链接。
- 必须重复展示的摘要，应标明“摘要/派生说明”，并注明规范来源；不得在多个文件中各自维护一套可独立生效的规则文本。
- 修改正式规则时，先更新对应规范决定，再同步受影响的架构、契约、模块说明、Issue、测试和进度状态。
- 不为追求整洁而大规模搬迁文档；优先修复当前任务涉及和已发现的冲突，保持历史链接稳定。
- 旧内容需要保留时，明确标注历史基线、适用版本、被替代关系或“非权威参考”，不静默删除历史证据。

### 5. 任务启动前执行轻量口径核对

每个任务不要求通读全仓库。执行者只需针对本任务涉及的规则、字段、状态、公式、命令和调用方：

1. 查看当前目标分支基线与相关 PR/Issue；
2. 找到对应 DEC/ADR、架构和契约规范来源；
3. 检查模块文档、测试、代码和 UI 是否存在不同数值、枚举、状态边界、时序或所有权口径；
4. 将差异归类为 A/B/C；
5. 无 C 类冲突则按规范来源继续；发现 B 类则同步修复；发现 C 类则局部升级裁决。

新增且不影响既有字段、行为和公共契约的独立字段，可由模块负责人按 ADR-0004 自主处理。修改既有字段语义、可空性、枚举、命令、存档、计算公式或跨模块所有权时，必须核对所有生产者、消费者和验证依据。

### 6. 责任归属与闭环

- **模块负责人**对本模块规则引用、字段/状态口径和模块文档的一致性负责；发现旧文档时主动修正或标记，不把维护责任推给总负责人。
- **正式决定修改者**负责更新对应规范来源，并列出受影响文档、Issue、测试和调用方；不要求用户逐个提醒同步。
- **Issue/PR 作者**负责保证任务描述不与规范来源冲突，并在发现冲突时链接权威依据。
- **项目负责人**只裁决 C 类实质冲突、冻结规则变更和跨模块关键取舍，不逐条审批措辞、过期副本修正或低风险模块内选择。
- 冲突修复后，PR/Issue 应记录采用口径、修正位置和仍未同步的明确例外；不能以“已讨论”代替实际同步。

### 7. 冲刺期授权与最小交付

截至首版截止时间 **2026-11-30 18:00**，在不改变冻结规则、核心架构、公共契约、经济权威数据和存档兼容边界的前提下：

- Agent 和模块负责人按 ADR-0004 取得模块内默认决策权；不要因未冻结细节、表述差异或可明确识别的旧文档而等待用户。
- 方案选择优先满足完整主流程和既定玩家功能，再简化实现复杂度。**最小实现不等于删减已确认功能、用占位替代真实流程，或把原定首版能力擅自延期。**
- 对局部、可逆的假设，在对应 Issue/PR 标记 `ASSUMPTION`，写明依据、理由、影响、回退方式和待验证点；不必为每个低风险细节另开审批或单独决策文件。
- 模块负责人对新增字段可自主处理；修改既有字段/契约必须检查上下游影响，并按工程变更等级升级。
- 如果一个问题存在 C 类冲突，隔离受影响的最小范围；不要因此停止无关模块、测试、文档核对或可独立集成工作。
- 已按现有规则和授权完成、测试合理且不违反契约的方案，不得仅因其他成员偏好不同而要求重新裁决或重写。

本节冲刺时限届满后，恢复正常里程碑与验收节奏；ADR-0004 的一般性模块自治、文档权威和局部阻塞原则继续有效。

## 后果

- Agent 在执行前能区分“没有决策”“文档过期”和“正式决策相互冲突”，减少错误实现与无效上报。
- 模块负责人承担本模块的文档一致性维护，总负责人不再成为所有文档同步的人工中转站。
- 正式决定仍有单一规范入口；摘要和任务说明通过引用保持一致。
- 冲突处理增加一次有目标的核对，但不要求全仓库扫描或全员重复阅读全部资料。
- 本 ADR 不修改任何玩法规则、数值、运行时字段、命令、存档格式或里程碑验收标准。

## 替代方案

- **简单规定“最新文档优先”：** 否决。新近更新的 Issue、审计报告或模块副本可能仍无权覆盖正式决定。
- **所有冲突一律上报项目负责人：** 否决。表述差异和过期副本可按明确权威来源自行修复。
- **允许 Agent 自行选择最合理口径：** 否决。可能把两项正式有效决定的实质矛盾伪装成实现细节。
- **一次性重写或重排全仓库文档：** 否决。冲刺期间成本高、易与在途 PR 冲突，也不解决后续维护责任。
