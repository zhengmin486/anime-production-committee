## 0. 结论速览

1. **审视开始时存在两套不一致口径**：仓库冻结并实现的是「整部作品五阶段串行」（口径 A）；「公共制作 + 单集六阶段」（口径 B）当时只存在于讨论，尚未进入仓库文档/契约/议题。本文现将 B 整理为方案 C；**C 若采纳仍属架构级变更，不是参数调整**（§1.1、§4.2）。
2. **公司级多作品并行已是重构框架基线**（2026-11-24 合入 main，[负责人已确认]）：不设固定槽位上限，由资金/人员/外包/管理自然约束；统一周推进、共享资源账本、项目级委员会。这与「作品内单集化」是**两条正交的轴**——前者决定公司同时做几部作品（框架已定），后者决定一部作品内部如何组织（框架保留整部五阶段，本文方案 C 提出异议）；两轴共享「公司级/项目级状态分离 + 共享资源账本」前置（§1.1、§4.2、§4.4）。
3. **行业结论**：真实 TV 动画是「项目级公共准备 + 多集错峰并行 + 集内按 cut 流转」的三层结构；公共准备与单集是解锁+供给关系而非先后关系；制作管理（制作进行/デスク）是产能核心；整集外包（グロス）是题材辨识度高且现有设计完全缺失的机制（§2）。
4. **案例结论**：成熟制作型游戏的共识是「过程模拟要粗，决策颗粒要准」——单作品内部串行自动是主流，并行放在单元级（多集/多部）或公司级；决策集中在开工配置、里程碑事件、完成后打磨；微操过多与概率可 S/L 是明确差评来源（§3）。
5. **作品内架构：V1 按重构框架执行（整部五阶段 + 多项目 + 计划机制）；方案 C（公共制作 + 单集单元 + 小组化）作为题材差异化的最强候选，提请负责人裁定是否修订框架或留待后续里程碑**。C 复用现有五阶段作单集流水线、小组制 + 沿用默认 + 里程碑事件控制决策密度，行业与案例证据从两个方向支持该结构，但与框架 §11「首版不做逐集模拟」冲突，须由负责人拍板（§4.2、§5 Q1）。
6. **八条跨架构设计判断**（公共资产解锁+上限+后补、retake 回路、management 系统性发力、跨集质量统一、声音解耦、背景折叠、分级止损、组织方式涌现）无论架构如何选择都值得讨论（§4.3）。
7. **顺带发现的现有问题**：M1 暂定质量权重与已确认「前重后轻」口径矛盾（远程 main 代码仍是 150/200/250/200/200）；management 能力被边缘化（§1.3）。
8. **文档权威**：重构框架是当前最高层设计基线（其 §14），本文是下位研究输入；与框架明确冲突的是方案 C 的作品内架构主张，已列为 Q1 待裁定。其余提案按研究输入保留：retake、management、分级止损可进入现有 WP2/WP3/WP7；グロス、总集篇等依赖单集架构的条目只在 Q1 选 C 时生效，均不是已确认规则。

## 1. 现状盘点：仓库里实际存在的制作系统

### 1.1 两套口径并存，且不一致

审视开始时仓库中存在两套「制作系统」口径，必须先区分：

| 口径 | 内容 | 载体 | 状态 |
| --- | --- | --- | --- |
| A. 整部作品五阶段串行 | script → storyboard → key_animation → animation_check → postproduction；阶段首配置锁定、阶段内自动推进、阶段不并行 | GAME_DESIGN §5、GAME_RULES V3.1 冻结项、DATA_MODEL V3.4 不变量 3、M1 C++ 实现（议题 #4 已验收） | **已冻结、已实现**；其中「一次一部作品」已被负责人 2026-11-24 方向覆盖（见下），其余仍有效 |
| B. 公共制作 + 单集单元 | 项目级公共制作达到最低交付要求后解锁单集；单集六阶段（内容设计→分镜与原画→动画制作→美术与视觉→摄影剪辑→声音交付）；单集异步推进、工序允许并行 | 近期会话讨论；本文整理为方案 C（§4.2） | **研究提案已形成**；未进入契约、议题或重构框架，且与框架首版范围冲突 |

这个差异本身就是审视的第一个发现：**B 方案若被采纳，是对已冻结契约和已验收实现的架构级变更，不是参数调整。** DATA_MODEL V3.4 不变量 3 明确「阶段不并行，完成后下一阶段 ready」；ProjectOffer.workloads 是整部作品一份五阶段工作量向量；TV 与剧场版在模型中除数值外没有结构差异。任何单集化方案都需要契约负责人裁定契约修订，并评估 M1 实现、校验器、夹具与浏览器测试的迁移成本。

**必须区分的两条轴（2026-11-24 修订新增）：**

- **公司级多作品并行**：已是重构框架基线（§3.2 [负责人已确认]、§4 [框架裁定]）。作品审计 §6 列出的 11 个待决问题中，框架已给出方向性答案：周推进=全公司统一动作（§2.3）、共享资源四类与主分配+支援（§4.2）、事件归属项目+每周限量（§5.5）、统一预检与原子结算（§9.2）、520 周统一收尾（§9.4）、委员会项目级临时组织（§3.4）、系列允许分支（§8.2）。**仍待负责人拍板的是工作流拆解 D1–D6**（员工支援边界、计划自动化边界、并行硬上限、设施地位、随机强度、资金危机处理），其中 D1/D2/D6 被列为最小先行决策集。
- **作品内单集化（口径 B/C）**：重构框架 §5.1 保留整部五阶段骨架、§11 明确首版不做逐集模拟。本文方案 C 与该基线冲突，作为研究提案提请裁定（§5 Q1），不是默认方向。

两者正交：可以「多作品 + 整部五阶段」（框架现状），也可以「单作品 + 单集化」，或两者叠加。但**叠加时复杂度相乘**（公司×作品×单集三层调度），且共享同一前置——公司级/项目级状态分离与人员、供应商、周成本的共享资源账本（作品审计 §7、工作流拆解 WP0/WP2/WP3）。本文推荐：先按框架落公司级多作品的状态与账本基础（WP0→WP2→WP3→WP4），作品内架构按 §5 Q1 裁定；若未来选 C，单集单元天然成为多作品调度中的资源竞争颗粒，两轴互相增强而非互相冲突。

### 1.2 口径 A 的已确认规则与实现细节

以下均为仓库已核实内容（远程 main 文档 + 代码 + 议题验收记录）。注意区分「规则口径已确认」与「行为已实现」：远程 GAME_RULES V3.9–V3.13 的多数商业/竞争/系列规则**尚未实现**（作品审计 §4），本文引用时按规则口径对待。

- **时间**：周制，520 周经营；「一次一部作品」限制已废止（重构框架 §3.2），多项目统一周推进（§2.3），行为尚未实现；阶段内按周自动推进，不逐周微操。
- **阶段配置（历史实现）**：阶段开始（ready）时一次提交 assignments/policy/overtime，转 active 后常规配置锁定（STAGE_LOCKED）；事件提供受控改配例外。**重构框架 §5.2 已将其改为「持续方针 + 周度调整」计划机制**（[框架裁定]：默认沿用上周、不要求每周重设；维度建议为投入强度/项目优先级/外包策略/赶工开关），旧锁定语义在迁移完成前仍描述 M1 实现。
- **随机工作结果（框架新增方向）**：重构框架 §5.4 [负责人已确认的近期方向]——周产出有随机波动、质量从阶段相关维度中抽取若干项改善、幅度有区间、可能因返工/赶工/外包损失；结果可解释、同 seed 可复现、界面不提前泄露。具体强度待 D5 裁定。本文 §3.3 的防 S/L 与种子纪律证据支持该方向。
- **三维数据**：工作量（work_total/work_done）、阶段质量（0–100）、完成度（work_done/work_total 隐含）分离；质量按产出批量加权。
- **质量传递**：有限传递——本阶段质量 ≤ 前阶段质量 × 0.6 + 40（[game_rules.hpp](https://github.com/zhengmin486/anime-production-committee/blob/4d62bb3/packages/game-core/include/game_rules.hpp) carry_over_permille/offset）；前阶段未完成时不封顶。
- **产能公式**：speed = 90 × ability × fit(1200/800) × policy.speed × (600 + 4×morale) × (1000 − 4×fatigue)；同专业边际递减提案 1000/800/600/400‰（V3.6，待 #4 校准）。
- **方针三档**：quality/balanced/deadline，影响速度、质量、士气消耗与周生产成本。
- **六能力**：planning/direction/drawing/animation/management/postproduction；岗位、能力、阶段三维度独立。阶段能力权重提案（V3.6）：script=planning700+management300；storyboard=direction800+planning200；key_animation=drawing850+direction150；animation_check=animation700+drawing300；postproduction=postproduction850+management150。
- **外包**：供应商六属性（专业/容量/质量/速度/单价/可靠性）；外包专业须匹配且该能力在目标阶段权重 ≥300‰；普通外包阶段首确认，应急外包走事件受控通路。
- **临时员工**：weekly_salary=0、一次性 project_fee；V3.6 提案公式 project_fee = 同能力核心周薪 × 工期周数 × 1.3（TODO 待定，hire 时一次支付）；不培养、项目结束释放。
- **事件**（V3.9 §8 确认框架）：每周最多一个、同一时间最多一个待处理、表现+随机触发、暂停推进、即时/阶段/项目三类效果、不追溯已结算阶段、首版不做跨项目永久效果；重大事件入履历；处理方式含放弃/加班/应急外包/延期。
- **交付与结算**：整部作品一次交付；收入统一结算，不分批入账；承制扣罚、委员会渠道分账。
- **预算与投资口径**（V3.12，当前有效，覆盖本地旧「总投资×20%」口径）：contract_budget 即制作预算；仅委员会模式生成 total_investment = contract_budget × 2；承制不生成投资规模、不付投资本金。投资比例 10%–100%、按 10 个百分点调整；其他投资方共同补足剩余份额，不记录成员细分比例。开工时制作预算并入公司统一现金池；预算用尽后仍由公司现金承担，不中止制作。制作经营亏损与投资本金亏损分开核算。
- **商业渠道**（V3.9 §4 / V3.11 / V3.12）：BD 是所有企划基础渠道，承制与委员会统一按初始 50% 毛收入归公司、50% 计 BD 综合成本，独立于投资比例；委员会非 BD 渠道按玩家投资比例分配；承制不参与非 BD 分成，但商业表现达标可获委托方成功奖励。一个委员会成员对应一个渠道，加入即开放，渠道开放不由投资比例推导；无电视台成员时可付费购买播出服务（记 distribution）。爆款 ×5 作用于分账前渠道毛收入。channel_breakdown 逐渠道对账。
- **制作评价框架**（V3.9 §3）：五阶段质量综合为 0–100 最终质量；**阶段权重模板按规模选择、由前期向后期递减**（企划脚本＞分镜演出＞原画＞动画检查＞摄影后期）；作品评价 S/A/B/C/D 固定分数线；企划适配度为辅助因素、只影响评价不改质量；重大事故独立影响评价、可致作品彻底失败；制作评价与商业表现分离。
- **市场竞争**（V3.9 市场竞争节 / V3.13）：30 家竞争公司（固定大型+种子生成小型），不模拟其日常经营；每次玩家作品结算触发一轮竞争；NPC 质量 = 制作能力映射基础质量 + 均匀波动 [-30,+30]，上限 90（>90 只允许玩家后期作品）；玩家作品与竞争作品按商业收入排名，入榜数 ceil(N/2)，玩家最终名次写入作品历史（commercial_rank）。
- **作品系列**（V3.9 §6 / 市场竞争 §3）：同一 IP 可续作/前传/外传，经 previous_work_id 关联；最近三部前作按 BD 销量区间加权积累，映射 -1/0/1/2/3 档修正商业基础；换主要题材降一档；续作制作质量与评价独立计算、不继承前作质量；第一版不做系列市场疲劳。
- **委员会生命周期**（框架 §3.4）：委员会随单部作品成立，项目结算后停止活动并保留历史快照，合作关系可沉淀；剩余细化是未结分成、渠道收入与成员义务的归档边界（作品审计 §6.10、WP0/WP8）。

### 1.3 审视中发现的现有问题（与架构选择无关，先记录）

1. **M1 暂定质量权重与已确认口径矛盾**：远程 main GAME_RULES V3.9 §3 确认「常规模板权重由前期向后期递减」（script＞storyboard＞key_animation＞animation_check＞postproduction），但远程 main `packages/game-core/include/game_rules.hpp:51` 的 M1 暂定值仍为 150/200/250/200/200（中期最重）。代码标注 TODO(待定) 属 M1 暂定，但后续 #4/#8 校准时必须以确认口径为准，不能把实现值当设计依据。证据边界：INDUSTRY_RESEARCH §21 论文审查指出「没有行业证据支持按工序先后递减」——前重后轻是**游戏设计取舍**（前期决策杠杆大），不是行业事实，平衡文档应如此声明。
2. **management 能力被边缘化**：在 V3.6 权重提案中，管理只参与 script（300‰）与 postproduction（150‰），即「制作管理」能力几乎不影响制作产能。这与动画行业的现实（制作进行/制作 desk 是产能核心，见 §2）和经营游戏的直觉（管理岗应该影响组织效率）都不符。员工审计 §5 同样把「管理容量/管理跨度」列为 E 级缺口；并行会话的 STAFF_ORG_SYSTEM_DESIGN.md §4.2/§6.1 已提案把 management 改为团队乘数（管理跨度决定并行项目数、降低磨合、改善外包对接）。无论架构如何选择，都应给 management 一个系统性作用（见 §4.3-3），且两文口径应统一。
3. **TV 与剧场版结构同质**：口径 A 下 TV 只是「工作量更大、工期更长的单件产品」。动画行业里 TV 的多集并行生产组织（本作题材最有辨识度的部分）完全没有被表达。这是 B 方案讨论的根源，也是本次审视的核心问题。负责人 2026-11-24 多作品方向确认后，此问题更突出：若公司可同时做几部作品而每部内部仍是单件流水线，「动画公司」与「通用项目工厂」的体验差异将进一步缩小。
4. **「动画与作画检查」合并了动画制作与质量检查**：口径 A 第 4 阶段把「产出」与「检查」放在同一阶段，检查没有独立的返工/拦截语义；V2 历史实现曾有返工（质量<45 回退进度），V3 取消后只剩质量传递封顶。质量检查点是否应有独立机制，见 §4.3。

## 2. 行业研究：动画真实生产流程与组织方式

本节基于公开行业资料（来源见 §7），区分「行业普遍事实」与「个别公司特例」。目的不是复刻流程，而是找出对经营决策有意义的结构。仓库已有系统行业研究 `docs/INDUSTRY_RESEARCH.md`（origin/main，21 节，含十篇论文精读与文献综述），本节不重复其市场规模/公司财务数据，聚焦生产流程结构，与其 §4（供应链）、§15（制作周期/延期/外包产能）、§19–20（公司组织案例）互引。

### 2.1 一部 TV 动画的三层结构

现实中的 TV 动画（12–13 集季番）生产分三层，**不是整部作品一条串行流水线**：

| 层 | 内容 | 粒度 | 关键事实 |
| --- | --- | --- | --- |
| 企划层（製作） | 原作授权/原创企划、制作委员会、监督与预算、电视台档期 | 项目级 | 对应本作的企划选择与合作模式，已在现有设计中覆盖 |
| 公共准备（プリプロダクション） | 系列构成、角色/机械/小物设定、美术设定与美术板、色彩设计、音乐（BGM/OP/ED 曲）、音响监督与声优签约 | 项目级，整部共享、只做一次 | 与第 1 集分镜**并行**推进；是原画、仕上、背景三条线的共同输入 |
| 单集制作 | 脚本→分镜→演出/作打ち→Layout→作监修正→原画→（第二原画）→动画→动检→仕上→摄影→编集→アフレコ→ダビング→V编→纳品；背景与作画并行 | 单集级，多集错峰并行 | 单集周期明显拉长：过去约 3 个月、目前平均约 6 个月、较长可达 8 个月（2026 从业者访谈口径，非官方抽样均值，INDUSTRY_RESEARCH §15.1）；多个制作小组错峰并行推进数集（资料常见口径为 4–5 集），集间进度差约 1 周，保证每周出货 |

对游戏抽象最重要的四个结构性事实：

1. **公共准备与单集制作不是先后关系，而是解锁+供给关系。** 角色设定、色彩设计、美术板分别是原画、仕上、背景工序的输入；设定拖延会连锁推迟下游，是工期崩坏的常见起因。现实中允许「最低设定先行、后续滚动补充」，后补设定会引发返工——比「公共制作全部达标才解锁单集」的硬锁更真实，也更有经营意味。
2. **脚本是混合粒度**：系列构成（全话剧情框架）是项目级公共资产，各话脚本由多名脚本家分担、系列构成统一检查。把「内容设计」整体放进单集或整体放进公共制作都不准确。
3. **集内按 cut（镜头）流转，不是整段锁定。** 一集约 300 cut，每 cut 独立走过原画→动画→仕上→摄影；背景基本 1 cut 1 张、照 Layout 独立推进，与角色作画并行。但**逐 cut 模拟对轻量经营游戏没有意义**，用「集内完成度 + 瓶颈工序」近似即可保留错峰与返工的经营含义。
4. **声音与画面解耦**：アフレコ（配音）通常在画面未完成时用线撮（原撮/动撮/分镜撮）先行录制；BGM 是项目级资产，ダビング时贴入各集。声音不必等画面 100%，这给了工期抢救一条现实路径。OP/ED 影像独立于单集流程，常另组团队、晚启动、短工期。

### 2.2 工序职责、交付物与雇佣形态

| 工序 | 职责与交付物 | 依赖输入 | 典型雇佣形态 |
| --- | --- | --- | --- |
| 系列构成/脚本 | 全话框架；各话脚本 | 企划、原作 | 自由职业 |
| 分镜/演出 | 分镜（絵コンテ）、作打ち、单集演出处理 | 脚本、角色设定 | 社内核心或自由职业；各话演出轮替，是单集「小监督」 |
| 原画 | Layout + 原画（关键帧） | 分镜、角色设定、作监修正 | **几乎全是自由职业者**，按 cut 计价、档期争夺激烈 |
| 作画监督/总作监 | 逐张修正本集 Layout/原画；总作监跨集统一画风 | 原画 | 社内核心或资深自由职业 |
| 动画/动检 | 中间帧 + 动画检查 | 原画 | 大量外包（韩/中/越） |
| 仕上（色指定/彩色） | 上色 | 动画、色彩设计 | 大量外包 |
| 背景 | 背景美术（约 250 张/集） | Layout、美术设定/美术板 | 专门外包公司为主；**与作画并行** |
| 摄影（合成） | 图层合成、特效、镜头处理 | 仕上完成 + 背景 + 3DCG | 社内或专门外包 |
| 编集 | 剪辑锁尺 | 摄影素材（工期紧时可用分镜撮提前 offline 编集） | 专门外包 |
| 音响（アフレコ/ダビング） | 配音、混音 | 线撮即可，不必等成片 | 音响监督/声优项目级签约，执行按集 |
| 制作进行/制作 desk | 日程表、集人、催稿、素材流转 | 全工序 | **社内员工，产能核心** |

两个对游戏设计关键的行业结论：

- **首都圈主流公司社内常备的是管理线 + 少量核心创作，产能靠外部人才市场逐集拼装。** JAniCA 调查中自由职业/自雇长期占 5–7 成。京阿尼式全员内制是特例（且即使京阿尼，TV 工期下也会部分委托外部）。这意味着「内制 vs 外包 vs 混合」不是开关，而是**公司人员结构长期演化的结果**——游戏里应由核心名册构成自然涌现，而不是一个模式按钮。
- **制作进行/制作 desk 是稀缺的社内管理岗，决定能同时开几集、能否抢到画师档期。** 「优秀的作品始于良好的日程管理」是行业共识。现有设计的 management 能力只贡献脚本与后期少量权重（§1.3 问题 2），与行业现实严重不符。

### 2.3 组织方式：工程外包、整集外包（グロス）与内制

| 方式 | 现实含义 | 经营权衡 |
| --- | --- | --- |
| 工程外包 | 原画发自由画师；动画/仕上/背景发专门公司（韩/中/越） | 便宜、扩产能；质量与 retake 率参差、档期不可控 |
| 整集外包（グロス請け） | 演出→作画→美术→仕上→摄影整段交给另一家公司，音响后回元请 | 大幅释放社内产能；失去过程控制、风格统一风险、依赖对方可靠性 |
| 内制 | 全工序社内社员（京阿尼/ufotable 近似） | 质量稳定、管理成本低；固定成本高、产能弹性差 |

现有供应商系统（专业/容量/质量/速度/单价/可靠性）已经能表达工程外包；**グロス是现有设计完全没有、但题材辨识度极高的机制**——它只在「单集作为独立单元」的架构下才有意义，是支持单集化的一个有力论据。

### 2.4 产能、质量与工期风险的现实量级

- 一集约 300 cut、动画 3000–4000 张（高质量 5000–6000）、背景约 250 张、原画师 20–30 人、单集相关 staff 可达 150–200 人。
- 深夜档一集制作费约 2000 万日元，一季 12 集约 2.4 亿起（INDUSTRY_RESEARCH §9 有公开量级汇总）。本作 M1 暂定 TV **合同预算（即制作预算）** 3000–4000 万日元，比现实低一个数量级——应在数值平衡时明确声明为游戏轻量缩放，不是口径错误（见 §5 Q9）。委员会投资规模另按 V3.12 的合同预算×2 生成，不能把投资规模与制作预算混为同一缩放对象。
- 质量检查点链：作监修正→动检→仕上检→ラッシュ检查→V编+监督 OK。不合格贴リテイク表退回上游重做；**时间不够时作监来不及修正 = 作画崩坏**。retake 回路是「质量 vs 工期」张力的最小现实实现。
- 工期崩溃（万策尽きた）的分级止损：压缩张数/静止画 → 硬播半成品（BD 再修）→ 总集篇/重播续命 → 延期停播。前集延误挤压后集是连锁机制。这套「分级止损选项」比单一延期按钮更有戏剧性，且与现有事件系统（放弃/加班/应急外包/延期）天然兼容。
- **延期与成本传导**（INDUSTRY_RESEARCH §15.2，公取委 2026 指针）：前序工程延误导致后续延期、委员会成员/原作者意见导致返工、质量追求引起重做、追加宣传等合同外工作；延期补偿并非必然获得。设计含义：延期成本应与延期原因匹配（人力驻留/管理投入/返工），单纯日历时间变化不应自动等价于所有成本同比增加；延期适合做成项目风险而非每周必然惩罚。
- **外包不是无限产能池**（INDUSTRY_RESEARCH §15.3，TDB 2025/2026）：国内下游同样人手不足、可承接供应商有限、外包单价上涨；海外外包关系占比 41.8% 但不能视为低价随时可用的产能补充。设计含义：供应商 capacity 是稀缺资源，多项目同时外包时必须定义产能预留/锁定规则（作品审计 §6.4 待决）；这直接支持本作保留供应商容量与可靠性属性、拒绝「无风险外包」。
- 制作委员会：动画公司多数只收制作费、不出资不分红；公取委调查显示约 6 成元请公司仅靠制作费是赤字。本作「承制 vs 委员会投资」的双路线正是对这一现实的正确抽象，**应保留**。论文证据边界（INDUSTRY_RESEARCH §21，吉见 2025）：委员会购买播出时段、播出本身不直接产生委员会收入（对应本作 buy_tv_service 设计）；制作公司成功报酬存在但确认晚、不确定高（对应承制成功奖励设计）；**50% BD 分成与「承制商业分成为零」都不是行业通则**，属游戏抽象，平衡文档不得引用为行业惯例。

### 2.5 行业事实 → 游戏抽象的取舍

**值得抽象**（有经营决策意义）：公共准备的解锁+质量上限作用、最低设定先行与后补返工、多集错峰并行与小组轮转、总作监式跨集质量拉平、制作管理的组织效率作用、工程外包/整集外包/内制的组织权衡、retake 回路、分级止损、声音与画面解耦、OP/ED 与音乐的项目级独立管线。

**不值得抽象**（无经营意义的细节）：cut 袋物理流转、第二原画/直原/LO 变体、色指定细分、offline/online 编集区别、V编字幕、录音技法、逐 cut 追踪。这些全部折叠进「完成度/质量/检查通过率」参数。

## 3. 游戏案例研究：制作型经营游戏如何抽象生产

本节考察成熟制作型经营游戏的生产系统抽象（来源见 §7）。核心问题：单作品内部该串行还是并行？决策点放在哪？微操如何防？仓库「核心玩法研究」已归档于 `main@4d62bb3`（15 轮 167 节），对同一批游戏（游戏发展国、动画制作物语、漫画道场、MGT2、双点医院、足球经理、RCT2 等）做过系统拆解；本节不重复其成长曲线/人才经营/商业循环结论，聚焦生产过程抽象，两者互引。

### 3.1 逐案例要点

| 游戏 | 生产抽象 | 对本作的关键证据 |
| --- | --- | --- |
| 开罗《动画制作物语》（アニメスタジオ物語，2014 手游/2022 Steam，已核验存在） | **一条总进度条 + 40%/80% 两个里程碑事件**（选主角/试映会）；立项选电视台+题材组合+指定监督（监督职业决定方向）；员工挑战事件成功加点、失败产 NG 镜头；后期独立「修正 NG」阶段，修 NG 返还研究点；缺钱接转包合同 | 同题材最直接参照：**没有真实工序链**，靠里程碑事件制造决策点；NG=负资产+可回收资源；玩家差评「与游戏发展国数据相似 90%」、概率事件可 S/L 刷成功（支配解反例） |
| 开罗《游戏发展国++》 | 严格串行三段：提案（方向加点）→开发（剧本→画面→音乐依次）→DEBUG（可跳过省钱省时）；四维点数（趣味/创意/画面/音乐）；员工随机提案、可外包部分工程 | WIRED 采访真实开发者指出「先剧本后画面再音乐最后 debug」现实中不存在——**串行不是真实，而是认知负担管理手段**；方向加点与续作引擎是长期成长线 |
| Mad Games Tycoon 2 | 工序=部门/房间；单游戏配置后自动推进，完成后选「打磨改 bug」或直接发售；重负载部门扩第三方工作室 | **并行性放在公司级（多部门/多项目），不在单项目内部**；差评「多部门协同手忙脚乱」 |
| Software Inc | 团队制开发，技能专精+团队兼容/凝聚力；**管理可委托给团队领导**（领导不写代码只做管理）；任务池+技能匹配而非硬阶段锁 | 并行流水线可行，但**必须配委托机制否则微操爆炸**；差评集中在交互难上手、后期重复 |
| Hollywood Animal（2025 EA） | 最完整影视阶段链：剧本→前期（班底一次性锁定）→拍摄（放手+救火谈判）→后期→发行；**多部影片并行、档期重叠**；每阶段质量可升可降 | 多项目并行+重过场的翻车样本：差评「要管的事太多、利润薄、过场不可跳过，多项目时从迷人变折磨」 |
| Production Line | 产线槽位随研究从粗到细拆分；决策全在布局与节拍 | 「拆分工序本身做成成长线」有效，但纯优化玩法受众窄（国内评分 5.9）；连续流与作品制同构度低 |
| Rise of Industry | 公共基础设施（路网/研发）服务多条并行产线；配方链+合同竞标 | 「共享资产层+多生产单元」结构成熟可行；但其单元无质量差异，不是「作品」 |
| Two Point Hospital | 房间=工序、资质员工、工作件排队流动 | 警示：颗粒度细到动画级时，玩家发展出「秒诊布局」支配解——**模拟颗粒度过细会催生微操优化玩法** |
| The Movies / Moviehouse / Filmmaker Tycoon | 影视系普遍「剧本→选角→拍摄→后期」线性流程+设施经营 | 阶段锁定是影视题材主流；拍摄期靠事件救火而非过程微操 |

### 3.2 横向归纳

- **单作品内部串行/自动是绝对主流**；并行放在公司级（多项目、多部门）或单元级（多集/多部影片），没有任何成功案例把单作品内部做成全自由工序网。
- **好评共性**：重立项配置、过程自动、里程碑事件给惊喜、完成后一次打磨决策。
- **差评共性**：过程微操过多（Hollywood Animal、Software Inc）、不可跳过演出、概率可 S/L（动画物语）、细颗粒布局支配解（Two Point）、后期重复。
- **工作量/完成度/质量分离**是共识（开罗进度条 vs 四维点数 vs bug/NG 负资产）；本作三维分离方向正确。
- **外包**在开罗系几乎无风险（花钱换点数），被本作现有供应商可靠性/质量属性超越；应保留「可定价的质量风险」而非无风险外包。

### 3.3 对本作架构的证据结论

案例证据**支持把 C 作为题材差异化候选**，但**不支持 B 原样**（每集六阶段全自由并行没有成功先例，Hollywood Animal 的多单元重管理已以不可读著称）。C 的杂交结构——项目级公共前置 + 单集为最小调度单元；集内串行自动、集间异步并行；决策集中在开工配置、里程碑事件、修正打磨与档期博弈——与 §4.2 一致。若首版按框架选择 A，那是范围与迁移成本的取舍，不是行业证据证明 A 更真实；应通过里程碑事件、公共资产质量门槛、管理覆盖与可解释返工补足决策，而不是把 A 描述成行业同构。

两条需要警惕的案例教训：

1. **防微操三原则**：集内不逐人逐日指派；调度以小组为单位并可委托（Software Inc 领导委托）；概率不可 S/L（本作种子确定性纪律已天然满足，须坚持「失败请求不消耗种子、周种子固定」）。
2. **质量展示口径**：案例中常见的「作画/演出/剧情/音响四维展示」与本作已冻结的「不向玩家展示大量细分分数」（GAME_DESIGN §8.1）冲突。本作应坚持单一质量分 + 可见的 retake/问题计数，不引入四维质量条。NG 可回收为资源的思路可借鉴，但须落在现有经验/工作量口径内，不新建「研究点」货币。
3. **多项目不得退化为多条进度条**：核心玩法研究 §153 风险六明示「项目数量增加，却没有产生关键人才、资金、渠道和管理注意力之间的竞争」；§149 把「单项目集中投入 vs 多项目并行」列为目标冲突之一。这是负责人多作品方向的设计红线，也是本文坚持 management 覆盖约束与共享资源账本的原因（§4.3-3、§4.4）。随机性口径同理（§152）：不确定性必须改变局势、可被准备降低，不能替代决策。

## 4. 设计判断与方案比较

### 4.1 先回答「玩家究竟在管理什么」

行业研究（§2）表明，动画制作公司经营的本质不是「把一道工序做完」，而是**在有限资金、人员与工期下组织一个多单元、多专业、高度依赖外部资源的生产网络**。玩家有意义的决策集中在六处：

1. **机会与融资**：接什么企划、承制还是委员会投资（现有设计已覆盖，保留）。
2. **公共资产投资**：设定/系列构成/美术/音乐投多少、先做哪个——决定下游解锁与质量上限。
3. **生产日程**：各集何时开工、以什么节奏错峰推进——决定工期风险与产能利用率。
4. **团队组织**：谁做哪集哪道工序、小组如何轮转、管理岗覆盖多少并行单元。
5. **外包组织**：工程外包还是整集外包（グロス）、给谁、多少量——成本/质量/控制权的权衡。
6. **风险应对**：事件处理、retake、分级止损、延期。

现有口径 A 只覆盖 1、4（单阶段组队）、5（工程外包）、6 的一部分；**2、3 完全缺失**，而这两项恰是动画题材最有辨识度、也是行业现实中产能核心的部分。这是本次审视的基本判断：制作系统应当表达「组织生产」，而不只是「配置工序」。

### 4.2 四个架构方案

#### 方案 A：维持整部作品五阶段串行（现状）

整部作品一条流水线，TV 只是工作量更大的单件产品。

- **适用**：开发窗口极紧、优先保住已验收实现与轻量体验。
- **优点**：已冻结已实现；契约简单；无微操；平衡与测试成本最低。
- **缺点**：TV 与剧场版结构同质；没有独立的单集日程决策；management 能力在现有实现中无处发力；グロス、跨集质量统一、错峰并行等题材机制无法表达。若不补里程碑事件，现有 A 的决策密度甚至低于同题材的开罗《动画制作物语》——后者用 40%/80% 里程碑补足决策点，也仍被玩家批评与游戏发展国同质。
- **体验影响**：玩家管理的是「每阶段派谁」，不是「组织生产」。题材辨识度损失最大。

#### 方案 B：公共制作 + 单集六阶段（讨论稿原样）

按讨论稿：公共制作达标解锁单集；单集六阶段（内容设计→分镜与原画→动画制作→美术与视觉→摄影剪辑→声音交付）；单集异步、工序不整段锁定。

- **适用**：追求行业同构、愿意承担契约与实现重构。
- **优点**：结构与现实同构（§2.1）；日程与组织决策成立；グロス可行；TV 按集数自然缩放。
- **缺点（讨论稿的具体问题）**：
  1. **工序划分失准**：「分镜与原画」合并了演出（direction）与作画（drawing）两个专业，丢失现有六能力映射与作监修正语义；「美术与视觉」排在动画之后，把现实中并行的背景串行化；「声音交付」垫底，但配音可用线撮先行（§2.1 事实 4）；音乐/OP/ED 的项目级管线缺失；脚本的混合粒度（系列构成公共 + 各话脚本）未表达。
  2. **微操风险**：若每集每阶段都走「阶段首配置」，13 集 × 6 阶段 = 78 次配置决策/部，直接违反已冻结的「不逐周重复微操」原则。
  3. **重构成本**：六阶段是全新工序表，M1 的五阶段实现、能力权重、校验器、夹具几乎全部重写。
  4. **无成功案例支撑**：没有任何成熟制作型游戏把单作品内部做成全自由工序网；Hollywood Animal 的多单元重管理已以「要管的事太多、不可读」著称（§3.1）。
- **体验影响**：决策密度高，但按原样落地大概率变成排班表管理员。

#### 方案 C：公共制作 + 单集单元 + 小组化宏观管理（研究提案，与现行框架基线冲突，见 Q1）

**核心思路：把现有五阶段机制下沉为「单集流水线」，新增项目级公共制作；用小组（团队）与默认模板控制决策密度。** 不是推翻 M1，而是让 M1 的阶段机器成为单集引擎。行业研究（§2.1 三层结构）与游戏案例（§3.3 杂交结构共识）从两个方向支持这一结构。

**与公司级多作品方向的关系（2026-11-24 修订新增）：** 方案 C 解决的是作品内部结构，不以「一次一部」为前提——公司可同时持有多个在制项目，每个项目各有公共制作 + 单集单元，核心员工/供应商/资金经共享资源账本跨项目竞争。单集单元恰是多作品调度中资源竞争的天然颗粒（哪个小组投到哪部作品的哪一集）。反之，若 Q1 裁定维持 A，多作品方向仍可落地（每部作品一条流水线），只是 management 覆盖约束落在「项目数」层而非「集数」层。两轴共享同一前置：公司级/项目级状态分离 + 人员/供应商/周成本共享账本（作品审计 §6–7）；推进层改造应一次设计到位，避免先按单项目重写、再按多项目二次重写。

**与现行框架基线的冲突（Q1 裁定前必读）：** 重构框架 §5.1 保留整部五阶段骨架，§11 明确首版不做「逐镜头、逐集、逐卡」模拟。方案 C 的单集单元属于「逐集」范畴，采纳它需要**修订框架**——这是框架级决策，不是模块级参数调整。本文的诚实判断：框架的反微操意图与 C 的小组化设计其实兼容（C 不做逐集微操，决策密度≈每集开工一次 + 事件，符合框架 §1.2「决策少而有分量」）；但框架已作「首版不做」裁定，且开发窗口与迁移成本是真实约束。因此推荐调整为 **V1 按框架执行，C 作为下一里程碑候选**（§5 Q1），行业与案例证据保留为未来修订框架的输入，而不是现在绕过框架。

结构：

~~~text
项目 = 公共制作（项目级） + N 个单集单元
  公共制作：系列构成 / 角色设定 / 美术设定·色彩 / 音乐·OP·ED（可选投资）
    → 每项资产有完成度与质量；达到最低门槛解锁对应单集工序
    → 资产质量成为对应工序的质量上限（泛化现有 carry-over 封顶）
  单集单元：沿用五阶段 script → storyboard → key_animation → animation_check → postproduction
    → 声音折叠进 postproduction（配音可在完成度达标后提前并行，见 4.3-5）
    → 背景折叠进 animation_check/postproduction 的工作量或供应商子任务（见 4.3-6）
  OVA/剧场版 = 1 个单元（退化为现有行为 + 可选公共制作）
  TV = 12–13 个单元；短篇 = 1–3 个单元
~~~

管理层面（防微操的关键设计）：

- **小组制**：玩家把核心员工+临时员工编成若干制作小组（或使用推荐小组），小组绑定到单集；小组随单集自动走完五阶段，配置沿用框架「持续方针 + 周度调整」机制并提供「沿用上一集方针」默认与推荐配置。玩家决策点 ≈ 每集开工一次（选小组、定方针、定外包）+ 事件 + 必要时重组，而不是每集每阶段一次。
- **开工节奏**：玩家决定每集何时开工（可多集同时 active）；并行集数受 management 覆盖能力约束（见 4.3-3），超出则效率递减——把「制作进行稀缺」变成可读的产能规则。
- **里程碑决策点**：集内工序自动推进，但在固定完成度里程碑（如原画完成、摄影完成）触发表现型事件（抽检/试映/员工挑战），给玩家过程干预机会而不要求过程微操。依据：开罗动画物语 40%/80% 里程碑（§3.1）；完全复用现有事件系统的表现触发，不新建机制。
- **周结算框架不变**：一次 advance_week 推进全部在制项目的所有 active 单元（含多作品情形）；费用预检、事件暂停、终局优先级沿用 V3.2 顺序，但共同成本归属、事件暂停范围（暂停该项目还是全公司）、同周多项目交付/终局的结清顺序须按作品审计 §6.2/6.6/6.7/6.8 重定；「当前阶段」变为「各 active 单元的阶段集合」。
- **整集外包（グロス）**：单集可整集委托供应商（复用供应商六属性），释放社内小组；质量=供应商质量、风格统一风险与可靠性风险独立表达。这是单集化独有的新决策。

- **适用**：愿意做契约修订，但希望最大化复用 M1 与冻结规则哲学。
- **优点**：行业同构（公共+单集+错峰）；决策密度可控（小组+默认）；五阶段公式、能力权重、供应商、事件、财务口径大部分复用；OVA/剧场版退化兼容；グロス、跨集质量统一、分级止损全部有落点。
- **缺点**：仍需契约修订（不变量 3、workloads 形状、StageState 多实例、事件作用域）；周结算从单阶段变为多单元，核心与测试要重写推进层；平衡维度增加（集数×并行度×小组数）。
- **体验影响**：玩家管理「日程 + 小组 + 外包组织」，每集开工是有意义的决策，周推进仍是单次点击。

#### 方案 D：整部阶段 + 抽象「生产节奏」参数（最小改动折中）

保留整部五阶段，TV 内部记集数；玩家设一个「并行生产节奏」档位（如集中/标准/铺开），影响速度、质量、疲劳与 management 需求；不建立单集状态。

- **适用**：判定 B/C 超出开发窗口时的保底。
- **优点**：契约几乎不动；一个旋钮表达「多集并行」的存在感。
- **缺点**：没有真实日程决策、没有单集事件/グロス/跨集质量；旋钮很快被求出最优档，沦为假决策。
- **体验影响**：比 A 略好，但本质仍是 A。

### 4.3 跨架构的设计判断（无论选哪个方案都应讨论）

以下判断有行业与案例依据，但多数涉及规则口径，列为提案而非定案。重构框架已为其中部分提供落点：management → §4.2 共享资源第 4 类「管理能力」；retake/返工损失 → §5.4 随机质量损失；分级止损选项 → §10.1 事件选项；供应商产能稀缺 → §4.2 第 3 类。这些提案与框架兼容，可作为 WP2/WP3/WP7 的输入；**依赖单集架构的条目（4 跨集质量统一、7 中的总集篇、グロス）仅在 Q1 选 C 时生效**。

1. **公共资产 = 解锁门槛 + 质量上限 + 后补惩罚**，取代「全部达标才解锁」的硬锁。每项资产（系列构成/角色设定/美术·色彩/音乐）独立达标，分别解锁相应工序或交付条件；允许低质量先行开工，后补投入触发下游返工。依据：§2.1 事实 1（设定拖延连锁、滚动补充是现实常态）。这比硬锁多了「先开工抢工期 vs 等设定保质量」的真实权衡。
2. **retake 回路应成为质量-工期张力的主机制**。现有 carry-over 封顶（≤前阶段×0.6+40）只表达「上限传递」，不表达「检查不合格退回重做」。提案：阶段/单集交接时按质量与检查能力判定 retake 概率，retake 消耗工作量与周数、可被管理/作监能力降低；玩家可见「检查通过率」或问题计数（不引入细分质量分数，见 §3.3）。依据：§2.4（作监来不及修正=作画崩坏）。V2 曾有返工雏形，V3 取消后质量投资缺少「不投就返工」的痛感。可选深化：借鉴开罗动画物语「NG 可回收」思路，返工修复可返还少量经验/成长收益，使返工是资源循环而非纯惩罚——但不得新建「研究点」类货币，须落在现有经验口径内。
3. **management 能力系统性发力**（修复 §1.3 问题 2）：管理覆盖形成并行项目/单元的软约束、降低 retake 概率、提升外包可靠性监控与应急成功率、提供延误预警，不另设固定项目槽位。管理岗不是某道工序的加权，而是生产网络的组织效率。依据：§2.2（制作进行/デスク是产能核心）。
4. **跨集质量统一（总作监语义）**：项目级指派资深作画员工做「统一修正」，拉平各集质量下限（降低集间方差），代价是该员工产能占用。依据：§2.1/§2.4（总作监统一画风）。这是「公司内制质量优势」的可操作表达。
5. **声音与画面解耦**：配音（アフレコ）在单集完成度达到阈值（线撮语义）后即可开始，不必等画面全部完成；音乐/BGM 是项目级公共资产，OP/ED 是可选的项目级独立小投资（晚启动、短工期、可请名家提升话题度）。依据：§2.1 事实 4、§2.5。
6. **背景不单独成阶段**：现实背景与作画并行，但为它单开一条玩家要管理的并行线会增加微操而无对应决策深度。提案：背景工作量折叠进单集美术/合成相关阶段，或作为供应商子任务（背景几乎全外包是行业事实）；「美术设定」公共资产质量封顶背景质量。依据：§2.2（背景专门外包为主）。
7. **分级止损取代单一延期**：工期危机事件提供「压缩张数（降质量保工期）/ 硬交付（BD 修正语义，扣罚后置）/ 总集篇（TV 限定，替换一集、低成本、声望损伤）/ 延期（委员会一次，承制不可）」选项链。依据：§2.4（万策尽きた的分级止损）。全部走现有事件系统，不新建子系统。
8. **内制/外包/混合不做模式按钮**：由核心名册构成 + 外包比例自然涌现。京阿尼式体验 = 玩家选择养大而全的核心团队（高固定成本、高质量稳定、低弹性）；主流体验 = 小核心 + 大外包。依据：§2.3。现有核心/临时/供应商三类资源已足够表达，不需新系统。

### 4.4 单集化下的关键规则衔接（方案 C 的契约影响预览）

仅列影响面，供契约负责人评估，**不是字段提案**。分两部分：作品内单集化的影响（Q1 选 C 时），与公司级多作品的影响（**无论 Q1 如何选择都需处理**，对应作品审计 §6 的 11 个待决问题）。公司级部分已由重构框架 §3–§9 与工作流拆解 WP0/WP2/WP3 给出方向，本表是制作系统专项的影响面核对清单：

| 现有契约 | 影响 |
| --- | --- |
| DATA_MODEL V3.4 不变量 3「阶段不并行」 | 需改为「单元内阶段不并行；单元间可并行」或等价表述 |
| ProjectOffer.workloads（整部五阶段向量） | 需表达「公共制作工作量 + 单集工作量 × 集数」；集数与规模挂钩 |
| StageState / current_stage | 单实例 → 公共制作 + 每单元阶段实例；current_stage 语义需重定义 |
| StageConfiguration / 推荐配置 | 增加小组/模板语义；「沿用上一集」默认 |
| OutsourceTask.stage | 增加整集外包（グロス）模式与单集引用 |
| GameEvent.stage / 效果作用域 | 框架已定为项目归属+每周限量；C 下再增加单元引用，全局每周最多一个保持不变（Q5） |
| WeekReport.stage_deltas | 扩展为单元级增量 |

### 4.5 对七个成果问题的回答（以方案 C 为基准）

- **玩家在管理什么**：生产网络的组织——日程、小组、公共资产、外包与风险（§4.1）。
- **资源投在哪**：公共制作（解锁+上限）、单集工序（工作量）、小组人力（工资/加班/疲劳）、外包费（工程/整集）、临时招募、音乐/OP·ED 可选投资。
- **有意义的决策**：接约与融资、公共资产优先级与质量目标、各集开工节奏、小组编成与指派、工程外包 vs グロス、retake/止损/延期应对。每个决策都有成本-质量-工期三角的权衡，不存在无条件最优。
- **工作如何相互影响**：公共资产→工序解锁与质量上限；前序阶段→后序上限（carry-over）；并行集数→管理覆盖→效率；retake→工期；前集延误→后集开工挤压（日程连锁）。
- **规模/能力/组织差异**：规模=集数×单集工作量；员工能力=工序产能与质量 + 管理覆盖 + 统一修正；组织差异=核心名册厚度与外包比例涌现（内制稳定但贵、外包弹性但失控风险）。
- **不确定性既可理解又可控**：种子确定性不变；周预览给出确定费用与已知风险、不泄露随机工作结果；日程视图暴露瓶颈与延误预警；retake/外包失败/事件都有可见原因与分级应对选项。未知保留在供应商可靠性与事件风险等级，不搞不可读赌博。
- **与其他系统衔接**：经济（单集成本归集、整部结算、V3.12 预算/投资/BD/成功奖励口径不变）；员工（小组、疲劳士气、成长按实际参与工序；多作品下每周单点投入 + 跨周轮换，与员工组织设计 Q1-B 一致）；供应商（工程+グロス复用六属性，capacity 跨项目预留）；项目管理（日程、并行度、延期）；作品评价（集间质量方差 + 统一修正 + 重大事故，沿用质量/商业分离与 S/A/B/C/D 固定分数线）；系列（单集化不改变续作质量独立计算口径；同一 IP 多作品并行时系列身份需先补最小模型）；委员会（随项目结算停止活动并保留历史快照；未结分成与成员义务的归档边界由 WP0/WP8 细化）。

## 6. 建议的后续工作

以下工作直接映射到工作流拆解，不另建一套开发计划。**当前开始核心规则前的最小决策集是 D1/D2/D6**；本文的 Q1 是独立的制作架构政策决策，不应等所有内容工作包完成后才讨论。

1. **负责人最小决策与架构边界**：先确认 D1（核心员工主项目+有限支援）、D2（计划只执行已配置资源，还是允许自动补招/外包）、D6（资金不足立即破产，还是允许短期危机窗口）。D3/D4 按建议候选推进，D5 先确认中等随机方向；Q1 决定 V1 是否维持整部五阶段。未裁定前，WP2/WP3 只交规则选项与草案，不写正式排班或结算算法。
2. **WP0 领域边界与数据所有权**：落地 §4.4 的公司级/项目级拆分、共享资源账本、系列身份、项目结算与委员会停止的生命周期；先保证同一事实只有一个所有者，再讨论单集字段。
3. **WP1/WP10 周决策与信息架构**：用普通周、资源冲突周、阶段完成周、交付周原型验证“持续方针+周度调整”；界面先表达项目阶段、人员负荷、供应商占用、预计工期与风险。若 Q1 选 C，再增加集×工序视图；没有 C 就不提前做逐集 UI。
4. **WP2/WP3 资源分配与统一周结算**：把 management 覆盖、供应商 capacity 预留、retake/质量损失、分级止损选项写成可结算的规则候选；遵守“统一预检→原子扣费→各项目产出→人员状态→事件/交付→统一推进”的顺序，不允许项目顺序造成半结算。
5. **WP4 最小多项目模拟器**：在 WP0/WP2/WP3 可用后，用 2–3 个项目、少量员工与供应商验证资源竞争、统一现金池、工作量/质量分离、固定 seed 回放和原子性。用模拟结果检验“多项目是否只是多条进度条”、随机性是否压过经营选择，以及管理能力不足是否产生可理解的代价。
6. **WP6/WP7/WP8 内容与规则迁移**：WP6 准备不同规模的作品、供应商与合作方静态样本；WP7 先做里程碑事件、预警和分级止损的内容层，不擅自定触发概率；WP8 将 V3.9–V3.13 的预算、投资、BD、渠道、排名与系列规则整理成“旧规则—新框架—待核验”映射表，制作评价与商业表现继续分离。
7. **WP5/WP9 组织与成长**：员工内容可独立准备，但正式成长规则要等 WP2/WP3；同一 IP 的续作/前传/外传先补关系身份，再实现商业基础积累，不继承前作质量。设施只作辅助成长候选，不新建科技树。
8. **参数校准与验收**：修正质量权重矛盾；为整部五阶段建立手算样例，只有 Q1 选 C 才增加公共制作与多集样例。对照实验覆盖并行项目数、管理覆盖、内制/工程外包比例、随机强度与计划自动化，重点排查“外包无风险”“概率 S/L”“逐周重复确认”等支配解或坏体验。
9. **裁定回写与文档维护**：Q1 与 D1–D6 有结论后，更新重构框架/工作流拆解及必要的 GAME_DESIGN、GAME_RULES、DATA_MODEL、API、PROGRESS；本文保留研究论证，不把提案改写成已确认事实。另需核查工作流拆解头部链接：`PLAYABILITY_FOCUSED_RESEARCH_AND_VALIDATION_2026-11-24.md` 不存在于 `main@4d62bb3` 的 docs 树，不能以现有 `PLAYABILITY_RESEARCH_AND_RANDOMNESS.md` 或 `PLAYABILITY_COMPETITOR_RESEARCH_V0.1.md` 擅自替换，应由文档负责人确认预期来源。
