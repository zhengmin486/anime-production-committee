# 工程变更治理：持续修补与重构边界

> 状态：已确认（2026-11-25）
> 适用范围：M0–M7 全阶段，以及阶段完成后的维护、缺陷修复和版本演进。
> 目的：允许工程成果持续修补，避免每进入一个阶段就重写前一阶段；同时防止未经评审的契约漂移。

## 1. 核心原则

**阶段成果是可持续演进的基线，不是一次性交付后不可触碰的遗产。**

M0/M1 冻结或验收的是某一时点的规则、契约和能力基线。后续发现缺陷、遗漏、跨模块冲突或合理的新需求，可以修补；但不能把“允许修改”理解为可以随意推翻，也不能把“冻结”理解为永远不能修改。

默认顺序：

1. 复现问题并确认当前 main 上的真实实现和契约。
2. 优先在现有模块、数据结构和接口内寻找最小充分修补。
3. 评估兼容扩展、适配层或局部迁移是否足够。
4. 只有证据表明现有边界无法合理承载需求时，才提出契约变更或重构。
5. 按变更级别审批、实现、测试并同步文档。

## 2. 变更分级

| 级别 | 定义 | 处理方式 |
| --- | --- | --- |
| A — 内部修补 | 修复实现缺陷、补齐遗漏、调整内部函数/文件，不改变对外行为、契约或存档语义 | 普通增量 PR；补针对性测试 |
| B — 兼容扩展 | 新增可选字段、读模型或接口能力，既有调用方和合法存档保持原语义 | 说明缺省语义、兼容边界、调用方和回归范围 |
| C — 契约修订 | 改变既有字段含义/可空性、不变式、命令签名/守卫、错误码、结算顺序或失败行为 | 变更说明；负责人明确裁决；同步全部依赖方 |
| D — 破坏性迁移/架构重构 | 破坏既有数据/调用方兼容性，替换模块边界、状态所有权或重写已验收成果 | 先提交独立方案并获负责人明确批准，再实施 |

不能确定级别时，按较高一级处理。一个 PR 同时包含多级变更时，按最高级别审批；应尽量拆分，避免把普通修复与大规模重构捆绑。

## 3. 变更说明的最低要求

B–D 级变更，以及可能影响已确认玩法的修复，必须说明：

- 问题或需求是什么，如何复现，有什么证据；
- 当前实现为什么不足，评估过哪些更小方案；
- 修改范围与影响模块、接口、状态、存档、UI、内容资产和下游任务；
- 是否向后兼容；若否，迁移、版本升级或拒绝旧数据策略是什么；
- 测试、回归范围和验收标准；
- 是否改变已确认决策；若是，明确标记“决策变更”，由 zm 裁决。

## 4. Agent 与贡献者约束

- 开始前检查最新 main、相关 PR/分支、契约和测试；不得只依据旧对话摘要或过期本地副本。
- 先判断现有模块能否修补，不得默认另起一套实现。
- 不得以“架构更优雅”“代码更清晰”“进入新阶段”为单独理由重写已有模块。
- 不得顺手重写无关文件、改变无关接口、全仓格式化或升级无关依赖。
- 发现必须进行 C/D 级变更时，先提交分析和方案，等待 zm 裁决；未获批准不得实施破坏性改动。
- 获批后仍须拆分实施范围，保留可追溯提交，补齐迁移和回归证据。

## 5. 验收与阶段成果保护

- 修改什么，就验证什么；涉及状态、命令、财务、随机性或事务原子性时，覆盖正常、边界、错误及失败后状态不变。
- 若修改影响已通过的阶段出口标准，必须重跑受影响的验收项，并更新阶段证据；不受影响的验收项无需无差别全量重跑。
- 旧实现若已被新架构明确废弃（例如 V3 单项目运行时），按既定迁移/隔离决策处理；本原则不要求保留已经正式废止的设计。
- 关闭或合并 PR 不代表其未解决问题自动消失；应将仍有效的缺陷和契约缺口迁入当前权威任务。

## 7. 开放式增量开发

首版范围是最低交付目标与优先级约束，不是禁止提前实现未来功能。无既定决策、主框架、跨模块契约、核心数值或重大风险冲突的新增能力，成员可自主推进；通过相应工程验收后默认接纳，不另设“负责人是否愿意要”的产品审批。

这不改变 C/D 级变更的负责人裁决要求，也不免除测试、文档同步、PR 评审和集成验收。阶段出口标准仍须独立满足。详细规则见[开放式增量开发与提前实现原则](OPEN_INCREMENTAL_DEVELOPMENT_POLICY.md)。
