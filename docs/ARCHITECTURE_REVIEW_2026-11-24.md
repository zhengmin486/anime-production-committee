## 0. 结论先说：是优化，不是重做

你问的"重做还是优化"，答案分两半：

- **架构骨架不用重做。** 9 个有状态领域 + 无状态规则内核 + 快照 + 单点结算事务 + 单一账本 + 坐标式随机，这些判断没有被任何已确认决策推翻，反而被 DEC-FIN-001（统一现金池、原子结算）、DEC-RNG-001（随机流隔离）、DEC-PLAY-002（不自动花钱）逐条印证。
- **但 v1.0 有四处必须改，其中一处是"结构级"的。** 单集六阶段不是把五阶段改个名字，而是把生产单位从"整部作品"下沉到"单集"，并引入工作项依赖。这层我之前按"未定案"处理、只留了接缝；现在它已确认，接缝要变成主结构。

所以本轮做的是：**保留骨架，替换生产模型，修正人员与财务两条状态机，删掉全部"待裁决"措辞。**

### 1.1 制作模型：为什么是"工作项"而不是"阶段"

已确认的规则是"依赖细化到工作项、达到最低交付即解锁下游、前序可继续完善、不互斥可并行"。这四条只要有一条成立，就不能用"阶段整体完成才进下一阶段"的模型。

因此：**阶段只是工作项的分组与展示层**，真正被依赖、被交付、被计算的是工作项。

- 依赖写在 `WorkItem.deps`，可以跨容器（公共制作的"角色设定" → 单集的"分镜与原画"）。
- 门槛写在 `deliver_at`（占 `work_total` 的千分比），**达到门槛即解锁下游**，工作项本身仍可做到 100% 只提质量。
- 没有 `status` 字段：`unlocked / delivered / complete` 全部由 `work_done` 与依赖推导，避免"状态说交付了但工作量不够"这类非法组合。校验器只需两条不变式。

### 1.2 玩家到底点什么（本轮最重要的可玩性判断）

工作项有 200 多个，摊给玩家就是微操地狱。所以定死一条边界：

> **玩家决定"谁进哪个项目"，内核决定"这些人在项目里做哪些工作项"。**

内核排序规则固定且可解释：未达门槛优先 → 阶段靠前优先 → 按项目方针（质量/进度/成本）→ id 打破平局。玩家影响节奏的手段是四个方针旋钮，不是一个工作项列表。

代价必须说清：玩家不能"这周专攻第 7 集"。这是刻意的。若以后需要更强的定向能力，正确做法是加"项目优先级 / 指定关键单集"这类**低维**决策，而不是把工作项摊开。

### 1.3 磨合损失：不加计时器

规则要求"接手已开工工作才有损失、接手未开工没有、一次性、只扣工作量、累计不超过可扣减产出"。用计时器实现会引入"这个人还剩几周磨合"的隐性状态，存档与 UI 都要背。

本版改成**可推导**：每个容器（单集/公共制作）存 `contributors[]`（谁参与过），员工存 `last_participation`（上周在哪个单元、哪个项目）。两个字段足够判定四种情形，第二次进入同一单元自然不再触发。

监督人员切换项目是团队级损失，同样由 `last_participation.work_id` 与本周归属比较得出，不存额外状态。

### 1.4 资金危机：把"期限"落成能算的东西

已确认的是方向，并明确留了两个局部语义（周数是否推进、工资是否继续）。架构若继续写"待定"，实现就会卡住，所以本版给默认值并说明可替换：

- **危机周推进周数、只扣固定成本、不生产、允许负余额。**
- 理由：期限必须能用周数表达；成本必须继续，否则玩家可以无限挂机等好转；生产必须停，否则与"预检失败不得部分推进"直接矛盾。
- 融资进入强制费用（本金入账，未来每周还款 + 利息），所以"借钱"是买时间，不是免费续命。
- 危机中禁止一切新增承诺（立项、签外包、招聘、买电视服务），只允许减少承诺与自救。

这是**默认值**，不是新决策。若你认为太狠，"时间冻结 + 成本冻结"也能接，只需替换危机结算的 3 个步骤，不影响其他结构。

## 3. 架构现在长什么样（一屏版）

```text
UI → API → Application（编排/结算/读模型）
              ├── Company     周数·声望·终局
              ├── Staff       唯一项目归属·能力·疲劳士气·磨合判定输入
              ├── Project     公共制作 + 单集×6 阶段×工作项（唯一生产状态）
              ├── Vendor      供应商·外包合同（落到具体工作项）
              ├── Partnership 合作方·委员会
              ├── Market      企划槽·热度·竞争
              ├── Finance     现金·流水·贷款·偿付状态
              ├── Event       单槽事件·冷却
              └── Archive     只追加履历·系列·结局
                        ↓
        Rules Kernel（production/allocation/commerce/evaluation/competition/rng，纯函数）
```

周结算仍是 13 阶段，但内容换了：需求合成 → **人员→工作项分派** → 预检 → 记账 → 制作执行 → 人员结算 → 生命周期 → 交付 → 事件 → 时间与市场 → 终局。预检失败时走**另一条 7 步危机结算**，不混进正常流程。

## 4. 需要你知情的三处（不是待裁决）

这三处不是产品方向问题，但都会改变你实际看到的行为，所以列出来而不是埋在文档里：

| # | 事项 | 本版做法 | 如果你不同意 |
| --- | --- | --- | --- |
| 1 | 招聘/抽卡不再要求"全公司空闲" | 经营中随时可做，成本立即入账、下周生效 | 想保留"停下来才能招人"的节奏，需作为独立玩法决策提出（多项目下会变成长期无法招聘） |
| 2 | 门槛达标后玩家可主动交付 | `deliver_work`：提前交省周数，拖满更高质量 | 若不想让玩家控制交付时机，退回"仅到期/完成自动交付"，删掉该命令即可 |
| 3 | 危机默认"周数推进 + 继续计固定成本" | 见 §1.4 | 可换成"时间与成本冻结"，只需改危机结算 3 步 |

另有一条旧冲突已登记但未改文档：框架 §4.2 仍写着"管理能力不足会产生执行损耗"，与 DEC-PLAY-001"不引入管理负荷数值"冲突。本架构按决策执行（管理能力只作为岗位能力影响监督与磨合），框架那句话建议下次文档整理时改掉。

## 5. 是否具备实施条件

**具备，但顺序不能错。**

已具备：领域边界、状态所有权、工作项模型、依赖与门槛语义、分派规则、磨合判定、危机状态机、结算契约、命令表、读模型、随机与存档、迁移里程碑与退出标准。

三个前置：

1. **先冻结 v4 契约与制作蓝图 schema（M0），再写任何行为。** 工作项字段一旦在实现中漂移，200 多个实例会一起返工。
2. **蓝图粒度必须先做纸面验证。** 每集几个工作项、依赖拓扑怎么画，直接决定可读性与状态体积。这是内容设计，但会反向约束契约，不能等到 M2 之后。
3. **危机参数（期限/额度/利率）先给占位值跑通流程，再交给模拟。** 不要因为参数没定就不写状态机。

不建议现在做：大规模重写 `game_core.cpp`、并行保留 v3/v4 双状态、在迁移期同时改玩法。
