## 1. 最终推荐的整体架构

**模块化单体：9 个有状态领域 + 1 个无状态规则内核 + 应用层编排 + 单点结算事务。**

```text
UI（只展示读模型、只发命令）
  → API 适配层（JSON schema 校验、错误映射）
    → Application（用例编排、周结算 13 阶段、快照组装、读模型）
      → Domain（Company / Staff / Project / Vendor / Partnership / Market / Finance / Event / Archive）
        → Rules Kernel（production / allocation / commerce / evaluation / competition / rng，纯函数）
          → Infrastructure（存档编解码、内容目录、诊断、版本）
```

三句话概括它的取舍：

1. **状态与规则彻底分离。** 领域只管"谁拥有什么事实、什么不变式必须成立"，所有公式进入可穷举测试的纯函数。这解决的是历史审计反复出现的"公式散落在巨型结算函数里、改一处崩三处"。
2. **跨领域不互相读状态，只读一次快照。** 结算前组装不可变 `WeekSnapshot`，所有计算只读快照。这让"项目遍历顺序不得影响结果"从纪律变成结构性性质。
3. **产能与现金都不设第二份账本。** 员工主项目归属是唯一字段，外包合同是唯一产能凭据，现金只有 Finance 一处。所有"占用/预留/项目钱包"都是派生视图。这从根上消灭重复占用、陈旧预留、项目账与公司账不一致三类缺陷。

## 2. 与当前讨论稿相比的重要调整

| # | 讨论稿 v0.1 | 本版 | 为什么改 |
| --- | --- | --- | --- |
| 1 | Project 管生命周期，Production 管生产规则，Production 在项目范围内持工作执行记录 | Project 独占制作状态；Production 降为无状态内核 | 同一阶段进度出现两个所有者，每周要双向同步，校验器无法判定"阶段已完成但工作量不足"。这里该切的是**状态与算法**，不是两份状态 |
| 2 | 独立 Resource Allocation 领域，持有分配与占用 | 取消该领域：归属在 Staff、计划在 Project、合同在 Vendor、算法在内核、编排在应用层 | 可变的分配账本必然带来"承诺未兑现是否释放、取消是否回滚、存档恢复是否仍有效"。分配本质是纯函数，不是状态 |
| 3 | Collaboration 管合作、委员会、合同、权利 | Partnership 只管合作方、关系、委员会；付款归 Finance；分账归内核 | 原边界把"关系"和"钱"混在一个模块，导致合同付款义务与 Finance 长期交界不清（审计已记录） |
| 4 | Market 管企划、渠道、商业表现 | Market 只管机会、热度、竞争；商业结算归内核，在交付时一次算完 | 商业表现不是市场状态，它是交付结算的规则 |
| 5 | Event & Risk 合一 | Event 为领域；Risk 降为 Project 的派生属性 | 风险没有独立生命周期，每周从状态重算；给它一个领域只会产生"风险值谁更新"的问题 |
| 6 | 未单列外部产能与历史 | 新增 Vendor、Archive | 外包是采购合同（有交付、失败、产能占用）；作品履历是唯一"写入即冻结"的数据，与可变状态混放是历史缺陷的根源 |
| 7 | 候选模块 9 个，但边界靠文字描述 | 9 个模块 + 一张所有权矩阵 + 逐项不变式清单 + 13 阶段结算契约 | 讨论稿的第 8 节把关键问题全部列为"尚待讨论"，无法指导实现；本版逐项给了答案 |
| 8 | 随机数只在基础设施层提了一句"应避免互相干扰" | 坐标式无状态随机：`hash(seed, week, stream, purpose, index)` | 单 LCG 在多项目下必然"项目顺序影响结果、加模块改变历史"，且无法局部复现 |

**保留了讨论稿的哪些判断**：模块化单体、Company/Project 双层、应用层负责跨领域流程、不引入 Portfolio 领域、不拆微服务、项目组合只作为视图、委员会随作品成立。这些是对的，不应为体现重构价值而推翻。

## 3. 旧设计的保留 / 修改 / 废弃

### 3.1 保留（明确不动）

| 设计 | 理由 |
| --- | --- |
| 五阶段骨架与阶段键 `script…postproduction` | 已冻结，且有实现与夹具；改它会把制作研究的分歧提前变成契约分歧 |
| 六项专业能力、岗位/能力/阶段三者独立 | 已冻结，且与员工内容库绑定 |
| 成本分类（八类 + development/distribution） | 已确认，足以覆盖现有玩法 |
| BD 50/50、非 BD 按投资比例、承制不参与非 BD | 已确认（V3.11/V3.12） |
| 声望唯一写入点、不衰减、只由经营改变 | 已确认且已实现 |
| 公司单一现金池、项目账只做归因 | 已确认；本版把它从"纪律"变成"结构" |
| JSON-in/JSON-out、C++ 纯规则、WASM、无后端、单槽本地存档 | 技术形态有效，不需要动 |
| 存档拒绝旧版本、不迁移 | 现有政策正确，继续沿用（升级到 v4） |

### 3.2 修改（保留意图，换结构）

| 旧设计 | 新结构 | 保留了什么 |
| --- | --- | --- |
| 单一 `project` 字段 | `works: Project[]` | 项目内部结构、阶段状态机、交付语义 |
| 全局 `phase`（idle/producing/event_pending/…） | 派生：由公司状态 + 待处理事件 + 项目集合推出 | UI 的状态提示语义；不再作为权威字段 |
| `StageConfiguration`（阶段首提交后锁定） | `WorkPlan`（持续方针 + 周度调整） | "阶段内不再逐周确认"的意图；改为默认沿用 |
| `project.finance` + `company.finance` 两套汇总 | Finance 流水 + 按 `work_id` 的归因视图 | 两套口径的**需求**（公司账与项目账），去掉两套数据 |
| `StageResult.costs` | 删除；金额只在 Finance | 阶段成本仍可查（按 work_id + 周区间过滤） |
| 单一 uint32 LCG 每周推进一次 | 坐标式无状态随机 | 同 seed 可复现；且不再与调用顺序耦合 |
| `apply_decision(type, ...)` 巨型分支 | 19 个用例级命令 | 现有全部动作都有对应入口 |
| `committee_members` 旧结构（`share_percent`/多渠） | `{id, name, channel}`，一成员一渠道 | 玩家投资比例与拉渠道两个维度的玩法 |
| `preview` 写入存档 | 读模型，加载时重算 | 玩家仍能看到下周费用与风险 |

### 3.3 废弃（明确不应继续投入）

| 设计 | 原因 | 处置 |
| --- | --- | --- |
| "同一时间只能一个在制项目" | 已被 2026-11-24 多项目方向覆盖，但 `GAME_RULES` V3.10 与 `DATA_MODEL` 不变量 2 仍写着 | 在 v4 契约删除；历史段落标注"已失效"，不改写历史 |
| 日制、三工序（pre/mid/post） | v2 遗留 | 不迁移 |
| 委员会长期化（跨项目持续活动） | 已确认委员会随作品成立、结算即停 | 不实现"活动中委员会" |
| 统一委员会单渠道分账公式 `floor(revenue×pct/100)` | 与 V3.11/V3.12 冲突；未推送的 `46a0b47` 分支仍在用 | 不合入；分账只在 commerce 内实现一次 |
| 设施科技树 / 培训树 / 部门晋升 | 框架 §6.3 明确暂缓 | 只留 `Company.facilities[]` 空集合接缝 |
| 隐藏供应商可靠性、临时周薪×1.3 等 v2 口径 | 已被 V3.6 覆盖 | 不迁移 |
| 单一 `apply_decision` 兼容层 | 会把所有守卫重新塞回一个函数 | 一次性替换，不做兼容 |

## 4. 必须由负责人决定的问题（4 项）

只列触及玩家控制权、失败语义或核心循环的。其余已由架构设计裁定。

| # | 问题 | 推荐 | 为什么必须你定 | 若改变推荐，架构代价 |
| --- | --- | --- | --- | --- |
| **P1** | 首版作品内制作粒度：整部五阶段（A/A'），还是单集化（C） | **A + 保留 `units[]` 接缝** | 这是"动画公司"与"通用项目工厂"的体验分界，属产品方向；且 C 会让"公司 × 作品 × 单集"三层调度相乘 | A→C：推进层、事件作用域、UI、校验器重写（接缝已留，但不是零成本）；A→A'：可压平一层 |
| **P2** | 核心员工跨项目支援的表达 | **1 主项目 + 至多 1 个支援（有上限与损耗）** | 直接决定玩家的操作量与"资源竞争"的手感 | 若选严格一人一项目，只是参数与 UI 收紧；若选自由拆分工时，分配求解与 UI 需重做 |
| **P3** | 资金不足：立即破产，还是短期危机窗口 | **维持立即破产（F1）** | 已确认规则就是立即破产；改它等于改失败语义 | 若选 F2，需新增 Financing 聚合与预检分支，属新增子系统 |
| **P4** | 计划自动执行能否替玩家花钱（自动补临时员工/外包） | **不能（A1）**：只在已配置资源内执行，缺口表现为进度不足与预警 | "系统是否替我做了我没意识到的承诺"是控制权问题 | 若选 A2，需在结算中插入购买决策与预算上限语义，并新增"为什么这周花了钱"的解释负担 |

**建议的最小裁决集**：P1 与 P4 先定（影响推进层与金钱控制权），P2/P3 按推荐先落地，试玩后再复核。P2/P3 的推荐值都可作为参数调整，不阻塞开工；P1 影响结构，越早定越好。

> 另有一项不需要裁决、但需要知情的规则冲突：`game_rules.hpp` 的质量权重（150/200/250/200/200）与已确认的"前重后轻"口径矛盾。这是平衡参数问题，v4 不沿用代码值，由平衡任务按已确认口径定值，并在文档注明"设计取舍，非行业事实"。

## 5. 架构是否具备进入实施阶段的条件

**结论：具备，但有三个前置条件。**

已具备：

- 领域边界、状态所有权、逐项不变式清单、13 阶段结算契约、命令与读模型契约、随机与存档机制、迁移里程碑与退出标准，均已具体到可实现。
- 每个关键争议都给了判断与理由，没有把"尚待讨论"留成空白（讨论稿第 8 节的 7 个问题已全部回答）。
- 迁移路径不要求一次性重写：先 M0 契约、M1 内核、M2 单项目等价性，再开第二个项目。

三个前置条件：

1. **P1 需要裁定**（或明确"按推荐 A 先做，后续再议"）。`units[]` 接缝让 A→C 不必重写结算，但 UI 与事件作用域仍会受影响。
2. **契约冻结要先于行为实现。** 若边写行为边改状态形状，会重演历史上"文档与代码漂移、版本号同号不同义"的问题。M0 必须先交付 v4 形状 + 校验器 + 夹具，且拒绝在 M0 期间写业务逻辑。
3. **等价性基线要先建立。** M1/M2 的验收依赖"与 v3 在单项目场景下逐字段等价"。这需要先把 v3 的关键场景固化成回归样例（承制、破产、到期、终局），否则"新架构更好"无法被证明。

**不建议现在做的事**：大规模重写 `game_core.cpp`、并行保留 v3/v4 双状态、在迁移期同时调整玩法规则。三者都会让差异来源不可归因。
