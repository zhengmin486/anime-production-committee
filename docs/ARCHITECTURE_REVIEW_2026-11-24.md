### 1.1 制作模型：为什么是"工作项"而不是"阶段"

已确认的规则是"依赖细化到工作项、达到最低交付即解锁下游、前序可继续完善、不互斥可并行"。这四条只要有一条成立，就不能用"阶段整体完成才进下一阶段"的模型。

因此：**阶段只是工作项的分组与展示层**，真正被依赖、被交付、被计算的是工作项。

- 依赖写在 `WorkItem.deps`，可以跨容器（公共制作的"角色设定" → 单集的"分镜与原画"）。
- 门槛写在 `deliver_at`（占 `work_total` 的千分比），**达到门槛即解锁下游**，工作项本身仍可做到 100% 只提质量。
- 没有 `status` 字段：`unlocked / delivered / complete` 全部由 `work_done` 与依赖推导，避免"状态说交付了但工作量不够"这类非法组合。校验器只需两条不变式。

### 1.2 玩家到底点什么（本轮最重要的可玩性判断）

工作项有 200 多个，摊给玩家就是微操地狱。所以定死一条边界：

> **玩家决定"谁进哪个项目"，内核决定"这些人在项目里做哪些工作项"。**

内核排序规则固定且可解释：未达门槛优先 → 阶段靠前优先 → 按项目方针（质量/进度/成本）→ id 打破平局。玩家影响节奏的手段是四个方针旋钮，不是一个工作项列表。

代价必须说清：玩家不能"这周专攻第 7 集"。这是刻意的。若以后需要更强的定向能力，正确做法是加"项目优先级 / 指定关键单集"这类**低维**决策，而不是把工作项摊开。

### 1.3 磨合损失：不加计时器

规则要求"接手已开工工作才有损失、接手未开工没有、一次性、只扣工作量、累计不超过可扣减产出"。用计时器实现会引入"这个人还剩几周磨合"的隐性状态，存档与 UI 都要背。

本版改成**可推导**：每个容器（单集/公共制作）存 `contributors[]`（谁参与过），员工存 `last_participation`（上周在哪个单元、哪个项目）。两个字段足够判定四种情形，第二次进入同一单元自然不再触发。

监督人员切换项目是团队级损失，同样由 `last_participation.work_id` 与本周归属比较得出，不存额外状态。

### 1.4 资金危机：把"期限"落成能算的东西（已确认）

2026-11-24 已确认（DEC-FIN-003），不再是设计默认值：

- **危机周推进周数、只扣固定成本、不生产、允许现金暂时为负。**
- **融资是唯一允许的新增资金动作**；其余新增承诺与新增项目支出（立项、签外包、招聘、买电视服务、自定企划）一律拒绝。
- 融资进入强制费用（本金入账，未来每周还款 + 利息），所以"借钱"是买时间，不是免费续命。

**由此得到一个必须写清的推论**：危机期不生产，所以没有"再赶一周工"这条路。自救只剩三条：借钱、砍承诺、把**已达门槛未交付**的作品立刻交付回款。这也让 `deliver_work` 在危机时刻变成了现金储备——"早交还是晚交"因此有了真实后果。

**一个容易踩的坑**：危机周的人员结算不能写 `last_participation`，否则停工数周后恢复生产会被判成"全员换人"，凭空吃满磨合损失。这条已写进 §9.3.1 与测试用例。

## 3. 架构现在长什么样（一屏版）

```text
UI → API → Application（编排/结算/读模型）
              ├── Company     周数·声望·终局
              ├── Staff       唯一项目归属·能力·疲劳士气·磨合判定输入
              ├── Project     公共制作 + 单集×6 阶段×工作项（唯一生产状态）
              ├── Vendor      供应商·外包合同（落到具体工作项）
              ├── Partnership 合作方·委员会
              ├── Market      企划槽·热度·竞争
              ├── Finance     现金·流水·贷款·偿付状态
              ├── Event       单槽事件·冷却
              └── Archive     只追加履历·系列·结局
                        ↓
        Rules Kernel（production/allocation/commerce/evaluation/competition/rng，纯函数）
```

周结算仍是 13 阶段，但内容换了：需求合成 → **人员→工作项分派** → 预检 → 记账 → 制作执行 → 人员结算 → 生命周期 → 交付 → 事件 → 时间与市场 → 终局。预检失败时走**另一条 7 步危机结算**，不混进正常流程。

## 7. v1.2 架构评审补充（2026-11-24）

### 7.1 总体结论

**架构骨架通过，实施前需要修正一项规则映射，并验证两项玩家行为语义。** 不建议重做九领域、纯规则内核、快照与原子结算的整体结构；但不应把本版“当前没有待产品裁决事项”理解为所有玩家控制细节均已由负责人确认。

### 7.2 必须修正：磨合损失记录粒度过粗

DEC-STAFF-001 的约束对象是“其他员工已经开始的具体工作”：
- 接手已开始的工作项，且新加入者此前未参与该工作项，才产生一次性个人工作量效率损失；
- 接手尚未开始的新工作项，不产生损失；
- 同一员工此前参与过该工作项，不重复产生损失。

当前 §7.2.1 将 `contributors[]` 放在 `CommonProduction` / `EpisodeProduction` 容器级，并以容器内 `Σwork_done > 0` 判断是否已经开工。这会把“某一集/公共制作中任意工作项已经开始”误当成“当前接手的工作项已经开始”，可能导致：
1. 同一单集内，员工接手一个尚未开始的工作项，却因为该集其他工作项已有产出而被扣磨合；
2. 员工曾参与同一单集的其他工作项，却因此被视为参与过当前工作项，漏掉真正的接手损失。

**修正要求：** 将磨合判定依据落到工作项或等价的、可证明具体工作接手关系的记录上。实现可由架构智能体选择最简模型，但必须逐项覆盖 DEC-STAFF-001 的四种情形，并添加“同一单集不同工作项”的反例测试。不得把已确认规则改成“按整集判断”。

### 7.3 需要负责人确认的玩家控制边界：单集定向能力

§7.3.5 / A11 将玩家控制收敛为“选择员工所属项目”，工作项由内核全自动分派，并明确玩家不能指定某一集作为本周重点。

自动分派本身符合减少微操的目标，但“不能对关键单集施加低维优先级”并非 DECISION_LOG.md 已明确确认的规则，而是架构新增的玩家控制限制。建议：
- 保留默认自动分派，不向玩家暴露 200 多个工作项；
- 评估是否需要一个低维的单集优先级/关键单集指定入口；
- 在该控制边界确认前，M0 契约不要把“永远不能指定单集”写成不可扩展的硬限制。

该项不阻止员工档案、企划内容、供应商目录、事件内容、静态 UI 信息架构等并行工作；但涉及单集定向字段与 UI 的实现应暂缓冻结。

### 7.4 需要补充说明：交付命令的业务粒度

DEC-PROD-004 使用“单集/作品”表述，而 §7.3.6 当前定义的 `deliver_work` 是 Project 级命令，作品全部 `is_gate` 工作项达标后才能交付；没有单集独立交付命令。

请在命令契约中明确：
- 单集达到门槛是否只解锁整部作品的最终交付，还是允许单集分别交付；
- 若只允许整部作品交付，说明这是项目合同与交付粒度的架构解释，不要让“单集进度独立”被误读为“单集可独立结算”。

这首先是契约语义澄清；若涉及改变玩家可交付对象，再提交负责人裁决。

### 7.5 文档一致性修正

当前 `CORE_GAMEPLAY_REBUILD_FRAMEWORK.md` §4.2 仍把管理能力描述为多项目执行损耗来源，与 DEC-PLAY-001“不引入独立管理负荷数值”的边界不够一致。应明确区分：
- 员工的管理专业能力可以影响其实际承担的监督/协调工作；
- 不得把项目数量或管理跨度转化成独立的管理负荷、惩罚数值。

### 7.6 开工门槛与并行工作

| 工作 | 是否可开始 | 边界 |
| --- | --- | --- |
| v4 状态/命令契约、校验器骨架 | 可开始，先形成 M0 冻结候选 | 单集定向控制字段先保留扩展空间；修正工作项级磨合记录 |

| 事件域设计 | 可开始 | 先适配 v4 Event 状态所有权、周结算顺序和危机白名单；PR #19/#24 不直接迁移 |
