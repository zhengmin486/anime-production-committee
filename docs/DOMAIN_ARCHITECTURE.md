## 1. 架构目标

本项目采用**领域模块化单体（Modular Monolith）+ 应用层统一协调**作为目标架构。

核心目标：

- 以业务领域组织系统，而不是以页面、旧代码目录或人员分工组织系统。
- 各领域拥有明确的业务职责、数据所有权和对外接口。
- 跨领域流程由应用层组织，避免业务规则散落在 UI 或单一巨型结算函数中。
- 首版保持单体部署，不拆分微服务，不为尚未出现的规模提前引入分布式复杂度。
- 允许多个 Project 并行经营，共享 Company 持有的员工、资金和外部资源。
- 让核心领域能够独立理解、验证和演进，同时保证统一周结算的一致性。

## 2. 总体结构

采用 Company 与 Project 双层经营结构。Company 是长期经营主体；Project 是单部作品的独立项目主体。两者通过资源分配、财务交易和应用层流程协作。

```text
                       Application Layer
              （用例编排、跨领域流程、统一周结算）
                              |
          +-------------------+-------------------+
          |                   |                   |
       Company             Project          Resource Allocation
          |                   |                   |
          |              Production               |
          |                   |                   |
          +---------+---------+---------+---------+
                    |                   |
              Staff / People     Collaboration
                    |                   |
                 Finance             Market
                    |
                Event & Risk

       Infrastructure：存档、随机数、配置、日志、持久化等
```

上图是职责关系示意，不是完整依赖图。具体接口、允许的依赖方向和模块拆分仍需在领域建模阶段确定。

## 3. 已确认的架构决策

### 3.1 采用 B 为主体，吸收 C 的部分能力

**[负责人已确认]** Company 与 Project 各自承担独立职责，不采用 Company 聚合管理所有 Project 内部行为的结构。

- Company 管理公司自身的长期经营状态。
- Project 管理单部作品的项目状态与生命周期。
- Project 不直接修改 Company 的现金、员工资产或其他公司级资源。
- Company 不直接接管 Project 内部的制作过程。
- 两者通过明确的领域操作、资源分配和应用层流程协作。

吸收 C 的部分能力：提供公司级项目组合视图，集中展示项目列表、优先级、资源竞争、资金占用和风险汇总。首版不建立一个拥有独立业务规则、独立状态和独立结算流程的 Portfolio 领域。

### 3.2 Company 的职责

Company 是跨作品持续存在的经营主体，负责公司级长期状态和资产，包括：

- 公司经营状态、经营周数与终局；
- 公司现金及公司级财务概况；
- 公司声望、履历与长期成长；
- 公司拥有的员工及其长期状态；
- 设施与公司能力；
- 长期合作关系及可复用的外部资源关系。

Company 不负责决定某部作品每周具体生产什么，也不直接计算项目的工作量和质量。

### 3.3 Project 的职责

每部作品拥有独立 Project。Project 负责该作品的业务身份和项目生命周期，包括：

- 企划与作品基本信息；
- 项目启动、制作中、交付、结算和结束等生命周期状态；
- 项目当前制作阶段及阶段推进状态；
- 项目目标、项目计划和阶段级配置；
- 项目交付条件、期限和项目级风险状态；
- 项目级合作安排的引用或快照；
- 项目成本、产出和结果的归因关联。

Project 是作品状态的权威归属方，但不因此拥有公司资产，也不必独占所有制作计算规则。

### 3.4 共享资源与财务边界

- 员工归 Company 所有；Project 只获得明确时间范围内的分配或使用资格。
- 外包供应商及其产能属于公司可使用的外部资源；同一时段的可用产能不能被多个项目重复承诺。
- 资源分配由独立的资源分配职责协调，不由 Project 私自占用公司资源。
- 公司只有一个真实现金池；Project 不拥有可独立支配的公司现金钱包。
- 财务领域记录真实资金变化，并保留项目成本、收入和投资的归因视图。
- Project 可以提出预算和付款需求，但实际支付必须经过财务规则与应用层协调。

### 3.5 应用层职责

应用层负责协调跨领域用例，不替代领域内部规则。主要包括：

- 新项目立项与启动；
- 项目计划提交及资源分配；
- 统一周结算；
- 项目交付与结算；
- 融资和资金危机处理；
- 公司终局处理。

统一周结算需要保证全公司同一时间步的一致性。各领域提供预检、计算、状态变更提案或领域操作；应用层组织执行顺序、处理跨领域约束，并确保失败时不会留下部分推进的状态。

## 4. 制作领域边界

本节记录当前建议，仍需结合领域模型继续确认。

### 4.1 建议：Project 管生命周期，Production 管生产规则

不建议把制作阶段、工作定义、工作量与质量计算、实际产出公式全部放进 Project。也不建议把 Project 的生命周期整体搬进 Production。

建议采用以下分工：

**Project 负责作品层面的制作生命周期：**

- 当前处于哪个制作阶段；
- 阶段顺序、阶段状态和阶段切换条件；
- 项目整体进度、交付状态与期限；
- 项目采用的制作目标、阶段要求和项目级配置；
- 接收制作结果，并据此判断是否满足阶段完成或项目交付条件。

**Production 负责作品如何被生产出来：**

- 制作工作类型及其专业要求；
- 阶段内具体工作项及其生产规则；
- 工作量、质量和返工等生产指标；
- 员工能力、资源投入、制作方案如何转化为产出；
- 每周制作结果的计算，以及阶段生产结果的汇总。

**两者的协作方式：**

1. Project 提供当前阶段、项目目标、阶段要求和本周计划。
2. 应用层汇集员工分配、外包能力等资源信息。
3. Production 根据输入计算本周生产结果，不直接扣公司现金或修改员工长期状态。
4. 应用层将生产结果交回 Project，由 Project 更新项目进度并判断阶段是否完成。
5. 员工疲劳、士气、经验等公司人员状态由相应领域根据本周实际参与情况结算。

因此，制作阶段作为项目生命周期状态归 Project；阶段中的工作组织与产出计算归 Production。Production 可以维护项目范围内的生产执行数据，但不能成为第二个 Project 生命周期管理器。

### 4.2 五阶段生产骨架

当前玩法框架沿用五阶段：

1. 企划与脚本（script）
2. 分镜与演出（storyboard）
3. 原画制作（key_animation）
4. 动画与作画检查（animation_check）
5. 摄影与后期（postproduction）

五阶段是当前设计基线。各阶段的工作拆分、质量维度、交付门槛和阶段间影响，仍应以制作领域的后续设计为准；不在本文件中预先规定具体工作项或公式。

### 4.3 关键数据所有权原则

| 数据 / 状态 | 权威归属 | 说明 |
| --- | --- | --- |
| 项目当前阶段、阶段生命周期状态 | Project | Project 决定项目处于哪个阶段及何时进入下一阶段 |
| 项目期限、交付状态 | Project | 作品级生命周期信息 |
| 制作工作定义、专业要求 | Production | 定义工作如何生产 |
| 项目阶段内工作执行记录 | Production（项目范围内） | 记录生产工作进展，不接管项目生命周期 |
| 工作量、质量、返工与实际产出计算 | Production | 生产规则的唯一权威实现 |
| 员工能力、疲劳、士气、经验 | Staff / People | 员工长期状态归人员领域 |
| 员工本周分配与资源占用 | Resource Allocation | 由资源分配职责协调 |
| 公司现金与实际资金流水 | Finance | 真实资金变化的唯一权威记录 |
| 项目成本与收入归因 | Finance | 项目分析视图，不构成独立钱包 |

以下是当前候选划分，用于继续讨论和识别边界。**除第 3 节明确确认的总体职责外，本节不表示每个候选模块都已最终定型。** 后续允许合并、拆分或调整名称。

| 候选模块 | 主要职责 | 需要进一步确认的边界 |
| --- | --- | --- |
| Company（公司与经营） | 公司长期状态、声望、设施、公司资产与终局 | 公司成长与设施是否需要独立子域 |
| Project（项目与企划） | 项目身份、立项、项目生命周期、阶段状态与交付 | 企划市场的机会生成是否归 Market |

| Resource Allocation（资源分配） | 员工、供应商及其他共享资源的分配和冲突协调 | 资源需求模型、优先级和默认分配规则 |
| Collaboration（合作与委员会） | 合作方、委员会、投资安排、合同与权利 | 合同付款义务与 Finance 的交界 |

| Finance（财务） | 公司现金、实际收支、项目归因、融资与资金危机 | 投资、收入分账和合同支付的业务来源 |
| Event & Risk（事件与风险） | 事件触发、风险变化、后果与玩家决策 | 哪些事件归项目，哪些事件影响公司整体 |

### 5.1 项目组合视图

项目组合视图属于 Company 的经营观察与决策入口，至少可以汇总：

- 当前全部项目及其阶段；
- 项目优先级和关键期限；
- 员工、外包产能等资源冲突；
- 项目预算占用、预期支出与风险；
- 项目进度和交付风险。

首版不因存在项目组合视图，就引入一个独立 Portfolio 领域或额外的项目组合生命周期。

## 6. 应用层与基础设施层

### 6.1 应用层（Application Layer）

应用层承载跨领域用例和流程编排，例如：

- StartProject：校验立项条件、合作安排、资金与资源，建立项目；
- AllocateResources：协调共享资源并生成项目可用资源；
- WeeklySettlement：统一预检、费用处理、制作计算、人员状态结算、事件处理、阶段推进和公司周数推进；
- DeliverProject：处理作品交付、商业结算、历史归档和合作关系沉淀；
- CloseCompany：处理破产、经营期限结束等公司终局。

这些是用例示例，不是要求按名称或类数量实现。应用层不得把各领域的公式复制到流程编排代码中。

### 6.2 基础设施层（Infrastructure）

基础设施提供技术能力，不拥有游戏业务规则：

- 持久化、存档和数据迁移；
- 随机数生成、Seed 管理与结果回放；
- 配置、规则参数和内容数据加载；
- 日志、诊断和测试支持；
- 事务或状态快照提交机制。

随机数基础设施提供可复现能力；各领域决定何时、因何业务行为消费随机数。随机流应避免因无关模块的随机调用而互相干扰。

## 7. 模块协作原则

1. **单一数据所有权。** 同一业务事实只允许一个领域作为权威写入方，其他领域通过接口或只读视图使用。
2. **禁止跨领域直接改内部状态。** 领域只能通过对方公开的业务操作或应用层编排完成协作。
3. **业务规则归属明确。** 制作领域不扣公司工资；财务领域不决定制作进度；员工领域不决定项目最终产出；Project 不复制制作公式。
4. **应用层组织流程。** 跨领域的先后顺序、预检和整体提交由应用层负责。
5. **项目与公司状态分离。** 项目结束不会重置公司；项目结算结果可以沉淀为公司历史和长期资产。
6. **项目并行不复制资源。** 多个项目可以同时运行，但共享员工、供应商产能和公司资金必须经过统一协调。
7. **模块边界服务于玩法。** 不因追求形式上的独立而制造大量小模块；若两个职责在业务上无法独立变化，应考虑合并。
8. **先确定业务契约，再决定代码结构。** 不把当前 C++/WASM、React 目录或旧 GameState 字段直接当作目标领域边界。

## 8. 尚待讨论的架构问题

以下问题尚未在当前讨论中定案：

1. Project 与 Production 的精确数据模型：阶段实例、工作项实例、质量快照和历史结果分别由谁持有。
2. Collaboration 与 Finance 的边界：投资承诺、实际到账、合同付款、分账和项目归因如何衔接。
3. Market 与 Project 的边界：企划机会、项目立项、发行渠道、商业表现和系列 IP 价值如何分配。
4. Staff 与 Resource Allocation 的边界：员工岗位、雇佣状态、可用状态、项目占用和临时人员如何建模。
5. Event & Risk 是否作为统一领域，或按项目、员工、财务等业务归属拆分事件规则。
6. 统一周结算的具体事务边界、失败恢复策略和随机流设计。
7. 领域模块在代码中的具体目录、接口和依赖方向。

重大玩法取舍由负责人讨论确认；普通领域细节可在不改变已确认边界的前提下继续设计。
