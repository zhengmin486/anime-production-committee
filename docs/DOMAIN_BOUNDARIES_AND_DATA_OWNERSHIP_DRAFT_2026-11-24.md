# 《动画制作委员会》领域边界与数据所有权草案

> 日期：2026-11-24
> 状态：WP0 第一版草案；用于约束后续设计与讨论，不代表运行时已经实现
> 上位规则：[核心玩法重构框架](CORE_GAMEPLAY_REBUILD_FRAMEWORK.md) 第 17 节
> 依据：当前核心框架、负责人已确认的 D1-D6、仓库审查登记及现有 v3 代码结构

## 1. 目的与边界

本文件先回答四个问题：

1. 游戏中有哪些长期存在的业务实体？
2. 每项数据由谁拥有，谁有权修改？
3. 项目、员工、委员会和供应商在什么时点创建、变更、结束或归档？
4. 每周结算如何读取这些实体，并以一次性提交维护全局一致性？

本文件不冻结 ORM、数据库表、JSON 字段、API 或具体结算算法。当前运行时仍以单个 `GameState.project` 为中心；新架构应重建领域边界，不在旧单项目对象上直接追加项目数组。

## 2. 领域分层

### 2.1 公司级长期实体

| 实体 | 所有者 | 生命周期 | 主要职责 |
|---|---|---|---|
| Company | 游戏会话/存档根 | 开局至 520 周终局 | 公司周数、经营状态、统一现金池、声望、长期经营状态 |
| Staff | Company | 招聘至离职/解雇/退休 | 公司长期雇员资料、能力、经验、潜力、疲劳、士气 |
| Supplier | 外部供应商目录；公司持有合作关系 | 供应商资料可长期存在 | 专业方向、产能、可靠性、报价等基础资料 |
| PartnerRelationship | Company | 首次合作至关系失效/归档 | 公司与投资方、版权方、发行方、渠道、供应商等的长期合作关系 |
| Facility | Company | 建设至拆除/终局 | 公司拥有的设施及其有限、直观的辅助能力 |
| Market | 世界/经营环境 | 随经营周持续刷新 | 可接触的企划机会与市场环境，不归属于单一项目 |
| WorkHistory | Company | 项目交付后永久归档 | 已完成作品、结果、商业表现和公司履历快照 |

公司是长期经营主体。任何项目的开始、暂停、交付或失败都不应重置公司现金、员工、声望和长期关系。

### 2.2 项目级实体

| 实体 | 所有者 | 生命周期 | 主要职责 |
|---|---|---|---|
| Project | Company 创建并拥有 | 立项至交付/取消/失败 | 单部作品的制作生命周期 |
| ProjectPlan | Project | 立项后至项目结束 | 持续方针、阶段计划和已确认的周度调整 |
| ProjectStaffSnapshot | Project / 周度分配记录 | 按周生成 | 记录当周参与项目的人员及其角色/能力快照 |
| SupplierReservation | Project 对 SupplierCapacity 的预约 | 按合同/周预留至交付或释放 | 记录项目占用的外包产能、费用和交付承诺 |
| Committee | Project | 委员会成立至作品项目结算 | 项目级投资、成员、权益与渠道安排 |
| ProjectLedgerView | Project 对 CompanyLedger 的归因视图 | 随项目记账至归档 | 统计项目成本、投资、收入与盈亏，不拥有独立现金 |
| ProjectEvent | Project | 触发至处理/过期/归档 | 项目级风险、机会与待处理事项 |

项目可以并行存在，拥有独立阶段、计划、风险和账目归因，但不拥有独立现金池。公司级资源必须通过明确的分配或预留记录进入项目。

### 2.3 周度记录与事务实体

| 实体 | 权威所有者 | 生命周期 | 主要职责 |
|---|---|---|---|
| StaffAllocation | WeeklySettlement 输入快照 | 每周创建，结算后归档 | 记录核心员工当周唯一项目归属 |
| StaffTransition | WeeklySettlement | 发生人员切换时创建 | 记录切换前后项目、阶段边界、监督身份及磨合损失依据 |
| SupplierCapacityReservation | WeeklySettlement / SupplierReservation | 按周或合同有效期 | 防止供应商同一产能被多个项目重复占用 |
| LedgerEntry | Company | 每笔业务发生时追加 | 公司现金的唯一变动记录，并附项目归因 |
| WeeklySettlement | Company | 每周一次 | 收集输入、预检资源、计算结果、原子提交并生成周回执 |
| SettlementReport | WeeklySettlement | 结算提交后生成 | 面向玩家解释公司与各项目的本周变化 |
| Event | Company 或 Project | 触发至处理/过期/归档 | 统一事件实体，通过 scope 区分公司级与项目级 |

周度记录是历史事实，不应被下一周的新分配覆盖。当前有效配置可以更新，但已经结算的快照必须保留，以支持复盘、对账和固定 seed 回放。

## 3. 数据所有权矩阵

| 数据事实 | 唯一权威写入方 | 其他模块允许的行为 | 禁止事项 |
|---|---|---|---|
| 公司现金余额 | CompanyLedger / WeeklySettlement | 财务与项目模块读取 | 项目自行维护可支配现金；多个模块重复扣款 |
| 项目成本与收入归因 | LedgerEntry 写入时附 project_id | 项目详情读取汇总 | 项目账再次扣公司现金 |
| 员工基础资料与状态 | Staff 模块；周结算统一写入时间性状态变化 | 项目与 UI 读取 | 项目复制一份可独立修改的员工实体 |
| 员工当周项目归属 | StaffAllocation | 项目制作模块读取快照 | 同一核心员工同周进入多个项目或重复计产能 |
| 人员切换与磨合损失 | WeeklySettlement | 项目制作模块读取结算结果 | 员工模块、项目模块各自重复扣减 |
| 供应商基础资料 | Supplier 目录 | 项目查看可用供应商 | 项目直接修改供应商全局基础属性 |
| 供应商产能占用 | SupplierReservation / WeeklySettlement | 项目读取自身预约 | 多个项目重复承诺同一产能 |
| 委员会成员与投资条款 | Project.Committee | 公司关系模块读取合作结果 | 委员会作为公司永久可操作的全局对象 |
| 长期合作关系 | PartnerRelationship | 新项目邀请时读取 | 项目结束时删除公司关系历史 |
| 作品最终结果 | WorkHistory | 公司履历、IP 和市场系统读取 | 通过实时项目对象反复改写历史作品结果 |
| 周数与时间推进 | WeeklySettlement | 所有系统读取当前周 | 事件、项目或页面单独推进周数 |
| 随机种子与随机结果 | WeeklySettlement 随机流 | 各计算模块接收本次分配的随机结果 | 各模块自行推进共享随机序列，导致回放漂移 |

## 4. 已确认规则对领域模型的约束

### 4.1 核心员工每周单项目分配

- 核心员工归 Company 所有，不归某一 Project 所有。
- 每名核心员工每周只能参与一个项目；当周不允许跨项目支援、借调或拆分工时。
- 每周结算后可重新分配，不受制作阶段限制。
- 分配记录应以周为粒度留存，不能只在 Staff 上保存一个会被覆盖的 current_project_id。
- 临时员工和外包人员不自动套用该规则，其跨项目调度仍待设计。

### 4.2 人员切换与磨合损失

- 切换损失属于周结算计算结果，不属于员工基础能力，也不属于作品质量。
- 非监督人员在阶段内切换产生一次性磨合损失；阶段结束时切换无额外磨合损失。
- 监督人员无论何时切换均产生一次性磨合损失。
- 非监督人员切换影响新加入人员的工作量产出效率；监督人员切换影响整个项目团队的工作量产出效率。
- 磨合损失只影响工作量产出效率，不直接影响作品质量。
- 磨合损失采用一次性比例扣减；具体比例留给模拟器验证。
- StaffTransition 应保存计算所需事实，避免后续根据当前人员状态反推历史切换。

### 4.3 公司现金池与资金危机

- Company 持有唯一现金余额；ProjectLedgerView 只负责项目归因。
- 每周结算先预检公司现金与必要共享资源，再执行项目工作量、质量和状态变化。
- 资金不足时不得部分提交项目结果；公司进入有期限的资金危机状态。
- 玩家可通过融资、缩减开支或调整项目自救；首版不自动借款。
- 危机期限、融资条件和阈值尚未确定，不能写成固定数值或假定规则。

### 4.4 计划自动执行与玩家确认

- ProjectPlan 保存已配置的持续方针和资源计划；普通周由系统自动执行，不要求玩家重复确认。
- 人员重新分配、新增外包、重大预算承诺由玩家确认。
- 系统不得自动招聘临时员工或静默新增外包。
- 资源缺口必须成为可见的预检结果或玩家决策项。

### 4.5 项目并行与设施

- Project 不受固定项目槽位数量限制。
- 首版不设置独立管理负荷数值；经营压力由资金、人员、供应商产能和项目风险体现。
- Facility 属于公司级辅助成长资产，不是项目立项硬门槛。
- 首版不纳入培训设施；制作工作室、管理办公室、设备设施仍是候选，具体实现范围待原型验证。

## 5. 生命周期草案

### 5.1 项目生命周期

```text
企划机会（Market）
    ↓ 玩家选择并确认合作模式/预算
项目立项（Project）
    ↓ 建立计划、人员配置、外包预约、必要时成立委员会
制作中（Project + WeeklySettlement）
    ↓ 阶段推进、人员按周分配、风险/事件处理
交付/取消/失败
    ↓ 最终商业结算、委员会停止、项目账归档
作品历史（WorkHistory） + 公司关系沉淀（PartnerRelationship）
```

### 5.2 核心员工分配生命周期

```text
公司员工（Staff）
    ↓ 玩家为下一周配置项目
周度分配快照（StaffAllocation）
    ↓ WeeklySettlement 读取并执行
本周项目贡献、疲劳/士气/经验变化、可能的磨合损失
    ↓ 本周结算完成
下一周重新配置（可留在原项目，也可切换）
```

### 5.3 委员会与合作关系生命周期

```text
公司合作方关系（PartnerRelationship）
    ↓ 项目邀请并确认
项目委员会（Committee）
    ↓ 作品项目结束
委员会停止活动并归档
    ↓ 合作结果回写
公司长期合作关系（PartnerRelationship）
```

委员会是项目级临时组织；公司合作关系是长期资产。两者不能使用同一生命周期。

## 6. WeeklySettlement 的责任边界

WeeklySettlement 是唯一允许改变公司周数的入口，也是每周业务结果的唯一提交边界。

建议职责顺序：

1. 收集 Company、所有活动 Project、当周 StaffAllocation、SupplierReservation 与持续方针的输入快照。
2. 校验核心员工一周一项目、供应商产能不重复占用、项目计划合法。
3. 预检公司现金与必要资源；若资金不足，不提交本周制作结果，转入资金危机处理路径。
4. 锁定本周所需资源和强制费用，防止并行项目重复使用。
5. 计算人员切换的一次性磨合损失。
6. 计算各项目工作量、质量和阶段状态；磨合损失只进入工作量效率计算。
7. 统一计算员工状态、市场变化、事件与项目交付。
8. 以原子方式提交公司现金、项目状态、人员状态、资源占用、周数与随机种子。
9. 生成公司级周回执和各项目结果摘要。

此处只确定职责边界，不冻结模块调用顺序、事务实现方式或具体公式。预检失败后“进入资金危机”是否需要推进公司周数、危机期间哪些固定成本继续发生，仍需专项决定。

## 8. 与当前代码的关系

当前仓库 v3 类型与 C++ 核心仍包含单个 `GameState.project`、单个 `pending_event` 和项目内 `temporary_staff` 等单项目结构。现有代码可作为历史实现与迁移证据，不应被误认为本文件中的 Company/Project/StaffAllocation 等边界已经落地。

本草案只定义概念边界和数据所有权。后续若开始实现，必须先形成新的领域状态契约与迁移方案，再决定 JSON 结构、持久化方式和模块接口。

## 9. 验收检查

- [ ] 每项长期数据只有一个权威所有者。
- [ ] 公司现金池与项目账目归因分离。
- [ ] 员工归公司所有，周度项目分配可追溯。
- [ ] 核心员工同周不能重复参与多个项目。
- [ ] 人员磨合损失只由周结算计算，且只影响工作量效率。
- [ ] 供应商产能不能被多个项目重复承诺。
- [ ] 委员会随项目结束，长期合作关系留在公司。
- [ ] 任何时间推进只能经过 WeeklySettlement。
- [ ] 资金不足不会造成部分项目已推进、部分项目未推进。
- [ ] 所有未决事项明确标记，未把候选规则写成已确认事实。
