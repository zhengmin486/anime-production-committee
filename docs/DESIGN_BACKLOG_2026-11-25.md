## 0. 整理口径

### 0.1 纳入来源

本轮盘点覆盖：

1. 外部独立游戏设计评审及其后续讨论记录；
2. 三条智能体研究线的汇编复核：设计策略线、美术指导线、技术方向线；
3. 核心玩法架构研究、开罗游戏专项研究、补充研究、日本动画产业研究；
4. 可玩性与随机性研究、玩法痛点专项研究；
5. 委员会商业、公司经济与成长、员工组织、作品制作四份系统审计；
6. 架构评审、统一重构审查清单、M2 集成审查及经济/排班/随机性实验中提出的工程和验证建议。

### 0.2 分类定义

- **A｜明确属于优化**：不必先改变核心玩法方向，主要改善信息呈现、操作便利、开发流程、测试、文档和工程质量。可以进入优化储备，但仍需排期。
- **B｜需要讨论**：会改变玩家决策、经营策略、资源关系、时间节奏、经济结果或核心系统边界。必须讨论后才能决定是否采纳。
- **C｜已讨论 / 已确认 / 暂缓 / 撤回**：保留状态，避免重复提问或把旧提案重新包装成新议题。
- **D｜实现与契约缺口**：不是玩法提案，而是已确认方向的工程落地、跨模块一致性或验收问题，应进入对应开发任务，不混入玩法待讨论清单。

### 0.4 首版架构与后续更新的划分原则

每项设计议题均区分底层架构、首版玩法和后续可扩展内容：

- **首版架构必需**：影响核心数据结构、系统边界、结算逻辑、模块接口或存档兼容的内容，首版必须设计好；必要时预留扩展接口，但不意味着相关功能必须首版开放。
- **首版玩法必需**：直接影响核心循环和玩家基本决策的内容，首版应实现。
- **后续可扩展**：不破坏现有架构、只增加新规则、新内容或新玩法的内容，可以留给后续更新包。
- **后续表现优化**：只影响界面展示、信息可视化或操作便利性的内容，可以留给后续更新包。

不得以首版暂不实现为由，忽略必要的底层扩展空间；也不得以未来可能扩展为由，要求首版提前实现全部功能。

### 0.3 重要约束

- 单集制作流程为**六阶段**，其中分镜与原画合并；外部报告提出的“四工序集束”不能直接替换六阶段规则。
- 经营周期为十年、520 周，周制已确认；半月回合不是当前候选默认方案。
- 周内没有操作次数上限；「下一周」是统一周结算入口，动作按即时生效、下一周执行、延迟生效分类。
- 多项目并行已确认；核心员工每周严格归属一个项目，不设固定项目数量上限，也不引入独立管理负荷数值。
- 设施作为辅助成长路径已确认；首版不做复杂科技树、培训设施或独立养成系统。
- 委员会围绕单部作品成立，作品结束后停止；合作关系可以沉淀为公司资产。
- 玩家经营的是动画制作公司，作品是核心目标，产业关系服务于作品目标。
- 中等随机性已确认：玩家决策影响期望与风险区间，结果在周结算揭晓。
- 加速键、批量操作和自动化属于后期便利功能，不能替代前期有意义的每周经营内容。

# D. 工程、集成与协作约束：进入开发与验收，不混入玩法讨论

以下事项不是需要负责人重新决定的玩法问题，而是当前架构落地、跨模块集成和团队协作必须持续执行的检查。玩法规则以 DECISION_LOG 为准，协作流程详见 [重构复盘与协作约定](REBUILD_RETROSPECTIVE_AND_WORKING_RULES_2026-11-25.md)。

1. **财务与结算一致性**：公司现金、项目账、制作成本、投资本金、BD 收入、非 BD 分账、成功奖励和应收必须只记账一次。
2. **委员会完整路径**：企划允许模式、立项、周推进、交付、结算、渠道和成员快照必须形成完整闭环，不能只开放立项入口。
3. **共享资源唯一占用**：核心员工每周只能被分配一次；供应商容量、临时人员和外包任务需有明确的占用/释放规则。
4. **统一周结算入口**：所有周数变化通过 WeeklySettlement；事件、招聘、即时经营动作不得私自推进周数。
5. **事件边界**：实现必须遵循 STATUS-47：事件按项目独立触发，每项目每周最多一个，不同项目可同周触发；多个待处理事件分别保留，由玩家自由选择处理顺序，不设置全局优先级或 FIFO 排队机制，也不得因全局单事件上限永久丢弃其他项目的候选事件。待处理事件触发后按既定规则阻塞周推进，直到玩家完成选择。事件状态、作用域、有效期、暂停范围和选项效果必须与多项目及统一结算契约一致。
6. **历史记录**：作品结算时保存必要快照，员工释放后仍可展示历史贡献；合作关系与作品档案分层。
7. **存档、财务不变式与确定性**：同一初始状态、操作序列和 seed 应可复现；失败动作不得部分修改状态或消耗随机流。DEC-FIN-003 允许资金危机期间现金暂时为负；经 2026-11-25 M0 契约修订，INV-25 明确允许负余额仅存在于危机或破产关闭状态，与资金危机规则保持一致。STATUS-18 已确认直接 Pro-rata、不设本金优先；适用渠道/代理成本在形成净分配池前扣除。应收与现金分离遵循 STATUS-65。
8. **M2 前契约修正**：统一 INV-11 与 last_participation 的语义和存储形状；完成成员快照、WorkRecord 留档及 partners 字段的数据量级评估。
9. **经济与产能标定**：使用当前六阶段蓝图、v4 内核和真实员工/供应商模型进行验证；旧单项目模拟器只作为历史实验参考。委员会项目制作费/制作预算占总投资 0.5（50%）已确认，是首版游戏参数；实际生产成本仍需独立标定，不按固定比例推导。成本类别与路线经济目标遵循 STATUS-66。
10. **统一开发基线**：新任务从最新 main 创建分支，记录基线 SHA；发现本地分支、旧 PR 或文档与 main 冲突时先报告，不在过时架构上续写。架构切换后明确唯一目标架构，旧运行时仅作为迁移参照。
11. **跨模块不变式与智能体任务边界**：涉及事件、周结算、财务、存档和多项目的任务，开始前列明产品规则来源、状态唯一所有者、正常/失败/边界行为及验收测试；智能体任务必须明确允许修改范围、禁止改变的规则、依赖和交付标准。
12. **旧成果迁移处置**：旧分支和 PR 按直接合并、迁移后合并、归档保留、关闭作废分类；关闭 PR 不等于删除历史成果，保留历史也不意味着继续兼容旧模型。迁移后核对代码、文档和测试是否真正进入目标分支。
13. **PR 集成验收**：除 CI 外，还要审查产品规则、领域状态所有权、M0 契约、多项目与失败路径、记账/结算完整性、文档同步和任务范围；CI 通过是必要条件，不是充分条件。
14. **实验结论版本绑定**：模拟和标定报告记录规则/代码版本、参数配置、随机种子、运行命令、样本量和适用边界；关键前提变化后，旧实验只能作为历史结果，不能直接充当当前模型证据。

### STATUS-67｜委员会成员中期诉求

**状态：首版纳入；规则方向已确认，事件卡与数值待落实**

- 委员会成员中期诉求是委员会项目制作期间的差异化经营机制。
- 复用项目事件系统；仅委员会项目触发；每部作品最多 1–2 次，具体上限与概率待标定。
- 玩家通常在妥协/拒绝之间取舍。妥协可能换取商业预期或降低委员会压力，但带来额外工作量、工期或质量代价；拒绝可能保留创作自由与制作进度，但带来委员会压力、渠道预期或合作机会损失。
- 单张事件卡可定义不同的代价与收益，不要求统一模板；拒绝不必然是坏结果。
- 不做投票、派系、复杂政治博弈或独立好感度系统。
- 事件卡由内容团队提交并按既有事件卡格式接入；触发频次、概率和效果幅度由数值标定。
- 是否新增项目级 committee_pressure 字段属于工程数据契约问题，不在玩法归档中预设实现方案。


### STATUS-68｜老板作为轻量特殊角色实体

**状态：后续更新候选；实现方向已明确，具体字段与玩法待设计**

- 老板不是普通核心员工，但后续人物化不需要另建一套庞大角色系统。
- 可在 Staff 实体上增加特殊标记，或设置独立角色槽位，作为特殊角色实体接入。
- 特殊标记/能力可表达不可解雇、专属能力或特长、可切换出战模式等差异；这些是可选设计方向，不代表全部必须实现。
- 复用现有角色数据、能力或周结算接入点；不重写周结算事务、核心状态机或普通员工流程。
- 具体实体归属、字段和玩法效果在后续版本确定；不得阻塞首版核心员工系统。
