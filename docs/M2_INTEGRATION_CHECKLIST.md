# M2 跨模块集成清单

> 历史资料说明：本文记录旧版 V2/V3 契约、旧五阶段制作模型或当时的研究建议，不代表当前目标玩法。现行决策以 [DECISION_LOG.md](DECISION_LOG.md) 为准：项目级公共制作 + 单集六阶段、工作项依赖并行、核心员工每周严格单项目分配、多项目并行；资金规则按 DEC-FIN-002/003 刚性支出预检不足直接破产，限时危机周仅为未来更新候选。本文中的旧阶段、资源分配和资金规则仅作为历史证据/旧实现迁移参考，不得直接作为新架构依据。


> 核对基线：2026-11-22 main。本文由项目负责人用于核心集成准备，不替代 #6/#7/#11 模块负责人的内部设计，也不表示下列行为已经实现。
>
> 核心原则：模块可以独立推进，但进入主干时必须共用同一份 GameState、同一套状态迁移、周结算、随机数和财务规则。TypeScript 契约存在不等于 C++/WASM 已实现。

## 2. 进入集成前必须打通的核心边界

### 2.1 GameState 校验器必须从 M1 静态假设转为 V3 契约校验

当前 `game_core.cpp` 的完整状态校验包含以下 M1 限制：

- 公司员工数量必须等于静态 `rules::staff.size()`，且每个员工必须匹配静态员工目录。
- `recruitment_pool` 和 `suppliers` 被要求为空。
- 项目 `temporary_staff` 与 `outsourcing` 被要求为空。
- `pending_event` 被要求为 null。
- 企划与作品履历通过静态 `OfferSpec` 目录反查，无法自然接受动态原创、员工提案、上门企划或续作 ID。
- 项目校验强制 `mode=contract`、投资比例为 0、延期次数为 0、委员会压力为 null。

集成要求：

- 保留完整结构、数值范围、ID 唯一性、引用关系和阶段状态校验；不要为了接入 M2 而整体放松校验。
- 将“静态目录身份校验”改为“契约字段与规则不变量校验”。动态报价必须能通过同一套校验；作品历史应以立项时保存的 offer 快照为依据，而不是要求每个 ID 永远存在于固定目录。
- 公司 `staff` 仍只存核心员工（可为空）；项目 `temporary_staff` 独立存放临时员工，`recruitment_pool` 存候选人。三处分别校验 employment 与费用字段，并统一检查 ID 不重复；不要把临时员工或候选人混入公司核心名册。
- 供应商、外包任务、事件及委员会结构按 DATA_MODEL 的引用与生命周期规则校验。
- 可选字段仍按 V3.6/V3.7 缺省语义兼容；旧 M1 V3 存档必须继续合法，不做未经批准的迁移。

### 2.2 状态机与动作入口

对外仍维持现有六个核心入口：`initialize_game`、`start_project`、`apply_decision`、`advance_week`、`resolve_event`、`calculate_result`。

集成时逐项核对：

- `idle`：四个市场槽位；可选 `custom_offer` 与 `pending_proposal` 独立存在；招聘/抽卡/原创创建等经营动作只能在规则允许的经营窗口发生。
- `producing`：阶段配置锁定；允许的招聘、临时用工、外包、延期、电视服务及事件效果各自受项目模式和阶段约束。
- `event_pending`：必须有且仅有一个待处理事件；除解决事件或结束公司外不能推进周。
- `project_ready`：只允许项目结算；结算只能入账一次。
- `project_settled`：展示结算结果；返回市场不推进周，但后续空闲周仍正常收费。
- `closing`：不再接企划、不再推进；只允许待交付项目结算和公司总结。

当前校验器虽然把 `event_pending` 列入 phase 枚举，但后续分支没有接受该状态；同时强制 `pending_event=null`。这是 #11 接入前必须修复的核心阻塞，不应让事件模块绕开校验器。

### 2.3 周推进是唯一时间入口

所有按周发生的变化必须挂接 `advance_week`，不能在模块动作或前端单独推进时间：

1. 校验公司、阶段和当前状态。
2. 汇总本周强制支出并进行资金预检；不足时原子失败，不扣款、不推进周、不消费 seed。
3. 资金足够后一次性扣款并更新公司账、项目区间账。
4. 结算核心员工、临时员工、外包任务的实际工作量与质量；只推进当前阶段，不跨阶段消费产能。
5. 更新经验、疲劳、士气等周度状态；项目结束集中展示不能重复结算。
6. 推进 week，生成周回执；按已冻结优先级处理阶段完成、截止、公司 520 周终局。
7. 只有公司仍 running、项目仍在制、阶段仍 active 时，才检查事件；最多产生一个待处理事件。
8. 更新 preview 并返回完整新状态。

具体事件顺序必须服从 GAME_RULES V3.2：不能在阶段切换、项目交付或公司终局后追加事件；终局优先于事件。

### 2.4 随机数必须保持单一、可复现

- 继续使用现有 uint32 seed 与 LCG，不引入第二套 RNG 或前端随机。
- 初始化、市场生成、抽卡、员工提案、事件触发/结果、商业彩蛋等新增随机点，必须登记消费顺序和遍历顺序。
- 同种子、同操作序列得到同结果；失败动作不消费 seed。
- 每个模块不能自行保存独立随机状态；所有随机状态仍由 GameState.seed 持有并由 C++ 更新。
- 新增随机消费点时同步更新随机协议说明和固定种子测试。

当前市场生成读取 seed 决定目录起点；空闲周推进和 return_to_market 会推进 seed。后续不能只看某个模块内部是否“随机”，必须核对全局消费顺序。

### 2.5 财务统一入账

每一笔真实现金变化必须满足：公司 funds 只改变一次；公司 Finance 记录一次；若属于项目期间，再同步进入项目 Finance 一次。公司账与项目账是同一交易的两个汇总视图，不是两笔现金流。

必须统一处理：

- contract：合同预算开工时一次到账；承制商业分成恒为 0。
- committee：立项时投资本金只扣一次；合同预算来自项目总投资用途；交付时按 V3.8 渠道框架计算公司实际分成。
- development：自定原创前期开发费用，创建时支付，不参与分成。
- distribution：电视播出服务等发行费用，购买时支付，不参与分成。
- temporary / outsourcing / events / extension / penalty：严格按已冻结成本分类归属，已预付费用不得在周推进或结算时重复扣除。
- WorkRecord.finance、StageResult.costs、OutsourceTask.fee_paid 是历史/分析快照，不得再次计入现金或项目成本。

当前 C++ 的 `zero_costs`、`check_costs`、`costs_total` 和初始化 Finance 仍只包含原八类；V3.8 新增的 `development`、`distribution` 必须在同一轮集成中贯通，不能只加 TS 类型或只改显示。

### 2.6 制作产能、人员与阶段结果

- 岗位、六项专业能力、制作阶段是三个独立维度。
- 阶段产能由内部核心员工、项目临时员工和已确认的外包任务按统一口径合并。
- 专业匹配、能力权重、同专业边际递减、供应商专业/产能匹配由核心规则统一计算。
- 每周只结算真实贡献；未参与工作者不能获得专业经验。
- 阶段完成时形成一次 StageResult，保存当时团队快照、质量、耗时、成本与遗留问题。
- 历史 WorkRecord 保存永久快照；临时员工释放后仍能从作品履历看到当时参与者。
- 推荐配置只提供建议，不覆盖玩家实际配置，也不能由前端复制产能公式。

### 2.7 结算、履历与存档

- `calculate_result(project)` 是项目唯一结算入口；原子计算商业收入、渠道分账、扣罚、声望、历史记录和公司资金。
- 项目结算后清理当前项目与临时资源，但保留 WorkRecord 的完整快照。
- `calculate_result(company)` 只生成总结，不再次入账；关闭状态不可因回款转正而解锁。
- WorkRecord 的 origin/style/rating/channel_breakdown/previous_work_id 与 ProjectOffer、Project、Finance 保持一致。
- V3 存档继续保存完整 GameState；新增状态字段、事件暂停、人员池、供应商、委员会和槽位均需通过保存/读取校验。
- 不新增存档版本或迁移，除非负责人另行批准；旧 M1 V3 存档的可读性是回归验收项。

## 4. 已发现的负责人侧待处理项

这些是核心集成问题，不是要求模块负责人额外承担的内部任务：

- [ ] **动态实体校验**：移除对固定员工目录、固定企划目录、空供应商池、空临时人员、空事件的 M1 假设，同时保留严格不变量。
- [ ] **phase 完整性**：让 event_pending 在 C++ 校验、状态转换、preview、终局约束中形成闭环。
- [ ] **成本分类贯通**：development / distribution 进入初始化、校验、汇总、预览、报告和结算。
- [ ] **RNG 消费协议**：整理现有 seed 消费点，给 M2 新随机行为确定统一顺序。
- [ ] **项目/历史解耦静态目录**：允许动态企划 ID 和续作引用，历史记录依靠快照校验。
- [ ] **初始声望参数**：文档与进度已确认目标初始声望为 100；当前 `game_rules.hpp` 仍为 0，集成参数同步时修正并补测试。
- [ ] **市场热度契约缺口**：规则已确认四档热度及其影响面，但当前 TS GameState 与 C++ 状态尚无对应状态字段；先确定最小状态表达和归属，再实现，不自行增加第二套市场系统。
- [ ] **财务对账用例**：承制、委员会 10%/100%、原创开发费、电视服务、临时员工、外包、事件支出和强制结清场景均能手算。

## 5. 建议集成顺序

1. **核心兼容层先行**：调整状态校验和动态实体引用方式，保持旧 M1 V3 输入输出兼容；先用旧夹具回归。
2. **企划与财务主干**：接入 #6 报价、槽位、承接模式、投资、委员会与渠道结算；同时打通 development/distribution 和财务不变量。
3. **人员与产能主干**：接入 #7 人员池、临时人员、供应商和外包，统一周度工作量/质量/费用计算。
4. **事件接入周推进**：接入 #11 触发、暂停和选项；复用已经存在的动作与费用规则。
5. **长期反馈**：在 M2 行为稳定后接入 #8 成长、作品评级、续作和结局。
6. **固定场景平衡**：主行为通过后，再做多 seed / 多场景模拟、参数对比和回归。

这只是核心集成顺序，不改变各模块负责人自己的推进方式；模块可以并行准备，但共享核心文件、契约、夹具和浏览器测试仍由负责人单点合入。

## 6. 集成验收门槛

- 旧 M1 V3 存档与现有 M1 固定种子用例继续通过。
- 新字段缺省与显式填写两种状态均通过 TS 与 C++ 校验。
- 非法动作失败时 state、funds、week、seed 均不变。
- 同 seed、同操作序列，市场、抽卡、事件和结算结果一致。
- 每笔资金变化能从公司账、项目账和 WorkRecord 逐项对上，无重复扣款/入账。
- 项目完成、截止交付、主动结束、破产、520 周终局均可结算一次且不可重复。
- 核心 native、真实 WASM、前端 typecheck/unit、browser 与 dist 验收分别提供真实结果；不能用一种测试代替另一种。

---

**当前结论：** M2 的主要风险不是缺少字段，而是 M1 C++ 校验器和执行路径仍把静态目录、固定人员、空事件、承制路线当作前提。先把这些核心边界改造成可承载 V3 动态状态的兼容层，再逐个接入模块行为，能显著降低后续合并冲突。
