## 1. 总体判断与研究边界

> 归档说明：本文件记录研究阶段的研究范围和验证目标。研究工作已提交，后续智能体不得把本文件当作要求重新开展三项研究的任务单；当前规则以 [DECISION_LOG.md](DECISION_LOG.md) 为准。

当前资料在以下方面已足以支撑本轮重构，不再把扩大范围作为优先事项：

- 动画产业背景、合同与现实约束；
- 旧版规则、代码实现和系统审计；
- 开源参考项目与工程实现方式；
- 旧经济模型及员工/制作随机性实验。

继续广泛收集行业资料、文献或开源仓库，边际收益已经降低。本轮研究阶段已结束。后续工作转入架构设计、模拟器验证与实现；只有实施中出现具体证据缺口时，才进行范围受限的补充研究。

本计划是研究阶段的任务定义，不代表其中假设已经得到验证或候选机制已经成为正式规则。三项研究的共同目标是：把抽象原则变成玩家可理解的决策，再通过最小原型、模拟或试玩验证其效果。

## 2. 专项一：多项目并行下的决策节奏与防过载

### 2.1 要解决的问题

公司同时推进多部作品后，玩家每周究竟是在做有分量的经营权衡，还是在重复查看进度、填写参数、调整人员和处理多个弹窗？

多项目并行不能只意味着项目数量增加。它必须带来资源竞争、优先级取舍、作品组合策略等经营深度，同时不能按项目数量线性增加玩家的操作负担。

### 2.2 研究重点

1. **并发信息如何折叠**
   - 项目阶段、进度、风险、资源占用不同步时，如何形成公司级总览？
   - 哪些信息需要每周主动呈现，哪些可以摘要、聚合或按需展开？
   - 如何让玩家快速发现真正需要干预的项目，而不是逐个检查所有项目？

2. **持续方针与自动执行边界**
   - 哪些计划可以在玩家设定后持续执行？
   - 哪些普通变化可以由默认策略接管？
   - 哪些情况必须暂停并请求玩家决策？
   - 自动执行是否需要预算、风险或资源边界，避免系统擅自做出不可逆选择？

3. **打断条件与决策节奏**
   - 资金危机、关键人员冲突、重大质量风险、项目阶段切换、重要合作机会等，哪些值得打断玩家？
   - 多个项目同周出现问题时，如何合并、排序、延后或汇总？
   - 普通周是否可以只给一份公司周报，不要求玩家逐项目确认？

4. **不同经营路线的真实取舍**
   - 集中资源制作一部精品，与并行推进多部中小型/委员会项目，收益、现金流、声望、失败风险和资源压力应如何不同？
   - 是否存在适合不同公司阶段、不同玩家风格的有效策略？
   - 避免出现“多开必然收益更高”或“集中做精品永远最优”的单一答案。

### 2.3 需要形成的设计产物

- 玩家每周决策流程图；
- 公司总览与项目详情的信息分层；
- 持续方针、自动执行和玩家干预的边界表；
- 重要打断条件与事件优先级规则；
- 精品路线与多项目路线的对比模型；
- 至少一组双项目/三项目情境，用于验证操作负担和资源取舍。

### 2.4 验证标准

- 增加项目数量时，玩家需要处理的重复操作不应同比例增长；
- 玩家能识别本周最值得处理的问题，并理解不处理的后果；
- 自动执行不会暗中替玩家做重大、不可逆的经营决定；
- 集中制作与多项目并行都存在可行策略，且优势取决于条件；
- 项目间共享资源确实产生决策，而不是单纯增加惩罚。

**优先级：最高。** 多项目是新架构的基础，同时也是最容易造成微操膨胀的风险源，应先验证玩家每周如何玩，再冻结更细的项目计划和资源调度界面。

## 3. 专项二：随机性与事件如何制造决策

### 3.1 要解决的问题

随机性不能只是让玩家无法预测结果；事件也不能只是突然扣钱、延期或降低质量。好的随机机制应当让玩家在信息不完全的情况下识别风险、选择应对方式，并承担不同赌注。

### 3.2 研究重点

1. **信息不完全但有线索**
   - 推进前可以展示哪些信号：人员疲劳、阶段瓶颈、资源冲突、供应商可靠性、项目压力、市场风向等？
   - 哪些信号可以明确，哪些只给出模糊预警？
   - 如何避免把未来随机结果、具体数值或事件内容直接剧透？

2. **风险可识别、可应对**
   - 玩家能采取哪些行动降低发生概率、缩小损失或换取更高收益？
   - 风险是否有累积过程和可观察迹象？
   - 哪些风险可以通过人员、资金、外包、计划强度或合作关系进行缓解？
   - 是否保留少量不可控风险，以维持经营的不确定性？

3. **事件选项的赌注结构**
   - 选项应具有不同成本、风险、时效和潜在收益；
   - 避免一个明显最优选项搭配几个送命/送钱选项；
   - 允许短期收益与长期关系、质量、声望或人员状态之间发生冲突；
   - 事件应服务项目或公司经营目标，不为弹窗数量而制造事件。

4. **随机流与玩家决策的关系**
   - 工作量波动、质量变化、市场变化和事件触发应有清晰的随机职责；
   - 不同随机流隔离，避免一次事件改变其他系统的随机序列；
   - 同一 seed 和相同决策序列应可复现，便于调试和对比；
   - 界面不提前泄露未来结果，但结算后必须能解释结果来源。

### 3.3 需要形成的设计产物

- 风险信息分级表（明确数值、区间、趋势、模糊预警、隐藏结果）；
- 风险来源—预警信号—玩家应对—结算后果映射；
- 事件选项设计规范与反例清单；
- 随机流职责和回放规则；
- 至少若干个覆盖不同风险类型的事件原型；
- 固定 seed 与不同决策序列的对照模拟。

### 3.4 验证标准

- 玩家推进前能说出主要风险来自哪里，但不能准确猜中随机结果；
- 玩家拥有至少一种有代价的风险应对方式，而非只能被动接受；
- 不同事件选项有各自成立的适用情境，不存在长期显著占优的通用答案；
- 随机波动能改变局势，但长期结果仍主要受经营决策、团队能力和资源条件影响；
- 结算回执能够解释关键变化，不把结果归因于不可理解的“运气”。

**与核心系统的关系：** 本专项必须与统一周结算契约同步设计。随机结果在周结算中揭晓，事件不能绕过周结算、单独推进时间或跳过工资、运营和其他时间成本。

## 4. 专项三：520 周中后期的成长转化与目标演进

### 4.1 要解决的问题

十年共 520 周。前期可以依靠生存、接项目、积累资金和招聘人才驱动；但如果后期只是资金更多、员工能力更高、项目规模更大，玩家最终会进入稳定套路，失去继续经营的理由。

成长必须让玩家获得此前做不到的能力，同时带来新的目标、约束或挑战。

### 4.2 研究重点

1. **成长如何转化为新能力**
   - 公司声望是否能解锁更高规格企划、优质人才和重要合作方？
   - IP 积累是否能带来续作、系列化、衍生企划或更稳定的商业基础？
   - 人才成长是否能支持更复杂的制作目标、关键岗位和团队组合？
   - 委员会与渠道网络是否能让公司尝试过去无法承担的合作模式？
   - 资金与组织能力是否能提高并行项目和风险承受能力？

2. **解锁与挑战配对**
   - 新能力不能只是无成本的数值奖励；
   - 更高规格作品应有更高的资源要求、质量门槛、合作约束或失败代价；
   - 更强的渠道与关系应带来新的商业选择，而非简单提高所有收入；
   - 解锁应改变玩家可采取的策略，而不是只扩大数字上限。

3. **阶段性目标与经营课题**
   - 前期：活下来、形成稳定团队、完成第一批作品；
   - 中期：建立口碑、扩大制作能力、形成代表作和长期合作；
   - 后期：打造系列 IP、承接高难度企划、形成多项目组合、实现公司定位；
   - 终局：以代表作品、商业成果、声望、人才和经营韧性综合评价十年经营。

以上是目标结构候选，不是已经冻结的阶段任务或奖励表。需要通过原型验证阶段转换是否自然，避免强制打卡。

4. **避免后期躺平**
   - 检查资金和人才积累后是否出现没有代价的最优循环；
   - 让后期挑战来自新的经营维度，而不是单纯把数值膨胀；
   - 让玩家有机会追求不同公司定位和作品履历，不要求所有路线最终收敛为同一套玩法。

### 4.3 需要形成的设计产物

- 520 周阶段目标结构；
- 公司声望、IP、人才、关系和组织能力的成长转化图；
- 解锁内容与新挑战的配对表；
- 代表作、系列化和高难度企划的候选目标；
- 长周期模拟中期/后期样本；
- 不同经营路线的终局评价对照。

### 4.4 验证标准

- 成长能解锁此前不可行的新选择，而不是只增加同类数值；
- 新解锁会带来新的取舍、成本或风险；
- 中后期仍有玩家主动设定的目标，不只是等待 520 周结束；
- 不同经营路线能形成有辨识度的公司履历；
- 长周期模拟中不存在过早进入“资源充足、风险消失、每周无事可做”的稳定状态。

## 5. 三项研究的依赖关系与推进顺序

| 顺序 | 专项 | 与其他工作的关系 |
|---|---|---|
| 1 | 多项目决策节奏与防过载 | 先明确玩家每周操作与干预边界，反向约束项目计划、资源分配和 UI 信息架构 |
| 2 | 随机性与事件决策 | 与统一周结算契约同步；风险信号、事件触发和事件效果必须纳入同一时间推进 |
| 3 | 中后期成长与目标演进 | 可先建立目标结构；在最小模拟器具备长周期运行能力后做系统验证 |

三项研究可以并行收集材料，但设计定案按上述顺序推进。多项目决策节奏的关键结论应先进入核心玩法框架，避免后续围绕错误的微操结构开发。

## 6. 研究方法与证据要求

每个专项必须按以下结构提交结论：

1. **具体玩法问题**：描述玩家会遇到的真实问题，不只写抽象原则。
2. **参考机制**：说明参考作品/机制解决了什么问题，不能只罗列游戏名称。
3. **机制拆解**：说明输入、玩家决策、系统反馈、失败代价和长期影响。
4. **本作抽象**：说明保留什么、删掉什么、如何适配动画公司经营主题。
5. **待验证假设**：明确哪些判断仍然只是推论。
6. **原型或模拟**：给出最小验证场景、对照组和观察指标。
7. **设计结论**：标记为推荐、待定或不采用，并说明依据。

不再为“资料完整”而扩展搜索。只有当某个具体机制的设计判断缺少必要证据时，才开展针对性调研。竞品机制不直接照搬，旧版模拟器参数不直接升级为新规则。

## 7. 并行工作与当前禁止事项

专项研究推进期间，团队可以继续开展不依赖新运行时契约的工作：

- 员工、企划、事件的内容样本与模板；
- 作品、供应商、合作方等静态样本数据；
- 素材清点、来源与授权核查；
- UI 信息架构和静态原型。

在新契约确定前，暂不扩展旧版单项目排班、旧财务结算、旧单项目模拟器、旧事件运行时，也不基于旧 GameState.project 开发多项目逻辑。内容资产可以先按可迁移的数据字段和语义整理，但不要擅自冻结最终 API 或运行时数据结构。

## 8. 最终交付与验收

本专项完成不以“写完三篇调研报告”为唯一标准。最终应形成：

- 三项专项研究结论；
- 更新后的核心玩法重构框架；
- 玩家每周决策流程与自动执行边界；
- 风险信息和事件选项设计规范；
- 520 周成长目标与解锁结构；
- 至少一个能运行的最小玩法原型或模拟验证方案；
- 需要负责人拍板的重大事项清单。

**总验收问题：** 玩家是否能在有限操作下，持续做出有意义的经营决策；是否能理解风险、承担赌注；是否能在十年经营中不断获得新的目标和能力？如果没有原型或模拟证据，不应宣称专项已经验证完成。
