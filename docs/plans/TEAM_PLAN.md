## 三条标注

**1. 公司经营层归入 zm。** 时间、资金、声望、终局和经营总结由 zm设计与实现。声望状态由这一层唯一写入；其他模块只在各自结算节点产出 `reputation_delta`，不自行修改 `company.reputation`。

**2. 边界约定：**

- **渠道分账（K3）** 归核心规则层。企划系统提供报价与委员会成员候选，`start_project` 固化渠道并校验持股总和；BD 保底 50%、`channel_breakdown` 精确对账、付费电视服务由核心规则层实现。
- **事件系统** 只能调用既有员工、供应商、财务与阶段配置规则，不能直接改状态、不能改合同目标或条件。应急外包走供应商系统，承制不可延期、委员会最多一次延期仍按既有规则。
- **作品履历** 由跨系统集成层唯一写入 `WorkRecord` 与 `previous_work_id`。核心规则层只产出阶段质量、作品评价和结算输入，不另写一份历史。
- **员工提案** 由企划系统提供报价形状与生命周期，采纳/拒绝后进入 `custom_offer` 槽位；核心负责开工校验与资金原子入账。

**3. 文件所有权由 zm单点合入：**

- zm 独占：`packages/game-core/src/game_core.cpp`、`packages/game-core/include/game_rules.hpp`、`packages/game-core/bindings/embind.cpp`、原生与真实 WASM 核心测试、`apps/web/src/types/gameV3.ts`、`apps/web/src/test/fixtures.ts`、`scripts/browser.test.mjs`、存档格式与校验。
- 其他模块交规则提案、夹具和测试用例，不直接改上述文件。规则提案写进 `GAME_RULES.md` 待定表，注明推荐值、理由、影响面和验收方式。
- 各模块自己的界面改动由模块负责人提交；zm 负责整体集成与最终验收。

## 推进方式

1. 模块负责人从最新 `main` 建短期分支，先提交规则提案和验收用例，再提交实现。
2. 涉及核心规则或契约字段的改动，由 zm合并到共享文件；不允许并列 PR 各改一份 `game_core.cpp`。
3. 一个 PR 对应一个可验收任务，认领走对应议题评论，模板见 [CONTRIBUTING.md](../CONTRIBUTING.md#认领拆分与完成标准)。
4. 数值全部 `TODO(待定)`，集中进核心参数配置；前端不另写公式。

## 验收纪律

- 规则以 C++ 核心为准，前端不复制计算公式；验收只认真实 WASM 和可以手算的账。
- 契约字段存在不等于玩法已实现。核心行为落地前，新决策返回 `INVALID_INPUT`，文档和议题按这一边界表述。
- 规则变化进 `GAME_RULES.md`，协议变化进 `API.md` / `DATA_MODEL.md`，实现状态进 `PROGRESS.md`。文档不得领先于实现。
- 同一初始状态、种子和决策序列必须可复现；新增随机消耗点须同步随机协议并保持存档兼容纪律。

2026-11-21 的 M0 以独立 `gameV3.ts` 冻结目标契约，运行时先保持 v2；M1 再由 `9e2d023` 切 C++/WASM、`c2bb934`/`5608422` 切前端。当时的「核心负责人独占共享文件」约定在模块分工下继续有效，且扩展到契约与集成文件。M0 手算账与周结算顺序见 `GAME_RULES.md` V3.1–V3.4，不要再按旧 T01–T06 开工。
