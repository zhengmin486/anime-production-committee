## 4. 仓库文档、代码与历史决定之间的差异

1. **契约先行 ≠ 行为已实现**【A】。文档自认："契约字段已存在不代表招聘、外包等行为已实现"（STAFF_MODULE.md:7）。代码中 `hire_core`/`hire_temporary`/`outsource` 均直接 `invalid()`，`scout` 亦未实现（game_core.cpp:941-955）；PROGRESS.md:59 标"M2 开发中、行为待实现"。
2. **经验只记录、无成长公式**【A,B】。game_core.cpp:1089 仅计算 experience 的 delta；经验→能力提升的公式未找到，归 #8（M3，PROGRESS.md:61）。所以"成长"目前是设计意图而非可运行行为。
3. **"核心员工可跨项目成长"（STAFF_MODULE.md:18）与"至多一个项目"（DATA_MODEL.md:48）矛盾**【A】——前者是继承的讨论假设，后者是冻结契约。
4. **"固定核心团队+临时招募"的定性存疑**（见第 6、7 节重点查证）。
5. **文档版本分层**：GAME_RULES.md 中 V2 历史公式与 V3 现行规则并存（文档开头明确"V2 不能混入 V3"），审计时若误引 V2 会得出错误结论【A】。

## 5. 与其他系统的依赖和冲突

**依赖**（员工是连接"作品制作"与"公司经营"的关键资源，与用户最新方向第5点一致）：

- **财务/周结算（#3）**【A】：工资进 salary、临时进 temporary、外包进 outsourcing 八类账；疲劳士气挂周结算第4步（GAME_RULES.md:9-24）。
- **阶段配置/产能（#4）**【A】：configuration 引用 staff_id；能力×权重→阶段工作量；边际递减与校准依赖 #4 参数（DATA_MODEL.md:32；Issue#7 草案）。
- **履历/结局（#8，M3）**【A】：team 快照、成长、离职预警输入、结局评价（GAME_DESIGN.md:160,167）。
- **声望**【A】：影响招募候选人质量分布，但不直接影响能力/疲劳/士气/效率（GAME_DESIGN.md:153-155）。
- **事件（#11）**【A】：personnel 类事件、应急外包复用供应商（EVENT_MODULE_DESIGN.md；GAME_DESIGN.md:124）。

**冲突**（多项目并行引入后）：

- **人员分配**【A 推 E】：现有 `company.staff` + `project.temporary_staff` 二元结构绑定单项目（DATA_MODEL.md:26,31），多项目下核心员工如何在多个 project 间分配、临时是否可复用，无任何规则。
- **疲劳/士气归属**【A】：周结算针对"当前项目"，多项目共享员工时疲劳是全局还是按项目计，未定义（GAME_RULES.md:9-15）。
- **管理能力**【E】：六能力中的 management 只是阶段权重系数（企划300‰、后期150‰），没有独立"管理容量/管理跨度"概念；实验分支有"多能力与管理 scheduling v0.3"（commit `1fe60de`）但未引入管理约束。
- **产能竞争**【A】：调度报告结论4明示当前贪心算法"没考虑跨阶段培养、临时费用、未来人力储备"；经济模拟 V0.6 明确"没有临时员工/复杂招聘决策"（ECONOMIC_SIMULATION_REPORT_V0.6.md:80）。
- **事件归属**【A】：事件"依附当前项目、不设跨项目永久效果"（GAME_DESIGN.md:118,121），多项目下事件归属冲突。
- **结算顺序与破产判定**【A】：V3.2 固定顺序是单项目假设，多项目需重定费用预检/结算/破产优先级。
- **协作层**【A】：game_core.cpp/game_rules.hpp 多模块共改，须串行集成（TEAM_ASYNC_COLLABORATION.md:63-66）——多项目改造会加剧共享文件冲突。

## 6. 新架构需要重新讨论的问题

以下均因新增方向（多项目、长期能力、员工连接两系统）与 V1.0 冻结规则冲突而必须重议：

1. **是否支持多项目并行**——V1.0 明令不做（GAME_DESIGN.md:20,171；GAME_RULES.md:507），最新研究方向要求支持；研究文档 §7 也列为未定【A】。这是所有员工规则的**前置决策**。
2. **"固定核心团队＋临时招募"是否保留**——见第 7 节查证结论【A/C】。
3. 多项目下核心员工分配规则、疲劳共享口径、是否需要"管理容量"资源【E】。
4. 六能力模型与岗位/专业/阶段三分是否保留——研究文档把"是否使用员工技能树、职业体系或团队属性"重新列为未定【D】。
5. 经验→成长的触发与上限（#8 未实现）；成长如何真正提高"长期制作能力"而非只堆数值【A/D】。
6. 培训、导师、设施、团队关系是否引入——V1.0 明确不做，研究文档建议"抽象为长期成长，不必模拟培训课程/岗位晋升/技能树"【A/D】。
7. 全部数值参数与招聘具体机制的方向确认（本次不重新设计）【A】。

## 7. 有证据支持的改进建议

> 遵守限制：以下均为"决策与方案层面的建议"，不涉及重新设计员工生成/职业体系/招聘机制，不给出数量、数值或成长公式。

1. **将"固定核心团队＋项目临时招募"从"已确认规则"降级标注为"V1.0 工作流假设，待新架构确认"**【A】。依据：它是 owner 于 2026-11-22 随 V1.0 文档整体写入（commit `998be6e`/`34efc62`/`a97d77e`/`de2aaf7`），但 Issue #7 全 17 条评论中，owner 对招募、彩蛋、契约、渠道都有逐条"批准/裁定"，**唯独对这条基础假设没有独立拍板记录**；且 owner 本人在 2026-11-24 的研究文档中声明现有设计"仅作为审计对象，不构成新架构约束"，并重开相关方向。**按委托要求，不应认定为已确认规则，应视为被重新打开的讨论方向。**
2. **先定"多项目并行"决策，再细化任何员工规则**【A】。人员分配、疲劳口径、招聘时机、临时绑定、事件归属、结算顺序全部依赖它；否则细化出的规则会随该决策推翻而返工（依据第 5 节冲突清单）。
3. **明确"经验→成长"链路归 #8 并承认当前无成长行为**【A,B】。避免文档造成"成长已实现"的误读（game_core.cpp:1089 只有 delta；PROGRESS.md:61 标 M3）。
4. **招聘数值参数在落地前一律保持 TODO**【A】。STAFF_MODULE.md:37 与 comment `7104223489` 都禁止把提案值说成已冻结；避免重蹈 V2 固定数值被废止的覆辙。
5. **稳固且可复用的部分予以保留**【A】：能力/潜力分离、岗位-专业-阶段三分、只预警不随机离职、供应商六属性、临时与外包区分——这些在多份文档高度一致且已入契约，无重议必要。
6. **动态排班先定位为"玩家手动配置的辅助推荐"，而非正式玩法 AI**【D】。依据调度报告结论4与"下一轮建议"，且 STAFF_MODULE.md:20 已定"系统推荐+玩家可手动调整，不做全自动"。
7. **培训/导师/设施/团队关系先按研究建议处理**【D】：不急于落地，可抽象为"公司长期制作能力/稳定性"，与"提升长期制作能力"的目标对齐，同时遵守"不做独立养成游戏"的红线。
