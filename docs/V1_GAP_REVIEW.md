## 3. 两个已复现的问题

**① 现金变化与项目利润不一致。** 默认样例的真实 WASM 结果：

```text
初始资金 200 万
+ 开工拨款 800 万
- 累计成本 510 万
+ 结算收入 632 万
= 最终资金 1122 万

实际现金增加：922 万
显示项目利润：122 万
```

`start_project` 计入拨款，`calculate_result` 的 `profit = revenue - spent` 不含拨款，见 [game_core.cpp:330](../packages/game-core/src/game_core.cpp#L330)。这不是文案问题：当前也没有区分合同收入与投资商业分成。应当先按总案重定收支口径再改测试，不能只修前端利润数字。

**② 破产没有结束公司经营。** 破产结算后回到 `idle`，仍可接新项目并再次获得拨款。必须把「项目结束」和「公司结束」拆成两个状态。

现有测试把这些旧规则写成了预期值（类型测试的阶段顺序与三项日报、App 测试的三报价与日推进、存档测试的 v2 与 DB 版本 1、浏览器脚本的金额与天数），所以「测试通过」不代表符合 V1.0。更新预期时要保留并发锁、失败保状态、事件阻塞、确定性重放这些真正有价值的保障，不把 mock 链路当经营规则验收。

## 4. 数据结构建议

升级到**状态协议 v3**，继续用 JSON 交换，不重写架构。

| 对象 | 需要明确的内容 |
| --- | --- |
| 公司 / 经营周期 | 当前周、经营状态、终局原因、资金、声望；与项目状态分离 |
| 企划 | 来源类型、规模、合同预算（即制作预算）、工期、工作量、质量要求、受众基础、可选合作模式；委员会投资规模在选定委员会模式后按合同预算2倍生成 |
| 在制项目 | 合作模式、投资比例、委员会模式下派生的投资规模与已支付投资、当前阶段、阶段配置与成果、委员会压力 |
| 员工 | 岗位、六项能力、雇佣类型、专业经验、潜力及揭示程度、疲劳、士气、少量特性 |
| 外部资源 | 临时人员、供应商目录、已解锁供应商、外包任务及剩余工作量 |
| 结算与历史 | 分类收支、制作评价、商业表现、作品记录、团队快照、前作关联、经营总结 |

约束：

- 预算不等于收入，投资支出不等于制作成本。
- 工资、运营、制作成本分类统计，不重复计入。
- 历史作品必须进存档状态，不能只留在临时结算面板。
- 金额、工作量与公式参数继续集中配置，不在 React 重算。
- 潜力由核心维护，界面只展示允许揭示的线索。
- 版本内保证同种子重放；引入随机生成后不再要求与旧版轨迹一致。

存档目前只保存完整 `GameState`，不保存临时 `report` / `result`，见 [saveGame.ts](../apps/web/src/services/saveGame.ts)。信封与状态都锁 v2、DB 版本却是 1，升级时必须明确迁移或拒绝策略，不能只改 TS 类型。

## 5. 接口影响

保留现有六类职责，不另建平行规则系统。

| 现有接口 | 建议调整 |
| --- | --- |
| `initialize_game` | 初始化周制经营、员工数据、企划池与基础供应商 |
| `start_project` | 增加合作模式与投资比例；资格与资金校验后原子完成入账 |
| `apply_decision` | 支持阶段配置、招聘、外包、延期申请、主动结束；按状态限制调用 |
| `advance_day` | 改为 `advance_week`；空闲与制作共用周结算，事件待处理时禁止推进 |
| `resolve_event` | 保留「提交当前选项 ID」；效果受合作模式、阶段与实际状态约束 |
| `calculate_result` | 区分项目结算与经营总结；项目结算不得自动解除公司终局 |

改名和协议变化要同步 C++ 声明、[Embind 导出](../packages/game-core/bindings/embind.cpp)、TS 类型与校验、服务封装、存档和测试，不能只改一个入口。新增导出或错误码也要同步名单。

**旧档策略建议：**原型阶段直接拒绝 v2 并提示新开，不静默转换、不自动覆盖。是否投入迁移开发单独确认。

## 6. 里程碑

### M0 · 冻结契约

交付 v3 状态、动作、状态机与跨端夹具；财务分类、付款时点与周结算顺序；旧档处理策略；把任务池范围调整到 V1.0。

验收：承制与委员会各有一套可手算核对的资金样例；项目交付、事件暂停、经营终局之间的转换明确；核心与前端能依同一契约并行。

### M1 · 承制纵切

交付周制、五阶段、六能力基础模型；承制正确记账；阶段首配置、单周推进、交付、下一企划；最小作品记录与公司终局；少量固定内容验证结构。

验收：空闲等待确实支付成本；五阶段不能跳过，常规方针不能每周随意切换；承制没有商业分成、不能申请延期；破产后不能再接项目；浏览器跑通新局 → 交付 → 下一部并验证存读档。

此阶段是中间检查点，不代表 V1.0 完成。

### M2 · 经营闭环

交付四企划市场、来源与规模组合；委员会投资、商业表现与分成、延期压力；临时人员、供应商与外包任务；状态驱动事件；配套比较、合作选择与阶段组队界面。

验收：10% 与 100% 投资、原创必须入会、超支不改变投资比例；投资本金只扣一次，合同收入不重复入账；招聘与外包能解决实际专业或产能缺口；事件能说明触发原因，选项确实带代价。

### M3 · 完整 V1

交付核心员工成长、潜力揭示与少量特性；疲劳、士气、休整与预警，不增加随机离职；供应商解锁、续作、最佳作品与团队展示；经营结局、参数平衡与内容量。

验收：完整十年经营可结束，主动结束与破产路径可用；同种子同操作可重放，存读档不改变后续结果；浏览器完整链路与边界场景通过；不同团队与方针对照质量、成本、工期，不能仅凭测试通过宣称平衡完成。

不把上述范围承诺为一周完成；若时间固定，应说明交付到哪个里程碑，而不是暗中删掉已确认玩法。

## 11. 跨系统契约缺口（2026-11-22 审查）

| 缺口 | 已确认的规则依据 | 当前不足 | 后续需要明确的契约问题 |
| --- | --- | --- | --- |
