## 1. 这一版能做什么

```bash
npm run test:v4      # 构建 v4 模块 + 跑 12 条契约测试
```

- 初始化 v4 状态（公司 + 3 名员工 + 空项目集）。
- 用蓝图实例化一个项目：公共制作 + N 个单集 × 6 阶段 × 工作项。
- 设置计划（投入强度/取向/外包策略/赶工 + 定向目标）。
- 把员工分配到项目。
- 推进一周：分派产能到工作项、写入工作量与质量、结算疲劳士气经验、周数 +1。
- 计算状态哈希，验证同输入可复现、遍历顺序无关。

## 4. 规则公式（全部 `[PLACEHOLDER]`）

```text
产能（千分比，1000 = 1 人周）
  ability_q = 500 + ability × 5          // 0..100 → 0.50..1.00
  morale_q  = 600 + morale  × 4
  fatigue_q = 1000 − fatigue × 4
  fit_q     = 1000（主专业匹配）/ 800（不匹配）
  capacity  = 1000 × ability_q/1000 × morale_q/1000 × fatigue_q/1000 × fit_q/1000

工作点 = capacity × 100 / 1000           // 1 人周 = 100 点
分派折算 = round(take × fit / 1000)       // 四舍五入，不截断；否则剩余量小的项会算成 0 点
质量     = work_done × 100 / 1000          // 由累计工作量派生，逐周取差值；不累加每周增量
质量落点 = 阶段权重非零的某一维，坐标 (seed, week, quality, hash(item|staff), 0)
磨合：该员工在该工作项产出 × 75%（只影响工作量，不影响质量）
监督换项目：该项目本周团队产能 × 90%（系数只在 kernel 定义一次）
疲劳：有产出 +8，无产出 −4；士气：有产出 −2，无产出 +1
```

数值不是平衡结论，只用于让 M1 的结果可手算、可回归。

## 5. 手算对照（测试 3）

夹具：1 个公共项 + 1 集 6 阶段各 1 项，均 `work_total=100`、`deliver_at=1000`。

| 员工 | 主专业 | 周产能 | 实际投入 |
| --- | --- | --- | --- |
| `staff_anim`（animation 75） | animation | 80 点 | 公共项 80 → 折 64 |
| `staff_dir`（direction 80） | direction | 82 点 | 公共项余 20 → 折 16；脚本 62 → 折 50 |
| `staff_ka`（drawing 85） | drawing | 85 点 | 脚本余 38 → 折 30 |

结果：公共项 `work_done=80`、质量 8；脚本 `work_done=80`、质量 8；三人疲劳 8、士气 78。
（质量 8 来自 `80 × 100‰`，不再按每周增量截断成 6+1。）

同日多人协作**不**触发磨合：判定只看"本周开始前"的进度与参与者快照。

## 6. 已知取舍与下一步

1. **先做原生可复现，再接前端**：M1 只导出测试用模块，`apps/web` 完全没动，v3 运行时原样保留。
2. **分配期按剩余量扣减**：同一周多人不会重复承诺同一段工作量（这是 M1 里真抓到并修掉的一个缺陷）。
3. **未做财务**：所以 `advance_week` 目前不会失败；预检与危机是 M2/M2.5 的核心。
4. **CMake 目标已加但未在本机验证**（环境无 cmake）：`game_core_v4` 只编译，不参与 wasm 产物；M6 才切换入口。

## 7. 自查修正（2026-11-24 21:10）

提交 `105329e` 之后按"先审查再继续"的要求逐文件自查，修掉 5 处。每条都有可复跑的用例，且**反证过**（把实现改回旧写法，对应用例必须失败）。

| # | 缺陷 | 后果 | 修正 |
| --- | --- | --- | --- |
| 1 | `order_candidates` 在 `focus=quality`（默认）时把"已过门槛"排在"未达门槛"之前，与同函数的下一条规则自相矛盾 | 已过门槛的项持续吸走产能，下游永远不解锁；单集内并行失效 | 恢复档案 §7.3.5 的优先级：定向 → 未达门槛 → 阶段 → 取向 → id。新增回归用例连跑三种取向 |
| 2 | `set_plan` 只要请求里没有 `target` 就把已有定向清空 | 玩家改一次 focus 就静默丢失"本周保第 7 集"的指令 | 字段缺省保持原值，只有显式 `null` 才清除 |
| 3 | 质量随机的 `index` 取自一个从未写入的 `item_order`，恒为 0 | 坐标随机第 5 维等于废掉；同一项同周多人必落同一维度；日后若有人"修好"这个 map，历史回放全部改变 | 删掉死变量，坐标改为 `hash(item|staff)`，与分派顺序、员工数量无关 |
| 4 | `set_plan` 不校验枚举 | `focus="bogus"` 落库后排序静默退回默认行为，玩家看不出原因 | 四个枚举全部校验；`validate()` 也补了同样的检查（INV-01） |
| 5 | 两处整数截断：`take × fit / 1000` 与 `gain × 100 / 1000` | 剩余量小的工作项一周投入算成 0 点；质量的小数部分每周被丢弃 | 分派折算四舍五入；质量改为由累计工作量派生（`work_done × 100‰`），读档重算不漂 |

顺带修的两处工程问题：

- `build-v4.mjs` 原先从**另一个 worktree** 的构建缓存里找 `nlohmann/json.hpp`，干净克隆或 CI 上必然失败。改为：先找本仓库 `build/deps`，找不到就按 `CMakeLists.txt` 里固定的 v3.12.0 下载单头文件（`JSON_DOWNLOAD=1` 可强制验证自举）。
- `state_hash` 只排序了 staff/works/items，`deps` 与 `contributors` 仍是追加顺序。已改为规范化排序，否则哈希会随追加顺序漂移。

## 8. 仍未做（M2 起）

- **财务**：不扣工资、不计制作费，零流水；INV-16 / INV-25 目前空转，"一周"没有经济含义。
- **质量聚合**：工作项六维质量不汇总到阶段/单集/作品。
- **生命周期**：`deadline_week` 从不检查，项目不会转 `delivering`；`Project::deliverable()` 尚无调用点。
- **回执 `causes`**：契约要求能解释"为什么只推进这么多"，现在只有数字。
- **`last_participation` 语义待对齐**：契约 INV-11 写的是"∈ {week-1, null}"，但磨合判定需要保留"上次参与的项目"，两者冲突，M2 统一。
- 计划取向 `quality` 目前不参与排序（同一阶段内质量权重相同），它对结果的影响只体现在质量落点；是否需要更强的语义由平衡阶段定。
