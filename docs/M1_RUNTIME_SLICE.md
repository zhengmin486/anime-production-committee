## 1. 这一版能做什么

```bash
npm run test:v4      # 构建 v4 模块 + 跑 25 条契约测试
```

- 初始化 v4 状态（公司 + 3 名员工 + 空项目集）。
- 用蓝图实例化一个项目：公共制作 + N 个单集 × 6 阶段 × 工作项。
- 推进一周：预检强制费用 → 记账 → 分派产能到工作项 → 写入工作量与质量 → 结算疲劳士气经验 → 周数 +1。
- 现金不足时整周不提交（返回 `INSUFFICIENT_FUNDS`，状态与流水都不变）。
- 计算状态哈希，验证同输入可复现、遍历顺序无关。

## 4. 规则公式（全部 `[PLACEHOLDER]`）

```text
产能（千分比，1000 = 1 人周）
  ability_q = 500 + ability × 5          // 0..100 → 0.50..1.00
  morale_q  = 600 + morale  × 4
  fatigue_q = 1000 − fatigue × 4
  fit_q     = 1000（主专业匹配）/ 800（不匹配）
  capacity  = 1000 × ability_q/1000 × morale_q/1000 × fatigue_q/1000 × fit_q/1000

工作点   = capacity × 100 / 1000         // 1 人周 = 100 点
分派折算 = round(take × fit / 1000)       // 四舍五入，不截断
质量样本 = clamp(能力 + 适配(±4) + 随机(−5..+5), 0, 100)
          // 能力取该工作项驱动能力；随机坐标 (seed, week, quality, hash(item|staff), 维度+1)
质量落点 = 按阶段权重加权抽取（700/300 → 70% / 30%，不是非零维度等概率）
质量更新 = 首次接触 = 样本；之后 = 前值 + (样本 − 前值) × 30%
          // 质量是评级，不是增量：点数翻倍不会让质量翻倍
质量上限 = min(已交付依赖项质量) × 60% + 40（无已交付依赖 = 100）
          // 公共制作通过这条通道压低下游；不单独出作品分，避免两套质量数字
质量聚合 = 工作项(按 work_total 加权) → 阶段均权 → 单集均权 → 作品
磨合：该员工在该工作项产出 × 75%（只影响工作量，不影响质量）
监督换项目：该项目本周团队产能 × 90%
疲劳：有产出 +8，无产出 −4；士气：有产出 −2，无产出 +1
周成本：工资 = Σ 核心员工 weekly_salary；运营 = 30000；
        制作 = 60000 × 强度系数（low 0.8 / standard 1.0 / high 1.3），仅对"有人的 producing 项目"计
```

数值不是平衡结论，只用于让 M1 的结果可手算、可回归。

## 5. 手算对照（测试 3）

夹具：1 个公共项 + 1 集 6 阶段各 1 项，均 `work_total=100`、`deliver_at=1000`。

| 员工 | 主专业 | 周产能 | 实际投入 |
| --- | --- | --- | --- |
| `staff_anim`（animation 75） | animation | 80 点 | 公共项 80 → 折 64 |
| `staff_dir`（direction 80） | direction | 82 点 | 公共项余 20 → 折 16；脚本 62 → 折 50 |
| `staff_ka`（drawing 85） | drawing | 85 点 | 脚本余 38 → 折 30 |

结果：公共项 `work_done=80`、脚本 `work_done=80`；三人疲劳 8、士气 78。

质量不再是可手算的点数换算：它由"谁在做 + 本周随机"给出 0..100 的评级，首次接触直接取样本，之后向新样本靠拢 30%。测试因此只断言落点维度与评级范围；"同工作量不同质量、不同工作量同质量"由 §11 的专门用例覆盖。

本周记账：工资 120000 + 运营 30000 + 制作 60000 = **210000**，余额 2000000 → 1790000，账面 5 条流水。

同日多人协作**不**触发磨合：判定只看"本周开始前"的进度与参与者快照。

## 6. 已知取舍

1. **先做原生可复现，再接前端**：M1 只导出测试用模块，`apps/web` 完全没动，v3 运行时原样保留。
2. **分配期按剩余量扣减**：同一周多人不会重复承诺同一段工作量（这是 M1 里真抓到并修掉的一个缺陷）。
3. **财务只做最小切片**：工资/运营/制作费预检失败时整周不提交；收入、危机与融资仍未做（M2/M2.5），所以长跑必然越玩越穷。
4. **CMake 目标已加但未在本机验证**（环境无 cmake）：`game_core_v4` 只编译，不参与 wasm 产物；M6 才切换入口。
5. **工作项 id 带项目前缀**（`work_01.common.x` / `work_01.ep01.x`）：INV-02 要求实体 id 全局唯一，旧的无前缀命名会让两个项目的 `common.series_comp`、`ep01.script` 撞 id。M1 没有正式存档，改动只影响夹具与回执。

## 8. 产品向复查（2026-11-24 21:50）

> 本节的质量实现已被 §11 取代：当时仍是"点数 × 能力系数"，只是把固定系数换成了能力系数，质量仍然随工作量线性增长。

按"这是在为正确的游戏搭地基吗"复查，补了四件事、明确了三条不做。

**补上的（都在 M1 结构内，不提前塞后续功能）**

1. **财务最小切片 + 统一周结算**：原实现"一周"不花钱，现金对玩法毫无约束，与"经营决策有取舍"直接冲突。现在每周预检工资/运营/制作费，单一账本逐条归因（`work_id` 可查），余额恒等式由 `validate` 守住；钱不够就整周不提交。危机路径仍是 M2.5，这里只保证"钱不够时周不会假装过完"。
2. **质量与工作量解耦**：上一版把质量写成 `work_done × 固定系数`，等于"完成多少就得多少质量"，正好违反"工作量与质量相互独立"。现在质量由**做这件事的人的能力**决定（同一周、同一点数，能力高的人质量更高），并保留阶段限定维度与上限。
3. **质量聚合**：六维数字原来散在 174 个工作项里，玩家看不到作品层面的质量，随机性也只是换个位置加数。现在聚合到作品并在周回执里给出六维与均值，`随机提升若干质量项` 才在结果上可读。
4. **结算内一律按 id 排序**：新增账本后，`works` 数组顺序会改变流水追加顺序，进而改变哈希——"遍历顺序无关"当场被破坏。已把项目/员工遍历、流水写入、哈希规范化统一到 id 序。

**明确不做（并说明理由）**

| 事项 | 判断 | 理由 |
| --- | --- | --- |
| 周产能随机波动 | 留到 M7 | `Stream::production` 的坐标已就位；波动幅度是手感/平衡问题，现在加会让手算回归失去意义 |
| 交付、评级、收入 | 留到 M2/M5 | 合同回款是 M2 的经营闭环，评级要六维聚合后再定分数线 |
| 危机与融资 | 留到 M2.5 | 预检失败在 M1 只是"这一周过不去"，危机是失败之后的路径 |

**已知会让 M1 看起来"越玩越穷"**：没有合同回款（M2），而工资与制作费每周照扣。这是刻意的——现金约束必须真实存在，否则多项目与取舍都无从谈起。测试用 3–4 周即可，长跑留给 M2 接入收入之后。

## 11. 复审修正（2026-11-25）

按 PR #42 复审的四项 P1 与四项一并修正。每条都对应 `scripts/v4.test.mjs` 里的用例。

### 11.1 质量与工作量真正解耦

旧实现 `quality_total = round(gain × ability_q / 1000)` 仍是"点数 × 系数"：工作量翻倍，质量跟着翻倍。新实现：

- 每次投入产生一个**质量样本** `clamp(能力 + 适配 ±4 + 随机 ±5, 0, 100)`；
- 工作项记录的是评级：首次接触取样本，之后 `前值 + (样本 − 前值) × 30%`；
- 点数只决定 `work_done`，不进入质量公式。

证据：

| 断言 | 用例 |
| --- | --- |
| 同 seed 同员工，`work_total` 20 vs 200（点数 20 vs 82），质量相同 | 质量：工作量不同不改变质量评级 |
| 同为 10 点工作量，planning 90 vs 20，质量差 > 40 | 质量：同等工作量下，能力与随机都会改变质量 |
| 同能力同工作量、5 个 seed，质量不全相同 | 同上 |
| 未开工 0、部分完成是评级、完成后仍在 0..100 | 质量：未开工为 0… |

### 11.2 不变式补全

| 不变式 | 改法 |
| --- | --- |
| INV-02 | staff / work / common / item / ledger 共用一个 id 集合；工作项 id 改为 `work_id.` 前缀，否则两个项目必然撞 `common.series_comp`、`ep01.script` |
| INV-03 | 公共制作与单集工作项共用同一校验函数（此前只查单集） |
| INV-09 | 归属必须指向存在且 `producing` 的项目 |
| INV-11 | 只接受 `week-1` 或 `null`；周结算未产出即清空 |
| INV-12 | 贡献者去重、必须引用在职员工、未开工项不得有贡献者 |
| INV-21 | `running ⇒ week < 520`；命令守卫仍先返回 `INVALID_PHASE` |

`from_json` 的默认值不再掩盖缺字段：命令入口先做结构检查（`company.week`、`item.work_total` 等），缺失返回 `INVALID_INPUT`。

### 11.3 维度权重真正生效

`dimension_weights` 从"筛非零维度后等概率"改为**加权抽样**：`draw_below(..., total_weight)` 后按区间落点，700/300 即 70%/30%。测试用 40 个 seed 统计落点，story 至少占一半且两个维度都出现。

### 11.4 公共制作进入质量体系

按 §7.3.4 实现传递上限：下游工作项每维上限 = `min(已交付依赖质量) × 60% + 40`。公共制作不单独出作品分（否则同一质量有两套数字），但低质量公共项会把脚本等下游压住，作品层聚合随之下降。测试用 common=20 vs 90 对照，低质量时下游被压到 52 以内。

### 13.1 缺陷修复：坏输入缺字段不再静默归零

`decode_state` 是 5 个带 state 命令的统一入口（`instantiate_work` / `set_plan` / `assign_staff` / `advance_week` / `hash_state`）。此前必填检查只覆盖结构字段，`from_json` 对下列字段提供了默认值，导致坏输入被读成"合法但错误的状态"：

| 字段 | 旧默认值 | 静默后果 |
|---|---|---|
| `staff[].weekly_salary` | 0 | 工资按 0 计，周结算与手算不一致 |
| `staff[].project_fee` | 0 | 临时员工费用丢失 |
| `staff[].fatigue` / `staff[].morale` | 0 | 产能按满值/零士气算 |
| `finance.solvency.state` | `"normal"` | 危机中的存档被洗白成正常经营 |

现在这些字段在入口显式要求，缺失返回 `INVALID_INPUT`、状态逐字段不变。回归用例扩展了 §"输入边界：缺必填字段返回 INVALID_INPUT"，覆盖 6 个新字段 × 3 个命令入口，并断言失败前后 `state_hash` 一致。

### 13.2 未做的两项（说明理由，非遗漏）

- **`assign_staff` 缺 `company.status` 守卫**：当前主线没有 `end_company` 命令，公司状态恒为 `running`，该分支不可达。`advance_week` 已有 `COMPANY_ENDED` 守卫。等到 M2 接入生命周期、状态机可以真正进入 `closing`/`ended` 时再补，避免提前写不可达防御代码。
- **`experience` 累加但不进产能公式**：2026-11-25 DEC-STAFF-004 已确认"成长由实际工作参与驱动、受潜力上限约束"，但成长系统实现属于 M5。M1 只记录经验、不改变能力，与已确认规则一致，保留现状。
