# M1 运行时切片：能跑一周

> 状态：M1 实现中（内核 + 状态骨架 + 单周结算已可运行，两轮复查后补上财务最小切片与质量聚合；交付、事件、危机未实现）
> 契约依据：[M0_CONTRACT_FREEZE.md](M0_CONTRACT_FREEZE.md)、[DOMAIN_ARCHITECTURE.md](DOMAIN_ARCHITECTURE.md)
> 路线依据：[DEVELOPMENT_ROADMAP.md](DEVELOPMENT_ROADMAP.md) 的 M1 条
> 分支：`feat/v4-m1-runtime`

## 1. 这一版能做什么

```bash
npm run test:v4      # 构建 v4 模块 + 跑 15 条契约测试
```

- 初始化 v4 状态（公司 + 3 名员工 + 空项目集）。
- 用蓝图实例化一个项目：公共制作 + N 个单集 × 6 阶段 × 工作项。
- 推进一周：预检强制费用 → 记账 → 分派产能到工作项 → 写入工作量与质量 → 结算疲劳士气经验 → 周数 +1。
- 现金不足时整周不提交（返回 `INSUFFICIENT_FUNDS`，状态与流水都不变）。
- 计算状态哈希，验证同输入可复现、遍历顺序无关。

## 4. 规则公式（全部 `[PLACEHOLDER]`）

```text
产能（千分比，1000 = 1 人周）
  ability_q = 500 + ability × 5          // 0..100 → 0.50..1.00
  morale_q  = 600 + morale  × 4
  fatigue_q = 1000 − fatigue × 4
  fit_q     = 1000（主专业匹配）/ 800（不匹配）
  capacity  = 1000 × ability_q/1000 × morale_q/1000 × fatigue_q/1000 × fit_q/1000

工作点   = capacity × 100 / 1000         // 1 人周 = 100 点
分派折算 = round(take × fit / 1000)       // 四舍五入，不截断
质量增量 = round(点数 × ability_q / 1000)  // ability_q = 500 + 能力 × 5，即 0.50..1.00
          // 量纲：100 点的工作项由能力 1.00 的人做满 = 该维 100 分
          // 同样点数，能力高的人质量增量更高：工作量 ≠ 质量
质量落点 = 阶段权重非零的某一维，坐标 (seed, week, quality, hash(item|staff), 0)
质量聚合 = 工作项(按 work_total 加权) → 阶段均权 → 单集均权 → 作品
磨合：该员工在该工作项产出 × 75%（只影响工作量，不影响质量）
监督换项目：该项目本周团队产能 × 90%
疲劳：有产出 +8，无产出 −4；士气：有产出 −2，无产出 +1
周成本：工资 = Σ 核心员工 weekly_salary；运营 = 30000；
        制作 = 60000 × 强度系数（low 0.8 / standard 1.0 / high 1.3），仅对"有人的 producing 项目"计
```

数值不是平衡结论，只用于让 M1 的结果可手算、可回归。

## 5. 手算对照（测试 3）

夹具：1 个公共项 + 1 集 6 阶段各 1 项，均 `work_total=100`、`deliver_at=1000`。

| 员工 | 主专业 | 周产能 | 实际投入 |
| --- | --- | --- | --- |
| `staff_anim`（animation 75） | animation | 80 点 | 公共项 80 → 折 64 |
| `staff_dir`（direction 80） | direction | 82 点 | 公共项余 20 → 折 16；脚本 62 → 折 50 |
| `staff_ka`（drawing 85） | drawing | 85 点 | 脚本余 38 → 折 30 |

结果：公共项 `work_done=80`、质量 58；脚本 `work_done=80`、质量 62；三人疲劳 8、士气 78。

质量按"谁在做"算，不再等于 80 × 固定系数：

| 工作项 | 贡献 | 质量 |
| --- | --- | --- |
| 公共项 | anim（planning 40 → 700‰）64 点 | 45 |
| 公共项 | dir（planning 60 → 800‰）16 点 | 13 |
| 脚本 | dir（planning 60 → 800‰）50 点 | 40 |
| 脚本 | ka（planning 45 → 725‰）30 点 | 22 |

本周记账：工资 120000 + 运营 30000 + 制作 60000 = **210000**，余额 2000000 → 1790000，账面 5 条流水。

同日多人协作**不**触发磨合：判定只看"本周开始前"的进度与参与者快照。

## 6. 已知取舍

1. **先做原生可复现，再接前端**：M1 只导出测试用模块，`apps/web` 完全没动，v3 运行时原样保留。
2. **分配期按剩余量扣减**：同一周多人不会重复承诺同一段工作量（这是 M1 里真抓到并修掉的一个缺陷）。
3. **未做财务**：所以 `advance_week` 目前不会失败；预检与危机是 M2/M2.5 的核心。
4. **CMake 目标已加但未在本机验证**（环境无 cmake）：`game_core_v4` 只编译，不参与 wasm 产物；M6 才切换入口。

## 7. 自查修正（2026-11-24 21:10）

提交 `105329e` 之后按"先审查再继续"的要求逐文件自查，修掉 5 处。每条都有可复跑的用例，且**反证过**（把实现改回旧写法，对应用例必须失败）。

| # | 缺陷 | 后果 | 修正 |
| --- | --- | --- | --- |
| 1 | `order_candidates` 在 `focus=quality`（默认）时把"已过门槛"排在"未达门槛"之前，与同函数的下一条规则自相矛盾 | 已过门槛的项持续吸走产能，下游永远不解锁；单集内并行失效 | 恢复档案 §7.3.5 的优先级：定向 → 未达门槛 → 阶段 → 取向 → id。新增回归用例连跑三种取向 |
| 2 | `set_plan` 只要请求里没有 `target` 就把已有定向清空 | 玩家改一次 focus 就静默丢失"本周保第 7 集"的指令 | 字段缺省保持原值，只有显式 `null` 才清除 |
| 3 | 质量随机的 `index` 取自一个从未写入的 `item_order`，恒为 0 | 坐标随机第 5 维等于废掉；同一项同周多人必落同一维度；日后若有人"修好"这个 map，历史回放全部改变 | 删掉死变量，坐标改为 `hash(item|staff)`，与分派顺序、员工数量无关 |
| 4 | `set_plan` 不校验枚举 | `focus="bogus"` 落库后排序静默退回默认行为，玩家看不出原因 | 四个枚举全部校验；`validate()` 也补了同样的检查（INV-01） |
| 5 | 两处整数截断：`take × fit / 1000` 与 `gain × 100 / 1000` | 剩余量小的工作项一周投入算成 0 点；质量的小数部分每周被丢弃 | 分派折算四舍五入；质量当轮改为由累计工作量派生（**后被 §8 推翻**：那让质量变成工作量的函数，与「两者独立」冲突） |

顺带修的两处工程问题：

- `build-v4.mjs` 原先从**另一个 worktree** 的构建缓存里找 `nlohmann/json.hpp`，干净克隆或 CI 上必然失败。改为：先找本仓库 `build/deps`，找不到就按 `CMakeLists.txt` 里固定的 v3.12.0 下载单头文件（`JSON_DOWNLOAD=1` 可强制验证自举）。
- `state_hash` 只排序了 staff/works/items，`deps` 与 `contributors` 仍是追加顺序。已改为规范化排序，否则哈希会随追加顺序漂移。

## 8. 产品向复查（2026-11-24 21:50）

按"这是在为正确的游戏搭地基吗"复查，补了四件事、明确了三条不做。

**补上的（都在 M1 结构内，不提前塞后续功能）**

1. **财务最小切片 + 统一周结算**：原实现"一周"不花钱，现金对玩法毫无约束，与"经营决策有取舍"直接冲突。现在每周预检工资/运营/制作费，单一账本逐条归因（`work_id` 可查），余额恒等式由 `validate` 守住；钱不够就整周不提交。危机路径仍是 M2.5，这里只保证"钱不够时周不会假装过完"。
2. **质量与工作量解耦**：上一版把质量写成 `work_done × 固定系数`，等于"完成多少就得多少质量"，正好违反"工作量与质量相互独立"。现在质量由**做这件事的人的能力**决定（同一周、同一点数，能力高的人质量更高），并保留阶段限定维度与上限。
3. **质量聚合**：六维数字原来散在 174 个工作项里，玩家看不到作品层面的质量，随机性也只是换个位置加数。现在聚合到作品并在周回执里给出六维与均值，`随机提升若干质量项` 才在结果上可读。
4. **结算内一律按 id 排序**：新增账本后，`works` 数组顺序会改变流水追加顺序，进而改变哈希——"遍历顺序无关"当场被破坏。已把项目/员工遍历、流水写入、哈希规范化统一到 id 序。

**明确不做（并说明理由）**

| 事项 | 判断 | 理由 |
| --- | --- | --- |
| 周产能随机波动 | 留到 M7 | `Stream::production` 的坐标已就位；波动幅度是手感/平衡问题，现在加会让手算回归失去意义 |
| 交付、评级、收入 | 留到 M2/M5 | 合同回款是 M2 的经营闭环，评级要六维聚合后再定分数线 |
| 危机与融资 | 留到 M2.5 | 预检失败在 M1 只是"这一周过不去"，危机是失败之后的路径 |

**已知会让 M1 看起来"越玩越穷"**：没有合同回款（M2），而工资与制作费每周照扣。这是刻意的——现金约束必须真实存在，否则多项目与取舍都无从谈起。测试用 3–4 周即可，长跑留给 M2 接入收入之后。

## 9. 仍未做（M2 起）

- **收入与合同回款**：只有支出没有进账（M2 立项/交付），所以长跑必然破产；INV-25 的负余额分支与危机仍未实现。
- **质量传递上限**：架构 §7.3.4 的 `600‰ + 40` 依赖项质量上限未实现；六阶段模板权重目前取等权。
- **生命周期**：`deadline_week` 从不检查，项目不会转 `delivering`；`Project::deliverable()` 尚无调用点。
- **回执 `causes`**：契约要求能解释"为什么只推进这么多"，现在只有数字。
- **`last_participation` 语义待对齐**：契约 INV-11 写的是"∈ {week-1, null}"，但磨合判定需要保留"上次参与的项目"，两者冲突，M2 统一。
- 计划取向 `quality` 目前不参与排序（同一阶段内质量权重相同），它对结果的影响只体现在质量落点；是否需要更强的语义由平衡阶段定。

## 10. M2 接入点（给 Event / 后续领域）

事件域（`feat/11-event-m2`）要接的三处，位置与形状先定下来，避免实现时再改契约：

| 接入点 | 位置 | 约定 |
| --- | --- | --- |
| 抽取时机 | `runtime.cpp::advance_week`，人员结算之后、`state.company.week = week + 1` 之前 | 读本周已提交的结果，不碰账；本周结算已完整，抽取失败只丢弃事件，不影响已结算部分 |
| 周回执 | `report` 增加 `events: {drawn, event_id?, dropped_*}` | 与 `funds`/`works`/`staff` 平级；空周为 `{drawn:false}` |
| 命令 | `resolve_event(event_id, option_id)` 单独文件 `event.hpp/.cpp`，`runtime.cpp` 只加一行分发 | 与"事件在结算完成后抽取"配合：事件阻塞的是下一次 `advance_week` |

两条确定性要求（写在这里，防止 M2 踩坑）：

1. `events.pending.options[]` 必须按事件目录顺序生成，不能按 map 遍历顺序拼——它原样进哈希。
2. `state_hash` 已对 `staff`/`works`/`items`/`deps`/`contributors`/`finance.entries` 做规范化；M2 新增的集合语义数组要一并加进去。

文件边界：`model.hpp` 与 `runtime.cpp` 由本分支持有；事件域可以先在 `feat/v4-m1-runtime` 之上开 stacked 分支只加 `event.hpp/.cpp` + CMake，等 #42 合入后再做 `model.hpp` 的 `Json events` → 强类型替换。
